Criação de plugins

Um plugin adiciona uma visualização, uma ação ou uma página ao Mongo Manager: um mapa dos locais de uma coleção, um gráfico, um localizador de duplicatas, um tradutor de SQL. Este guia é para quem cria um plugin. Ele descreve os arquivos de que um plugin é feito, tudo o que ele pode pedir ao app, as regras que o app aplica e como empacotar, testar e publicar. Os administradores instalam e aprovam plugins na página Plugins; veja o modelo de aprovação em Segurança. Essa página lista todos eles e restringe a lista aos ativados, aos que precisam de um administrador (aguardando aprovação, alterados ou com defeito) ou aos desativados, a uma origem, e aos que uma busca encontra por nome, descrição, id, versão, permissões solicitadas ou o que eles adicionam.

O que é um plugin

Um plugin é uma pasta de arquivos estáticos: uma página HTML, seus scripts, estilos, imagens e fontes, e um manifesto chamado mongo-manager-plugin.json que diz o que ele adiciona e o que pode fazer. O app exibe a página em um frame isolado (sandbox) e a página conversa com o app apenas por mensagens: ela pede documentos e o app responde como o usuário conectado, com os direitos desse usuário e com o mascaramento do app.

  • Sem código de servidor. Nada de um plugin é executado no servidor. O servidor armazena os arquivos dele, verifica-os e os entrega ao frame.
  • Sem rede. A página não pode buscar nada em nenhum endereço, nem mesmo no servidor de onde veio. Ela não tem cookies, nem armazenamento, nem acesso à página do app. Restam duas saídas que dependem do navegador: o WebRTC só é bloqueado por navegadores que aplicam a diretiva webrtc da política — os navegadores baseados em Chromium (Chrome, Edge) a ignoram a partir da versão 149, e não conte com o Firefox também — portanto, neles um plugin ainda pode enviar o que lê por WebRTC; e uma dica de prefetch (dns-prefetch, preconnect) pode fazer um nome ser consultado. O frame pede ao navegador que não faça prefetch e a verificação sinaliza ambos como riscos altos — mas a verificação lê o texto dos arquivos em busca de padrões conhecidos: código escrito para escapar dela não é encontrado. Aprove apenas plugins em que você confia.
  • Nada sem aprovação. Um plugin só é executado depois que um administrador aprova seus arquivos exatos e as permissões que ele pede. Toda alteração nos arquivos exige uma nova aprovação.
  • As alterações passam pelo usuário. Um plugin que pode alterar documentos pede; o app mostra a alteração em uma caixa de diálogo própria e o usuário decide. Uma consulta ou um pipeline que um plugin prepara é colocado nos editores do próprio usuário, onde nada é executado até que o usuário o execute.

O Mongo Manager inclui vários plugins próprios (Mapa, Gráficos, Saúde do esquema, Localizador de duplicatas, Busca de valores, Referências, Comparação de documentos, SQL para MongoDB, Dicas de tempo, Visualização de binários, Dicionário de dados, Hora local, Analisador de logs, Dados de teste, Remodelagem, Anonimizador, Playground de busca, Analisador de chave de shard, Relatório de armazenamento, Verificação de validação, UUIDs legados, Filtros de data, Script de índice, Expiração (TTL), Localizador de dados pessoais, Tamanho do documento). Eles são executados no mesmo sandbox, conversam pela mesma ponte e são verificados da mesma forma que os seus; por serem código do próprio app, aprovar um deles nunca pede o id (veja Versões e aprovação). Os plugins podem ser desativados em todo o servidor com MM_PLUGINS=0 (veja Implantação).

Início rápido

Comece pelo modelo inicial: na página Plugins, em Crie seu próprio plugin, escolha Baixar o modelo inicial (.zip) (ele também é a pasta packages/plugins/starter do código-fonte do Mongo Manager). É um plugin completo em JavaScript simples, sem etapa de build e sem dependências: uma aba de coleção e uma página da barra lateral que listam os documentos de uma coleção.

  1. Descompacte-o, ou copie a pasta, para um novo repositório seu.
  2. Em mongo-manager-plugin.json, altere id, name, author e repository. O id deve ser único: ele dá nome à pasta do plugin em todos os servidores.
  3. Escreva sua página em main.js e style.css.
  4. Experimente no seu próprio servidor: node scripts/pack.mjs --folder ~/.mongo-manager/plugins, depois Plugins → Verificar novamente, veja a verificação e aprove. Veja Testes no seu próprio servidor.
  5. Empacote com node scripts/pack.mjs, que grava <id>-<version>.tgz, e anexe esse arquivo a um release do GitHub. Veja Publicação no GitHub.

O modelo inicial também contém arquivos de instruções para assistentes de programação com IA (CLAUDE.md, AGENTS.md, GEMINI.md e .github/copilot-instructions.md); veja Criação com um assistente de IA.

Arquivos e estrutura de pastas

hello-documents/
  mongo-manager-plugin.json   the manifest (required, at the top)
  index.html                  the entry page every contribution opens
  main.js                     the page's script (an ES module)
  style.css                   the page's styles
  README.md                   shown to administrators on the plugin's details page
  README.tr.md, README.zh.md  the same in another language of the app (optional)
  scripts/pack.mjs            packaging (not part of the plugin: left out of the archive)
  CLAUDE.md, AGENTS.md, ...   AI assistant files (left out of the archive)

As regras do app para os arquivos de um plugin:

  • No máximo 500 arquivos e 25 MB no total; o manifesto, no máximo 64 KB.
  • Todo caminho é relativo e simples: cada parte começa com uma letra, um dígito, _ ou - e contém apenas letras, dígitos, ., _ e -, com no máximo 100 caracteres; no máximo 16 níveis de profundidade e 240 caracteres no total. Sem arquivos ou pastas ocultos (um nome que começa com .), sem espaços, sem nomes de dispositivo (con, nul, com1...), sem __proto__, constructor ou prototype.
  • Somente arquivos e pastas: links, junções e arquivos especiais tornam o plugin inutilizável.
  • Nenhum par de caminhos que difira apenas por maiúsculas e minúsculas.
  • Os arquivos são servidos com um tipo tirado da extensão: html, js, mjs, css, json, map, txt, svg, png, jpg, jpeg, gif, webp, avif, ico, woff, woff2, ttf, otf. Qualquer outro é servido como bytes e nunca é executado.

O manifesto

O mongo-manager-plugin.json é verificado de forma rigorosa: um campo desconhecido, um tipo errado ou um valor fora do intervalo torna o plugin inutilizável, e a página Plugins diz qual campo está errado. Textos que uma pessoa lê (nomes, títulos, notas) não podem conter caracteres de controle nem caracteres que ocultam ou invertem texto. 

{
  "id": "hello-documents",
  "name": { "en": "Hello documents", "tr": "Merhaba belgeler" },
  "version": "0.1.0",
  "description": { "en": "Lists the documents of a collection.", "tr": "Bir koleksiyonun belgelerini listeler." },
  "entry": "index.html",
  "permissions": ["documents:read"],
  "contributes": {
    "collectionTabs": [{ "id": "list", "title": { "en": "Hello", "tr": "Merhaba" }, "icon": "table" }],
    "sidebarPanels": [{ "id": "page", "title": { "en": "Hello documents" }, "icon": "puzzle" }]
  },
  "settings": {},
  "author": { "name": "Your Name", "url": "https://example.com" },
  "homepage": "https://example.com/hello-documents",
  "repository": "https://github.com/your-name/hello-documents",
  "license": "MIT",
  "publishedAt": "2026-10-11",
  "changelog": [
    { "version": "0.1.0", "date": "2026-10-11", "notes": { "en": "First release.", "tr": "İlk sürüm." } }
  ]
}
Campo Obrigatório Regras
id sim Letras minúsculas e dígitos, separados por hífen (geojson-map), com no máximo 64 caracteres. Deve ser igual ao nome da pasta do plugin. O id de um plugin incluído no Mongo Manager não pode ser usado, nem um que se leia como um nome que o app reserva (abaixo).
name sim Texto localizado, com no máximo 60 caracteres: { "en": "...", "tr": "..." }. Sem caracteres invisíveis (largura zero, tag, seletor de variação — os próprios de um emoji são permitidos) e nunca um nome que se leia como mensagens do próprio app: Mongo Manager (ou um que comece assim), MongoDB, System, Session, Security, Admin, Server, Update e semelhantes, em qualquer idioma do app, comparados como são lidos: sem considerar maiúsculas, espaços, acentos e letras parecidas. Em cada palavra, as letras são todas latinas ou nenhuma delas (nunca grego e cirílico juntos), e nenhum parêntese contém o que se leia como um id ((value-search); (beta) é permitido). O app mostra as mensagens e perguntas de um plugin com o id ao lado do nome.
version sim Versionamento semântico: major.minor.patch, opcionalmente com uma pré-versão (1.2.0-beta.1), com no máximo 64 caracteres.
description não Texto localizado, com no máximo 300 caracteres.
entry sim A página que toda contribuição abre: um caminho simples para um arquivo .html do plugin.
permissions não Qualquer uma entre documents:read, documents:write, collection:read, database:read, cada uma no máximo uma vez. Padrão: nenhuma. Veja Permissões.
contributes não collectionTabs, documentActions, sidebarPanels e cellRenderers: listas de no máximo 5 cada, com ids únicos dentro de cada lista. Veja Pontos de contribuição.
settings não No máximo 10, por chave (uma letra, depois letras e dígitos, com no máximo 32 caracteres): { "type": "url" | "text" | "boolean", "title": texto localizado de no máximo 60 }. Os administradores definem os valores; a página os lê no contexto.
author não { "name": texto de no máximo 80, "url": um endereço https (opcional) }.
homepage, repository não Um endereço https:// com host, de no máximo 300 caracteres, sem credenciais, espaços ou barras invertidas.
license não Uma expressão SPDX, com no máximo 40 caracteres: MIT, Apache-2.0 OR MIT.
publishedAt não Um dia que exista, YYYY-MM-DD, entre 1900 e 2100.
changelog não No máximo 50 entradas { "version", "date": "YYYY-MM-DD", "notes": texto localizado de no máximo 1000 }; cada versão no máximo uma vez e nenhuma posterior à version do manifesto.

Texto localizado é um objeto com en (obrigatório) e, opcionalmente, qualquer um dos outros idiomas do app: tr, zh (chinês simplificado), ja, es, pt (português do Brasil), ko, de, fr e ru; o inglês é exibido quando falta o idioma do leitor. Uma contribuição é { "id", "title": texto localizado de no máximo 40, "icon" }: seu id é uma letra minúscula, seguida de letras minúsculas, dígitos e hífens, com no máximo 32 caracteres, e seu ícone é um entre map, chart, table, file, image, globe, layers, puzzle, book, wand, shapes, scroll, code, calendar, hourglass, shield, fingerprint, ruler (os ícones do próprio app: um plugin não traz nenhum). Um renderizador de célula é { "id", "match" }, com um "display" opcional: inline (o padrão) ou tooltip.

Uma configuração url deve ser um endereço https sem credenciais (http simples apenas para este computador: localhost, 127.0.0.1 ou [::1]); seu esquema, host e porta são adicionados às imagens que o frame pode carregar (para blocos de mapa: um {s}. inicial vira qualquer subdomínio, apenas antes de um nome de duas partes ou mais, nunca de um endereço). O endereço de uma imagem pode carregar dados: o plugin pode enviar o que lê a esse servidor, e a aprovação e a configuração informam isso. Uma configuração text tem no máximo 500 caracteres. Todo usuário do plugin pode ler suas configurações: nunca peça um segredo. O servidor as armazena criptografadas com a chave dele, como qualquer outro valor salvo.

Pontos de contribuição

Toda contribuição abre a mesma página de entrada. A página descobre qual é pelo fragmento do endereço, #<kind>=<id> (por exemplo #collectionTab=list), e por contribution no contexto.

Tipo Onde aparece e como abre
collectionTabs Uma aba de cada coleção, depois das abas do próprio app, também nas visualizações. O frame preenche a aba. Seu place é essa coleção, com o filter de Documentos que o usuário definiu. A página é carregada de novo cada vez que a aba é exibida, a menos que ela tenha pedido para permanecer com ui.keepOpen: então ela permanece carregada enquanto outra seção da aba dessa coleção é exibida (fora de vista, ela pode ler, mas não agir: not_visible).
documentActions Uma entrada no menu de ações de um documento em Documentos, exibida apenas para um plugin aprovado para documents:read. Abre uma caixa de diálogo com a página; place.documentId é o _id desse documento. A caixa de diálogo fecha quando o plugin coloca uma consulta ou um pipeline no lugar (ui.useQuery, ui.useQueryIn, ui.useAggregation).
sidebarPanels Uma entrada na barra lateral que abre uma página própria, uma aba do espaço de trabalho em /plugin/<id>/<contribution>. Se clicada enquanto a aba de uma coleção está ativa, a página abre nessa coleção (/plugin/<id>/<contribution>/<connection>/<db>/<collection>) e place a nomeia; de qualquer outro lugar, place é null. Uma página aberta a partir de um link pergunta ao usuário antes de ler essa coleção, e o usuário pode continuar sem uma. A página permanece carregada enquanto outra aba é exibida; fora de vista, ela ainda pode ler, mas não agir (not_visible).
cellRenderers Um texto curto sobre valores em qualquer lugar em que Documentos os mostra (tabela, árvore, cartões, a página do documento, detalhes do change stream), como a data em que um ObjectId foi criado: ao lado do valor ("display": "inline", o padrão) ou em uma dica de ferramenta ("display": "tooltip") que a célula ou a linha exibe quando recebe o ponteiro ou o foco, abaixo do valor inteiro e marcada com o nome do plugin. O texto de uma dica de ferramenta é simples, e seu tone não é usado; um leitor de tela o lê junto com o valor. Um plugin diz um texto ao lado de um valor e um em sua dica de ferramenta: seu primeiro renderizador para cada lugar que responde. A página é executada em um frame oculto, um por plugin, apenas para um plugin aprovado para documents:read; ela nunca se mostra. match é um entre geojson, string, number, date, object, objectId, binary (não um UUID). Veja Renderizadores de célula.

Renderizadores de célula

O app pergunta ao frame oculto sobre os valores que mostra, em lotes de no máximo 200, com uma mensagem cells.render. Com o kit, responda por meio de client.onCells: 

client.onCells((renderer, values, locale, paths, place) =>
  values.map((v) => (typeof v?.$oid === 'string' ? { text: createdAt(v.$oid, locale), tone: 'info' } : null)),
)
  • renderer é o id da contribuição, values são os valores como Extended JSON canônico, locale é o idioma do app, paths é o caminho do campo de cada valor (ou null), place é a coleção de onde vêm os valores (ou null).
  • Um valor binary é enviado apenas com o início, nunca inteiro: { "$binaryHead": { "base64", "subType", "length" } } com seus primeiros 2.048 bytes — o suficiente para dizer o tipo e o tamanho de uma imagem.
  • Responda com um item por valor, em ordem: { "text", "tone" }, null para nenhum texto, ou { "retry": true } para ser perguntado de novo mais tarde. Uma lista de outro tamanho é ignorada.
  • O texto é exibido como texto simples — no máximo 80 caracteres ao lado do valor, 200 em uma dica de ferramenta — com caracteres de controle e ocultos removidos. tone é um entre neutral, info, success, warning, danger.
  • Uma resposta deve chegar em 3 segundos; caso contrário, o valor simples permanece e o valor é perguntado de novo após 30 segundos. As respostas são mantidas por valor, idioma e configurações do plugin: uma alteração nas configurações pergunta de novo, e uma resposta com mais de um minuto é pedida de novo na próxima vez que seu valor for exibido, com a resposta antiga permanecendo até a nova chegar (e permanecendo se o novo pedido falhar). A resposta de um valor binary é mantida sob o tamanho, o subtipo e um hash do início dele.
  • Um renderizador pode ler antes de responder (referências a outros documentos, por exemplo): ele passa o place que recebeu em seu pedido, { place, filter, ... }, e só pode ler ali. O place do contexto dele é null.

O contexto

context.get responde onde a página está e qual deve ser a aparência dela. Chame-o primeiro; quando uma coleção está aberta, a resposta pode levar até 3 segundos enquanto o app verifica se ela é uma visualização. 

{
  "plugin": { "id": "hello-documents", "version": "0.1.0" },
  "contribution": { "kind": "collectionTab", "id": "list" },
  "locale": "en",
  "theme": "dark",
  "accent": "emerald",
  "place": {
    "connectionId": "6650...",
    "connectionName": "Production",
    "db": "shop",
    "coll": "orders",
    "view": false,
    "documentId": null,
    "filter": { "status": "open" }
  },
  "settings": { "tileUrl": "https://tile.example.org/{z}/{x}/{y}.png" }
}
  • kind é collectionTab, documentAction, sidebarPanel ou cellRenderer.
  • locale é o idioma do app: en, tr, zh, ja, es, pt, ko, de, fr, ru.
  • theme é light ou dark.
  • accent é a cor de destaque do usuário: emerald, indigo, violet, ocean ou rose. Trate qualquer outro valor como emerald.
  • place é null quando a página foi aberta sem nenhuma coleção (uma página da barra lateral, um renderizador de célula). connectionName pode ser null. view é verdadeiro para uma visualização: ela pode ser lida, nunca gravada, e não tem índices. documentId é o documento de uma ação de documento, como Extended JSON canônico, ou null. filter é o filtro de Documentos para uma aba de coleção, ou {}. Ambos são dados: um plugin sem documents:read recebe null e {}.
  • hidden lista os caminhos de campo que as regras de dados pessoais ocultam do usuário na coleção, como listas de chaves ([["contact", "phone"]]; "*" uma chave, "**" qualquer número de chaves, em qualquer profundidade) — apenas nomes, para um plugin com documents:read; [] caso contrário; null quando o app não conseguiu descobrir a tempo (3 segundos). Os valores desse campo chegam como "***": nunca os tome pelo tipo dele.
  • settings contém os valores que um administrador definiu; uma configuração não definida está ausente.

Quando o usuário muda o idioma, o tema ou a cor de destaque, o app envia context.changed com locale, theme e accent (o client.onContext do kit). Aplique-os imediatamente: a página nunca deve exibir o outro tema ou idioma. Um plugin que pode ler documentos também recebe context.changed quando o filtro de Documentos muda enquanto a página dele está carregada — uma aba de coleção que chamou ui.keepOpen fica sabendo de todo filtro que o usuário define enquanto ela está fora de vista. Chame context.get de novo para obter o novo place.

A API da ponte

O protocolo

A página e o app trocam JSON simples com postMessage. O kit (packages/plugins/kit/src/client.ts) e o main.js do modelo inicial o implementam; as regras, caso você escreva o seu:

  1. Leia apenas mensagens cujo event.source seja window.parent e cujo mm seja 1.
  2. Quando a página termina de carregar, o app a cumprimenta: { "mm": 1, "type": "hello", "token": "..." }. Guarde o primeiro token. Não envie nada antes dele.
  3. Um pedido é { "mm": 1, "id": 1, "method": "documents.find", "params": { ... }, "token": "..." }, enviado a window.parent com o destino '*' (a origem do frame é opaca). O id é um número ou uma string de no máximo 64 caracteres; o app ignora um pedido sem o token.
  4. A resposta traz o mesmo id: { "mm": 1, "id": 1, "result": ... } ou { "mm": 1, "id": 1, "error": { "code": "...", "message": "..." } }.
  5. O app envia { "mm": 1, "type": "context.changed", "locale", "theme", "accent" } quando o usuário os altera (e, para um plugin com documents:read, o filtro de Documentos), e pergunta a um renderizador de célula { "mm": 1, "id": "h1", "method": "cells.render", "params": { ... } }, que é respondido com { "mm": 1, "id": "h1", "token", "result": [...] }.

A página não deve sair do endereço dela. Se carregar outra página (um link, um formulário, uma alteração de location), o app fecha a ponte e remove o frame, e o usuário precisa abrir o plugin de novo. Mantenha tudo em uma única página. 

import { createClient, askMessage, AskError } from './kit/client'

const client = createClient()                       // requests time out after 15 s ("timeout")
client.onContext((locale, theme, accent) => restyle(locale, theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  if (!context.place) return showNoCollection()
  try {
    const { documents, hasMore } = await client.ask('documents.find', { filter: context.place.filter, limit: 100 })
    show(documents, hasMore)
  } catch (e) {
    showError(askMessage(e, context.locale))         // the app's code, in the user's language
  }
})

Métodos

Os valores são Extended JSON canônico nos dois sentidos: um ObjectId é { "$oid": "..." }, uma data { "$date": { "$numberLong": "..." } }, um int { "$numberInt": "3" }. Toda leitura é executada como o usuário, com os direitos dele e com o mascaramento do app. Os métodos marcados com "na sua coleção" funcionam na coleção em place e falham com no_collection sem uma.

Método e permissão Parâmetros → resultado Regras
context.get
nenhuma		 nenhum → o contexto Veja O contexto.
documents.find
documents:read		 { filter?, projection?, sort?, limit?, fit? } → { documents, hasMore, cut? } Na sua coleção. limit de 1 a 1000, padrão 100. No máximo 10 segundos. Um documento que o usuário não pode ver é omitido. Não é uma das consultas recentes do usuário.
documents.get
documents:read		 { id } → o documento, ou null Na sua coleção. id é o valor de _id.
documents.aggregate
documents:read		 { pipeline, limit?, fit? } → { documents, truncated, cut? } Na sua coleção. Apenas estágios de leitura: $match, $group, $sort, $limit, $skip, $project, $addFields, $set, $unset, $count, $unwind, $sortByCount, $bucket, $bucketAuto, $facet (sem $facet dentro dele), $replaceRoot, $replaceWith, $sample; no máximo 50 estágios. Com database:read, também um $lookup simples com exatamente from, localField, foreignField e as, de uma coleção do mesmo banco de dados. limit de 1 a 1000, padrão 100. No máximo 10 segundos, sem nunca gravar em disco, um pipeline por vez (busy: o serialAsk do kit os coloca em fila).
documents.update
documents:write		 { id, set?, unset? } → { modified } Na sua coleção, apenas à vista, somente logo após um clique na página do plugin. set é um objeto de campos e valores, unset uma lista de nomes de campo; pelo menos uma alteração; um nome de campo com caractere de controle, de quebra de linha ou de direção é recusado (bad_params). O app mostra ao usuário cada campo alterado, cada um entre aspas, na primeira linha da pergunta, e depois a alteração inteira, com todo caractere oculto ou invisível escrito por extenso, e só a aplica se o usuário concordar; o botão Confirmar só aceita um clique depois de um instante sem pressionar nada, depois que o ponteiro foi movido até ele. Recusado em uma visualização (read_only), para uma alteração longa demais para ser mostrada (mais de 2000 caracteres: too_large), enquanto outra pergunta aguarda (busy) e depois que o usuário recusou duas vezes (blocked, até que o plugin seja aberto de novo). Uma recusa é declined.
indexes.list
collection:read		 { coll? } → [{ name, key, options, usage }] Na sua coleção, ou em outra do banco de dados dela (coll, uma que collections.list nomeie), o que exige também database:read. Uma visualização não tem nenhum: [].
collections.list

Limites

  • Uma mensagem tem no máximo 1 MB em qualquer sentido; uma resposta maior falha com too_large. Peça menos documentos ou projete menos campos, ou passe fit: true para documents.find, documents.findIn ou documents.aggregate: o app então responde com tantos documentos inteiros, em ordem, quantos couberem, e cut: true indica que deixou o resto de fora (hasMore ou truncated fica true). Uma amostra pode ficar com o que chegou; uma leitura em páginas continua depois do último documento recebido. Se nem um documento couber, continua sendo too_large.
  • No máximo 8 pedidos aguardam ao mesmo tempo (too_many).
  • No máximo 60 leituras por minuto por frame (documents.find, .get, .aggregate, .findIn, collections.list, database.model) e, à parte, 120 leituras de definições (indexes.list, validation.get): um dicionário de 50 coleções é um modelo e 100 definições.
  • Logo após um clique na página do plugin. ui.copy, ui.useQuery, ui.useAggregation, ui.importSql, ui.exportSql, ui.openDocument, ui.download, ui.importDocuments e documents.update só são aceitos enquanto o clique ou o toque de tecla do usuário na própria página do plugin é recente: o frame deve ter o foco, portanto um clique em outro lugar do app nunca conta. Chame-os diretamente no manipulador de clique, antes de aguardar qualquer outra coisa; caso contrário, falham com no_activation. Toda tentativa de ui.copy, de um ui.use…, de uma página de SQL ou de ui.openDocument conta para o limite desse método, recusada ou não: um plugin que tenta de novo e de novo, esperando um clique, gasta o seu minuto (too_many); documents.update é limitado, em vez disso, por sua única pergunta por vez e pelos dois nãos. Um frame pode receber o foco sem um clique, portanto um ui.copy, ui.download ou ui.importDocuments pedido até 5 segundos depois de um clique ou toque de tecla em outro lugar do app (o tempo que dura a ativação dele pelo navegador) não é feito apenas porque o plugin pediu: o app pergunta ao usuário, nomeando o plugin e o que ele quer (quantos caracteres e como o texto começa, com caracteres ocultos escritos por extenso; o nome e o tamanho do arquivo; quantos documentos para qual coleção), e o faz com um clique no próprio botão Copiar, Salvar ou Abrir; a resposta do plugin aguarda por isso (declined quando o usuário dispensa, unanswered quando fica sem resposta, busy enquanto uma aguarda). Toda pergunta que o app faz por um plugin — essas, uma alteração, estágios colocados no lugar — termina após 150 segundos, mesmo com o ponteiro sobre ela; o kit espera 180 segundos por esses pedidos, de modo que uma página ouve a resposta do app, nunca o próprio tempo limite.
  • À vista. documents.update, ui.openDocument e os métodos acima falham com not_visible a partir de um renderizador de célula ou de uma página mantida enquanto outra aba é exibida.

Permissões

Um administrador aprova um plugin para as permissões que ele lista, como a página Plugins as nomeia. Peça o mínimo de que você precisa: cada uma é um motivo para um administrador dizer não.

Permissão O que o administrador lê O que ela permite
documents:read ler documentos documents.find, .get, .aggregate; ações de documento e renderizadores de célula só são oferecidos com ela.
documents:write alterar documentos (cada alteração confirmada) documents.update, cada alteração confirmada pelo usuário. Pedi-la é sempre um achado de gravidade média da verificação, por si só.
collection:read ler os índices desta coleção indexes.list.
database:read ler as outras coleções do mesmo banco de dados (nomes e documentos) collections.list, documents.findIn, um $lookup simples.

Um plugin sem nenhuma permissão ainda pode exibir uma página, ler seu contexto e suas configurações e usar os métodos ui.*. Uma permissão nunca é mais do que o direito do próprio usuário: um usuário que não pode ler uma coleção também não consegue lê-la por meio de um plugin.

O sandbox

A página é carregada em um iframe com sandbox="allow-scripts", a partir de um endereço assinado que nomeia o plugin, sua versão, seus arquivos aprovados e a sessão do usuário, selado (um ticket: a página deve carregar em até 10 minutos, os outros arquivos dela enquanto essa sessão durar, no máximo 12 horas — uma sessão renovada no lugar, por um login em outra aba ou uma troca de senha, é acompanhada; depois de sair, o endereço não serve mais nada, e o navegador não guarda nenhum de seus arquivos). Todo arquivo servido é verificado em relação ao seu SHA-256 aprovado. A política dele (Content-Security-Policy), com X-DNS-Prefetch-Control: off: 

default-src 'none'; script-src <its files>; style-src <its files>;
img-src <its files> data: blob: <the origins of its url settings>; font-src <its files>;
connect-src 'none'; webrtc 'block'; frame-ancestors 'self'; base-uri 'none'; form-action 'none';
sandbox allow-scripts

O que isso significa para o seu código:

  • Nenhuma rede. Nenhum pedido a qualquer endereço, inclusive aos arquivos do próprio plugin: coloque os dados em um módulo de script (data.js) em vez de em um arquivo .json que você carregaria. Também não use WebRTC nem dicas de prefetch: nem todo navegador os bloqueia, e a verificação os sinaliza como riscos altos.
  • Nenhum código ou estilo embutido. Scripts e estilos vêm apenas dos arquivos do plugin. Nenhum <script> embutido, nenhum elemento <style>, nenhum atributo style, nenhum manipulador de evento embutido, nenhum eval. Definir uma propriedade no script (el.style.width = '40px') funciona.
  • Uma origem opaca. Sem cookies, sem localStorage, sem IndexedDB: eles falham. Mantenha o estado na memória; as configurações que um administrador escolhe vêm de settings do manifesto.
  • Sem pop-ups, caixas de diálogo, formulários ou downloads. window.open, alert, confirm e o envio de formulários não fazem nada. Copie com ui.copy; entregue arquivos ao usuário por meio da importação e exportação do próprio app.
  • Nenhum acesso ao app. A página não pode ler a página do app, a sessão dele nem o armazenamento dele. Ela apenas troca mensagens com ele.
  • Fontes e imagens são arquivos do próprio plugin (ou imagens data: e blob:).

A verificação de segurança

Os arquivos de todo plugin são verificados quando são encontrados ou instalados, antes de um administrador aprová-los. A verificação lê arquivos de script (.js, .mjs, .cjs), de marcação (.html, .htm, .svg) e de estilo (.css) linha por linha, comentários incluídos, e lista cada achado com sua gravidade, regra, arquivo, linha e um trecho. Os arquivos de marcação também são lidos inteiros, de modo que uma tag <script> ou um manipulador embutido espalhado por várias linhas também é encontrado. As bibliotecas incluídas no plugin são verificadas como o seu próprio código. A verificação é heurística: ela procura padrões conhecidos no texto, portanto código escrito para se esconder dela (um nome montado em partes, por exemplo) não é encontrado — uma verificação limpa não é prova de nada. Um plugin com um achado de gravidade alta só pode ser aprovado depois que o administrador digitar o id dele para aceitar o risco; o servidor aplica isso, e o log de auditoria registra as contagens da verificação e se um risco foi aceito. Evite todo achado alto e limite os médios ao que você consegue explicar.

Como passar na verificação:

  • Escreva texto com textContent, append('text') ou o auxiliar h() do kit; crie elementos com document.createElement. Para limpar um elemento, use replaceChildren(). Nenhum deles é sinalizado; atribuir ou acrescentar marcação (innerHTML = ou innerHTML +=) sempre é.
  • Anexe manipuladores com addEventListener, nunca na marcação.
  • Passe funções para setTimeout e setInterval. Alcance o app apenas por window.parent.postMessage.
  • Salve todo arquivo como UTF-8, sem bytes NUL (nunca como UTF-16).
  • Não inclua código que alcance o exterior, mesmo que não seja usado: confira o que uma biblioteca traz. Prefira um build que não seja minificado, ou explique o achado minified no seu README, e mantenha dados grandes fora de strings base64.
  • Lembre-se de que os comentários também são verificados: um comentário que cita eval( ou innerHTML = é um achado.
  • Diga no seu README por que cada achado restante é seguro: qual biblioteca, qual linha, por que ele nunca é executado ou por que o sandbox o impede.

Apenas arquivos de script, marcação e estilo são verificados; o manifesto é lido em busca de documents:write (sempre um achado de gravidade média: peça-o somente quando o plugin alterar documentos). São listados no máximo 10 achados de uma regra em um arquivo e no máximo 200 achados no total (os mais graves primeiro); as contagens sempre abrangem todos os achados. Todo padrão é executado em tempo linear, portanto a verificação termina rapidamente em qualquer arquivo. Se a própria verificação falhar, o plugin não é marcado como com defeito: ele fica sem verificação e (a menos que seja incluído no Mongo Manager) só pode ser aprovado com o id dele digitado, como com um achado alto. A verificação de um plugin incluído no Mongo Manager também é exibida, mas aprová-lo nunca pede o id.

Interface e temas

Um plugin deve parecer parte do app: suas cores, sua tipografia, seus espaçamentos, no tema e na cor de destaque do usuário. Os plugins do próprio Mongo Manager usam o kit de plugins em packages/plugins/kit:

  • kit/src/ui.css: os tokens de design do app (--ds-surface, --ds-fg, --ds-accent...) para claro e escuro e cada cor de destaque, e componentes (mm-btn, mm-table, mm-empty, mm-callout...). As fontes dele são arquivos dos pacotes @fontsource: inclua-as no seu plugin ou remova as regras @font-face para usar a fonte do sistema.
  • kit/src/ui.ts: applyLook(theme, accent) define html.dark e html[data-accent]; h(tag, props, ...children) cria elementos em que o texto é sempre texto; e icon, button, segmented, switchControl, chip, badge, pageHeader, emptyState, skeleton, callout, table, valueView, describeValue, formatNumber, statusLine, setBusy, serialAsk.
  • kit/src/client.ts: createClient, AskError, askMessage.

O kit é TypeScript, feito para ser empacotado: copie kit/src para o seu projeto e faça o build com o Vite (ou outro bundler) para caminhos relativos e sem script embutido, como o vite.config.ts dos plugins próprios: base: './', modulePreload: { polyfill: false }, assetsInlineLimit: 0. Empacote a saída do build, não os seus fontes. O modelo inicial, em vez disso, traz uma cópia curta do cliente e das cores em JavaScript e CSS simples. 

import './kit/ui.css'
import { createClient } from './kit/client'
import { applyLook, h, pageHeader, emptyState, button } from './kit/ui'

const client = createClient()
client.onContext((locale, theme, accent) => applyLook(theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  applyLook(context.theme, context.accent)
  document.body.append(
    h('div', { class: 'mm-page' },
      pageHeader({ icon: 'table', title: 'Hello', description: context.place?.coll ?? '' }),
      emptyState({ icon: 'search', title: 'Nothing yet', action: button({ label: 'Load', variant: 'primary' }) }),
    ),
  )
})

Projete para o lugar em que a página aparece: uma aba de coleção é larga, uma ação de documento é uma caixa de diálogo, uma página da barra lateral preenche o espaço de trabalho. Mostre um estado vazio quando não houver nada a exibir e place for null, um esqueleto durante a leitura e as palavras do app para uma recusa. Use botões e controles reais, para que a página funcione pelo teclado.

Idiomas

O app fala inglês, turco, chinês simplificado, japonês, espanhol, português do Brasil, coreano, alemão, francês e russo: context.locale é um entre en, tr, zh, ja, es, pt, ko, de, fr e ru. Um plugin deve falar quantos deles puder, e sempre inglês:

  • No manifesto, dê cada idioma que você tiver ao lado de en em todo texto localizado.
  • Na página, mantenha suas palavras em uma tabela por idioma, escolha por context.locale (inglês para um idioma que você não tem), defina document.documentElement.lang como o idioma em que seus textos realmente estão — en se você recorreu ao inglês — (zh-CN e pt-BR para chinês e português, para que os glifos corretos apareçam), formate os números nesse mesmo idioma e renderize de novo em context.changed.
  • Um renderizador de célula responde no locale em que cada lote é pedido.
  • Formate números e datas para o idioma (Intl.NumberFormat, Intl.DateTimeFormat).
  • Adicione README.<language>.md ao lado de README.md para cada idioma (README.tr.md, README.zh.md, …), e notas de versão em cada um.

README e notas de versão

O README.md no topo do plugin é exibido na página de detalhes dele, onde os administradores o leem antes de aprovar o plugin; o README.<language>.md (README.tr.md, README.ja.md, …) é exibido no lugar dele para quem usa o app nesse idioma. O README localizado só é exibido quando o README.md também existe. Ele é exibido como Markdown seguro: títulos, parágrafos, listas (um nível), negrito, itálico, código em linha e blocos de código. Links, imagens, tabelas e HTML são exibidos como texto simples. São exibidos no máximo 64 KB.

Um bom README diz, nesta ordem:

  1. O que o plugin faz, em duas ou três frases.
  2. Onde ele aparece: qual aba, ação, página ou texto de célula.
  3. Como usá-lo, passo a passo, com um exemplo.
  4. Cada permissão e por que ela é necessária.
  5. Suas configurações, se houver.
  6. Seus limites: quantos documentos ele lê, o que ele não trata.
  7. Cada achado da verificação que permanece e por que é seguro.

As notas de versão vão no changelog do manifesto, da mais recente para a mais antiga, uma entrada por versão com o dia e as notas em inglês e em cada um dos seus idiomas. A página de detalhes as exibe; depois de uma atualização, as versões desde a última são marcadas como novas.

Versões e aprovação

  • Uma aprovação vale para arquivos exatos: o resumo (digest) deles, o SHA-256 do caminho e do SHA-256 de cada arquivo. O administrador o vê antes de aprovar.
  • Qualquer alteração em qualquer arquivo de um plugin enviado ou de uma pasta de plugin (uma nova versão, um erro de digitação corrigido no README) o desativa até que um administrador o aprove de novo. Aumente version e adicione uma entrada de changelog a cada release, para que os administradores saibam o que aprovam.
  • Enviar um plugin cujo id já está instalado o substitui; ele permanece ativado apenas se os arquivos forem exatamente os aprovados. As configurações dele são mantidas enquanto o novo manifesto ainda as declarar com o mesmo tipo.
  • Uma pasta de plugin colocada manualmente é gerenciada manualmente: um envio do mesmo id é recusado, e removê-la no app a esquece sem excluir a pasta.
  • Apenas os plugins incluídos no Mongo Manager mantêm a aprovação em uma atualização, e somente enquanto estão ativados e a atualização não pede nenhuma permissão nova; nada é pedido a um administrador então, e a página de detalhes do plugin informa que ele manteve a aprovação. Uma atualização que um administrador aprovou manualmente informa que foi aprovada por um administrador.

Empacotamento

Um plugin viaja como um arquivo tar compactado com gzip (.tgz) cujos arquivos ficam na raiz do arquivo, com o mongo-manager-plugin.json entre eles. Uma única pasta de nível superior contendo tudo (como o package/ do npm pack) é aceita e removida. O arquivo deve conter apenas arquivos regulares (as pastas ficam implícitas); links, dispositivos, entradas especiais, caminhos que não são simples e caminhos repetidos são recusados; no máximo 500 arquivos e 25 MB descompactados, e no máximo 30 MB enviados.

O scripts/pack.mjs do modelo inicial faz isso somente com o Node.js:

Ele verifica os caminhos e os limites como o app faz, deixa de fora o que não faz parte do plugin (arquivos ocultos, scripts/, node_modules/, os arquivos do assistente de IA, arquivos de pacote e arquivos compactados; edite a lista SKIP dele conforme sua necessidade), grava <id>-<version>.tgz e imprime o digest que o administrador verá. Se você usa um bundler, empacote a pasta de saída do build, com o manifesto no topo.

Publicação no GitHub

Os administradores podem instalar um plugin diretamente de um repositório público do GitHub, em um servidor configurado para permitir isso (MM_PLUGINS_GITHUB=1; vem desativado por padrão). Na página Plugins, eles colam um destes endereços:

  • https://github.com/<owner>/<repo>, …/releases ou …/releases/latest para o release mais recente;
  • https://github.com/<owner>/<repo>/releases/tag/<tag> para um específico. A tag pode conter barras (no máximo 4 partes).

O endereço não contém mais nada: nenhuma consulta, fragmento, porta ou credenciais. Um repositório renomeado é acompanhado: o próprio endereço da página do release nomeia o repositório dele. O app baixa o arquivo do plugin desse release, seu único recurso cujo nome termina em .tgz ou .tar.gz. Um release sem esse recurso, ou com vários, é recusado. Os nomes da tag e do recurso devem ser ASCII imprimível. O recurso deve pertencer aos releases desse repositório e não pode ser maior que um envio (30 MB), tanto como declarado quanto como lido.

O app fala apenas com github.com, api.github.com, objects.githubusercontent.com e release-assets.githubusercontent.com, por https, apenas em endereços públicos, e não envia nada do servidor (nenhum cookie, token ou credencial). Ele segue no máximo 4 redirecionamentos, apenas entre esses hosts, lê a descrição do release até 5 MB e dá 4 minutos para a instalação inteira. O plugin é instalado desativado, com a verificação, e aguarda aprovação como um envio. Ele lembra de onde veio (repositório, release e arquivo), o que aparece na página de detalhes dele.

Quando a instalação falha, a página Plugins diz por quê: o repositório não tem release publicado, o limite de requisições do GitHub foi atingido, o GitHub recusou (o repositório não é público), não foi possível alcançar o GitHub a partir do servidor, um redirecionamento foi para um host não permitido, houve redirecionamentos demais, o release não tem arquivo ou tem vários, ou o arquivo não está nos releases desse repositório.

  1. Aumente version, adicione uma entrada de changelog e defina publishedAt.
  2. Execute node scripts/pack.mjs.
  3. Crie um release no GitHub (tag v0.1.0, por exemplo) e anexe hello-documents-0.1.0.tgz como recurso dele. Não anexe nenhum outro arquivo .tgz ou .tar.gz.
  4. Marque-o como o release mais recente. Coloque o digest impresso por pack.mjs nas notas do release, para que os administradores possam compará-lo com o que o app mostra.

As instalações pelo GitHub ficam desativadas, a menos que MM_PLUGINS_GITHUB=1 esteja definido; um servidor também pode não conseguir alcançar o GitHub, ou alcançá-lo apenas por um proxy (a instalação se conecta diretamente ao GitHub e não usa as configurações de proxy HTTP); os administradores dele então baixam o .tgz e o enviam com Enviar plugin.

Para que outras pessoas o encontrem, inclua seu plugin no Awesome Mongo Manager (github.com/mongo-manager/awesome-mongo-manager): abra lá um pull request que adicione uma linha ao README. As verificações da lista baixam sua versão mais recente e a verificam com o próprio código do app, como faz uma instalação a partir do GitHub; depois, um mantenedor lê o plugin antes de incluí-lo.

Testes no seu próprio servidor

  1. Execute o Mongo Manager com plugins ativados (o padrão) e entre como administrador. Encontre o diretório de dados dele: ~/.mongo-manager, a menos que MM_DATA_DIR diga outra coisa.
  2. Copie o plugin para <data-dir>/plugins/<id>: node scripts/pack.mjs --folder ~/.mongo-manager/plugins. O nome da pasta deve ser o id, e ela não pode conter arquivos ocultos (é por isso que o script copia apenas os arquivos do plugin). ~/ é a sua pasta pessoal em qualquer shell; ~\ no cmd e no PowerShell, ou entre aspas (bash e zsh descartam uma barra invertida sem aspas, e o script então recusa o que sobra). O script substitui apenas uma pasta deste plugin que contenha somente arquivos e pastas que ele poderia ter copiado (sem scripts, arquivos ocultos, links, pipes ou sockets) e não tenha nenhum sistema de arquivos montado nela ou dentro dela, trocando a nova cópia de modo que uma cópia interrompida deixe a pasta como estava. Ele recusa um destino que seja a própria pasta do plugin, esteja dentro dela ou a contenha, seja qual for a forma como o caminho a nomeia (um link simbólico, uma junção ou um compartilhamento); nada é gravado então.
  3. Abra Plugins e clique em Verificar novamente. Um plugin que não pode ser usado diz por quê (um campo do manifesto, um caminho). Abra os detalhes dele: leia os achados da verificação, as permissões e o README como um administrador faria.
  4. Clique em Aprovar e ativar, depois abra uma coleção e experimente cada contribuição.
  5. Após cada alteração, copie de novo, clique em Verificar novamente e aprove de novo (os arquivos mudaram), depois reabra a aba, a página ou a caixa de diálogo. Experimente vários idiomas, os dois temas, uma visualização, uma coleção sem documentos e uma página da barra lateral aberta sem coleção.
  6. Por fim, envie o próprio .tgz com Enviar plugin em um servidor limpo, como os seus usuários farão.

As ferramentas de desenvolvedor do navegador funcionam dentro do frame: escolha o frame do plugin no console para ver os erros e as mensagens dele. Uma violação de política no console significa que a página tentou algo que o sandbox proíbe.

Criação com um assistente de IA

O modelo inicial contém arquivos de instruções que ensinam a um assistente de programação com IA tudo o que está nesta página: as regras do manifesto, os métodos e permissões da ponte, o sandbox, a verificação, os idiomas, o README, o empacotamento e a publicação. Mantenha-os no topo do repositório do seu plugin; o pack.mjs os deixa de fora do arquivo. A página Plugins salva o modelo inicial como um .zip, e cada arquivo em separado, em Instruções para o seu assistente de IA, para adicionar a um plugin que você já tem; o do Copilot é salvo como copilot-instructions.md, para a pasta .github do seu repositório.

  • CLAUDE.md: Claude Code.
  • AGENTS.md: OpenAI Codex e outros agentes que leem AGENTS.md.
  • GEMINI.md: Gemini CLI.
  • .github/copilot-instructions.md: GitHub Copilot.

Peça ao assistente o que o seu plugin deve fazer; ele deve responder com código que passe na verificação e na lista de verificação abaixo. Leia o que ele escrever antes de publicar: é você quem os administradores consideram confiável.

Lista de verificação antes de publicar

  • O id é único e igual ao nome da pasta; a versão foi aumentada e tem uma entrada de changelog com o dia de hoje.
  • Todo texto localizado tem en e tr; a página acompanha locale e context.changed.
  • As permissões são o mínimo que funciona, e o README diz por que cada uma é necessária.
  • A verificação não mostra nenhum achado alto, e o README explica todos os outros.
  • O texto é escrito com textContent ou h(); nenhuma marcação é criada a partir de texto.
  • Nada alcança a rede (nenhum fetch, WebRTC ou dica de prefetch), usa armazenamento, abre pop-ups ou sai da página.
  • Nenhum script, estilo ou manipulador de evento embutido; todo caminho é relativo (./main.js).
  • Todo arquivo é salvo como UTF-8, sem bytes NUL.
  • A página acompanha o tema e a cor de destaque e funciona pelo teclado.
  • Ela trata place sendo null, uma visualização, uma coleção vazia e cada código de erro que possa encontrar.
  • As chamadas que exigem um clique são feitas diretamente no manipulador de clique.
  • As leituras grandes são limitadas: um limit, uma projeção, um pipeline por vez.
  • O README.md e suas traduções descrevem o plugin; license, author e repository estão definidos.
  • O .tgz foi enviado a um servidor limpo, verificado, aprovado e testado ali.
  • O release do GitHub tem exatamente um arquivo de plugin, chamado <id>-<version>.tgz.
