Administração do servidor

Além dos seus dados, o Mongo Manager gerencia o próprio servidor MongoDB: os usuários e as funções do banco de dados, o sharding de um cluster, os alertas quando algo dá errado e a saúde de cada conexão em um relance.

Usuários e funções

A página de uma conexão → Usuários e funções gerencia as contas do próprio MongoDB, como o Database Access no Atlas. Essas são as contas que aplicativos e pessoas usam para entrar no MongoDB, não os usuários do Mongo Manager.

Quem pode usar

  • Usuários com a permissão do app databases:admin na conexão: administradores do app ou um usuário com administração concedida nessa conexão. Um usuário de quem um administrador oculta os dados pessoais nunca vê esta seção; quem os oculta de si mesmo a vê.
  • Os direitos do próprio MongoDB também se aplicam: a conta com a qual a conexão entra precisa de userAdmin no banco de dados, ou de userAdminAnyDatabase (viewUser e viewRole bastam para listar). Quando o MongoDB recusa, a página informa que o MongoDB recusou, e qual comando — e não o app.
  • Em uma conexão somente leitura, usuários e funções são listados, mas nunca alterados.

A lista

Usuários de todos os bancos de dados ou de um só (o filtro de banco de dados), com busca. As funções de cada usuário aparecem como chips, "readWrite on shop", por exemplo. A conta com a qual a própria conexão entra é marcada como Esta conexão.

Adicionar um usuário

  • Banco de dados de autenticação: onde o usuário entra. Recomenda-se admin (os usuários ali podem ter funções em qualquer banco de dados), mas qualquer banco de dados funciona. $external é para usuários x.509, LDAP, Kerberos e AWS IAM, que não têm senha: o nome deve corresponder exatamente ao que essa origem envia.
  • Nome de usuário.
  • Senha: digite uma ou pressione Gerar para obter 24 caracteres aleatórios criados no seu navegador a partir da fonte aleatória do sistema, seguros em uma string de conexão e exibidos para que você os copie.
  • Funções: funções integradas, cada uma com o que permite, ou as suas funções personalizadas, cada uma em um banco de dados. As funções que existem somente em admin (clusterMonitor, backup, root e semelhantes) ficam fixas nele.

As senhas usam SCRAM-SHA-256 e precisam ter pelo menos 12 caracteres. Uma senha é enviada ao MongoDB uma única vez; o Mongo Manager nunca a armazena, registra em log nem grava no log de auditoria. Copie a senha gerada antes de fechar o formulário. Conceder direitos amplos pede uma confirmação antes, e o servidor os recusa sem confirmação: as funções integradas root, userAdminAnyDatabase, userAdmin, dbOwner, clusterAdmin, clusterManager, hostManager, backup, restore, readWriteAnyDatabase e dbAdminAnyDatabase, todas as outras funções integradas do banco de dados admin (readAnyDatabase, clusterMonitor, enableSharding), qualquer função de local (ele contém o oplog, toda gravação feita) ou de config (os metadados de sharding) e qualquer função personalizada que herde uma delas ou tenha um privilégio sobre o cluster, sobre qualquer recurso, sobre todos os bancos de dados de uma só vez ou sobre local e config, ou que crie usuários ou funções (createUser, grantRole, changePassword e semelhantes). Essas funções personalizadas são marcadas como amplas, e criar uma também exige confirmação.

Alterar e descartar usuários

  • Editar define uma nova senha, novas funções ou ambos. As funções que você salva substituem a lista do usuário.
  • Alterar ou descartar a conta da própria conexão avisa que isso pode bloquear o acesso da conexão e exige confirmação. O mesmo vale para alterar ou descartar uma função personalizada que essa conta possui. Qual é essa conta, o próprio MongoDB informa (não as configurações da conexão, que um registro SRV ou um certificado podem alterar). Depois de uma nova senha, edite também a conexão.
  • Descartar um usuário ou uma função pede que você digite o nome dele.

Funções personalizadas

As Funções personalizadas dão a uma equipe exatamente as ações de que ela precisa, e nada além disso. Uma função tem um banco de dados, um nome, privilégios e funções herdadas.

  • Cada privilégio se aplica a um banco de dados e uma coleção (se deixado vazio, qualquer banco de dados ou qualquer coleção), ao cluster ou a qualquer recurso.
  • As ações são escolhidas na lista do MongoDB, agrupadas em consulta e gravação, gerenciamento de banco de dados, usuários e funções, implantação, replicação e sharding.
  • Uma função fora de admin herda apenas funções do próprio banco de dados (regra do MongoDB); uma função em admin pode herdar funções de qualquer banco de dados.

Toda alteração fica no log de auditoria como mongo.users.create, mongo.users.update, mongo.users.grant, mongo.users.revoke, mongo.users.drop, mongo.roles.create, mongo.roles.update e mongo.roles.drop, com os nomes e as listas de funções, nunca uma senha.

Sharding

A página de uma conexão → Sharding aparece quando a conexão é com um mongos. Todos que podem observar o servidor veem o estado do balanceador, a distribuição de chunks e a visão geral do cluster. As alterações exigem databases:admin e uma conexão que não seja somente leitura.

Distribuição de chunks

Uma barra por coleção fragmentada, uma cor por shard, com as contagens também em texto para leitores de tela.

O balanceador

  • Inicie-o ou pare-o; parar pede confirmação antes. Enquanto estiver parado, nenhum chunk se move entre shards; uma migração em andamento termina primeiro. Pare-o para um backup ou uma manutenção e depois inicie-o novamente.
  • Janela ativa: de–até, no relógio do servidor de configuração. Os chunks então se movem apenas dentro desses horários. A qualquer momento a remove.

Fragmentar uma coleção

  1. Escolha o banco de dados e a coleção.
  2. Monte a chave de shard campo a campo. Cada campo é por intervalo (ranged) ou com hash, com no máximo um campo com hash. A ordem importa: mova os campos para cima e para baixo.
  3. Verificar esta chave: o servidor coleta uma amostra de 1000 documentos e responde apenas com contagens, de modo que nenhum valor sai do MongoDB: a proporção de documentos que têm cada campo, o número de valores distintos, a proporção do valor mais comum, se os valores crescem com o tempo (ObjectId, datas) e se existe um índice que começa com os campos da chave. O veredicto é bom, razoável ou ruim.
  4. Opções: única (apenas chaves por intervalo); criar chunks antecipadamente (uma chave com hash em uma coleção vazia, MongoDB 6.0 e anteriores, de 1 a 8192 chunks); criar chunks por zona (uma chave com hash, com zonas já definidas).
  5. Fragmentar não pode ser desfeito: confirme digitando o namespace.

Um campo que cresce com o tempo, usado como chave por intervalo, envia cada novo documento para um único shard: use hash nele ou coloque outro campo primeiro. Uma coleção com dados precisa de um índice que comece com os campos da chave antes de poder ser fragmentada. Os namespaces do próprio MongoDB e os de sistema (admin, config, local, system.*) são recusados.

Zonas

  • Cada shard lista suas zonas; adicione uma zona a um shard ou remova uma.
  • Intervalos de chave por coleção: os limites são Extended JSON dos campos da chave de shard, com {"$minKey":1} e {"$maxKey":1} para extremos abertos, por exemplo {"region": "eu"} até {"region": "us"}. Operadores são recusados. O início é incluído; o fim, não.
  • Remova um intervalo quando os documentos dele puderem voltar a ficar em qualquer shard.

O log de auditoria registra sharding.collection.shard, sharding.zone.shard, sharding.zone.range (o namespace e a zona, nunca os valores dos limites), sharding.balancer e sharding.balancer.window. Os testes do Mongo Manager executam essas telas com respostas gravadas de um mongos.

Alertas

Os alertas avisam quando um servidor ultrapassa um limite ou quando uma das tarefas do próprio app falha: no sino, por e-mail ou em um webhook.

Limites de alerta

A página de uma conexão → Alertas, para administradores do app (settings:manage). Um limite de alerta observa uma métrica:

  • Conexões: conexões de clientes abertas (uma contagem).
  • Operações: operações por segundo, de todos os tipos juntos.
  • Atraso de replicação: segundos de atraso do secundário mais distante (conjuntos de réplicas).
  • Cache do WiredTiger: quão cheio está o cache, em porcentagem.
  • Uso de disco: porcentagem do disco dos arquivos de dados em uso (MongoDB 4.4 e posteriores).
  • Operações lentas: a contagem de operações em execução por mais segundos do que você escolher (exige clusterMonitor).

O servidor os avalia uma vez por minuto, a partir da mesma amostragem de serverStatus do histórico de métricas. Os alertas coletam amostras de uma conexão mesmo quando o histórico dela está desativado; as amostras só são armazenadas quando o histórico está ativado. No máximo 50 conexões são amostradas, somando histórico e alertas.

Sem oscilação: um alerta dispara quando o valor permanece acima do limite de alerta pelos minutos que você escolheu (de 1 a 60, padrão 2) e só é resolvido depois de permanecer em 90% do limite de alerta ou abaixo disso pelo mesmo tempo. Um limite de alerta de 80% de ocupação do cache é resolvido em 72% ou menos.

Alertas de evento

Na página Alertas, para todas as conexões ou uma só, ou na seção de uma conexão:

  • Backup com falha: uma tarefa de backup, envio ou busca falhou.
  • Backup agendado com falha: uma execução falhou ou alcançou apenas alguns dos seus destinos.
  • Sincronização em tempo real parada: ela falhou, parou ou precisa de atenção por conta própria — não quando uma pessoa a parou.
  • Tarefa com falha: qualquer outra tarefa (um teste de restauração tem o seu próprio evento).
  • Teste de restauração com falha: um teste de restauração agendado não conseguiu restaurar o backup, encontrou dados diferentes ou não conseguiu descartar o banco de dados temporário (um aviso: os dados correspondiam). Um teste que passou fica no histórico do agendamento, não é um alerta.
  • A sincronização bidirecional resolveu conflitos: os dois lados de uma sincronização em tempo real bidirecional alteraram os mesmos documentos; prevaleceu quem gravou por último (os _ids estão na atividade da sincronização).
  • O monitoramento correspondeu ao filtro de alerta: um feed de Observar cujo proprietário pediu alertas teve alterações que passaram pelo filtro (no máximo a cada 10 segundos, enquanto o feed estiver em execução).

As notificações carregam apenas nomes e números: nunca valores de documentos, textos de erro, strings de conexão nem hosts.

Relatórios agendados

Na página Alertas (administradores do app): um relatório informa algumas contagens de uma conexão em um agendamento — toda manhã, toda segunda-feira, com frequência de até uma hora — no sino, por e-mail ou em webhooks, da mesma forma que os alertas são enviados. Cada contagem tem seu rótulo, uma coleção e um filtro opcional (JSON; sem filtro, conta todos os documentos, a estimativa da coleção); uma contagem acima de um milhão diz "pelo menos". Execute um agora, altere-o, desative-o ou exclua-o na linha dele; as contagens da última execução são mostradas ali.

Apenas números, nunca um valor. Um filtro que cita um campo pessoal — ou que as regras de dados pessoais interpretariam de outro modo — é recusado quando o relatório é salvo e, quando as regras mudam depois, é omitido, com o motivo informado; o mesmo vale para os namespaces do próprio MongoDB, JavaScript de servidor, visualizações e séries temporais (o pipeline de uma visualização poderia escolher por um campo pessoal). Um relatório conta como credenciais da própria conexão: uma conexão em que cada pessoa entra por conta própria é recusada, assim como um filtro em uma conexão que criptografa campos no cliente (ele não corresponderia a nada que ela consiga ler). No sino e no histórico, os administradores veem as contagens de uma execução pelos rótulos delas; os demais veem que um relatório foi executado, não as contagens. As últimas 30 execuções de cada relatório são mantidas no histórico; um relatório cujo agendamento não pode mais ser calculado é desativado, com o motivo informado.

Canais

  • O sino. Cada usuário ativa Mostrar alertas no sino para si mesmo, em Preferências ou na página Alertas. Cada um vê alertas apenas das conexões cujo servidor pode observar (server:monitor).
  • E-mail. O servidor SMTP, a porta e o TLS desde o início (geralmente 465) ou STARTTLS (geralmente 587): um servidor que não oferece nenhum dos dois é recusado, e o e-mail nunca é enviado em texto simples. Um nome de usuário e uma senha (protegidos), o endereço De e até 20 destinatários. Um novo servidor, porta, criptografia ou nome de usuário exige que a senha seja digitada novamente: a senha salva nunca é enviada a outro servidor. Enviar mensagem de teste envia com as configurações salvas. Uma sessão que não conclui o handshake TLS ou a troca a tempo é abandonada. O e-mail passa pelo cliente do próprio Mongo Manager e pela proteção de saída (egress guard): endereços públicos e endereços privados somente dentro de MM_ALERTS_PRIVATE_NETWORKS.
  • Webhooks. Um endereço https; http simples somente para endereços dentro de MM_ALERTS_PRIVATE_NETWORKS. Sem credenciais no endereço, endereços de metadados de nuvem e link-local nunca, e os redirecionamentos não são seguidos. O servidor cria o segredo de assinatura de cada webhook e o mostra uma única vez; Gerar novo segredo o substitui, e o antigo deixa de funcionar imediatamente.

Cada regra escolhe para onde é enviada; uma regra sem canal apenas é registrada.

Entregas de webhook

Cada entrega é um POST com um corpo JSON:

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type é alert.firing, alert.resolved, alert.event ou alert.test (um teste carrega apenas type e at). Os alertas de evento definem event (backup.failed, schedule.failed, liveSync.stopped, job.failed) em vez de metric. Os cabeçalhos:

  • x-mm-event: o tipo novamente.
  • x-mm-delivery: um id único da entrega, o mesmo em cada nova tentativa.
  • x-mm-timestamp: segundos Unix em que esta tentativa foi assinada.
  • x-mm-signature: sha256= seguido do HMAC-SHA256 em hexadecimal, com o segredo do webhook, do timestamp, um ponto e o corpo.

Verifique a assinatura sobre o corpo bruto, antes de interpretá-lo, e recuse timestamps com mais de 5 minutos. Em Node.js: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

Em Python:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

Uma entrega é tentada até mais três vezes, após 2 segundos, 10 segundos e 60 segundos, em caso de erro de rede, resposta 5xx, 408 ou 429; nunca em qualquer outro 4xx, nem para um endereço que a proteção recusa. Cada tentativa é assinada novamente com um timestamp novo. Use x-mm-delivery para ignorar uma entrega que você já tratou.

Adiar, pausar e reconhecer

  • Adiar uma regra por 1 hora, 8 horas ou 1 dia: os alertas continuam sendo registrados, mas nada é enviado. Reativar agora encerra o adiamento antes do prazo.
  • Pause e retome uma regra com o interruptor dela.
  • Os administradores reconhecem um alerta para todos, que então veem quem o fez; os demais dispensam o alerta do próprio sino. Fora os administradores, o sino mostra o que aconteceu (seus códigos), mas não qual sincronização, tarefa, agendamento ou namespace.
  • As entregas saem poucas por vez a partir de uma única fila, não importa quantos canais e alertas disparem juntos.
  • O Histórico, na página Alertas e na seção de cada conexão, guarda 90 dias (no máximo 20.000 entradas), com o resultado de cada entrega e quantas tentativas foram necessárias.

MM_ALERTS=0 desativa os alertas no servidor: nada é avaliado nem enviado (veja Implantação). O log de auditoria registra alerts.rule.create, alerts.rule.update, alerts.rule.delete, alerts.rule.snooze, alerts.email.update, alerts.email.test, alerts.webhook.create, alerts.webhook.update, alerts.webhook.delete, alerts.webhook.test e alerts.acknowledge — nunca a senha SMTP nem o segredo de um webhook.

Saúde em tempo real

Os cartões de conexão na Visão geral mostram a latência de ping, a versão do MongoDB, a topologia de cada conexão e os alertas disparados nela. A página de uma conexão mostra o mesmo em seu cabeçalho, com um ponto de status.

  • O servidor mantém cada resposta por 30 segundos.
  • A lista nunca se conecta por conta própria: uma conexão que não está aberta mostra Não conectado. Abrir a página de uma conexão a verifica, como listar seus bancos de dados faria.
  • As contagens de alertas são mostradas apenas para conexões cujo servidor você pode observar.
