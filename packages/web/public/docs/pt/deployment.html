Implantação

Como serviço do sistema

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

O serviço roda com a própria conta sem privilégios, a partir de uma pasta de programa que somente administradores podem alterar, em modo equipe em 127.0.0.1:4321. A primeira inicialização guarda o token de configuração de uso único em setup-token, na pasta de dados, que somente a conta do serviço e os administradores podem ler; service install mostra como lê-lo. O token nunca é gravado no log, e o arquivo é removido assim que o primeiro administrador existe.

Instalado em modo local (--no-auth), o serviço só abre a partir de um link de acesso de uso único: service install mostra um, e service open mostra um novo sempre que você precisar (como administrador: ele é gerado a partir de launch.key, na pasta de dados). Abra-o no seu próprio navegador, não em um com privilégios elevados; esse navegador então continua autenticado enquanto mantiver os dados deste site, por no máximo seis meses após o último uso.

Docker

A imagem roda como um usuário sem privilégios em um sistema de arquivos raiz somente leitura, em modo equipe. Os dados ficam no volume /data. Máquinas offline podem carregar um arquivo de imagem com docker load -i. O token de configuração da primeira inicialização: docker exec <container> cat /data/setup-token. O arquivo compose publica a porta apenas no loopback do host (127.0.0.1:4321); para atender outras máquinas, coloque um proxy reverso HTTPS na frente em vez de publicar HTTP simples. Um proxy no host alcança o contêiner pelo gateway da rede do compose: confie em MM_TRUSTED_PROXIES=172.31.240.1, não em 127.0.0.1.

Dentro do contêiner, o servidor escuta em todos os endereços; por isso, sem MM_ALLOWED_HOSTS, ele responde apenas a endereços IP e a localhost (cada inicialização avisa isso). Tudo o que o alcança por um nome — um proxy que repassa o nome público, outro contêiner pelo nome do serviço (um Prometheus coletando mongo-manager:4321), um serviço do Kubernetes — recebe 403 até que esse nome esteja na lista: MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

No modo local (MM_AUTH=0), o log do contêiner indica o comando que mostra um link, nunca o link em si: docker exec <container> node /app/dist/cli.cjs open --no-open. Ele indica a porta em que o servidor escuta dentro do contêiner: se ela for publicada em outra porta do host (-p 127.0.0.1:8080:4321), troque a porta no link pela do host antes de abri-lo.

Em um servidor, coloque na frente um proxy reverso HTTPS que o sirva como mongo.example.com e inicie assim; a última linha lê o token de configuração. Conclua a configuração imediatamente: até que exista o primeiro administrador, quem tiver o token pode se tornar o administrador. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES é o endereço de onde um proxy no host alcança o contêiner: o gateway da rede do Docker, geralmente 172.17.0.1 na rede bridge padrão (docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}' o mostra). Sem ele, todas as requisições parecem vir do gateway, e o log de auditoria e os bloqueios de login não distinguem os usuários. Depois que MM_ALLOWED_HOSTS é definido, só os nomes listados são aceitos: adicione 127.0.0.1 para continuar abrindo http://127.0.0.1:4321 no host. --read-only, --tmpfs /tmp, --cap-drop ALL e no-new-privileges são o reforço que o arquivo compose aplica.

Alcançar o MongoDB a partir do contêiner

Dentro de um contêiner, localhost é o próprio contêiner, então mongodb://localhost:27017 falha com ECONNREFUSED mesmo quando o MongoDB roda na mesma máquina.

  • MongoDB em outro contêiner: coloque os dois em uma mesma rede do Docker (docker network create mm, depois docker network connect mm mongo-manager e docker network connect mm my-mongodb, ou --network mm ao iniciá-los) e conecte-se a mongodb://my-mongodb:27017.
  • MongoDB no host, Docker Desktop (Windows, macOS): mongodb://host.docker.internal:27017.
  • MongoDB no host, Linux: rode o Mongo Manager com --network host (então localhost é o host; mantenha-o privado com -e MM_HOST=127.0.0.1, atrás do proxy, confiável como 127.0.0.1) ou adicione --add-host=host.docker.internal:host-gateway. Esta segunda opção só alcança um MongoDB que escute no endereço do gateway da bridge: não um vinculado ao 127.0.0.1 do host, nem um contêiner publicado só ali (-p 127.0.0.1:27018:27017); para esses, use uma rede compartilhada ou a rede do host.
  • Um conjunto de réplicas cujos membros se chamam localhost:27017 manda o driver de volta para localhost: adicione ?directConnection=true.

Atrás de um proxy reverso

  • Confie somente no proxy: --trusted-proxies 127.0.0.1. Sem isso, o servidor não consegue saber que uma requisição chegou por HTTPS, então os cookies de sessão não são marcados como Secure; uma inicialização em modo equipe avisa isso, e avisa quando as autenticações atravessariam a rede por HTTP simples.
  • Informe o host público: --allowed-hosts mm.example.com.
  • Sirva sob um subcaminho com --base-path /mm/.
  • Cada endereço de cliente pode fazer 600 requisições de API por minuto; aumente o valor com MM_API_RATE_LIMIT (60–100000) quando muitas pessoas compartilham um mesmo endereço.
  • No máximo 1000 conexões ficam abertas ao mesmo tempo (MM_MAX_CONNECTIONS, 16–100000), e no máximo 256 de um mesmo endereço (MM_MAX_CONNECTIONS_PER_IP, 2–100000); uma conexão além desse limite é fechada, e o log informa isso uma vez por minuto para cada endereço. Um navegador mantém cerca de seis conexões abertas, então, onde muitas pessoas acessam o Mongo Manager de um mesmo endereço — atrás de um NAT, de uma VPN ou do Docker Desktop —, aumente MM_MAX_CONNECTIONS_PER_IP. Atrás de proxies confiáveis, vale apenas o total: todas as conexões vêm do proxy, que deve limitar os próprios clientes.
  • Os arquivos importados e exportados ficam em <data directory>/transfer: MM_TRANSFER_MAX_UPLOAD é o maior envio em MiB (padrão 1024, 1–65536), MM_TRANSFER_QUOTA o armazenamento que cada usuário pode ocupar em MiB (padrão 5120, 16–1048576), MM_TRANSFER_TOTAL_QUOTA o que todos os usuários juntos podem ocupar em MiB (padrão 51200, ou MM_TRANSFER_QUOTA quando este for maior; 16–16777216), MM_TRANSFER_TTL_HOURS por quanto tempo um arquivo é mantido (padrão 24, 1–720) e MM_TRANSFER_MAX_JOB_HOURS por quanto tempo uma importação ou exportação pode rodar (padrão 6, 1–72). Reserve espaço em disco para o total, ou para a cota vezes o número de pessoas que transferem arquivos, se isso for menor.

Configurações e variáveis de ambiente

Cada configuração do servidor pode ser informada como opção de linha de comando, como variável de ambiente ou em um arquivo de configuração JSON indicado por --config ou MM_CONFIG. A linha de comando prevalece sobre o ambiente, e o ambiente sobre o arquivo. Uma chave liga/desliga aceita 1/0, true/false, yes/no ou on/off. As configurações de cada recurso estão na seção correspondente, mais abaixo.

Variável Opção O que faz
MM_WEB_PORT -p, --web-port Porta da interface web (padrão 4321).
MM_HOST --host Endereço em que escutar (padrão 127.0.0.1). Um endereço de rede exige o modo equipe ou MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Modo equipe: usuários, funções e autenticação (padrão desativado).
MM_DATA_DIR --data-dir A pasta de dados (padrão ~/.mongo-manager).
MM_CONFIG --config Um arquivo de configuração JSON. No Linux e no macOS, um arquivo que contém um segredo não pode ser legível por outros usuários, ou o servidor o recusa.
MM_SECRET_KEY A chave de criptografia, no lugar do secret.key da pasta de dados.
MM_OPEN --open Abre o navegador ao iniciar (padrão ativado): no modo local, em um endereço de loopback, quando iniciado a partir de um terminal.
MM_URI --uri Uma conexão criada somente na primeira inicialização. Use a variável para uma string de conexão com senha: outros usuários podem ver as linhas de comando.
MM_READ_ONLY --read-only Nenhuma conexão pode alterar dados, seja qual for a sua própria configuração.
MM_TRUSTED_PROXIES --trusted-proxies Endereços de proxy ou intervalos CIDR cujos cabeçalhos X-Forwarded-* são aceitos como verdadeiros.
MM_ALLOWED_HOSTS --allowed-hosts Os únicos nomes de host aos quais o servidor responde. Sem definição, ele responde aos nomes de loopback quando escuta em loopback e, caso contrário, apenas aos nomes de loopback e a endereços IP, nunca a outro nome (uma defesa contra DNS rebinding; a inicialização avisa isso). Informe aqui todos os nomes de host pelos quais as pessoas o abrem.
MM_BASE_PATH --base-path Serve o app sob um subcaminho, como /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Permite um endereço de rede sem o modo equipe. Quem o alcançar terá acesso total.
MM_LOG_LEVEL --log-level fatal, error, warn, info (padrão), debug, trace ou silent.
MM_LOG_FILE --log-file Acrescenta o log JSON a este arquivo em vez da saída padrão. O arquivo é tornado privado (modo 0600; no Windows, o acesso de todos os usuários é retirado: esta conta, SYSTEM e Administrators o mantêm) e rotacionado a 10 MiB, com a parte anterior mantida como <file>.1. Um caminho que seja um link, um arquivo com outros nomes (hard links) ou que não seja um arquivo regular é recusado, e a inicialização falha informando isso: remova-o ou renomeie-o, ou indique outro arquivo de log. Uma linha que não possa ser gravada (disco cheio) é descartada e avisada uma vez na saída de erro padrão. As requisições são registradas pelo caminho, com todo valor de consulta e o id de um arquivo do GridFS gravados como ***.
MM_REQUIRE_ADMIN_2FA Todo administrador deve configurar a autenticação em dois fatores antes de qualquer outra coisa; ela não pode ser desativada no app depois disso. Sem esta variável, um administrador pode exigir o mesmo no app.
MM_REQUIRE_2FA Todo usuário, seja qual for a sua função, deve configurar a autenticação em dois fatores antes de qualquer outra coisa; ela não pode ser desativada no app depois disso. Sem esta variável, um administrador pode exigir o mesmo no app.
MM_METRICS_TOKEN Ativa as métricas do Prometheus em <base path>metrics, lidas com este token como token de portador (bearer), com pelo menos 32 caracteres. Os números não identificam nenhum usuário, conexão, banco de dados ou coleção.
MM_GRIDFS_MAX_MB O maior arquivo enviado ao GridFS, em MB (padrão 512, 1–10240).
MM_MODEL_MAX_DOCS Os documentos que um modelo de dados (a seção Modelo de um banco de dados) pode amostrar no total (padrão 20000, 100–1000000): com muitas coleções, a amostra de cada uma é reduzida, e a seção informa isso.
MM_ALLOW_KERBEROS Modo equipe: permite conexões Kerberos (GSSAPI) (padrão desativado). Elas se autenticam com o ticket Kerberos da conta sob a qual o servidor roda — todo usuário dessa conexão entra como essa conta. Veja Segurança.
MM_ALLOW_WORKLOAD_IDENTITY Modo equipe: permite que conexões OIDC usem a identidade de carga de trabalho da máquina (Azure, GCP, Kubernetes) quando escolhida na conexão (padrão desativado).
MM_OIDC_DEVICE_FLOW Autenticação OIDC com um código (o device flow), para provedores de identidade que não conseguem redirecionar o navegador de volta a este servidor. Quem aprova o código entra, por isso ele fica desativado no modo equipe, a menos que seja ativado aqui; no modo local, fica ativado.
MM_OIDC_PRIVATE_NETWORKS Redes privadas (CIDRs separados por vírgula) em que os provedores de identidade OIDC podem estar; http simples é permitido somente nelas. Sem esta variável, eles devem ser endereços https públicos.
MM_CRYPT_SHARED_LIB_PATH O caminho absoluto da biblioteca crypt_shared (mongo_crypt_v1) para a criptografia no cliente. No modo equipe, é a única carregada.
MM_KMS_PRIVATE_NETWORKS Redes privadas (CIDRs separados por vírgula) em que os serviços de gerenciamento de chaves (um servidor KMIP local) podem estar. Sem esta variável, eles devem ser endereços públicos.
MM_KMS_ALLOWED_HOSTS Hosts de serviços de gerenciamento de chaves (separados por vírgula, host ou host:port, porta 443 por padrão) que uma conexão pode acessar além dos próprios dos provedores (AWS KMS, Azure Key Vault e Managed HSM com a autenticação da Microsoft, Google Cloud KMS) e dos endpoints que as suas configurações indicam: um endpoint de VPC, um servidor KMIP. Qualquer outro host, ou outra porta, é recusado — a chave mestra de uma chave de dados não pode enviar o token do KMS para outro lugar.

Kerberos e criptografia no cliente (pacote npm)

O Kerberos (GSSAPI) e a criptografia no cliente em nível de campo / Queryable Encryption precisam de pacotes nativos, que o Mongo Manager não instala por conta própria: a instalação dele não executa o script de instalação de nenhum pacote. Para usá-los, instale os pacotes ao lado do pacote npm e depois reinicie: 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

O Mongo Manager os carrega somente da pasta global node_modules que contém o próprio mongo-manager (verificada pelo caminho real, nunca uma pasta acima dela) e somente quando uma conexão precisa de um deles pela primeira vez; o formulário de conexão informa qual está faltando e como instalá-lo. Os binários independentes, a imagem Docker (que define MM_DISTRIBUTION=docker) e a cópia a partir da qual um serviço do Windows roda não mantêm nenhum módulo nativo: nesses casos, esses dois recursos informam que não estão disponíveis neste pacote — use o pacote npm, executado em primeiro plano. A criptografia automática do Queryable Encryption também precisa da biblioteca crypt_shared (MM_CRYPT_SHARED_LIB_PATH) ou do mongocryptd, e do MongoDB Enterprise ou do Atlas; o MongoDB Community apenas descriptografa. O MONGODB-OIDC não precisa de nenhum pacote: o provedor de identidade deve ter o <address><base path>oidc/callback deste servidor como endereço de redirecionamento (ou outro que a conexão indicar), e as pessoas podem entrar com um código onde isso não for possível.

Instalar como app

No Chrome ou no Edge, escolha Instalar o Mongo Manager na barra de endereços para abri-lo em uma janela própria a partir da sua área de trabalho ou do menu Iniciar.

Destinos de backup

  • MM_BACKUP_FOLDER_ROOTS: as pastas que os destinos de pasta do servidor podem usar, como caminhos absolutos separados pelo separador de caminho do sistema (: no Linux e no macOS, ; no Windows), no máximo 16. Padrão: nenhuma, então nenhum destino de pasta pode ser criado. Um caminho relativo interrompe o servidor na inicialização. Dê à conta do serviço acesso de gravação a cada raiz e mantenha as raízes fora da pasta de dados: um destino de pasta dentro dela é recusado. Cada inicialização registra uma raiz na qual o servidor não consegue gravar. Para o serviço no Linux:
    • O sandbox dele permite gravar somente na sua pasta de dados e nas raízes que o arquivo de configuração e o arquivo env indicam quando ele é instalado: depois de alterá-los, execute sudo mongo-manager service install novamente (ele mantém os dados, a configuração e a chave) e reinicie o serviço depois de criar uma raiz que estava faltando. Raízes definidas em qualquer outro lugar, como um Environment= em um drop-in, a instalação não vê: as pastas delas continuam somente leitura para o serviço.
    • A instalação deixa de fora uma raiz sob /home, /root, /run/user, /tmp, /var/tmp ou /dev, que o serviço não consegue alcançar, e uma que desfaria o sandbox: uma que contenha um diretório do sistema (/, /var, /var/lib e semelhantes) ou esteja dentro de /etc, /usr, /run ou de outro diretório do sistema (sob /var, somente pastas dentro de /var/backups ficam abertas). Uma pasta dentro de /srv, /opt ou um ponto de montagem sob /mnt ou /media serve, mas não essas pastas em si; em um sistema de arquivos removível ou de rede, quem controla o disco ou o compartilhamento controla as pastas nele, então faça do próprio ponto de montagem a raiz (uma montagem FUSE de um usuário diz o que quiser sobre seus donos e links). Uma raiz dentro de outra raiz está no sandbox por meio dessa outra. Onde /srv, /opt ou /mnt é, ele próprio, um link para dentro de /var, como em sistemas ostree (Fedora Silverblue, CoreOS), a instalação informa para onde uma raiz leva, e ela é recusada ali: escolha uma pasta dentro de /var/backups.
    • Um link é avaliado pelo lugar para onde leva, e a unit nomeia esse lugar; um link que não leva a lugar nenhum é deixado de fora: para um que aponta para uma pasta ainda não criada, crie essa pasta e execute service install novamente; para um que dá voltas em um laço ou passa por um arquivo, escolha outra pasta ou remova o link. Mantenha cada pasta acima de uma raiz, e as pastas em que estão os links no caminho dela (inclusive um link no destino de um link), pertencentes ao root e fechadas para o grupo e para os outros, de modo que ninguém possa colocar um link no lugar de uma pasta ali; em uma pasta na qual outros podem gravar, com sticky bit ou não, faça o root ser dono da pasta que há nela e faça a raiz ficar dentro dessa.
    • Uma raiz abaixo de uma pasta que o usuário do serviço poderia alterar, em qualquer ponto até / e ao longo dos links do caminho, é deixada de fora: uma que esse usuário possui ou na qual pode gravar por meio de um de seus grupos, de uma ACL ou como qualquer pessoa, onde um processo rodando como esse usuário poderia colocar um link para /etc no lugar de uma pasta. Isso inclui um link em outra raiz, na qual o serviço grava. A instalação e o doctor executado com sudo também consultam o sistema: com setpriv, executam test -w como esse usuário, de modo que o kernel aplica os grupos dele (os que a unit dá ao serviço com Group= ou SupplementaryGroups=, inclusive os de um drop-in) e as ACLs. Sem setpriv, ou sem root, apenas os modos das pastas e os grupos do usuário são lidos, e ambos informam isso. O que os modos permitem conta mesmo onde uma ACL o retira, então uma pasta assim também deixa as suas raízes de fora.
    • A instalação pergunta ao systemd quem executa o serviço, lendo todos os drop-ins. Um drop-in que o executa como um usuário diferente de --user (ou como root), com DynamicUser=yes e nenhuma conta com esse nome, com um Group= diferente do grupo do próprio usuário, ou com um grupo que o sistema não conhece (caso em que o systemd se recusa a iniciá-lo) interrompe a instalação antes de a pasta de dados e a configuração mudarem; ela diz o motivo e deixa o serviço parado e desativado. Um grupo cuja consulta falha, ou um systemd que não pode ser consultado, deixa todas as raízes de fora.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json verifica o serviço instalado (o mongo-manager doctor simples verifica a sua própria pasta de dados e avisa que o serviço não foi o que ele verificou). Ele verifica cada raiz: se existe, se é um diretório no qual o servidor pode gravar, se está dentro do sandbox e se não está dentro da pasta de dados; também nomeia uma pasta na qual o sandbox permite que o serviço grave e que nenhuma raiz mais nomeia, ou que leva a uma raiz ou à pasta de dados por um link que alguém que não seja o root pode alterar, e avisa sobre um serviço que roda como root, um grupo que ninguém tem ou cuja consulta falha, e sobre DynamicUser=yes sem uma conta com esse nome. Ele verifica as raízes que a configuração e o arquivo env do serviço nomeiam, e é por isso que precisa de sudo: somente o root pode ler o arquivo env, que também é onde fica a chave secreta do serviço. Ele verifica o acesso de gravação como o usuário sob o qual o serviço roda; executado como root, lê o dono e o modo do root para o usuário que possui a pasta de dados, e aceita a palavra do sistema onde esse usuário pode gravar nela. As pastas acima das raízes são avaliadas para o usuário sob o qual a unit roda o serviço (o User= dela).
  • MM_BACKUP_PRIVATE_NETWORKS: intervalos privados que os destinos podem alcançar, como uma lista separada por vírgulas de no máximo 64 CIDRs (por exemplo 10.0.5.0/24); HTTP simples é permitido dentro deles. Padrão: nenhum. São aceitos os intervalos de loopback, 10/8, 172.16/12, 192.168/16, CGNAT (100.64.0.0/10) e unique-local (fc00::/7). Um intervalo público interrompe o servidor na inicialização, assim como um intervalo dentro de um intervalo link-local ou de metadados de nuvem (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200), em qualquer forma, inclusive IPv4 mapeado e NAT64; a mensagem nomeia o intervalo. Esses endereços nunca podem ser alcançados, nem mesmo dentro de um intervalo listado.
  • MM_BACKUP_PROXY: um proxy HTTP(S) pelo qual os destinos são alcançados, como http://proxy.corp:3128 ou https://user:password@proxy.corp; sem caminho nem consulta. Padrão: nenhum (nenhuma variável de proxy do ambiente é lida). O Mongo Manager ainda resolve e verifica por conta própria o endereço de cada destino e pede ao proxy que se conecte a esse endereço, então as regras de endereço acima valem também através do proxy; o TLS roda de ponta a ponta até o destino, cujo certificado é verificado como sem proxy. Os destinos dentro de MM_BACKUP_PRIVATE_NETWORKS são alcançados diretamente. Um proxy em um endereço link-local ou de metadados interrompe o servidor na inicialização. Mantenha a senha do proxy fora dos históricos de shell compartilhados: ela faz parte do endereço. Somente os destinos de backup o usam: os canais de alerta (e-mail e webhooks), os provedores de IA e os plugins nunca passam por ele. O que saber antes de escolher um proxy: um proxy http:// recebe o nome de usuário e a senha em texto claro (Basic), então prefira https:// ou um proxy dentro de uma rede confiável; um proxy que só permite CONNECT para nomes de host listados recusa essas conexões, pois recebe um pedido para um endereço IP; o certificado de um proxy https:// deve ser assinado por uma autoridade em que o Node.js confia (a lista embutida dele, ou uma acrescentada com NODE_EXTRA_CA_CERTS): não é possível indicar uma CA própria.
  • MM_BACKUP_DEST_PART_MB: o tamanho da parte de envio, de 16 a 512 MiB (padrão 64).
  • MM_BACKUP_DRILL_MAX_MB: o máximo que um teste de restauração grava, em MiB. Padrão: nenhum — um teste fica abaixo de metade do espaço livre em disco que o MongoDB informa (o do shard mais cheio, por meio de um mongos). Onde o MongoDB não o informa (camadas compartilhadas do Atlas), os testes só rodam com esta variável definida.
  • MM_BACKUP_DEST_TRANSFERS: envios e downloads simultâneos em cada destino, de 1 a 8 (padrão 2). Os demais esperam, mostrados como “Aguardando” esse destino na lista de tarefas.

Backups agendados

  • MM_BACKUP_SCHEDULES: o agendador, ativado por padrão. 0 o desativa: os agendamentos mantêm suas configurações, nada é executado, e a aba Backups agendados informa que o agendamento está desativado. As execuções que um servidor parado deixou inacabadas são encerradas na inicialização.
  • MM_BACKUP_SCHEDULE_CONCURRENCY: execuções agendadas simultâneas, de 1 a 8 (padrão 2). As demais execuções pendentes esperam até seis horas.

Monitoramento de alterações

  • MM_WATCH: feeds de change stream, ativados por padrão. 0 os desativa: as seções Monitorar informam que o monitoramento está desativado, e nada é aberto no MongoDB.
  • MM_WATCH_MAX_FEEDS: feeds ativos neste servidor ao mesmo tempo, de 1 a 500 (padrão 50). Cada usuário pode ter 5 e cada janela do navegador 3. Cada feed mantém um cursor de change stream no MongoDB.
  • O monitoramento exige um conjunto de réplicas, um cluster fragmentado (sharded) ou uma implantação com balanceamento de carga, e o usuário do banco de dados da conexão precisa de changeStream e find sobre o que é monitorado. Veja Monitoramento de alterações.

Sincronização em tempo real

  • MM_LIVE_SYNC: sincronizações em tempo real entre conexões, ativadas por padrão. 0 as desativa: as sincronizações em execução esperam, com o motivo, e nada é lido nem gravado; novas são recusadas. Ativadas de novo, elas continuam de onde estavam.
  • MM_LIVE_SYNC_MAX: sincronizações em tempo real não encerradas neste servidor, de 1 a 100 (padrão 10). Cada usuário pode ter 3. Cada sincronização em execução mantém um change stream na origem e mantém as duas conexões abertas.
  • A origem deve ser um conjunto de réplicas, um cluster fragmentado (sharded) ou uma implantação com balanceamento de carga (MongoDB 6.0 ou posterior); uma cópia que possa durar mais do que o oplog da origem pede uma confirmação. Veja Sincronização em tempo real.

Alertas

  • MM_ALERTS (arquivo de configuração: alerts.enabled): alertas, ativados por padrão. 0 os desativa: nada é avaliado nem enviado, e a página Alertas informa que os alertas estão desativados.
  • MM_ALERTS_PRIVATE_NETWORKS (arquivo de configuração: alerts.privateNetworks, uma lista): redes que os servidores de e-mail e os webhooks dos alertas podem alcançar além dos endereços públicos, como uma lista separada por vírgulas de no máximo 64 CIDRs (por exemplo 10.0.5.0/24). Padrão: nenhuma. HTTP simples para um webhook é permitido somente dentro delas. Os mesmos intervalos são aceitos e recusados como em MM_BACKUP_PRIVATE_NETWORKS: os endereços link-local e de metadados de nuvem nunca podem ser alcançados.
  • Em um arquivo de configuração: "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. Veja Administração do servidor.

O shell avançado

  • Desative-o por completo com --no-shell (ou MM_SHELL_ENABLED=0).
  • Limites: MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. Um shell que a sua página mantém continua aberto por mais tempo que fique sem uso, como no Compass; um que nenhuma página mantém é fechado dois minutos depois que a sua página some. O limite de inatividade fica desativado (0) a menos que você o defina (10000 a 86400000 ms); um shell dura no máximo 12 horas, a menos que você defina outra duração (60000 a 86400000 ms, ou 0 para nenhuma). Os shells mantidos abertos contam para MM_SHELL_MAX_TOTAL até que as suas páginas sejam fechadas; em um servidor que muitas pessoas compartilham, defina MM_SHELL_IDLE_MS para que os shells deixados abertos e sem uso sejam liberados. Com a autenticação ativada, um shell também termina quando a sessão do seu usuário termina, e quando a função do usuário muda ou a conta é desativada.
  • MM_SHELL_RSS_MB: a memória que o processo de um shell pode ocupar, de 128 a 16384 MB (padrão 384). O servidor a mede por conta própria a partir do sistema operacional (no Windows com tasklist, no macOS com ps) e reinicia um shell que a ultrapasse; as variáveis do shell se perdem. Um shell que deixa de responder por 15 segundos sem nenhum comando em execução também é reiniciado. MM_SHELL_OUTPUT_MB: a saída de um comando, de 1 a 64 MB (padrão 5); o restante é cortado. MM_SHELL_COMMANDS_PER_SECOND: comandos por shell por segundo, de 1 a 1000 (padrão 20).
  • Em um servidor POSIX com root, o worker do shell passa a rodar como MM_SHELL_UID/MM_SHELL_GID (padrão 65534); não rode o serviço como root.

Assistente de IA

  • MM_AI: o assistente de IA, ativado por padrão; ele só aparece depois que um administrador adiciona um provedor (Configurações → Assistente de IA). 0 o oculta em todo lugar e recusa as requisições.
  • MM_AI_PRIVATE_NETWORKS: redes (CIDR, separadas por vírgula) em que um provedor pode estar além dos endereços públicos, por exemplo um Ollama em 10.0.0.5; http simples somente ali. Os endereços de metadados de nuvem e link-local nunca podem ser alcançados. No modo local, esta máquina é sempre permitida.
  • MM_AI_PER_MINUTE (padrão 10, 1–120) e MM_AI_PER_DAY (padrão 200, 1–10.000): requisições por pessoa. MM_AI_MAX_CONCURRENT (padrão 8, 1–64): requisições simultâneas no servidor; cada pessoa pode ter 2. MM_AI_AGENT_PER_MINUTE (padrão 30, 1–120): as requisições adicionais de um agente ao provedor dentro de uma mensagem, por pessoa por minuto (elas contam também para o dia).
  • MM_AI_CHAT_DAYS (padrão 30, 0–365): por quanto tempo uma conversa é mantida após a sua última mensagem. 0 mantém as conversas apenas na memória (12 horas) e remove, quando o servidor inicia, as conversas armazenadas sob uma configuração anterior.

Plugins

  • MM_PLUGINS: plugins, ativados por padrão. Cada um ainda precisa da aprovação de um administrador, depois da sua verificação de segurança. 0 não encontra, instala nem executa nenhum (veja Plugins).
  • MM_PLUGINS_GITHUB: instalar um plugin a partir de uma release de um repositório público do GitHub, desativado por padrão (os plugins são instalados por envio de arquivo ou a partir de uma pasta); 1 o permite. O servidor então acessa api.github.com, github.com e os hosts de ativos de release do GitHub, por https, sem enviar nada de si mesmo. Desativado, um servidor nunca acessa o GitHub. O servidor se conecta diretamente ao GitHub: as configurações de proxy HTTP não são usadas, então um servidor que só consegue sair por um proxy instala plugins por envio de arquivo. Um serviço do sistema lê isso do seu config.json como "pluginsGithub": true (Linux /etc/mongo-manager/config.json, Windows %ProgramData%\Mongo Manager\config.json, macOS /Library/Application Support/Mongo Manager/config.json); reinicie o serviço depois.
