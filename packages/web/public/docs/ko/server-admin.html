서버 관리

Mongo Manager는 데이터 외에 MongoDB 서버 자체도 관리합니다. 데이터베이스 사용자와 역할, 클러스터의 샤딩, 문제가 생겼을 때의 알림, 각 연결의 상태를 한눈에 볼 수 있습니다.

사용자 및 역할

연결 페이지 → 사용자 및 역할에서는 Atlas의 Database Access처럼 MongoDB 자체 계정을 관리합니다. 이 계정은 애플리케이션과 사람이 MongoDB에 로그인할 때 사용하는 계정이며, Mongo Manager의 사용자가 아닙니다.

사용할 수 있는 사용자

  • 연결에 대한 앱 권한 databases:admin이 있는 사용자: 앱 관리자 또는 해당 연결에 대한 관리자 권한을 부여받은 사용자. 관리자가 개인 데이터를 숨긴 사용자에게는 이 섹션이 표시되지 않습니다. 스스로 숨긴 사용자에게는 표시됩니다.
  • MongoDB 자체의 권한도 적용됩니다. 연결이 로그인하는 계정에는 해당 데이터베이스의 userAdmin 또는 userAdminAnyDatabase가 필요합니다(목록 조회에는 viewUser와 viewRole이면 충분합니다). MongoDB가 거부하면 앱이 아니라 MongoDB가 거부했다는 점과 어떤 명령이었는지가 페이지에 표시됩니다.
  • 읽기 전용 연결에서는 사용자와 역할을 나열할 수만 있고 변경할 수 없습니다.

목록

모든 데이터베이스 또는 하나의 데이터베이스(데이터베이스 필터)의 사용자를 검색과 함께 보여 줍니다. 각 사용자의 역할은 칩으로 표시되며, 예를 들어 "readWrite on shop"처럼 나타납니다. 연결 자체가 로그인하는 계정에는 이 연결 표시가 붙습니다.

사용자 추가

  • 인증 데이터베이스: 사용자가 로그인하는 위치입니다. admin을 권장하지만 (여기에 있는 사용자는 모든 데이터베이스에 대한 역할을 가질 수 있습니다) 어떤 데이터베이스든 사용할 수 있습니다. $external은 비밀번호가 없는 x.509, LDAP, Kerberos, AWS IAM 사용자용이며, 이름은 해당 소스가 보내는 이름과 정확히 일치해야 합니다.
  • 사용자 이름.
  • 비밀번호: 직접 입력하거나 생성을 눌러 임의의 문자 24자를 만들 수 있습니다. 이 문자는 시스템의 난수 소스를 사용해 브라우저에서 만들어지고, 연결 문자열에 사용해도 안전하며, 복사할 수 있도록 표시됩니다.
  • 역할: 각각 허용하는 내용이 함께 표시되는 기본 제공 역할, 또는 데이터베이스별 사용자 지정 역할. admin에만 존재하는 역할(clusterMonitor, backup, root 등)은 admin에 고정됩니다.

비밀번호는 SCRAM-SHA-256을 사용하며 12자 이상이어야 합니다. 비밀번호는 MongoDB로 한 번 전송되며, Mongo Manager는 이를 저장하거나 로그에 남기거나 감사 로그에 기록하지 않습니다. 생성된 비밀번호는 양식을 닫기 전에 복사하세요. 넓은 권한을 부여할 때는 먼저 확인을 요청하며, 서버는 확인되지 않은 요청을 거부합니다. 해당 대상은 기본 제공 역할 root, userAdminAnyDatabase, userAdmin, dbOwner, clusterAdmin, clusterManager, hostManager, backup, restore, readWriteAnyDatabase, dbAdminAnyDatabase, admin 데이터베이스의 그 밖의 모든 기본 제공 역할(readAnyDatabase, clusterMonitor, enableSharding), local(oplog, 즉 수행된 모든 쓰기가 들어 있음) 또는 config(샤딩 메타데이터)의 모든 역할, 그리고 이들 중 하나를 상속하거나 클러스터, 모든 리소스, 모든 데이터베이스 전체, local 및 config에 대한 권한을 가지거나 사용자 또는 역할을 만드는 권한(createUser, grantRole, changePassword 등)을 가진 모든 사용자 지정 역할입니다. 이러한 사용자 지정 역할은 광범위한 역할로 표시되며, 만들 때도 확인을 거칩니다.

사용자 변경 및 삭제

  • 편집에서는 새 비밀번호, 새 역할 또는 둘 다 설정합니다. 저장한 역할이 사용자의 기존 목록을 대체합니다.
  • 연결 자체의 계정을 변경하거나 삭제하면 연결에 접근할 수 없게 될 수 있다는 경고가 표시되며 확인이 필요합니다. 해당 계정이 가진 사용자 지정 역할을 변경하거나 삭제할 때도 마찬가지입니다. 어느 계정인지는 연결 설정(SRV 레코드나 인증서로 바뀔 수 있음)이 아니라 MongoDB 자체가 알려 줍니다. 새 비밀번호를 설정한 뒤에는 연결도 편집하세요.
  • 사용자 또는 역할을 삭제하려면 해당 이름을 입력해야 합니다.

사용자 지정 역할

사용자 지정 역할을 사용하면 팀에 필요한 작업만 정확히 부여하고 그 이상은 부여하지 않을 수 있습니다. 역할에는 데이터베이스, 이름, 권한, 상속된 역할이 있습니다.

  • 각 권한은 데이터베이스와 컬렉션(비워 두면 모든 데이터베이스 또는 모든 컬렉션), 클러스터 또는 모든 리소스에 적용됩니다.
  • 작업은 MongoDB의 목록에서 선택하며, 쿼리 및 쓰기, 데이터베이스 관리, 사용자 및 역할, 배포, 복제, 샤딩으로 그룹화되어 있습니다.
  • admin 밖의 역할은 자신의 데이터베이스에 있는 역할만 상속할 수 있습니다(MongoDB의 규칙). admin의 역할은 모든 데이터베이스의 역할을 상속할 수 있습니다.

모든 변경은 감사 로그에 mongo.users.create, mongo.users.update, mongo.users.grant, mongo.users.revoke, mongo.users.drop, mongo.roles.create, mongo.roles.update, mongo.roles.drop으로 기록되며, 이름과 역할 목록은 포함되지만 비밀번호는 포함되지 않습니다.

샤딩

연결 페이지 → 샤딩은 연결이 mongos에 대한 것일 때 표시됩니다. 서버를 감시할 수 있는 모든 사용자는 밸런서 상태, 청크 분포, 클러스터 개요를 볼 수 있습니다. 변경하려면 databases:admin 권한과 읽기 전용이 아닌 연결이 필요합니다.

청크 분포

샤딩된 컬렉션마다 막대 하나가 있고 샤드마다 색상이 있으며, 화면 낭독기를 위해 개수도 글로 제공됩니다.

밸런서

  • 시작하거나 중지할 수 있으며, 중지하기 전에는 먼저 확인합니다. 중지된 동안에는 샤드 간 청크 이동이 없고, 진행 중인 마이그레이션은 먼저 끝납니다. 백업이나 유지 관리를 위해 중지한 뒤 다시 시작하세요.
  • 활성 시간대: 시작–종료 시각이며, 구성 서버의 시계 기준입니다. 이 경우 청크는 해당 시간대에만 이동합니다. 항상을 선택하면 설정이 해제됩니다.

컬렉션 샤딩

  1. 데이터베이스와 컬렉션을 선택합니다.
  2. 샤드 키를 필드별로 구성합니다. 각 필드는 범위 또는 해시 방식이며, 해시 필드는 최대 하나입니다. 순서가 중요하므로 필드를 위아래로 옮기세요.
  3. 이 키 점검: 서버가 도큐먼트 1000개를 샘플링하고 개수만 응답하므로 어떤 값도 MongoDB 밖으로 나가지 않습니다. 각 필드를 가진 도큐먼트의 비율, 고유 값의 수, 가장 흔한 값의 비율, 값이 시간에 따라 증가하는지 여부(ObjectId, 날짜), 키의 필드로 시작하는 인덱스가 있는지 여부가 제공됩니다. 판정은 좋음, 보통, 나쁨 중 하나입니다.
  4. 옵션: 고유(범위 키에만 해당), 청크를 미리 생성(빈 컬렉션의 해시 키, MongoDB 6.0 이하, 청크 1~8192개), 존별로 청크 생성(해시 키이며 존이 이미 정의된 경우).
  5. 샤딩은 되돌릴 수 없습니다. 네임스페이스를 입력하여 확인하세요.

시간에 따라 증가하는 필드를 범위 키로 사용하면 모든 새 도큐먼트가 하나의 샤드로 전송됩니다. 해시를 사용하거나 다른 필드를 앞에 두세요. 데이터가 있는 컬렉션을 샤딩하려면 먼저 키의 필드로 시작하는 인덱스가 필요합니다. MongoDB 자체 네임스페이스와 시스템 네임스페이스(admin, config, local, system.*)는 거부됩니다.

존

  • 각 샤드에 해당 존이 나열되며, 샤드에 존을 추가하거나 제거할 수 있습니다.
  • 컬렉션별 키 범위: 경계는 샤드 키 필드의 Extended JSON이며, 열린 끝에는 {"$minKey":1}과 {"$maxKey":1}을 사용합니다. 예를 들어 {"region": "eu"}부터 {"region": "us"}까지입니다. 연산자는 거부됩니다. 시작은 포함되고 끝은 포함되지 않습니다.
  • 범위에 속한 도큐먼트가 다시 어느 샤드에든 있을 수 있게 하려면 범위를 제거하세요.

감사 로그에는 sharding.collection.shard, sharding.zone.shard, sharding.zone.range(네임스페이스와 존이 기록되며 경계 값은 기록되지 않음), sharding.balancer, sharding.balancer.window가 기록됩니다. Mongo Manager의 테스트는 기록된 mongos 응답에 대해 이 화면들을 실행합니다.

알림

알림은 서버가 임계값을 넘었을 때 또는 앱 자체의 작업이 실패했을 때 벨, 이메일 또는 웹훅으로 알려 줍니다.

임계값

연결 페이지 → 알림이며, 앱 관리자(settings:manage)용입니다. 임계값은 하나의 지표를 감시합니다.

  • 연결: 열려 있는 클라이언트 연결(개수).
  • 작업: 모든 종류를 합한 초당 작업 수.
  • 복제 지연: 가장 뒤처진 세컨더리가 뒤처진 시간(초)(레플리카 세트).
  • WiredTiger 캐시: 캐시가 얼마나 찼는지(퍼센트).
  • 디스크 사용량: 사용 중인 데이터 파일 디스크의 비율(퍼센트)(MongoDB 4.4 이상).
  • 느린 작업: 선택한 초보다 오래 실행된 작업의 수(clusterMonitor 필요).

서버는 지표 기록과 같은 serverStatus 샘플링을 바탕으로 1분에 한 번 이를 평가합니다. 알림은 기록이 꺼져 있는 연결도 샘플링하며, 샘플은 기록이 켜져 있을 때만 저장됩니다. 기록과 알림을 합쳐 최대 50개 연결이 샘플링됩니다.

알림이 깜빡이지 않도록, 값이 선택한 시간(분, 1~60, 기본값 2) 동안 임계값을 넘은 상태로 유지되면 알림이 발생하고, 같은 시간 동안 임계값의 90% 이하로 유지된 뒤에야 해결됩니다. 캐시 사용률 임계값이 80%이면 72% 이하에서 해결됩니다.

이벤트 알림

알림 페이지에서 모든 연결 또는 하나의 연결에 대해, 또는 연결의 섹션에서 설정합니다.

  • 백업 실패: 백업, 전송 또는 가져오기 작업이 실패했습니다.
  • 예약 백업 실패: 실행이 실패했거나 일부 대상에만 도달했습니다.
  • 실시간 동기화 중지됨: 동기화가 실패했거나, 중지되었거나, 스스로 확인이 필요한 상태입니다. 사람이 중지한 경우는 해당되지 않습니다.
  • 작업 실패: 그 밖의 모든 작업(복원 훈련에는 자체 이벤트가 있습니다).
  • 복원 훈련 실패: 예약된 복원 훈련이 백업을 복원하지 못했거나, 다른 데이터를 발견했거나, 임시 데이터베이스를 삭제하지 못했습니다(경고이며 데이터는 일치했습니다). 통과한 훈련은 알림이 아니라 스케줄 기록에 남습니다.
  • 양방향 동기화가 충돌을 해결함: 양방향 실시간 동기화의 양쪽이 같은 도큐먼트를 변경했으며, 마지막에 쓴 쪽이 적용되었습니다(_id는 동기화 활동에 있습니다).
  • 감시가 알림 필터와 일치함: 소유자가 알림을 요청한 감시 피드에서 변경이 필터를 통과했습니다(피드가 실행되는 동안 최대 10초마다 한 번).

알림에는 이름과 숫자만 담기며, 도큐먼트 값, 오류 텍스트, 연결 문자열, 호스트는 절대 포함되지 않습니다.

예약 보고서

알림 페이지(앱 관리자)에서 설정합니다. 보고서는 한 연결의 몇 가지 개수를 스케줄에 따라(매일 아침, 매주 월요일, 최소 한 시간 간격) 알림과 같은 방식으로 벨, 이메일 또는 웹훅으로 알려 줍니다. 각 개수에는 레이블, 컬렉션, 선택 사항인 필터(JSON, 없으면 모든 도큐먼트를 세며 컬렉션의 추정치를 사용)가 있으며, 100만을 넘는 개수는 "이상"으로 표시됩니다. 행에서 바로 실행하거나, 변경하거나, 끄거나, 삭제할 수 있으며, 마지막 실행의 개수가 거기에 표시됩니다.

숫자만 전달하고 값은 절대 전달하지 않습니다. 개인 필드를 지정하는 필터(또는 개인 데이터 규칙이 달리 해석할 수 있는 필터)는 보고서를 저장할 때 거부되며, 이후 규칙이 바뀐 경우에는 제외되고 그 이유가 표시됩니다. MongoDB 자체 네임스페이스, 서버 JavaScript, 뷰, 시계열 컬렉션도 마찬가지입니다(뷰의 파이프라인이 개인 필드로 선택할 수 있기 때문입니다). 보고서는 연결 자체의 자격 증명으로 취급됩니다. 각 사용자가 직접 로그인하는 연결은 거부되며, 연결이 클라이언트에서 필드를 암호화하는 경우의 필터도 거부됩니다(읽을 수 있는 것과 일치하는 항목이 없기 때문입니다). 벨과 기록에서 관리자는 실행의 개수를 레이블과 함께 볼 수 있고, 다른 사용자는 보고서가 실행되었다는 사실만 보고 개수는 보지 못합니다. 각 보고서의 마지막 30회 실행이 기록에 보관되며, 스케줄을 더 이상 계산할 수 없는 보고서는 꺼지고 그 이유가 표시됩니다.

채널

  • 벨. 각 사용자가 환경설정 또는 알림 페이지에서 본인에 대해 벨에 알림 표시를 켭니다. 서버를 감시할 수 있는 연결(server:monitor)의 알림만 볼 수 있습니다.
  • 이메일. SMTP 서버, 포트, 처음부터 TLS(보통 465) 또는 STARTTLS(보통 587)를 사용합니다. 둘 다 제공하지 않는 서버는 거부되며, 메일은 절대 평문으로 전송되지 않습니다. 사용자 이름과 비밀번호 (봉인됨), 보내는 사람 주소, 최대 20명의 받는 사람이 필요합니다. 새 서버, 포트, 암호화 또는 사용자 이름에는 비밀번호를 다시 입력해야 합니다. 저장된 비밀번호는 다른 서버로 전송되지 않습니다. 테스트 메시지 전송은 저장된 설정으로 전송합니다. TLS 핸드셰이크나 교환을 제때 마치지 못한 세션은 중단됩니다. 메일은 Mongo Manager 자체 클라이언트와 송신 방어 장치를 통해 전송되며, 공용 주소는 허용되고 사설 주소는 MM_ALERTS_PRIVATE_NETWORKS 안에서만 허용됩니다.
  • 웹훅. https 주소이며, 일반 http는 MM_ALERTS_PRIVATE_NETWORKS 안의 주소에만 허용됩니다. 주소에 자격 증명을 포함할 수 없고, 클라우드 메타데이터 주소와 링크 로컬 주소는 절대 허용되지 않으며, 리디렉션은 따르지 않습니다. 서버가 각 웹훅의 서명 시크릿을 만들어 한 번만 보여 줍니다. 새 시크릿 만들기는 시크릿을 교체하며, 이전 시크릿은 즉시 작동하지 않습니다.

각 규칙이 전송 위치를 선택하며, 채널이 없는 규칙은 기록만 됩니다.

웹훅 전송

각 전송은 JSON 본문을 가진 POST입니다.

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type은 alert.firing, alert.resolved, alert.event 또는 alert.test입니다(테스트에는 type과 at만 있습니다). 이벤트 알림은 metric 대신 event (backup.failed, schedule.failed, liveSync.stopped, job.failed)를 설정합니다. 헤더는 다음과 같습니다.

  • x-mm-event: 같은 type 값.
  • x-mm-delivery: 전송의 고유 ID이며, 재시도할 때마다 동일합니다.
  • x-mm-timestamp: 이번 시도에 서명한 시각(Unix 초).
  • x-mm-signature: sha256= 뒤에 웹훅의 시크릿으로 계산한, 타임스탬프와 점과 본문의 HMAC-SHA256 16진수 값이 이어집니다.

본문을 파싱하기 전에 원본 본문으로 서명을 확인하고, 5분보다 오래된 타임스탬프는 거부하세요. Node.js의 경우: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

Python의 경우:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

전송은 네트워크 오류, 5xx 응답, 408 또는 429가 발생하면 2초, 10초, 60초 후에 최대 세 번 더 시도됩니다. 그 밖의 4xx 응답이나 방어 장치가 거부하는 주소에는 재시도하지 않습니다. 각 시도는 새 타임스탬프로 다시 서명됩니다. 이미 처리한 전송을 무시하려면 x-mm-delivery를 사용하세요.

스누즈, 일시 중지 및 확인

  • 규칙을 1시간, 8시간 또는 1일 동안 스누즈할 수 있습니다. 알림은 계속 기록되지만 아무것도 전송되지 않습니다. 지금 다시 켜기를 선택하면 스누즈를 일찍 끝냅니다.
  • 규칙은 스위치로 일시 중지하거나 재개합니다.
  • 관리자는 모든 사용자를 대신해 알림을 확인할 수 있으며, 그러면 다른 사용자도 누가 확인했는지 볼 수 있습니다. 그 밖의 사용자는 본인의 벨에서 알림을 닫을 수 있습니다. 관리자가 아닌 사용자에게는 벨에 무슨 일이 있었는지(코드)는 표시되지만 어떤 동기화, 작업, 스케줄 또는 네임스페이스인지는 표시되지 않습니다.
  • 채널과 알림이 동시에 몇 개가 발생하더라도, 전송은 하나의 대기열에서 한 번에 몇 개씩 이루어집니다.
  • 알림 페이지와 각 연결의 섹션에 있는 기록은 90일(최대 20,000개 항목) 동안 보관되며, 각 전송의 결과와 시도 횟수가 표시됩니다.

MM_ALERTS=0은 서버에서 알림을 끕니다. 아무것도 평가하거나 전송하지 않습니다 (배포 참조). 감사 로그에는 alerts.rule.create, alerts.rule.update, alerts.rule.delete, alerts.rule.snooze, alerts.email.update, alerts.email.test, alerts.webhook.create, alerts.webhook.update, alerts.webhook.delete, alerts.webhook.test, alerts.acknowledge가 기록되며, SMTP 비밀번호나 웹훅 시크릿은 절대 기록되지 않습니다.

실시간 상태

개요의 연결 카드에는 각 연결의 핑 지연 시간, MongoDB 버전, 토폴로지, 해당 연결에서 발생 중인 알림이 표시됩니다. 연결 페이지는 헤더에 같은 정보를 상태 표시 점과 함께 보여 줍니다.

  • 서버는 각 응답을 30초 동안 보관합니다.
  • 목록은 스스로 연결하지 않습니다. 열려 있지 않은 연결에는 연결되지 않음이 표시됩니다. 연결 페이지를 열면 데이터베이스를 나열할 때와 마찬가지로 연결을 확인합니다.
  • 알림 개수는 서버를 감시할 수 있는 연결에 대해서만 표시됩니다.
