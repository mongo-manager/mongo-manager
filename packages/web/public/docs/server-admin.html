Server administration

Beyond your data, Mongo Manager manages the MongoDB server itself: its database users and roles, the sharding of a cluster, alerts when something goes wrong, and each connection's health at a glance.

Users and roles

A connection's page → Users & roles manages MongoDB's own accounts, like Database Access in Atlas. These are the accounts applications and people use to sign in to MongoDB, not Mongo Manager's users.

Who may use it

  • Users with the app permission databases:admin on the connection: app administrators, or a user granted admin on that connection. A user an administrator hides personal data from never sees this section; one who hides it from themselves still does.
  • MongoDB's own rights apply too: the account the connection signs in with needs userAdmin on the database, or userAdminAnyDatabase (viewUser and viewRole are enough to list). When MongoDB refuses, the page says that MongoDB refused, and which command — not the app.
  • On a read-only connection, users and roles are listed but never changed.

The list

Users of every database, or of one (the database filter), with a search. Each user's roles show as chips, "readWrite on shop" for example. The account the connection itself signs in with is marked This connection.

Adding a user

  • Authentication database: where the user signs in. admin is recommended (users there can hold roles on any database), but any database works. $external is for x.509, LDAP, Kerberos and AWS IAM users, which have no password: the name must match exactly what that source sends.
  • Username.
  • Password: type one, or press Generate for 24 random characters made in your browser from the system's random source, safe in a connection string, shown so you can copy them.
  • Roles: built-in roles, each with what it allows, or your custom roles, each on a database. Roles that exist only on admin (clusterMonitor, backup, root and the like) are fixed to it.

Passwords use SCRAM-SHA-256 and need at least 12 characters. A password is sent to MongoDB once; Mongo Manager never stores it, logs it or writes it to the audit log. Copy a generated one before you close the form. Granting broad rights asks you to confirm first, and the server refuses them unconfirmed: the built-in roles root, userAdminAnyDatabase, userAdmin, dbOwner, clusterAdmin, clusterManager, hostManager, backup, restore, readWriteAnyDatabase and dbAdminAnyDatabase, every other built-in role of the admin database (readAnyDatabase, clusterMonitor, enableSharding), any role of local (it holds the oplog, every write made) or config (the sharding metadata), and any custom role that inherits one of them or holds a privilege on the cluster, any resource, every database at once or local and config, or one that makes users or roles (createUser, grantRole, changePassword and the like). Such custom roles are marked broad, and making one is confirmed too.

Changing and dropping users

  • Edit sets a new password, new roles, or both. The roles you save replace the user's list.
  • Changing or dropping the connection's own account warns that it can lock the connection out, and needs a confirmation. So does changing or dropping a custom role that account holds. Which account it is, MongoDB itself says (not the connection's settings, which an SRV record or a certificate can change). After a new password, edit the connection too.
  • Dropping a user or a role asks you to type its name.

Custom roles

Custom roles give a team exactly the actions it needs, nothing more. A role has a database, a name, privileges and inherited roles.

  • Each privilege applies to a database and collection (left empty, any database or any collection), to the cluster, or to any resource.
  • Its actions are picked from MongoDB's list, grouped as query and write, database management, users and roles, deployment, replication, and sharding.
  • A role outside admin inherits only roles of its own database (MongoDB's rule); a role in admin may inherit roles of any database.

Every change is in the audit log as mongo.users.create, mongo.users.update, mongo.users.grant, mongo.users.revoke, mongo.users.drop, mongo.roles.create, mongo.roles.update and mongo.roles.drop, with the names and role lists, never a password.

Sharding

A connection's page → Sharding appears when the connection is to a mongos. Everyone who may watch the server sees the balancer's state, the chunk distribution and the cluster overview. Changes need databases:admin and a connection that is not read-only.

Chunk distribution

One bar per sharded collection, a colour per shard, with the counts also in words for screen readers.

The balancer

  • Start or stop it; stopping asks first. While stopped, no chunk moves between shards; a migration under way finishes first. Stop it for a backup or maintenance, then start it again.
  • Active window: from–to, in the config server's clock. Chunks then move only within those hours. Any time clears it.

Sharding a collection

  1. Pick the database and the collection.
  2. Build the shard key field by field. Each field is ranged or hashed, with at most one hashed field. Order matters: move fields up and down.
  3. Check this key: the server samples 1000 documents and answers with counts only, so no value leaves MongoDB: the share of documents that have each field, the number of distinct values, the share of the most common value, whether values grow with time (ObjectId, dates), and whether an index starts with the key's fields. The verdict is good, fair or poor.
  4. Options: unique (ranged keys only); create chunks up front (a hashed key on an empty collection, MongoDB 6.0 and earlier, 1 to 8192 chunks); create chunks per zone (a hashed key, with zones already defined).
  5. Sharding cannot be undone: confirm by typing the namespace.

A field that grows with time, used as a ranged key, sends every new document to one shard: hash it, or put another field first. A collection with data needs an index that starts with the key's fields before it can be sharded. MongoDB's own and system namespaces (admin, config, local, system.*) are refused.

Zones

  • Each shard lists its zones; add a zone to a shard, or remove one.
  • Key ranges per collection: the bounds are Extended JSON of the shard key's fields, with {"$minKey":1} and {"$maxKey":1} for open ends, for example {"region": "eu"} to {"region": "us"}. Operators are refused. The start is included, the end is not.
  • Remove a range when its documents may again live on any shard.

The audit log records sharding.collection.shard, sharding.zone.shard, sharding.zone.range (the namespace and zone, never the bound values), sharding.balancer and sharding.balancer.window. Mongo Manager's tests run these screens against recorded mongos answers.

Alerts

Alerts tell you when a server crosses a threshold, or when one of the app's own jobs fails: in the bell, by e-mail, or to a webhook.

Thresholds

A connection's page → Alerts, for app administrators (settings:manage). A threshold watches one metric:

  • Connections: open client connections (a count).
  • Operations: operations per second, all kinds together.
  • Replication lag: seconds the furthest secondary is behind (replica sets).
  • WiredTiger cache: how full the cache is, in percent.
  • Disk use: percent of the data files' disk in use (MongoDB 4.4 and later).
  • Slow operations: the count of operations running longer than the seconds you choose (needs clusterMonitor).

The server evaluates them once a minute from the same serverStatus sampling as metric history. Alerts sample a connection even when its history is off; samples are stored only when history is on. At most 50 connections are sampled, for history and alerts together.

No flapping: an alert fires once the value has stayed above the threshold for the minutes you chose (1 to 60, default 2), and resolves only after it has stayed at or below 90% of the threshold for as long. A threshold of 80% cache fill resolves at 72% or less.

Event alerts

On the Alerts page, for every connection or one, or in a connection's section:

  • Backup failed: a backup, send or fetch job failed.
  • Scheduled backup failed: a run failed, or reached only some of its destinations.
  • Live sync stopped: it failed, stopped or needs attention on its own — not when a person stopped it.
  • Job failed: any other job (a restore drill has its own event).
  • Restore drill failed: a scheduled restore drill could not restore its backup, found data that differ, or could not drop its scratch database (a warning: the data matched). A drill that passed is in the schedule's history, not an alert.
  • Two-way sync settled conflicts: both sides of a two-way live sync changed the same documents; the last writer won (the _ids are in the sync's activity).
  • Watch matched its alert filter: a Watch feed whose owner asked for alerts passed changes through its filter (at most every 10 seconds, while the feed runs).

Notifications carry names and numbers only: never document values, error texts, connection strings or hosts.

Scheduled reports

On the Alerts page (app administrators): a report says a few counts of one connection on a schedule — every morning, every Monday, as often as an hour — in the bell, by e-mail or to webhooks, as alerts are sent. Each count has its label, a collection and an optional filter (JSON; none counts every document, the collection's estimate); a count past a million says "at least". Run one now, change it, turn it off or delete it from its row; its last run's counts are shown there.

Numbers only, never a value. A filter that names a personal field — or one the personal-data rules would read otherwise — is refused when the report is saved and left out, said why, when rules change after; so are MongoDB's own namespaces, server JavaScript, views and time series (a view's pipeline could pick by a personal field). A report counts as the connection's own credentials: one where each person signs in is refused, and so is a filter where the connection encrypts fields on the client (it would match nothing it can read). In the bell and the history, administrators see a run's counts by their labels; others see that a report ran, not its counts. Each report's last 30 runs are kept in the history; one whose schedule can no longer be worked out is turned off, said why.

Channels

  • The bell. Each user turns on Show alerts in the bell for themselves, in Preferences or on the Alerts page. They see alerts only for connections whose server they may watch (server:monitor).
  • E-mail. The SMTP server, port, and TLS from the start (usually 465) or STARTTLS (usually 587): a server that offers neither is refused, mail is never sent in plain text. A username and password (sealed), the From address and up to 20 recipients. A new server, port, encryption or username needs the password typed again: the saved one is never sent to another server. Send test message sends with the saved settings. A session that does not finish its TLS handshake or its exchange in time is given up. Mail goes through Mongo Manager's own client and its egress guard: public addresses, and private ones only inside MM_ALERTS_PRIVATE_NETWORKS.
  • Webhooks. An https address; plain http only to addresses inside MM_ALERTS_PRIVATE_NETWORKS. No credentials in the address, cloud metadata and link-local addresses never, and redirects are not followed. The server makes each webhook's signing secret and shows it once; Make a new secret replaces it, and the old one stops working at once.

Each rule chooses where it is sent; a rule with no channel is only recorded.

Webhook deliveries

Each delivery is a POST with a JSON body:

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type is alert.firing, alert.resolved, alert.event or alert.test (a test carries only type and at). Event alerts set event (backup.failed, schedule.failed, liveSync.stopped, job.failed) instead of metric. The headers:

  • x-mm-event: the type again.
  • x-mm-delivery: a unique id for the delivery, the same on every retry.
  • x-mm-timestamp: Unix seconds when this attempt was signed.
  • x-mm-signature: sha256= followed by the hex HMAC-SHA256, with the webhook's secret, of the timestamp, a dot and the body.

Check the signature over the raw body, before parsing it, and refuse timestamps older than 5 minutes. In Node.js: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

In Python:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

A delivery is tried up to three more times, after 2 seconds, 10 seconds and 60 seconds, on a network error, a 5xx answer, 408 or 429; never on any other 4xx, nor to an address the guard refuses. Each attempt is signed again with a fresh timestamp. Use x-mm-delivery to ignore a delivery you already handled.

Snoozing, pausing and acknowledging

  • Snooze a rule for 1 hour, 8 hours or 1 day: alerts are still recorded, nothing is sent. Wake now ends it early.
  • Pause and resume a rule with its switch.
  • Administrators acknowledge an alert for everyone, who then see who did; anyone else dismisses it from their own bell. Outside the administrators, the bell shows what happened (its codes) but not which sync, job, schedule or namespace.
  • Deliveries go a few at a time from one queue, however many channels and alerts fire together.
  • History, on the Alerts page and in each connection's section, keeps 90 days (at most 20,000 entries), with each delivery's outcome and how many attempts it took.

MM_ALERTS=0 turns alerts off on the server: nothing is evaluated or sent (see Deployment). The audit log records alerts.rule.create, alerts.rule.update, alerts.rule.delete, alerts.rule.snooze, alerts.email.update, alerts.email.test, alerts.webhook.create, alerts.webhook.update, alerts.webhook.delete, alerts.webhook.test and alerts.acknowledge — never the SMTP password or a webhook secret.

Live health

The connection cards on the Overview show each connection's ping latency, MongoDB version, topology and the alerts firing on it. A connection's page shows the same in its header, with a status dot.

  • The server keeps each answer for 30 seconds.
  • The list never connects on its own: a connection that is not open shows Not connected. Opening a connection's page checks it, as listing its databases would.
  • Alert counts are shown only for connections whose server you may watch.
