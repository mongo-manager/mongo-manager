备份与恢复

可备份集合、数据库或整个服务器，然后下载文件，或将其在服务器上保留一段时间。可将任一备份、mongodump 归档或 mongodump 文件夹的 zip 恢复到所选的命名空间。两者都作为后台任务运行，可在任务列表中跟踪。

可从侧边栏中集合或数据库的菜单、连接的菜单、连接的“备份”标签页、数据库或集合的“备份”部分开始，也可使用命令面板（“备份…”、“恢复备份…”）。

创建备份

备份在一个界面中打开，并针对打开它的位置给出推荐选项：数据包含个人字段时推荐加密备份，否则推荐压缩归档。旁边的检查项会随任何更改而更新：预计的大小和时间、可用的备份空间、文件中将可读的个人字段，以及被排除的内容。每个可修复的检查项都有对应的按钮。“自定义…”会打开各个步骤：范围、引擎、内容、保护和摘要。

备份在后台运行：可随时关闭对话框。备份开始后，会打开所备份对象的“备份”部分：集合的、数据库的或连接的。运行期间，“备份”部分和任务列表会显示每个命名空间各自的进度（已完成的数量、正在读取的命名空间和所处阶段）。完成后，通知中会提供“下载”和“打开报告”。

备份和恢复需要连接的服务器，并且只有在 Mongo Manager 已连接到该服务器（已读取其数据库）时才会显示。在连接过程中，或无法连接时（超时、网络、DNS 或 TLS 故障、登录被拒绝、服务器不可用），连接页面只显示其概览以及错误、“重试”和“编辑”：没有性能、监视、用户和角色、告警、个人数据或备份，也没有“新建数据库”或 Shell；数据库页面则不显示模型、监视或备份。树和这些页面的菜单中会去掉备份、恢复、实时同步、Shell、创建、重命名和删除，命令面板中针对服务器的命令会说明没有连接。以其他方式打开的备份或恢复会说明这一点，并提供“重试”，且不会启动任何操作。与连接服务器无关的响应（其所有连接暂时繁忙、查询超出时间限制）不会隐藏任何内容。一旦数据库被读取，所有内容都会恢复：执行“重试”、“刷新”，连接测试通过，或在原因自行消失时（网络、超时、DNS、服务器不可用）自动恢复：打开的页面只要浏览器正在显示它，就会每 15 秒重试一次。服务器拒绝的登录（用户名或密码、SSH 登录、已更改的 SSH 主机密钥）会保留五分钟，或直到连接被编辑、其用户重新登录（每个人各自登录的连接）或连接测试通过：在此期间，Mongo Manager 中的任何部分（页面、小组件、健康检查、任务、Shell）都不会为其再次登录，并且在保留期间只有该连接的管理员可以再次测试它，这样目录的锁定规则就不会锁定账户，错误信息会说明如何重试。

格式

  • .archive：mongodump 归档；可用 mongorestore --archive 打开。
  • .archive.gz：使用 gzip 压缩的同一种归档； mongorestore --archive --gzip。
  • .mmbak：先用 Zstandard 压缩，再以 AES-256-GCM 分块加密封装，每个分块在读取时都会单独验证。密码至少需要 12 个字符；“生成强密码”可为您生成一个。密码不会存储在任何地方，也无法找回：没有它，就无法打开该备份。可在 Mongo Manager 中打开，或使用 mongo-manager backup decrypt <file> -o <file.archive> 将其转换为普通归档（密码在不回显的情况下输入，或使用 --password-stdin 从管道读取）。 mongo-manager backup inspect <file> 会列出任一备份所含的内容。

引擎

  • 内置：通过 Mongo Manager 读取，因此个人字段规则和脱敏都会生效。它适用于所有安装，其归档可用 mongorestore 打开。
  • mongodump 和 mongorestore：MongoDB 自带的工具，处理超大数据时可能更快。它们只提供给能看到个人值的连接管理员，不适用于通过 SSH 隧道的连接。请安装 MongoDB Database Tools 100.9 或更高版本（MongoDB 8.3 及更高版本需要 100.16 或更高版本，而 Docker 镜像自带的工具尚不满足该要求：此时它会使用内置引擎），并设置 MM_MONGODB_TOOLS_PATH，或使用已包含它们的 Docker 镜像。凭据通过私有的临时配置文件传递给这些工具，该文件在工具结束时删除，绝不会出现在命令行上。

时间序列

时间序列按 mongodump 针对该服务器版本的保存方式保存：从 MongoDB 8.3 起使用其自身名称，通过 rawData 读取和写入；8.3 之前则保存在 system.buckets.<name> 下。内置引擎可将任一种（Mongo Manager 的或 mongodump 的）恢复到任何受支持的版本，8.3 的备份也可恢复到较旧的服务器。对于 8.3 或更高版本的备份或目标，mongorestore 需要 100.16 或更高版本，并且只有在备份由 mongodump 100.16 或更高版本，或由此版本的 Mongo Manager 创建时，才能找到 8.3 备份中的时间序列：对于以其他方式创建的备份，恢复计划会改为提供内置引擎。对于不提供其版本的服务器，绝不会进行猜测：其时间序列会从备份中排除并说明原因，恢复时会在其计划中被拒绝，而演练则会在写入其任何文档之前停止，并删除其临时数据库。在 MongoDB 8.3 及更高版本上启用登录时，备份或恢复时间序列的账户还需要 performRawDataOperations 权限（MongoDB 的 backup 角色拥有该权限；进行恢复时，请将其与 restore 一并授予）。

个人数据

  • 不允许查看个人值的用户备份的是替代它们的 ***：这样的备份始终是匿名的。任何人都可以选择匿名备份。
  • 含个人字段的时间序列，以及定义中包含会被脱敏的值的视图，会从脱敏备份中排除。验证器中包含此类值的集合会保留其脱敏数据，但不含验证器。报告会说明排除了什么以及原因。
  • 个人字段规则更改后，脱敏备份将无法再下载或恢复。
  • 将脱敏备份恢复到现有文档上需要确认，因为 *** 会替换已存储的值。

恢复

  1. 拖入文件、选择文件，或选择保留的备份之一。大文件会分块上传，并在连接中断后继续；文件所含内容在上传过程中即会显示。加密备份会要求输入其密码。
  2. 选择恢复什么以及恢复到哪里：一次性为所有命名空间重命名数据库、在名称后添加 _restored，或选择“恢复到新数据库”（以被备份的数据库和日期命名，绝不会是目标已有的数据库；包含多个数据库的备份会为每个数据库创建一个新数据库，因此同名的集合不会相互混淆）。已存在的目标会标出其文档数量。集合上的“恢复到此处…”会恢复到该集合中：无论其原名是什么，只含一个集合的备份都会进入该集合。
  3. 选择写入方式：添加（_id 已存在的文档会被拒绝并列出）、按关键字段 Upsert，或替换。替换会先恢复到暂存集合，只有在所有内容都到达后才将其就位，因此失败或被取消的恢复会保持目标原样。使用内置引擎时，替换不会从备份中取走的内容（其索引，或其选项和验证器，若被排除）仍保留目标自己的版本：如果目标自己的某个索引无法重建，或其自身的上限所保留的文档比写入的更少，则不会替换任何内容。mongorestore 无法保留它们。时间序列无法被替换，无论是在备份中还是在目标上；请将其恢复到新集合。再次运行的恢复会发现它已写入的文档保持原样，并将其计为已存在，而不是拒绝它们，试运行也是如此。
  4. 确认需要确认的内容：写入的集合将具有的 TTL 索引和集合过期设置（备份自带的，或替换所保留的目标自身的）（报告和试运行会统计一经写入就被删除的文档，即其日期已过期的文档，目标自身的 TTL 也包括在内）、目标缺少的个人字段规则（管理员可以添加），以及替换所覆盖的每个非空目标的名称，需手动输入。
  5. 运行试运行以查看会发生什么，然后选择“使用这些设置立即恢复”，或启动恢复。每个命名空间的校验和都会被验证；不匹配会使恢复失败。其进度按命名空间显示，然后是它所构建的索引和视图；完成后，其通知及其在任务列表中的行会打开它所写入的内容（“打开集合”，多个时为“打开数据库”）及其报告。

保留的备份

连接、数据库或集合的“备份”部分会列出您的备份（集合的部分列出包含该集合的备份）及其保护方式、大小、存在时间和过期时间，以及您对备份空间的使用情况。备份的“…”菜单可下载、发送或恢复它，或删除它（有五秒钟可撤销）。备份只属于您自己；当您失去对其连接的访问权限，或个人值对您变为隐藏时，这些备份会被撤回。

备份目标

备份还可以发送到其他位置：服务器上的文件夹、兼容 S3 的存储、Google Drive 或 WebDAV 服务器。管理员在账户菜单 → 备份目标下定义备份目标，并选择谁可以使用每一个；其他人只能看到备份目标的名称，看不到其地址或密钥。密钥以加密方式存储，只能被替换，无法读回。

  • 服务器文件夹：位于 MM_BACKUP_FOLDER_ROOTS 所列文件夹之一内、且在数据目录之外的绝对路径。没有该设置时，无法创建文件夹类备份目标。
  • 兼容 S3 的存储：端点、区域、存储桶、访问密钥 ID 和密钥。预设会尽可能为 Amazon S3、MinIO、Cloudflare R2（您的账户 ID）、Backblaze B2、DigitalOcean Spaces、DigitalOcean Spaces Cold Storage、Wasabi 或任何其他 S3 服务填入内容。
  • Google Drive：您自己的 Google Cloud OAuth 客户端（通过屏幕上显示的代码连接），或写入共享云端硬盘的服务账号（见下文）。
  • WebDAV：服务器地址、用户名和应用密码（Nextcloud、ownCloud 或任何 WebDAV 服务器）。Nextcloud 和 ownCloud 以可续传的分块方式接收大型备份。
  • Google Cloud Storage：存储桶、可选的前缀、备份写入时使用的存储类别（Standard、Nearline、Coldline 或 Archive：所有类别都可立即读取；较冷的类别有最短计费时间），以及在该存储桶上具有Storage Object User 角色的服务账号的 JSON 密钥（足够：它可读取、写入、列出和删除对象）。密钥在服务器上加密封存；只显示账号的地址。上传在连接中断后可续传，每份副本都会与 Google 的 MD5 进行核对。
  • Azure Blob Storage：存储账户、容器、可选的前缀，以及备份写入时使用的访问层（账户默认值、Hot、Cool、Cold 或 Archive），使用 SAS 令牌或账户密钥签名。仅针对该容器、允许读取、添加、创建、写入、删除和列出的 SAS 令牌是范围最窄的授权；它会在到期日期后失效。只接受 SAS 令牌可包含的字段，并且只保留所选签名方式用到的凭据。小型备份会整体与其 MD5 核对。大型备份以块的方式上传，每个块由 Azure 与其 MD5 核对，完成的 blob 通过其大小进行比较（Azure 不为由块组成的 blob 保留校验和）；中断的上传只会从其自己的块继续：每次上传都会标记其块，因此其他尝试遗留的块绝不会被当作本次上传的块。Archive 层中的 blob 显示为已归档：解冻…会以标准或高优先级将其重新水化到 Cool（它会保持在该层）。清单绝不会写入 Archive。高级可指定另一个 Azure 云的端点和 CA 证书。
  • SFTP：服务器、其端口、用户名、可选的文件夹（为空时为登录文件夹；它必须存在），以及密码或私钥（含其口令）。服务器的主机密钥通过其 SHA-256 指纹固定：将指纹留空，运行测试连接，将其显示的密钥与服务器自身的密钥比较（例如在服务器上执行 ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub），然后选择信任此密钥并重新测试。密钥不是受信任密钥的服务器不会收到任何内容；密钥变更后会再次要求输入密码或密钥。备份先写为 .part 文件，完整后再重命名，中断的上传会从停止处继续：前提是已读回部分文件所含的内容并确认它是备份的开头（即使关闭了读回也是如此）；不是的部分文件会重新开始。SFTP 不保留校验和，因此除非关闭通过回读验证，否则每份副本都会被完整读回。当服务器提供 posix-rename@openssh.com（OpenSSH 提供）时，重新写入的清单会立即替换旧清单。一分钟内没有收到任何数据的下载会被放弃。该连接与其他备份目标一样，经过相同的地址检查和代理。

在访问权限下，选择还有谁可以使用该备份目标：发送允许用户将自己的备份发送到那里，并恢复自己发送的备份；浏览全部允许他们读取那里的每个备份，包括其他用户的备份。管理员始终可以使用每个备份目标。

测试备份目标

编辑器的最后一步测试并保存会在真实的备份目标上运行测试连接，并显示每个步骤及其耗时：解析地址、建立安全连接、登录、写入测试文件、回读文件和删除文件。对于服务器文件夹，前两项显示为在此服务器上。失败的步骤会说明原因；其后的步骤显示未运行。测试之后更改的设置需要重新测试。在测试失败后选择保存，会先询问在测试未通过的情况下保存？；仍然保存会保持备份目标现状，留待以后修复。备份目标菜单中的立即测试会再次测试已保存的备份目标。其卡片会显示结果：正常、需要处理、需要重新连接（Google Drive，见下文）或尚未测试。

Google Drive

Mongo Manager 使用您自己的 Google Cloud OAuth 客户端，或 Google Workspace 中的服务账号登录 Drive。它只请求 drive.file 范围：只能看到它自己创建的文件和文件夹，看不到该 Drive 中的其他任何内容。

使用您的 Google 账号（编辑器中的我的 Google 账号）：

  1. 在 Google Cloud 控制台中，选择或创建一个项目。在APIs & Services → Library下，启用Google Drive API。
  2. 首先配置OAuth consent screen（在较新的控制台中为Google Auth Platform，包含Branding和Audience）。在 Google Workspace 中，选择用户类型Internal：只有您所在组织的账号可以连接。否则选择External，然后选择Publish app，使其状态为In production；drive.file 是非敏感范围，因此发布无需 Google 审核。请勿让 External 应用停留在Testing状态：Google 会让其登录在 7 天后过期，备份目标随后会显示需要重新连接。
  3. 前往Credentials → Create credentials → OAuth client ID，选择类型TVs and Limited Input devices。无需重定向地址。请保管好客户端 ID 和客户端密钥。
  4. 在编辑器中，输入OAuth 客户端 ID和OAuth 客户端密钥，然后选择连接 Google 账号。在倒计时结束之前，使用应保存备份的 Google 账号打开所显示的地址 (google.com/device) 并输入代码。编辑器随后会显示已连接为该账号。备份会存入应用创建的文件夹（文件夹名称，除非更改，否则为“Mongo Manager backups”）。
  5. 当 Google 不再接受该连接时（其访问权限已在 Google 账号中被移除、六个月未使用，或应用一直停留在 Testing），备份目标会显示需要重新连接。打开编辑…，选择重新连接，输入新代码，然后保存。此过程使用已存储的客户端密钥：无需再次输入，它也绝不会回传到浏览器。

使用服务账号（Google Workspace，编辑器中的服务账号）：

  1. 在同一个项目中，于IAM & Admin → Service accounts下创建服务账号（它不需要任何角色）。在其Keys下，选择Add key → Create new key，类型为 JSON。
  2. 在 Google Drive 中，打开应保存备份的共享云端硬盘，选择管理成员，并将服务账号的地址添加为内容管理员（服务账号自身没有存储空间）。共享云端硬盘的 ID 是其地址的最后一部分（drive.google.com/drive/folders/<id>）。
  3. 在编辑器中，将密钥粘贴到服务账号密钥（JSON），或将其文件拖放到该处，并输入共享云端硬盘 ID。屏幕上只保留账号的地址。

发送备份

创建备份时在位置下选择备份目标，或对保留的备份使用发送…。每份副本都会显示在备份的行上：正在发送到某个备份目标并显示其进度，已存在于某个备份目标（验证完成后），或未发送到某个备份目标并给出原因。

  • 备份目标只接受加密备份，除非管理员将其关闭（该更改会被审计）。
  • 含有个人字段规则的数据的备份，无论备份目标如何设置，只有在已加密或已脱敏时才会发送到备份目标。
  • 副本只有在通过验证后才算已发送。每个备份目标都会比较大小。兼容 S3 的存储还会在每个上传分块到达时将其与其 SHA-256 核对，Google Drive 则比较它报告的校验和。服务器文件夹会完整读回文件并比较其 SHA-256；当通过回读验证每次上传开启时，WebDAV 也是如此（这会使流量加倍）。若不开启，WebDAV 只检查大小，对话框会说明这一点。验证失败的副本会从备份目标中删除。
  • 验证上传成功后删除本地副本依赖该验证：只有当每个选定的备份目标都验证了其副本时，才会删除服务器上的副本。如果任何一个失败，本地副本会保留 7 天（发送可重试的时间），任务也会说明这一点；被取消的发送绝不会删除它。
  • 每个备份目标同时运行的传输数量有限（MM_BACKUP_DEST_TRANSFERS，默认 2，发送和下载合计）。其余的会等待，任务会显示等待该备份目标，直到有空闲名额。
  • 对未发送的副本选择重试会再次发送它，并保留其删除本地副本的选择：一旦它以及使用该选择发送的其他副本都已验证，本地副本就会被删除。丢弃会放弃失败的副本，并放弃其未完成的上传。
  • 因服务器重启而中断的发送会变为未发送的副本，原因为“The server restarted while it was being sent.”；重试会从已上传的分块继续，前提是服务商保留了这些分块（S3 分段上传、Nextcloud 分块）。

那里存储了什么

文件存放在备份目标的文件夹或前缀下的 mongo-manager/<year>/<month>/ 中，按日期、时间和一个短 ID 命名，旁边是一个小的 .json 清单，包含大小、格式和校验和，在文件验证通过后最后写入。名称和清单中都不包含数据库或集合名称。

从备份目标恢复

在“备份”卡片中选择备份目标的标签页，或在恢复面板中选择来自备份目标，然后选取备份。恢复需要对目标连接的写入权限。文件会下载到服务器，并在到达过程中预览；一旦下载完成，且其校验和与发送时记录的校验和或清单中的校验和一致，即可开始恢复。校验和不一致的文件会被删除。没有清单的文件（由其他工具或手动放入）会列为来自其他安装：可以恢复它，但无法事先验证它，恢复面板会说明这一点。

失败的下载会保留已收到的部分：再次选择同一个备份即可继续。被取消的下载会被丢弃，已收到的部分无用时（其校验和不同，或文件已不存在）也是如此。已收到的部分在被继续、丢弃或过期（MM_BACKUP_TTL_HOURS）之前，会一直占用您的备份空间。

在新的安装上，请使用相同的设置重新定义备份目标：相同的文件夹；相同的端点、存储桶和前缀；相同的 WebDAV 地址和文件夹。对于 Google Drive，请使用相同的 OAuth 客户端（或相同的服务账号和共享云端硬盘）以及相同的文件夹名称：使用 drive.file 时，客户端只能看到它自己创建的文件。管理员随后可以看到那里的每个备份，包括旧安装的备份。其他人则需要浏览全部：发送只显示该用户从此安装发送的备份。

冷存储和归档存储类别

DigitalOcean Spaces Cold Storage 以较低成本保存备份，并且备份仍可立即读取，但每个对象至少按 30 天计费，超出额度的读取服务商可能收费：发送后不久就删除或恢复会产生费用。

S3 备份目标的存储类别（位于高级下，默认为 STANDARD）适用于备份文件；清单保持为 STANDARD。处于 GLACIER 或 DEEP_ARCHIVE 的文件在解冻之前无法读取：备份目标的列表会将其显示为已归档，并提供解冻…操作，该操作会询问解冻后的副本可读取多长时间（1 到 30 天）以及服务商的处理速度（Standard、Bulk（最便宜也最慢）或 Expedited，Deep Archive 不适用）。服务商会对解冻及这些天数计费。解冻期间，副本显示为解冻中；解冻完成后，在天数用完之前可从列表中恢复。任何有权从该备份目标恢复的人都可以解冻（发送者只能解冻自己的副本），每分钟最多 10 次解冻，每次都会被审计。GLACIER_IR、STANDARD_IA、 ONEZONE_IA 和 INTELLIGENT_TIERING 可立即读取。

计划备份

计划会反复执行同样的备份，将每个备份发送到所选的备份目标，并按其保留规则保留相应数量的备份。打开账户菜单 → 计划备份、命令面板（“打开计划备份”），或连接或数据库“备份”部分中的计划…（它会为其启动一个计划）。编辑器共有六个步骤：内容、时间、保护、位置、保留策略，以及包含服务器检查结果的摘要。

谁可以创建计划

  • 任何可以备份该连接的人都可以为其创建计划（在那里读取文档、运行任务和导出）。每次运行都采用所有者在当时的权限，而绝不是保存计划时的权限。
  • 权限丧失会在读取任何数据之前暂停该计划，并在其卡片上给出原因：所有者的账户被禁用、所有者不能再备份该连接或发送到某个备份目标、某个备份目标已被删除、备份密钥未处于活动状态、范围现在包含未加密计划不能备份的个人数据、某个备份目标现在只接受加密备份、此服务器无法读取其周期或时区（其他版本才认识的时区），或其在此服务器上保留的副本占满了您的备份空间。原因消除后即可恢复。
  • 管理员可以看到每个计划，并可暂停、恢复、运行和删除它；他们不能编辑其他用户的计划。由管理员暂停的计划由管理员恢复。每个用户最多可拥有 10 个计划。

何时运行

  • 每 N 小时（1 到 24），在每小时的选定分钟。
  • 每天，每天最多四个时间点。
  • 每周，在所选的日期，于某个时间。
  • 每月，在 1 到 28 日之间的某一天或该月最后一天，于某个时间。
  • 高级：五个字段的 cron 表达式（分钟、小时、月中的日、月、星期），输入时会以文字回读。它遵循经典的 Vixie 规则：当月中的日和星期都被限定时，满足其中之一即可；以 * 开头的字段视为未限定。不支持 @ 快捷写法，不支持秒，也不支持 L、W 或 #。

两次运行的间隔必须至少为一小时，并且周期必须在未来五年内运行；编辑器会以该计划的时区显示接下来的运行，并在违反任一规则时予以说明。

时区和夏令时

每个计划都有自己的时区（默认为您的时区）；时间是该时区的本地时间。时钟拨快时，当天不存在的时间会在变更后的第一分钟运行。时钟拨回时，出现两次的时间只会运行一次，即第一次出现时。按小时的计划会在重复的那一小时内少运行一次，而不是在一小时内运行两次。

错过的运行、重叠和队列

  • 如果服务器在到期时间处于停止状态，则在下次启动时，若最近一次错过的时间距今不超过该计划自身的间隔（最长一天），就会运行一次补跑备份。其他所有错过的时间都会记录为错过；补跑从不超过一次。
  • 当某次运行到期时，上一次运行仍在运行或仍在等待轮到它，则该次运行会被跳过，并记录为已跳过，同时说明是这两种情况中的哪一种。
  • 同时工作的计划运行最多为 MM_BACKUP_SCHEDULE_CONCURRENCY 个（默认 2）。其余的按到期顺序最多等待六小时；等待更久的运行会被跳过。
  • 时钟向前跳变最多产生一次补跑；时钟回拨不会使任何运行执行两次。

立即运行和运行历史

立即运行会立刻开始一次运行，而不改变下一次运行的时间；一个计划同一时间只运行一次。每张卡片都以条带显示其最近的运行：绿色表示成功，琥珀色表示部分成功（某个备份目标失败），红色表示失败，灰色表示已跳过，虚线轮廓表示错过，闪烁的标记表示正在进行的运行。运行历史会列出每次运行的结果、持续时间和大小、每份副本的去向、保留策略删除了什么，以及未成功的运行的原因。每个计划保留最近 200 次运行。最近一次完成的运行失败或部分成功的卡片会说明这一点及原因。由计划启动的任务在任务列表中带有该计划的名称，您的计划被暂停或失败时，账户菜单上会出现标记。

保护和去向

  • 默认情况下，每次运行都是用您的备份密钥加密封装的 .mmbak（参见 备份密钥）：无需输入密码，其恢复套件可在任何地方打开它。请先在账户设置 → 备份密钥下创建密钥。
  • 只有当范围不包含个人数据，并且每个选定的备份目标都接受未加密备份时，才允许使用普通格式（.archive 或 .archive.gz）；两者在每次运行之前都会再次检查。
  • 每次运行都会发送到与您共享的、您所选的备份目标，然后在每个备份目标都有已验证的副本后，删除此服务器上的副本。同时保留在服务器上会把它也保留在这里，适用相同的保留策略，并占用您的备份空间；编辑器会说明它们大约会占用多少空间。将其关闭后，迄今保留的副本会获得正常的存活时间。

恢复演练

备份是否可靠，取决于它能否恢复。“测试备份能否恢复”（位于保留策略步骤中）会每隔若干次运行（1 到 30）执行一次恢复演练：该次运行的备份用您的备份密钥打开，并恢复到同一连接上新建的临时数据库（mm_drill_ 加 12 个随机字符）中，每个命名空间都会被读回并与备份比较：文档数量，以及每个文档逐字节比较，然后无论结果如何，临时数据库都会被删除。在它存在期间，对所有人都是关闭的，包括管理员：它不会出现在树、性能页面、慢查询或正在运行的操作中（也不计入数据库的总大小），并且任何页面、请求、Shell 命令、助手、变更数据源、实时同步、复制、比较、备份或恢复都不会读取或写入它：提到它的请求会被拒绝。有两件事超出应用的控制范围：连接管理员的 Shell 中的 listDatabases 响应仍会显示其名称（无法打开它），并且演练所写入的内容与每次写入一样，会出现在 oplog（local.oplog.rs，仅管理员）以及管理员 Shell 中打开的整个部署的变更流中。它还带有其所含内容的个人数据规则（备份的规则，以及连接对这些命名空间的规则），因此其值对不允许查看的人是隐藏的；这些规则不会添加到连接的列表中，会随该数据库一起消失。集合会在不带其选项的情况下恢复（验证器或上限会使其成为对目标的测试），视图则不检查。该次运行会保留其服务器副本直到演练完成，然后照常释放。运行历史会说明每次演练是通过还是失败（以及在哪些命名空间中），演练的报告在任务列表中，失败的演练会触发告警。演练需要在连接上创建数据库的权限；没有该权限（或在只读连接上），演练会被跳过，而绝不是备份被跳过。它的写入量与备份所含内容相同，并且无论连接指定的是哪个成员，写入都会发往主节点：请选择空闲时段。在写入任何内容之前，它会检查连接的 MongoDB 用户是否可以删除数据库（无法清理的演练会立即失败），选取任何数据库都没有使用的临时名称，并将其写入量保持在服务器可用磁盘空间的一半以下（通过 mongos 时按最满的分片计算），设置了 MM_BACKUP_DRILL_MAX_MB 时则保持在该值以下，不报告其可用空间的服务器（Atlas 共享层）需要设置该值；更大的备份会使演练失败，并如实说明。无法读取的删除权限不会被假定存在：演练不会启动。如果在结束时无法删除临时数据库，则演练失败，触发警告级告警，并且报告会指明该数据库：连接的管理员可以在连接页面上看到它，并通过输入其名称在那里将其删除（任何演练运行期间不可进行）。与此同时它对所有人保持关闭，重启会将其删除。

保留策略

保留策略决定计划在每个位置（每个备份目标，以及保留副本时的此服务器）保留哪些备份。共有四个层级，按计划的时区计算；只要任一层级保留某个备份，它就会保留：

  • 最新：最近的 N 个备份（1 到 100）。
  • 每天：每个日历日的最新备份，保留相应的天数（0 到 90）。
  • 每周：每个 ISO 周（周一到周日）的最新备份，保留相应的周数（0 到 52）。
  • 每月：每个日历月的最新备份，保留相应的月数（0 到 60）。

预设：每天一个，保留 30 天（最新的 7 个，加上 30 天内每天一个）、标准（最新的 7 个、14 天、8 周和 12 个月）、长期（最新的 7 个、30 天、26 周和 60 个月）和自定义。编辑器会在时间线上画出保留下来的内容。

  • 只会删除计划自己在某个位置上完整且已验证的副本；手动发送的副本，即使是计划备份的副本，绝不会被删除。在其所有者已不能使用的备份目标上，不会删除任何内容。
  • 最新的备份绝不会被删除，失败的运行不会删除任何内容。
  • 某个位置上的删除发生在本次运行在该位置的副本完成之后，每个位置每次运行最多删除 100 个；删除失败会在下一次运行之后重试。每次删除都会连同文件名记入审计日志。
  • 规则、时区、备份目标或保留位置的更改如果会一次删除十个以上的备份，会先要求您确认该数量。
  • DigitalOcean Spaces Cold Storage 对每个对象至少按 30 天计费：当某条规则会使备份在那里保留的时间更短时，编辑器会发出警告。

打开计划备份

  • 在此服务器上，像恢复其他备份一样恢复它：它用您的备份密钥打开，包括已停用的密钥，并且恢复会说明是哪个密钥打开了它。
  • 在其他位置，或当您的任何密钥都无法打开它时，恢复会要求提供该备份的恢复套件（粘贴它或选择其文件）。该套件仅用于这次恢复，不会被保留，除非勾选导入此密钥，这会将该密钥添加到您的备份密钥中。
  • 不使用应用时： mongo-manager backup decrypt <file.mmbak> --key-file <kit.txt> -o <file.archive> 会写出普通归档，可用 mongorestore --archive 打开。如果没有 --key-file，只能用其备份密钥打开的文件会在询问任何内容之前说明这一点。

限制和设置

  • MM_BACKUP_QUOTA：每个用户的备份空间，单位 MiB（默认 20 480）。
  • MM_BACKUP_TOTAL_QUOTA：所有用户的备份空间，单位 MiB（默认 102 400）。
  • MM_BACKUP_MAX_UPLOAD：可恢复的最大文件，单位 MiB（默认 20 480）。
  • MM_BACKUP_TTL_HOURS：备份和上传文件的保留时长（默认 24）。
  • MM_BACKUP_MAX_JOB_HOURS：一次备份或恢复最长可运行的时间（默认 12）。
  • MM_BACKUP_CHUNK_MB：加密备份的默认分块大小（默认 64）。
  • MM_MONGODB_TOOLS_PATH：mongodump 和 mongorestore 所在的文件夹。
  • 一个归档中最多 10 000 个命名空间；mongodump 文件夹的 zip 必须小于 4 GiB。
  • MM_BACKUP_SCHEDULES 和 MM_BACKUP_SCHEDULE_CONCURRENCY：计划功能的开关，以及同时进行的计划运行数量（参见 部署）。

不包括的内容

用户和角色、oplog 以及时间点恢复。备份是逐个集合读取的，而不是某一个时刻的状态：期间写入的文档可能只有一部分包含在内。如需某一时刻的副本，请备份已停止写入的副本集成员，或使用 MongoDB 自带的快照。
