Administración del servidor

Además de tus datos, Mongo Manager administra el propio servidor de MongoDB: sus usuarios y roles de base de datos, la fragmentación de un clúster, las alertas cuando algo falla y el estado de cada conexión de un vistazo.

Usuarios y roles

La página de una conexión → Usuarios y roles administra las cuentas propias de MongoDB, como Database Access en Atlas. Son las cuentas que las aplicaciones y las personas usan para iniciar sesión en MongoDB, no los usuarios de Mongo Manager.

Quién puede usarlo

  • Los usuarios con el permiso de la aplicación databases:admin en la conexión: administradores de la aplicación o un usuario al que se concedió administración en esa conexión. Un usuario al que un administrador oculta los datos personales nunca ve esta sección; quien los oculta para sí mismo sí la ve.
  • También se aplican los derechos propios de MongoDB: la cuenta con la que inicia sesión la conexión necesita userAdmin en la base de datos, o userAdminAnyDatabase (viewUser y viewRole bastan para listar). Cuando MongoDB lo rechaza, la página indica que lo rechazó MongoDB, y qué comando, no la aplicación.
  • En una conexión de solo lectura, los usuarios y roles se listan pero nunca se cambian.

La lista

Usuarios de todas las bases de datos, o de una (el filtro de base de datos), con búsqueda. Los roles de cada usuario se muestran como chips, por ejemplo "readWrite on shop". La cuenta con la que inicia sesión la propia conexión se marca como Esta conexión.

Añadir un usuario

  • Base de datos de autenticación: donde el usuario inicia sesión. Se recomienda admin (los usuarios de allí pueden tener roles en cualquier base de datos), pero sirve cualquier base de datos. $external es para usuarios de x.509, LDAP, Kerberos y AWS IAM, que no tienen contraseña: el nombre debe coincidir exactamente con lo que envía esa fuente.
  • Nombre de usuario.
  • Contraseña: escribe una o pulsa Generar para obtener 24 caracteres aleatorios creados en tu navegador a partir de la fuente de aleatoriedad del sistema, seguros dentro de una cadena de conexión, y que se muestran para que puedas copiarlos.
  • Roles: roles integrados, cada uno con lo que permite, o tus roles personalizados, cada uno en una base de datos. Los roles que solo existen en admin (clusterMonitor, backup, root y similares) quedan fijados a ella.

Las contraseñas usan SCRAM-SHA-256 y necesitan al menos 12 caracteres. Una contraseña se envía a MongoDB una sola vez; Mongo Manager nunca la guarda, la registra ni la escribe en el registro de auditoría. Copia la que generes antes de cerrar el formulario. Conceder permisos amplios te pide confirmar antes, y el servidor los rechaza sin confirmación: los roles integrados root, userAdminAnyDatabase, userAdmin, dbOwner, clusterAdmin, clusterManager, hostManager, backup, restore, readWriteAnyDatabase y dbAdminAnyDatabase, cualquier otro rol integrado de la base de datos admin (readAnyDatabase, clusterMonitor, enableSharding), cualquier rol de local (contiene el oplog, todas las escrituras realizadas) o de config (los metadatos de fragmentación), y cualquier rol personalizado que herede uno de ellos o tenga un privilegio sobre el clúster, sobre cualquier recurso, sobre todas las bases de datos a la vez o sobre local y config, o que cree usuarios o roles (createUser, grantRole, changePassword y similares). Estos roles personalizados se marcan como amplios, y crear uno también requiere confirmación.

Cambiar y eliminar usuarios

  • Editar establece una contraseña nueva, roles nuevos o ambos. Los roles que guardas reemplazan la lista del usuario.
  • Cambiar o eliminar la cuenta propia de la conexión avisa de que puede dejar la conexión sin acceso y requiere confirmación. Lo mismo ocurre al cambiar o eliminar un rol personalizado que esa cuenta tiene. Qué cuenta es lo dice el propio MongoDB (no la configuración de la conexión, que un registro SRV o un certificado pueden cambiar). Tras una contraseña nueva, edita también la conexión.
  • Eliminar un usuario o un rol te pide que escribas su nombre.

Roles personalizados

Los roles personalizados dan a un equipo exactamente las acciones que necesita, nada más. Un rol tiene una base de datos, un nombre, privilegios y roles heredados.

  • Cada privilegio se aplica a una base de datos y una colección (si se dejan vacías, cualquier base de datos o cualquier colección), al clúster o a cualquier recurso.
  • Sus acciones se eligen de la lista de MongoDB, agrupadas en consulta y escritura, administración de bases de datos, usuarios y roles, implementación, replicación y fragmentación.
  • Un rol fuera de admin hereda solo roles de su propia base de datos (regla de MongoDB); un rol de admin puede heredar roles de cualquier base de datos.

Cada cambio queda en el registro de auditoría como mongo.users.create, mongo.users.update, mongo.users.grant, mongo.users.revoke, mongo.users.drop, mongo.roles.create, mongo.roles.update y mongo.roles.drop, con los nombres y las listas de roles, nunca una contraseña.

Fragmentación

La página de una conexión → Fragmentación aparece cuando la conexión es a un mongos. Todas las personas que pueden observar el servidor ven el estado del balanceador, la distribución de chunks y el resumen del clúster. Los cambios necesitan databases:admin y una conexión que no sea de solo lectura.

Distribución de chunks

Una barra por colección particionada, un color por fragmento (shard), con los recuentos también en texto para los lectores de pantalla.

El balanceador

  • Inícialo o deténlo; detenerlo pide confirmación antes. Mientras está detenido, ningún chunk se mueve entre fragmentos; una migración en curso termina primero. Deténlo para una copia de seguridad o para mantenimiento y vuelve a iniciarlo después.
  • Ventana activa: de–a, según el reloj del servidor de configuración. Los chunks solo se mueven dentro de esas horas. Cualquier momento la borra.

Particionar una colección

  1. Elige la base de datos y la colección.
  2. Construye la clave de fragmentación (shard key) campo por campo. Cada campo es de rango o hash, con como máximo un campo hash. El orden importa: sube y baja los campos.
  3. Comprobar esta clave: el servidor toma una muestra de 1000 documentos y responde solo con recuentos, de modo que ningún valor sale de MongoDB: el porcentaje de documentos que tienen cada campo, el número de valores distintos, el porcentaje del valor más común, si los valores crecen con el tiempo (ObjectId, fechas) y si hay un índice que empieza con los campos de la clave. El veredicto es bueno, aceptable o malo.
  4. Opciones: única (solo claves de rango); crear chunks de antemano (una clave hash en una colección vacía, MongoDB 6.0 y anteriores, de 1 a 8192 chunks); crear chunks por zona (una clave hash, con zonas ya definidas).
  5. La fragmentación no se puede deshacer: confirma escribiendo el espacio de nombres.

Un campo que crece con el tiempo, usado como clave de rango, envía todos los documentos nuevos a un mismo fragmento: aplícale hash o pon otro campo primero. Una colección con datos necesita un índice que empiece con los campos de la clave antes de poder particionarse. Los espacios de nombres propios de MongoDB y del sistema (admin, config, local, system.*) se rechazan.

Zonas

  • Cada fragmento lista sus zonas; añade una zona a un fragmento o quita una.
  • Rangos de claves por colección: los límites son Extended JSON de los campos de la clave de fragmentación, con {"$minKey":1} y {"$maxKey":1} para los extremos abiertos, por ejemplo {"region": "eu"} a {"region": "us"}. Los operadores se rechazan. El inicio se incluye; el final, no.
  • Quita un rango cuando sus documentos puedan volver a estar en cualquier fragmento.

El registro de auditoría registra sharding.collection.shard, sharding.zone.shard, sharding.zone.range (el espacio de nombres y la zona, nunca los valores de los límites), sharding.balancer y sharding.balancer.window. Las pruebas de Mongo Manager ejecutan estas pantallas con respuestas grabadas de mongos.

Alertas

Las alertas te avisan cuando un servidor supera un umbral, o cuando falla una de las propias tareas de la aplicación: en la campana, por correo electrónico o en un webhook.

Umbrales

La página de una conexión → Alertas, para los administradores de la aplicación (settings:manage). Un umbral vigila una métrica:

  • Conexiones: conexiones de clientes abiertas (un recuento).
  • Operaciones: operaciones por segundo, de todos los tipos juntos.
  • Retraso de replicación: segundos de retraso del secundario más rezagado (conjuntos de réplicas).
  • Caché de WiredTiger: cuánto se ha llenado la caché, en porcentaje.
  • Uso de disco: porcentaje en uso del disco de los archivos de datos (MongoDB 4.4 y posteriores).
  • Operaciones lentas: el número de operaciones que tardan más que los segundos que elijas (necesita clusterMonitor).

El servidor las evalúa una vez por minuto a partir del mismo muestreo de serverStatus que usa el historial de métricas. Las alertas muestrean una conexión aunque su historial esté desactivado; las muestras solo se guardan cuando el historial está activado. Se muestrean como máximo 50 conexiones, entre historial y alertas en conjunto.

Sin oscilaciones: una alerta se dispara cuando el valor ha permanecido por encima del umbral durante los minutos que elegiste (de 1 a 60, 2 por defecto), y se resuelve solo cuando ha permanecido en el 90 % del umbral o por debajo durante el mismo tiempo. Un umbral de 80 % de llenado de la caché se resuelve al 72 % o menos.

Alertas de eventos

En la página Alertas, para todas las conexiones o para una, o en la sección de una conexión:

  • Falló la copia de seguridad: falló una tarea de copia de seguridad, envío o descarga.
  • Falló la copia de seguridad programada: una ejecución falló, o solo llegó a algunos de sus destinos.
  • Se detuvo la sincronización en vivo: falló, se detuvo o necesita atención por sí sola, no cuando la detuvo una persona.
  • Falló una tarea: cualquier otra tarea (un simulacro de restauración tiene su propio evento).
  • Falló el simulacro de restauración: un simulacro de restauración programado no pudo restaurar su copia de seguridad, encontró datos distintos o no pudo eliminar su base de datos temporal (una advertencia: los datos coincidían). Un simulacro que pasó queda en el historial de la programación, no es una alerta.
  • La sincronización bidireccional resolvió conflictos: ambos lados de una sincronización en vivo bidireccional cambiaron los mismos documentos; ganó la última escritura (los _id están en la actividad de la sincronización).
  • Observar coincidió con su filtro de alerta: un feed de Observar cuyo propietario pidió alertas pasó cambios por su filtro (como máximo cada 10 segundos, mientras el feed está en marcha).

Las notificaciones llevan solo nombres y números: nunca valores de documentos, textos de error, cadenas de conexión ni hosts.

Informes programados

En la página Alertas (administradores de la aplicación): un informe indica, según una programación, algunos recuentos de una conexión (cada mañana, cada lunes, hasta cada hora) en la campana, por correo electrónico o en webhooks, igual que se envían las alertas. Cada recuento tiene su etiqueta, una colección y un filtro opcional (JSON; si no hay ninguno, cuenta todos los documentos, la estimación de la colección); un recuento superior a un millón dice "al menos". Ejecuta uno ahora, cámbialo, desactívalo o elimínalo desde su fila; allí se muestran los recuentos de su última ejecución.

Solo números, nunca un valor. Un filtro que nombra un campo personal (o uno que las reglas de datos personales interpretarían de otro modo) se rechaza al guardar el informe y, si las reglas cambian después, se omite indicando el motivo; lo mismo ocurre con los espacios de nombres propios de MongoDB, el JavaScript del servidor, las vistas y las series temporales (el pipeline de una vista podría elegir por un campo personal). Un informe cuenta como credenciales propias de la conexión: se rechaza uno en el que cada persona inicia sesión por separado, y también un filtro en una conexión que cifra campos en el cliente (no coincidiría con nada de lo que puede leer). En la campana y en el historial, los administradores ven los recuentos de una ejecución con sus etiquetas; los demás ven que un informe se ejecutó, pero no sus recuentos. De cada informe se conservan en el historial las últimas 30 ejecuciones; uno cuya programación ya no se puede calcular se desactiva, indicando el motivo.

Canales

  • La campana. Cada usuario activa Mostrar alertas en la campana para sí mismo, en Preferencias o en la página Alertas. Solo ve las alertas de las conexiones cuyo servidor puede observar (server:monitor).
  • Correo electrónico. El servidor SMTP, el puerto, y TLS desde el inicio (normalmente 465) o STARTTLS (normalmente 587): se rechaza un servidor que no ofrezca ninguno de los dos; el correo nunca se envía en texto plano. Un nombre de usuario y una contraseña (selladas), la dirección del remitente (From) y hasta 20 destinatarios. Un servidor, puerto, cifrado o nombre de usuario nuevo requiere volver a escribir la contraseña: la guardada nunca se envía a otro servidor. Enviar mensaje de prueba envía con la configuración guardada. Se abandona una sesión que no termina a tiempo su handshake TLS o su intercambio. El correo sale por el cliente propio de Mongo Manager y su protección de salida: direcciones públicas, y privadas solo dentro de MM_ALERTS_PRIVATE_NETWORKS.
  • Webhooks. Una dirección https; http sin cifrar solo a direcciones dentro de MM_ALERTS_PRIVATE_NETWORKS. Sin credenciales en la dirección, nunca a los metadatos de la nube ni a direcciones link-local, y no se siguen redirecciones. El servidor genera el secreto de firma de cada webhook y lo muestra una sola vez; Generar un nuevo secreto lo reemplaza y el anterior deja de funcionar de inmediato.

Cada regla elige adónde se envía; una regla sin canal solo se registra.

Entregas de webhooks

Cada entrega es un POST con un cuerpo JSON:

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type es alert.firing, alert.resolved, alert.event o alert.test (una prueba lleva solo type y at). Las alertas de eventos establecen event (backup.failed, schedule.failed, liveSync.stopped, job.failed) en lugar de metric. Los encabezados:

  • x-mm-event: el tipo de nuevo.
  • x-mm-delivery: un id único de la entrega, el mismo en cada reintento.
  • x-mm-timestamp: segundos Unix en que se firmó este intento.
  • x-mm-signature: sha256= seguido del HMAC-SHA256 en hexadecimal, con el secreto del webhook, de la marca de tiempo, un punto y el cuerpo.

Comprueba la firma sobre el cuerpo sin procesar, antes de analizarlo, y rechaza las marcas de tiempo con más de 5 minutos de antigüedad. En Node.js: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

En Python:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

Una entrega se intenta hasta tres veces más, tras 2 segundos, 10 segundos y 60 segundos, ante un error de red, una respuesta 5xx, 408 o 429; nunca ante cualquier otro 4xx, ni hacia una dirección que la protección rechaza. Cada intento se firma de nuevo con una marca de tiempo nueva. Usa x-mm-delivery para ignorar una entrega que ya procesaste.

Posponer, pausar y reconocer

  • Posponer una regla durante 1 hora, 8 horas o 1 día: las alertas se siguen registrando, pero no se envía nada. Reactivar ahora lo termina antes.
  • Pausa y reanuda una regla con su interruptor.
  • Los administradores reconocen una alerta para todos, que entonces ven quién lo hizo; los demás la descartan de su propia campana. Fuera de los administradores, la campana muestra lo que ocurrió (sus códigos), pero no qué sincronización, tarea, programación o espacio de nombres.
  • Las entregas salen de pocas en pocas desde una sola cola, sin importar cuántos canales y alertas se disparen a la vez.
  • El Historial, en la página Alertas y en la sección de cada conexión, conserva 90 días (20 000 entradas como máximo), con el resultado de cada entrega y cuántos intentos requirió.

MM_ALERTS=0 desactiva las alertas en el servidor: no se evalúa ni se envía nada (consulta Implementación). El registro de auditoría registra alerts.rule.create, alerts.rule.update, alerts.rule.delete, alerts.rule.snooze, alerts.email.update, alerts.email.test, alerts.webhook.create, alerts.webhook.update, alerts.webhook.delete, alerts.webhook.test y alerts.acknowledge, nunca la contraseña SMTP ni el secreto de un webhook.

Estado en vivo

Las tarjetas de conexión del Resumen muestran la latencia de ping, la versión de MongoDB, la topología y las alertas que se están disparando en cada conexión. La página de una conexión muestra lo mismo en su encabezado, con un punto de estado.

  • El servidor conserva cada respuesta durante 30 segundos.
  • La lista nunca se conecta por su cuenta: una conexión que no está abierta muestra Sin conectar. Abrir la página de una conexión la comprueba, igual que lo haría listar sus bases de datos.
  • Los recuentos de alertas solo se muestran para las conexiones cuyo servidor puedes observar.
