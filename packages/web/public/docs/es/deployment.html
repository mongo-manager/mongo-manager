Implementación

Como servicio del sistema

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

El servicio se ejecuta con su propia cuenta sin privilegios, desde una carpeta de programa que solo los administradores pueden modificar, en modo de equipo en 127.0.0.1:4321. En el primer inicio, el token de configuración de un solo uso se guarda en setup-token, dentro de la carpeta de datos, que solo pueden leer la cuenta del servicio y los administradores; service install indica cómo leerlo. El token nunca se escribe en el registro, y el archivo se elimina en cuanto existe el primer administrador.

Instalado en modo local (--no-auth), el servicio solo se abre desde un enlace de inicio de un solo uso: service install muestra uno, y service open muestra uno nuevo siempre que lo necesites (como administrador: se genera a partir de launch.key, en la carpeta de datos). Ábrelo en tu propio navegador, no en uno con privilegios elevados; ese navegador mantiene después la sesión mientras conserve los datos de este sitio, como máximo seis meses después de su último uso.

Docker

La imagen se ejecuta como un usuario sin privilegios sobre un sistema de archivos raíz de solo lectura, en modo de equipo. Los datos residen en el volumen /data. Los equipos sin conexión pueden cargar un archivo de imagen con docker load -i. El token de configuración del primer inicio: docker exec <container> cat /data/setup-token. El archivo compose publica el puerto solo en el loopback del host (127.0.0.1:4321); para atender a otros equipos, coloca delante un proxy inverso HTTPS en lugar de publicar HTTP sin cifrar. Un proxy en el host llega al contenedor desde la puerta de enlace de la red de compose: confía en MM_TRUSTED_PROXIES=172.31.240.1, no en 127.0.0.1.

Dentro del contenedor el servidor escucha en todas las direcciones, así que sin MM_ALLOWED_HOSTS solo responde a direcciones IP y a localhost (cada inicio lo indica). Todo lo que lo alcance por un nombre (un proxy que reenvía el nombre público, otro contenedor por el nombre del servicio, como un Prometheus que consulta mongo-manager:4321, o un servicio de Kubernetes) recibe un 403 hasta que ese nombre figure en la lista: MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

En modo local (MM_AUTH=0), el registro del contenedor nombra el comando que imprime un enlace, nunca un enlace: docker exec <container> node /app/dist/cli.cjs open --no-open. Indica el puerto en el que escucha el servidor dentro del contenedor: si se publica en otro puerto del host (-p 127.0.0.1:8080:4321), cambia el puerto del enlace por el del host antes de abrirlo.

En un servidor, coloca delante un proxy inverso HTTPS que lo sirva como mongo.example.com e inícialo así; la última línea lee el token de configuración. Termina la configuración enseguida: hasta que exista el primer administrador, quien tenga el token puede convertirse en él. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES es la dirección desde la que un proxy en el host llega al contenedor: la puerta de enlace de la red de Docker, normalmente 172.17.0.1 en la red bridge predeterminada (la muestra docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}'). Sin ella, todas las solicitudes parecen venir de la puerta de enlace, así que el registro de auditoría y los bloqueos de inicio de sesión no distinguen a los usuarios. Una vez definida MM_ALLOWED_HOSTS, solo se aceptan los nombres que enumera: añade 127.0.0.1 para seguir abriendo http://127.0.0.1:4321 en el host. --read-only, --tmpfs /tmp, --cap-drop ALL y no-new-privileges son el refuerzo que aplica el archivo compose.

Llegar a MongoDB desde el contenedor

Dentro de un contenedor, localhost es el propio contenedor, así que mongodb://localhost:27017 falla con ECONNREFUSED aunque MongoDB se ejecute en la misma máquina.

  • MongoDB en otro contenedor: pon ambos en una misma red de Docker (docker network create mm y después docker network connect mm mongo-manager y docker network connect mm my-mongodb, o --network mm al iniciarlos) y conéctate a mongodb://my-mongodb:27017.
  • MongoDB en el host, Docker Desktop (Windows, macOS): mongodb://host.docker.internal:27017.
  • MongoDB en el host, Linux: ejecuta Mongo Manager con --network host (entonces localhost es el host; mantenlo privado con -e MM_HOST=127.0.0.1, detrás del proxy, de confianza como 127.0.0.1) o añade --add-host=host.docker.internal:host-gateway. Esto último solo llega a un MongoDB que escuche en la dirección de la puerta de enlace del bridge: no a uno ligado al 127.0.0.1 del host, ni a un contenedor publicado solo allí (-p 127.0.0.1:27018:27017); para esos, usa una red compartida o la red del host.
  • Un conjunto de réplicas cuyos miembros se llaman localhost:27017 devuelve al driver a localhost: añade ?directConnection=true.

Detrás de un proxy inverso

  • Confía solo en el proxy: --trusted-proxies 127.0.0.1. Sin esto el servidor no puede saber que una solicitud llegó por HTTPS, así que las cookies de sesión no se marcan como Secure; un inicio en modo de equipo lo avisa, y avisa también cuando los inicios de sesión viajarían por la red mediante HTTP sin cifrar.
  • Indica el host público: --allowed-hosts mm.example.com.
  • Sirve la aplicación bajo una subruta con --base-path /mm/.
  • Cada dirección de cliente puede hacer 600 solicitudes a la API por minuto; auméntalo con MM_API_RATE_LIMIT (60–100000) cuando muchas personas comparten una misma dirección.
  • Como máximo hay 1000 conexiones abiertas a la vez (MM_MAX_CONNECTIONS, 16–100000), y como máximo 256 desde una misma dirección (MM_MAX_CONNECTIONS_PER_IP, 2–100000); una conexión que supere ese límite se cierra, y el registro lo indica una vez por minuto y por dirección. Un navegador mantiene abiertas unas seis conexiones, así que si muchas personas acceden a Mongo Manager desde una misma dirección (tras un NAT, una VPN o Docker Desktop), aumenta MM_MAX_CONNECTIONS_PER_IP. Detrás de proxies de confianza solo se aplica el total: todas las conexiones proceden del proxy, que debería limitar a sus propios clientes.
  • Los archivos importados y exportados residen en <data directory>/transfer: MM_TRANSFER_MAX_UPLOAD es la subida más grande en MiB (por defecto 1024, 1–65536), MM_TRANSFER_QUOTA el almacenamiento que puede ocupar cada usuario en MiB (por defecto 5120, 16–1048576), MM_TRANSFER_TOTAL_QUOTA lo que pueden ocupar todos los usuarios juntos en MiB (por defecto 51200, o MM_TRANSFER_QUOTA si este es mayor; 16–16777216), MM_TRANSFER_TTL_HOURS cuánto tiempo se conserva un archivo (por defecto 24, 1–720) y MM_TRANSFER_MAX_JOB_HOURS cuánto tiempo puede ejecutarse una importación o exportación (por defecto 6, 1–72). Reserva en ese disco espacio para el total, o para la cuota multiplicada por el número de personas que transfieren archivos si esta cifra es menor.

Configuración y variables de entorno

Cada ajuste del servidor puede indicarse como opción de línea de comandos, como variable de entorno o en un archivo de configuración JSON indicado con --config o MM_CONFIG. La línea de comandos prevalece sobre el entorno, y el entorno sobre el archivo. Un interruptor acepta 1/0, true/false, yes/no u on/off. Los ajustes de cada función están en su propia sección más abajo.

Variable Opción Qué hace
MM_WEB_PORT -p, --web-port Puerto de la interfaz web (por defecto 4321).
MM_HOST --host Dirección en la que escuchar (por defecto 127.0.0.1). Una dirección de red requiere el modo de equipo, o MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Modo de equipo: usuarios, roles e inicio de sesión (desactivado por defecto).
MM_DATA_DIR --data-dir El directorio de datos (por defecto ~/.mongo-manager).
MM_CONFIG --config Un archivo de configuración JSON. En Linux y macOS, si contiene un secreto no debe poder leerlo otro usuario, o el servidor lo rechaza.
MM_SECRET_KEY La clave de cifrado, en lugar del secret.key del directorio de datos.
MM_OPEN --open Abre el navegador al iniciar (activado por defecto): en modo local, en una dirección loopback, cuando se inicia desde un terminal.
MM_URI --uri Una conexión que se crea solo en el primer inicio. Usa la variable para una cadena de conexión con contraseña: otros usuarios pueden ver las líneas de comandos.
MM_READ_ONLY --read-only Ninguna conexión puede modificar datos, sea cual sea su propio ajuste.
MM_TRUSTED_PROXIES --trusted-proxies Direcciones o rangos CIDR de proxies cuyas cabeceras X-Forwarded-* se consideran fiables.
MM_ALLOWED_HOSTS --allowed-hosts Los únicos nombres de host a los que responde el servidor. Si no se define, responde a los nombres de loopback cuando escucha en loopback y, en caso contrario, solo a los nombres de loopback y a las direcciones IP, nunca a otro nombre (una defensa contra el DNS rebinding; el inicio lo indica). Indica aquí todos los nombres de host con los que la gente lo abre.
MM_BASE_PATH --base-path Sirve la aplicación bajo una subruta, como /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Permite una dirección de red sin modo de equipo. Cualquiera que llegue hasta ella tiene acceso completo.
MM_LOG_LEVEL --log-level fatal, error, warn, info (por defecto), debug, trace o silent.
MM_LOG_FILE --log-file Añade el registro JSON a este archivo en lugar de a la salida estándar. El archivo se hace privado (modo 0600; en Windows se retira el acceso a todos los usuarios: esta cuenta, SYSTEM y Administrators lo conservan) y se rota a los 10 MiB, conservando la parte anterior como <file>.1. Se rechaza una ruta que sea un enlace, un archivo con otros nombres (enlaces físicos) o que no sea un archivo normal, y el inicio falla indicándolo: elimínala o renómbrala, o indica otro archivo de registro. Una línea que no se puede escribir (disco lleno) se descarta y se avisa una vez por la salida de error estándar. Las solicitudes se registran por su ruta, con cada valor de consulta y el id de un archivo de GridFS escritos como ***.
MM_REQUIRE_ADMIN_2FA Todos los administradores deben configurar el inicio de sesión de dos factores antes de hacer cualquier otra cosa; después no se puede desactivar desde la aplicación. Sin esta variable, un administrador puede exigir lo mismo desde la aplicación.
MM_REQUIRE_2FA Todos los usuarios, sea cual sea su rol, deben configurar el inicio de sesión de dos factores antes de hacer cualquier otra cosa; después no se puede desactivar desde la aplicación. Sin esta variable, un administrador puede exigir lo mismo desde la aplicación.
MM_METRICS_TOKEN Activa las métricas de Prometheus en <base path>metrics, que se leen con este token como token de portador (al menos 32 caracteres). Las cifras no nombran a ningún usuario, conexión, base de datos ni colección.
MM_GRIDFS_MAX_MB El archivo más grande que se sube a GridFS, en MB (por defecto 512, 1–10240).
MM_MODEL_MAX_DOCS Los documentos que un modelo de datos (la sección Modelo de una base de datos) puede muestrear en total (por defecto 20000, 100–1000000): con muchas colecciones, la muestra de cada una se reduce, y la sección lo indica.
MM_ALLOW_KERBEROS Modo de equipo: permite las conexiones Kerberos (GSSAPI) (desactivado por defecto). Inician sesión con el ticket Kerberos de la cuenta con la que se ejecuta el servidor: todos los usuarios de una conexión así inician sesión como esa cuenta. Consulta Seguridad.
MM_ALLOW_WORKLOAD_IDENTITY Modo de equipo: permite que las conexiones OIDC usen la identidad de carga de trabajo de la máquina (Azure, GCP, Kubernetes) cuando se elige en la conexión (desactivado por defecto).
MM_OIDC_DEVICE_FLOW Inicio de sesión OIDC con un código (el flujo de dispositivo), para proveedores de identidad que no pueden devolver el navegador a este servidor. Quien aprueba el código inicia sesión, por lo que en modo de equipo está desactivado salvo que se active aquí; en modo local está activado.
MM_OIDC_PRIVATE_NETWORKS Redes privadas (CIDR separados por comas) en las que pueden estar los proveedores de identidad OIDC; solo se permite http sin cifrar en ellas. Sin esta variable deben ser direcciones https públicas.
MM_CRYPT_SHARED_LIB_PATH La ruta absoluta de la biblioteca crypt_shared (mongo_crypt_v1) para el cifrado del lado del cliente. En modo de equipo es la única que se carga.
MM_KMS_PRIVATE_NETWORKS Redes privadas (CIDR separados por comas) en las que pueden estar los servicios de gestión de claves (un servidor KMIP local). Sin esta variable deben ser direcciones públicas.
MM_KMS_ALLOWED_HOSTS Hosts de servicios de gestión de claves (separados por comas, host o host:port, puerto 443 por defecto) a los que puede llegar una conexión además de los propios de los proveedores (AWS KMS, Azure Key Vault y Managed HSM con el inicio de sesión de Microsoft, Google Cloud KMS) y los endpoints que nombra su configuración: un endpoint de VPC, un servidor KMIP. Cualquier otro host, u otro puerto, se rechaza: la clave maestra de una clave de datos no puede enviar el token del KMS a otro lugar.

Kerberos y cifrado del lado del cliente (paquete npm)

Kerberos (GSSAPI) y el cifrado del lado del cliente a nivel de campo y Queryable Encryption necesitan paquetes nativos, que Mongo Manager no instala por sí mismo: instalarlo no ejecuta el script de instalación de ningún paquete. Para usarlos, instala los paquetes junto al paquete npm y reinicia: 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager los carga solo desde la carpeta global node_modules que contiene mongo-manager (comprobada por su ruta real, nunca una carpeta superior) y solo cuando una conexión necesita uno por primera vez; el formulario de conexión indica cuál falta y cómo instalarlo. Los binarios independientes, la imagen de Docker (que define MM_DISTRIBUTION=docker) y la copia desde la que se ejecuta un servicio de Windows no incluyen ningún módulo nativo: en ellos estas dos funciones indican que no están disponibles en este paquete; usa en su lugar el paquete npm, ejecutado en primer plano. El cifrado automático de Queryable Encryption necesita además la biblioteca crypt_shared (MM_CRYPT_SHARED_LIB_PATH) o mongocryptd, y MongoDB Enterprise o Atlas; MongoDB Community solo descifra. MONGODB-OIDC no necesita ningún paquete: el proveedor de identidad debe tener <address><base path>oidc/callback de este servidor como dirección de redirección (u otra que indique la conexión), y la gente puede iniciar sesión con un código donde no pueda hacerlo así.

Instalar como aplicación

En Chrome o Edge, elige Instalar Mongo Manager en la barra de direcciones para abrirlo en su propia ventana desde el escritorio o el menú de inicio.

Destinos de copias de seguridad

  • MM_BACKUP_FOLDER_ROOTS: las carpetas que pueden usar los destinos de carpeta del servidor, como rutas absolutas separadas por el separador de rutas del sistema (: en Linux y macOS, ; en Windows), como máximo 16. Por defecto: ninguna, de modo que no se puede crear ningún destino de carpeta. Una ruta relativa detiene el servidor al iniciar. Concede a la cuenta del servicio acceso de escritura a cada raíz, y mantén las raíces fuera del directorio de datos: se rechaza un destino de carpeta dentro de él. Cada inicio registra una raíz en la que el servidor no puede escribir. Para el servicio de Linux:
    • Su entorno aislado le permite escribir solo en su directorio de datos y en las raíces que nombran su configuración y su archivo de entorno cuando se instala: tras cambiarlas, ejecuta de nuevo sudo mongo-manager service install (conserva los datos, la configuración y la clave), y reinicia el servicio tras crear una raíz que faltaba. Las raíces definidas en cualquier otro lugar, como un Environment= en un drop-in, no las ve la instalación: sus carpetas siguen siendo de solo lectura para el servicio.
    • La instalación excluye una raíz situada bajo /home, /root, /run/user, /tmp, /var/tmp o /dev, a las que el servicio no puede acceder, y una que anularía el entorno aislado: una que contenga un directorio del sistema (/, /var, /var/lib y similares) o esté dentro de /etc, /usr, /run u otro directorio del sistema (bajo /var solo están abiertas las carpetas dentro de /var/backups). Sirve una carpeta dentro de /srv, /opt o un punto de montaje bajo /mnt o /media, no esas carpetas en sí; en un sistema de archivos extraíble o de red, quien controla el disco o el recurso compartido controla las carpetas que contiene, así que haz que el propio punto de montaje sea la raíz (un montaje FUSE de un usuario dice lo que quiere sobre sus propietarios y enlaces). Una raíz dentro de otra raíz queda dentro del entorno aislado por esa otra. Donde /srv, /opt o /mnt es en sí un enlace a /var, como en los sistemas ostree (Fedora Silverblue, CoreOS), la instalación indica adónde lleva una raíz, y allí se rechaza: elige una carpeta dentro de /var/backups.
    • Un enlace se juzga por adónde lleva, y la unidad nombra ese lugar; un enlace que no lleva a ninguna parte se excluye: para uno que apunta a una carpeta aún no creada, crea esa carpeta y ejecuta de nuevo service install; para uno que da vueltas en un bucle o pasa por un archivo, elige otra carpeta o elimina el enlace. Mantén cada carpeta situada por encima de una raíz, y las carpetas en las que están los enlaces de su camino (incluido un enlace dentro del destino de otro enlace), con root como propietario y cerradas a su grupo y a los demás, para que nadie pueda poner allí un enlace en lugar de una carpeta; en una carpeta en la que otros puedan escribir, con bit sticky o sin él, haz que root sea propietario de la carpeta que contiene, y que la raíz esté dentro de esa.
    • Se excluye una raíz situada bajo una carpeta que el usuario del servicio podría modificar, en cualquier punto hasta / y a lo largo de los enlaces de su ruta: una de la que ese usuario es propietario, o en la que puede escribir mediante uno de sus grupos, una ACL o como cualquiera, donde un proceso que se ejecute como ese usuario podría poner un enlace a /etc en lugar de una carpeta. Eso incluye un enlace dentro de otra raíz, en la que escribe el servicio. La instalación, y doctor ejecutado con sudo, también consultan al sistema: con setpriv ejecutan test -w como ese usuario, de modo que el kernel aplica sus grupos (los que la unidad da al servicio con Group= o SupplementaryGroups=, incluidos los de un drop-in) y sus ACL. Sin setpriv, o sin root, solo se leen los modos de las carpetas y los grupos del usuario, y ambos lo indican. Lo que permiten los modos cuenta incluso donde una ACL lo retira, por lo que una carpeta así también excluye sus raíces.
    • La instalación pregunta a systemd quién ejecuta el servicio, con todos los drop-ins leídos. Un drop-in que lo ejecuta como un usuario distinto de --user (o como root), con DynamicUser=yes y sin una cuenta con ese nombre, con un Group= distinto del propio del usuario, o con un grupo que el sistema no conoce (con el que systemd se niega a iniciarlo) detiene la instalación antes de que cambien el directorio de datos y la configuración; indica el motivo y deja el servicio detenido y desactivado. Un grupo cuya búsqueda falla, o un systemd al que no se puede preguntar, excluye todas las raíces.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json comprueba el servicio instalado (mongo-manager doctor a secas comprueba tu propio directorio de datos, e indica que el servicio no es lo que ha comprobado). Comprueba cada raíz: que existe, que es un directorio en el que el servidor puede escribir, que está dentro del entorno aislado y que no está dentro del directorio de datos; también nombra una carpeta en la que el entorno aislado permite escribir al servicio que ya no nombra ninguna raíz, o que lleva a una raíz o al directorio de datos por un enlace que puede cambiar alguien distinto de root, y avisa de un servicio que se ejecuta como root, de un grupo que nadie tiene o cuya búsqueda falla, y de DynamicUser=yes sin una cuenta con su nombre. Comprueba las raíces que nombran la configuración y el archivo de entorno del servicio, por lo que necesita sudo: solo root puede leer el archivo de entorno, que es también donde está la clave secreta del servicio. Comprueba el acceso de escritura como el usuario con el que se ejecuta; ejecutado como root, lee en su lugar el propietario y el modo de la raíz para el usuario que es propietario del directorio de datos, y da por bueno lo que dice el sistema sobre dónde puede escribir ese usuario. Las carpetas situadas por encima de las raíces las juzga para el usuario con el que la unidad ejecuta el servicio (su User=).
  • MM_BACKUP_PRIVATE_NETWORKS: rangos privados a los que pueden llegar los destinos, como una lista separada por comas de hasta 64 CIDR (por ejemplo 10.0.5.0/24); dentro de ellos se permite HTTP sin cifrar. Por defecto: ninguno. Se aceptan los rangos de loopback, 10/8, 172.16/12, 192.168/16, CGNAT (100.64.0.0/10) y de unicast local único (fc00::/7). Un rango público detiene el servidor al iniciar, y también un rango dentro de un rango de enlace local o de metadatos de la nube (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200), en cualquier forma, incluidas IPv4 mapeada y NAT64; el mensaje nombra el rango. Esas direcciones nunca se pueden alcanzar, ni siquiera dentro de un rango de la lista.
  • MM_BACKUP_PROXY: un proxy HTTP(S) por el que se llega a los destinos, como http://proxy.corp:3128 o https://user:password@proxy.corp; sin ruta ni consulta. Por defecto: ninguno (nunca se lee ninguna variable de entorno de proxy). Mongo Manager sigue resolviendo y comprobando por sí mismo la dirección de cada destino, y pide al proxy que se conecte a esa dirección, por lo que las reglas de direcciones anteriores se cumplen a través del proxy; TLS se ejecuta de extremo a extremo hasta el destino, cuyo certificado se comprueba igual que sin proxy. Los destinos dentro de MM_BACKUP_PRIVATE_NETWORKS se alcanzan directamente. Un proxy en una dirección de enlace local o de metadatos detiene el servidor al iniciar. Mantén la contraseña del proxy fuera de los historiales de shell compartidos: forma parte de la dirección. Solo los destinos de copias de seguridad lo usan: los canales de alertas (correo electrónico y webhooks), los proveedores de IA y los complementos nunca pasan por él. Conviene saber antes de elegir un proxy: un proxy http:// recibe su nombre de usuario y contraseña en claro (Basic), así que es preferible https:// o un proxy dentro de una red de confianza; un proxy que solo permite CONNECT a nombres de host de una lista rechaza estas conexiones, ya que se le pide una dirección IP; el certificado de un proxy https:// debe estar firmado por una autoridad en la que confíe Node.js (su lista integrada, o una añadida con NODE_EXTRA_CA_CERTS): no se puede indicar una CA propia.
  • MM_BACKUP_DEST_PART_MB: el tamaño de las partes de subida, de 16 a 512 MiB (por defecto 64).
  • MM_BACKUP_DRILL_MAX_MB: lo máximo que escribe un simulacro de restauración, en MiB. Por defecto: ninguno; un simulacro se mantiene por debajo de la mitad del espacio libre en disco que informa MongoDB (el del fragmento más lleno, a través de un mongos). Donde MongoDB no lo informa (niveles compartidos de Atlas), los simulacros solo se ejecutan si se define esta variable.
  • MM_BACKUP_DEST_TRANSFERS: envíos y descargas que se ejecutan a la vez en cada destino, de 1 a 8 (por defecto 2). Los demás esperan, y se muestran como «Esperando a» ese destino en la lista de tareas.

Copias de seguridad programadas

  • MM_BACKUP_SCHEDULES: el programador, activado por defecto. 0 lo desactiva: las programaciones conservan sus ajustes, no se ejecuta nada, y la pestaña Copias de seguridad programadas indica que la programación está desactivada. Las ejecuciones que un servidor detenido dejó sin terminar se cierran al iniciar.
  • MM_BACKUP_SCHEDULE_CONCURRENCY: ejecuciones programadas que funcionan a la vez, de 1 a 8 (por defecto 2). Las demás ejecuciones pendientes esperan hasta seis horas.

Observación de cambios

  • MM_WATCH: los feeds de change streams, activados por defecto. 0 los desactiva: las secciones Observar indican que la observación está desactivada, y no se abre nada en MongoDB.
  • MM_WATCH_MAX_FEEDS: feeds en vivo a la vez en este servidor, de 1 a 500 (por defecto 50). Cada usuario puede tener 5 y cada ventana del navegador 3. Cada feed mantiene un cursor de change stream en MongoDB.
  • Observar requiere un conjunto de réplicas, un clúster particionado o una implementación con balanceo de carga, y el usuario de base de datos de la conexión necesita changeStream y find sobre lo que se observa. Consulta Observación de cambios.

Sincronización en vivo

  • MM_LIVE_SYNC: las sincronizaciones en vivo entre conexiones, activadas por defecto. 0 las desactiva: las sincronizaciones en ejecución esperan indicando el motivo y no se lee ni se escribe nada; las nuevas se rechazan. Al activarlas de nuevo, continúan donde estaban.
  • MM_LIVE_SYNC_MAX: sincronizaciones en vivo que no han terminado en este servidor, de 1 a 100 (por defecto 10). Cada usuario puede tener 3. Cada sincronización en ejecución mantiene un change stream en su origen y mantiene abiertas las dos conexiones.
  • El origen debe ser un conjunto de réplicas, un clúster particionado o una implementación con balanceo de carga (MongoDB 6.0 o posterior); una copia que podría durar más que el oplog del origen pide una confirmación. Consulta Sincronización en vivo.

Alertas

  • MM_ALERTS (archivo de configuración: alerts.enabled): las alertas, activadas por defecto. 0 las desactiva: no se evalúa ni se envía nada, y la página Alertas indica que las alertas están desactivadas.
  • MM_ALERTS_PRIVATE_NETWORKS (archivo de configuración: alerts.privateNetworks, una lista): redes a las que pueden llegar los servidores de correo y los webhooks de las alertas además de las direcciones públicas, como una lista separada por comas de hasta 64 CIDR (por ejemplo 10.0.5.0/24). Por defecto: ninguna. Solo dentro de ellas se permite http sin cifrar hacia un webhook. Se aceptan y rechazan los mismos rangos que para MM_BACKUP_PRIVATE_NETWORKS: las direcciones de enlace local y de metadatos de la nube nunca se pueden alcanzar.
  • En un archivo de configuración: "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. Consulta Administración del servidor.

El shell avanzado

  • Desactívalo por completo con --no-shell (o MM_SHELL_ENABLED=0).
  • Límites: MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. Un shell que su página mantiene queda abierto por mucho tiempo que pase sin usarse, como en Compass; uno que ninguna página mantiene se cierra dos minutos después de que su página desaparece. El límite de inactividad está desactivado (0) salvo que lo definas (de 10000 a 86400000 ms); un shell vive como máximo 12 horas salvo que definas otra duración (de 60000 a 86400000 ms, o 0 para ninguna). Los shells mantenidos abiertos cuentan para MM_SHELL_MAX_TOTAL hasta que sus páginas se cierran; en un servidor que comparten muchas personas, define MM_SHELL_IDLE_MS para que se liberen los shells que quedan abiertos sin usarse. Con el inicio de sesión activado, un shell también termina cuando termina la sesión de su usuario, y cuando cambia el rol del usuario o se deshabilita la cuenta.
  • MM_SHELL_RSS_MB: la memoria que puede ocupar el proceso de un shell, de 128 a 16384 MB (por defecto 384). El servidor la mide por sí mismo a partir del sistema operativo (en Windows con tasklist, en macOS con ps) y reinicia un shell que la supere; se pierden las variables del shell. Un shell que deja de responder durante 15 segundos sin que se ejecute ningún comando también se reinicia. MM_SHELL_OUTPUT_MB: la salida de un comando, de 1 a 64 MB (por defecto 5); el resto se corta. MM_SHELL_COMMANDS_PER_SECOND: comandos por shell y segundo, de 1 a 1000 (por defecto 20).
  • En un servidor POSIX ejecutado como root, el proceso de trabajo del shell pasa a MM_SHELL_UID/MM_SHELL_GID (por defecto 65534); no ejecutes el servicio como root.

Asistente de IA

  • MM_AI: el asistente de IA, activado por defecto; solo se muestra cuando un administrador añade un proveedor (Configuración → Asistente de IA). 0 lo oculta en todas partes y rechaza las solicitudes.
  • MM_AI_PRIVATE_NETWORKS: redes (CIDR, separados por comas) en las que puede estar un proveedor además de las direcciones públicas, por ejemplo un Ollama en 10.0.0.5; allí solo se permite http sin cifrar. Los metadatos de la nube y las direcciones de enlace local nunca se pueden alcanzar. En modo local siempre se permite esta máquina.
  • MM_AI_PER_MINUTE (por defecto 10, 1–120) y MM_AI_PER_DAY (por defecto 200, 1–10,000): solicitudes por persona. MM_AI_MAX_CONCURRENT (por defecto 8, 1–64): solicitudes a la vez en el servidor; cada persona puede tener 2. MM_AI_AGENT_PER_MINUTE (por defecto 30, 1–120): las solicitudes adicionales de un agente al proveedor dentro de un mismo mensaje, por persona y minuto (también cuentan para el día).
  • MM_AI_CHAT_DAYS (por defecto 30, 0–365): cuánto tiempo se conserva un chat después de su último mensaje. 0 mantiene los chats solo en memoria (12 horas) y elimina los chats almacenados con un ajuste anterior cuando el servidor se inicia.

Complementos

  • MM_PLUGINS: los complementos, activados por defecto. Cada uno sigue necesitando la aprobación de un administrador, tras su análisis de seguridad. 0 no encuentra, instala ni ejecuta ninguno (consulta Complementos).
  • MM_PLUGINS_GITHUB: instalar un complemento desde una versión publicada de un repositorio público de GitHub, desactivado por defecto (los complementos se instalan por subida o desde una carpeta); 1 lo permite. El servidor accede entonces a api.github.com, github.com y a los hosts de recursos de versiones de GitHub, mediante https, sin enviar nada propio. Si se deja desactivado, un servidor nunca accede a GitHub. El servidor se conecta a GitHub directamente: no se usan los ajustes de proxy HTTP, así que un servidor que solo puede salir mediante un proxy instala los complementos por subida. Un servicio del sistema lo lee de su config.json como "pluginsGithub": true (Linux /etc/mongo-manager/config.json, Windows %ProgramData%\Mongo Manager\config.json, macOS /Library/Application Support/Mongo Manager/config.json); reinicia el servicio después.
