Bereitstellung

Als Systemdienst

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

Der Dienst läuft unter einem eigenen Konto ohne Sonderrechte, aus einem Programmordner, den nur Administratoren ändern können, im Teammodus auf 127.0.0.1:4321. Beim ersten Start wird das einmalige Einrichtungstoken in setup-token im Datenordner abgelegt, das nur das Dienstkonto und Administratoren lesen können; service install gibt aus, wie es gelesen wird. Das Token wird nie in das Protokoll geschrieben, und die Datei wird entfernt, sobald der erste Administrator existiert.

Wird der Dienst im Lokalen Modus (--no-auth) installiert, lässt er sich nur über einen einmaligen Startlink öffnen: service install gibt einen aus, und service open gibt bei Bedarf jederzeit einen neuen aus (als Administrator: Er wird aus launch.key im Datenordner erzeugt). Öffnen Sie ihn in Ihrem eigenen Browser, nicht in einem mit erhöhten Rechten gestarteten; dieser Browser bleibt dann angemeldet, solange er die Daten dieser Website behält, höchstens sechs Monate nach der letzten Nutzung.

Docker

Das Image läuft als Benutzer ohne Sonderrechte auf einem schreibgeschützten Root-Dateisystem im Teammodus. Die Daten liegen im Volume /data. Offline-Rechner können ein Image-Archiv mit docker load -i laden. Das Einrichtungstoken des ersten Starts: docker exec <container> cat /data/setup-token. Die Compose-Datei veröffentlicht den Port nur auf dem Loopback des Hosts (127.0.0.1:4321); um andere Rechner zu bedienen, stellen Sie einen HTTPS-Reverse-Proxy davor, anstatt reines HTTP zu veröffentlichen. Ein Proxy auf dem Host erreicht den Container über das Gateway des Compose-Netzwerks: Vertrauen Sie MM_TRUSTED_PROXIES=172.31.240.1, nicht 127.0.0.1.

Im Container lauscht der Server auf allen Adressen. Ohne MM_ALLOWED_HOSTS antwortet er daher nur auf IP-Adressen und localhost (jeder Start weist darauf hin). Alles, was ihn über einen Namen erreicht – ein Proxy, der den öffentlichen Namen weiterleitet, ein anderer Container über den Dienstnamen (ein Prometheus, der mongo-manager:4321 abfragt), ein Kubernetes-Service –, erhält 403, bis dieser Name aufgeführt ist: MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

Im Lokalen Modus (MM_AUTH=0) nennt das Protokoll des Containers den Befehl, der einen Link ausgibt, nie einen Link: docker exec <container> node /app/dist/cli.cjs open --no-open. Er nennt den Port, auf dem der Server im Container lauscht: Ist er auf einem anderen Port des Hosts veröffentlicht (-p 127.0.0.1:8080:4321), ändern Sie den Port im Link auf den des Hosts, bevor Sie ihn öffnen.

Auf einem Server stellen Sie einen HTTPS-Reverse-Proxy davor, der Mongo Manager als mongo.example.com ausliefert, und starten den Container so; die letzte Zeile liest das Einrichtungstoken. Schließen Sie die Einrichtung sofort ab: Solange es keinen ersten Administrator gibt, kann jeder mit dem Token einer werden. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES ist die Adresse, von der aus ein Proxy auf dem Host den Container erreicht: das Gateway des Docker-Netzwerks, im Standard-Bridge-Netzwerk meist 172.17.0.1 (docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}' zeigt es an). Ohne diese Angabe scheint jede Anfrage vom Gateway zu kommen, sodass Audit-Log und Anmeldesperren die Benutzer nicht unterscheiden können. Sobald MM_ALLOWED_HOSTS gesetzt ist, werden nur die dort genannten Namen angenommen: Fügen Sie 127.0.0.1 hinzu, um http://127.0.0.1:4321 auf dem Host weiter öffnen zu können. --read-only, --tmpfs /tmp, --cap-drop ALL und no-new-privileges sind die Härtung, die auch die Compose-Datei anwendet.

MongoDB aus dem Container erreichen

In einem Container ist localhost der Container selbst. Deshalb schlägt mongodb://localhost:27017 mit ECONNREFUSED fehl, selbst wenn MongoDB auf demselben Rechner läuft.

  • MongoDB in einem anderen Container: Bringen Sie beide in ein gemeinsames Docker-Netzwerk (docker network create mm, dann docker network connect mm mongo-manager und docker network connect mm my-mongodb, oder --network mm beim Start) und verbinden Sie sich mit mongodb://my-mongodb:27017.
  • MongoDB auf dem Host, Docker Desktop (Windows, macOS): mongodb://host.docker.internal:27017.
  • MongoDB auf dem Host, Linux: Starten Sie Mongo Manager mit --network host (dann ist localhost der Host; halten Sie es mit -e MM_HOST=127.0.0.1 privat, hinter dem Proxy, dem Sie als 127.0.0.1 vertrauen) oder fügen Sie --add-host=host.docker.internal:host-gateway hinzu. Letzteres erreicht nur ein MongoDB, das auf der Gateway-Adresse der Bridge lauscht: weder eines, das nur an 127.0.0.1 des Hosts gebunden ist, noch einen Container, der nur dort veröffentlicht ist (-p 127.0.0.1:27018:27017); nutzen Sie dafür ein gemeinsames Netzwerk oder das Host-Netzwerk.
  • Ein Replica Set, dessen Mitglieder localhost:27017 heißen, schickt den Treiber zurück zu localhost: Fügen Sie ?directConnection=true hinzu.

Aktualisieren

Ein Administrator sieht die installierte Version auf der Seite „Über Mongo Manager“ im Kontomenü. Jetzt prüfen fragt GitHub nach der neuesten veröffentlichten Version; Automatisch nach Updates suchen tut das einmal täglich. Die tägliche Prüfung ist aus, bis ein Administrator sie einschaltet, und nichts über Sie, Ihren Server oder Ihre Daten wird dabei gesendet: Zurück kommt nur die neueste Versionsnummer. Entwürfe und Vorabversionen werden nie angeboten.

Eine Version wird nur angeboten, wenn ihre SHA256SUMS die Signatur von Mongo Manager (Ed25519) tragen und ihre release.json dort aufgeführt ist. Aktualisieren lädt die Version nach app/ im Datenverzeichnis, prüft jedes Byte gegen die signierten Prüfsummen, kopiert die Datenbank und startet dann neu. Bei jedem Start wird jede Datei der laufenden Version erneut geprüft. Eine Version, die verändert vorgefunden wird, läuft nicht: Sie wird erneut heruntergeladen (außer Updates sind ausgeschaltet), oder die Version, von der aus sie installiert wurde, läuft, und die Seite „Über Mongo Manager“ sagt es. Beim Start wird sonst nichts heruntergeladen. Eine neue Version, die nicht innerhalb einer Minute startet, wird zurückgenommen: Die Datenbankkopie wird zurückgelegt, die vorherige Version läuft wieder, und die Seite „Über Mongo Manager“ sagt es.

  • npm-Paket, eigenständiges Programm, Systemdienst: Das installierte Programm bleibt, wie es ist, und startet die neueste geprüfte Version aus app/. Ein Dienst, der mit einer früheren Version eingerichtet wurde, wird einmal neu installiert (mongo-manager service install): Seine Unit startet dann mit --isolate-account, damit die anderen Prozesse des Dienstkontos beendet werden, bevor eine aktualisierte Version geprüft wird und startet. Unter Linux und macOS geschieht das nur für das Konto, das service install anlegt, nie als root; unter Windows, wo LocalService mit anderen Diensten geteilt wird, werden nur die Programme dieser Installation und die eigenen Prozesse des vorherigen Programms beendet.
  • Docker: Die neue Version liegt im Volume /data und läuft in dem Image, das Sie haben. Bevor sie geprüft wird und startet, werden die anderen Prozesse ihres Benutzers im Container beendet (nie, wenn der Container als root läuft oder die Prozesse des Hosts teilt). Eine Version braucht ein neueres Image nur, wenn die App auf Ihrem nicht laufen kann (ein neueres Node.js); die Seite „Über Mongo Manager“ sagt dann, wie Sie es bekommen, statt das Update anzubieten. Ein neueres Image, das nur Sicherheitskorrekturen für das System bringt, hält das Update nie auf: Die Seite empfiehlt es neben dem Update. Mit Docker Compose: docker compose pull && docker compose up -d. Mit docker run: docker pull ghcr.io/mongo-manager/mongo-manager:<version>, dann den Container entfernen und aus dem neuen Image mit denselben Optionen und demselben Volume /data neu starten (die Daten bleiben im Volume). Auf ein Image, das älter als 90 Tage ist, wird ebenfalls hingewiesen: Laden Sie ein neueres für die Sicherheitskorrekturen von Node.js und dem System.
  • Aus dem Quellcode: Aktualisieren Sie mit git.
  • Die erste Version, die sich selbst aktualisiert, wird von Hand installiert.
  • MM_UPDATES: off (oder 0, false) schaltet Updates ganz aus: keine Prüfung, keine Einstellung, keine Schaltfläche und keine Anfrage, und die Seite „Über Mongo Manager“ sagt es. Standard: an, die tägliche Prüfung aus, bis ein Administrator sie einschaltet.
  • MM_UPDATE_PROXY: ein HTTP(S)-Proxy, über den GitHub erreicht wird, wie MM_BACKUP_PROXY. Standard: keiner.

Hinter einem Reverse-Proxy

  • Vertrauen Sie nur dem Proxy: --trusted-proxies 127.0.0.1. Ohne diese Angabe kann der Server nicht erkennen, dass eine Anfrage über HTTPS kam, sodass Sitzungscookies nicht als Secure markiert werden; ein Start im Teammodus weist darauf hin und meldet, wenn Anmeldungen über reines HTTP durch das Netzwerk liefen.
  • Nennen Sie den öffentlichen Host: --allowed-hosts mm.example.com.
  • Bedienen Sie unter einem Unterpfad mit --base-path /mm/.
  • Jede Client-Adresse darf 600 API-Anfragen pro Minute stellen; erhöhen Sie den Wert mit MM_API_RATE_LIMIT (60–100000), wenn sich viele Personen eine Adresse teilen.
  • Höchstens 1000 Verbindungen sind gleichzeitig offen (MM_MAX_CONNECTIONS, 16–100000), und höchstens 256 von einer Adresse (MM_MAX_CONNECTIONS_PER_IP, 2–100000); eine darüber hinausgehende Verbindung wird geschlossen, und das Protokoll meldet dies einmal pro Minute und Adresse. Ein Browser hält etwa sechs Verbindungen offen. Erreichen viele Personen Mongo Manager von einer Adresse aus – hinter NAT, einem VPN oder Docker Desktop –, erhöhen Sie daher MM_MAX_CONNECTIONS_PER_IP. Hinter vertrauenswürdigen Proxys gilt nur die Gesamtzahl: Jede Verbindung kommt vom Proxy, der seine eigenen Clients begrenzen sollte.
  • Importierte und exportierte Dateien liegen unter <data directory>/transfer: MM_TRANSFER_MAX_UPLOAD ist der größte Upload in MiB (Standard 1024, 1–65536), MM_TRANSFER_QUOTA der Speicher, den jeder Benutzer belegen darf, in MiB (Standard 5120, 16–1048576), MM_TRANSFER_TOTAL_QUOTA das, was alle Benutzer zusammen belegen dürfen, in MiB (Standard 51200, oder MM_TRANSFER_QUOTA, wenn dieser Wert größer ist; 16–16777216), MM_TRANSFER_TTL_HOURS wie lange eine Datei aufbewahrt wird (Standard 24, 1–720) und MM_TRANSFER_MAX_JOB_HOURS wie lange ein Import oder Export laufen darf (Standard 6, 1–72). Geben Sie diesem Datenträger Platz für die Gesamtmenge, oder für die Quote mal die Zahl der Personen, die Dateien übertragen, falls das weniger ist.

Einstellungen und Umgebungsvariablen

Jede Servereinstellung kann als Kommandozeilenoption, als Umgebungsvariable oder in einer JSON-Konfigurationsdatei angegeben werden, die mit --config oder MM_CONFIG benannt wird. Die Kommandozeile hat Vorrang vor der Umgebung und die Umgebung vor der Datei. Ein Schalter akzeptiert 1/0, true/false, yes/no oder on/off. Die Einstellungen der einzelnen Funktionen stehen weiter unten in deren eigenem Abschnitt.

Variable Option Bedeutung
MM_WEB_PORT -p, --web-port Port der Weboberfläche (Standard 4321).
MM_HOST --host Adresse, auf der gelauscht wird (Standard 127.0.0.1). Eine Netzwerkadresse erfordert den Teammodus oder MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Teammodus: Benutzer, Rollen und Anmeldung (Standard aus).
MM_DATA_DIR --data-dir Das Datenverzeichnis (Standard ~/.mongo-manager).
MM_CONFIG --config Eine JSON-Konfigurationsdatei. Unter Linux und macOS darf eine Datei mit einem Geheimnis nicht für andere Benutzer lesbar sein, sonst lehnt der Server sie ab.
MM_SECRET_KEY Der Verschlüsselungsschlüssel anstelle der Datei secret.key des Datenverzeichnisses.
MM_OPEN --open Öffnet beim Start den Browser (Standard ein): im Lokalen Modus, auf einer Loopback-Adresse, wenn der Start aus einem Terminal erfolgt.
MM_URI --uri Eine Verbindung, die nur beim allerersten Start angelegt wird. Verwenden Sie für eine Verbindungszeichenfolge mit Passwort die Variable: Andere Benutzer können Kommandozeilen sehen.
MM_READ_ONLY --read-only Keine Verbindung kann Daten ändern, unabhängig von ihrer eigenen Einstellung.
MM_TRUSTED_PROXIES --trusted-proxies Proxy-Adressen oder CIDR-Bereiche, deren X-Forwarded-*-Header geglaubt wird.
MM_ALLOWED_HOSTS --allowed-hosts Die einzigen Hostnamen, auf die der Server antwortet. Ist die Variable nicht gesetzt, antwortet er bei Loopback-Betrieb auf die Loopback-Namen und sonst nur auf die Loopback-Namen und IP-Adressen, nie auf einen anderen Namen (ein Schutz gegen DNS-Rebinding; der Start weist darauf hin). Nennen Sie hier jeden Hostnamen, unter dem Personen ihn öffnen.
MM_BASE_PATH --base-path Stellt die App unter einem Unterpfad bereit, etwa /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Erlaubt eine Netzwerkadresse ohne Teammodus. Jeder, der sie erreicht, hat vollen Zugriff.
MM_LOG_LEVEL --log-level fatal, error, warn, info (Standard), debug, trace oder silent.
MM_LOG_FILE --log-file Hängt das JSON-Protokoll an diese Datei an, statt es auf der Standardausgabe auszugeben. Die Datei wird privat gemacht (Modus 0600; unter Windows wird der Zugriff für alle Benutzer entzogen: dieses Konto, SYSTEM und Administratoren behalten ihn) und bei 10 MiB rotiert, wobei der vorherige Teil als <file>.1 erhalten bleibt. Ein Pfad, der ein Link ist, eine Datei mit weiteren Namen (Hardlinks) oder keine reguläre Datei, wird abgelehnt, und der Start schlägt mit entsprechender Meldung fehl: Entfernen oder benennen Sie sie um, oder nennen Sie eine andere Protokolldatei. Eine Zeile, die nicht geschrieben werden kann (voller Datenträger), wird verworfen und einmalig auf der Standardfehlerausgabe gemeldet. Anfragen werden mit ihrem Pfad protokolliert, wobei jeder Abfragewert und die ID einer GridFS-Datei als *** geschrieben werden.
MM_REQUIRE_ADMIN_2FA Jeder Administrator muss vor allem anderen die Zwei-Faktor-Anmeldung einrichten; sie lässt sich danach in der App nicht mehr deaktivieren. Ohne diese Variable kann ein Administrator dasselbe in der App verlangen.
MM_REQUIRE_2FA Jeder Benutzer, unabhängig von seiner Rolle, muss vor allem anderen die Zwei-Faktor-Anmeldung einrichten; sie lässt sich danach in der App nicht mehr deaktivieren. Ohne diese Variable kann ein Administrator dasselbe in der App verlangen.
MM_METRICS_TOKEN Aktiviert Prometheus-Metriken unter <base path>metrics, die mit diesem Token als Bearer-Token gelesen werden (mindestens 32 Zeichen). Die Zahlen nennen keinen Benutzer, keine Verbindung, keine Datenbank und keine Collection.
MM_GRIDFS_MAX_MB Die größte Datei, die in GridFS hochgeladen wird, in MB (Standard 512, 1–10240).
MM_MODEL_MAX_DOCS Die Dokumente, die ein Datenmodell (der Abschnitt Modell einer Datenbank) insgesamt als Stichprobe nehmen darf (Standard 20000, 100–1000000): Bei vielen Collections wird die Stichprobe jeder einzelnen verkleinert, und der Abschnitt weist darauf hin.
MM_ALLOW_KERBEROS Teammodus: erlaubt Kerberos-Verbindungen (GSSAPI) (Standard aus). Sie melden sich mit dem Kerberos-Ticket des Kontos an, unter dem der Server läuft – jeder Benutzer einer solchen Verbindung meldet sich als dieses Konto an. Siehe Sicherheit.
MM_ALLOW_WORKLOAD_IDENTITY Teammodus: erlaubt OIDC-Verbindungen, die Workload-Identität des Rechners (Azure, GCP, Kubernetes) zu verwenden, wenn dies an der Verbindung gewählt wird (Standard aus).
MM_OIDC_DEVICE_FLOW OIDC-Anmeldung mit einem Code (Device Flow) für Identitätsanbieter, die den Browser nicht zu diesem Server zurückleiten können. Wer den Code genehmigt, meldet sich an; daher ist die Funktion im Teammodus aus, sofern sie hier nicht aktiviert wird, und im Lokalen Modus ein.
MM_OIDC_PRIVATE_NETWORKS Private Netzwerke (CIDRs, durch Kommas getrennt), in denen OIDC-Identitätsanbieter stehen dürfen; dort ist ausschließlich reines http erlaubt. Ohne diese Angabe müssen es öffentliche https-Adressen sein.
MM_CRYPT_SHARED_LIB_PATH Der absolute Pfad der crypt_shared-Bibliothek (mongo_crypt_v1) für die clientseitige Verschlüsselung. Im Teammodus ist dies die einzige, die geladen wird.
MM_KMS_PRIVATE_NETWORKS Private Netzwerke (CIDRs, durch Kommas getrennt), in denen Schlüsselverwaltungsdienste (ein KMIP-Server vor Ort) stehen dürfen. Ohne diese Angabe müssen es öffentliche Adressen sein.
MM_KMS_ALLOWED_HOSTS Hosts von Schlüsselverwaltungsdiensten (durch Kommas getrennt, host oder host:port, Port standardmäßig 443), die eine Verbindung zusätzlich zu den eigenen der Anbieter (AWS KMS, Azure Key Vault und Managed HSM mit Microsofts Anmeldung, Google Cloud KMS) und den in ihren Einstellungen genannten Endpunkten erreichen darf: ein VPC-Endpunkt, ein KMIP-Server. Jeder andere Host oder Port wird abgelehnt – der Hauptschlüssel eines Datenschlüssels kann das KMS-Token nicht anderswohin senden.

Kerberos und clientseitige Verschlüsselung (npm-Paket)

Kerberos (GSSAPI) und die clientseitige Field-Level- bzw. Queryable-Encryption benötigen native Pakete, die Mongo Manager nicht selbst installiert: Die Installation führt kein Installationsskript eines Pakets aus. Um sie zu verwenden, installieren Sie die Pakete neben dem npm-Paket und starten dann neu: 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager lädt sie nur aus dem globalen Ordner node_modules, der mongo-manager selbst enthält (anhand seines realen Pfads geprüft, nie ein Ordner darüber), und nur dann, wenn eine Verbindung erstmals eines benötigt; das Verbindungsformular nennt, welches fehlt und wie es installiert wird. Die eigenständigen Binärdateien, das Docker-Image (das MM_DISTRIBUTION=docker setzt) und die Kopie, aus der ein Windows-Dienst läuft, enthalten kein natives Modul: Dort melden diese beiden Funktionen, dass sie in diesem Paket nicht verfügbar sind – verwenden Sie stattdessen das npm-Paket und führen Sie es im Vordergrund aus. Die automatische Verschlüsselung der Queryable Encryption benötigt außerdem die crypt_shared-Bibliothek (MM_CRYPT_SHARED_LIB_PATH) oder mongocryptd sowie MongoDB Enterprise oder Atlas; MongoDB Community entschlüsselt nur. MONGODB-OIDC benötigt kein Paket: Der Identitätsanbieter muss die Adresse <address><base path>oidc/callback dieses Servers als Weiterleitungsadresse haben (oder eine andere, die die Verbindung nennt), und wo das nicht möglich ist, können sich Personen mit einem Code anmelden.

Als App installieren

Wählen Sie in Chrome oder Edge in der Adressleiste Mongo Manager installieren, um ihn in einem eigenen Fenster über den Desktop oder das Startmenü zu öffnen.

Backup-Ziele

  • MM_BACKUP_FOLDER_ROOTS: die Ordner, die Serverordner-Ziele verwenden dürfen, als absolute Pfade, getrennt durch das Pfadtrennzeichen des Systems (: unter Linux und macOS, ; unter Windows), höchstens 16. Standard: keine, sodass kein Ordnerziel angelegt werden kann. Ein relativer Pfad stoppt den Server beim Start. Geben Sie dem Dienstkonto Schreibzugriff auf jeden Stamm, und halten Sie die Stämme außerhalb des Datenverzeichnisses: Ein Ordnerziel darin wird abgelehnt. Jeder Start protokolliert einen Stamm, in den der Server nicht schreiben kann. Für den Linux-Dienst gilt:
    • Seine Sandbox erlaubt ihm nur das Schreiben in sein Datenverzeichnis und in die Stämme, die seine Konfigurations- und Env-Datei bei der Installation nennen: Führen Sie nach einer Änderung erneut sudo mongo-manager service install aus (Daten, Konfiguration und Schlüssel bleiben erhalten), und starten Sie den Dienst neu, nachdem Sie einen fehlenden Stamm angelegt haben. Stämme, die anderswo gesetzt werden, etwa als Environment= in einem Drop-in, sieht die Installation nicht: Ihre Ordner bleiben für den Dienst schreibgeschützt.
    • Die Installation lässt einen Stamm unter /home, /root, /run/user, /tmp, /var/tmp oder /dev aus, den der Dienst nicht erreichen kann, sowie einen, der die Sandbox aufheben würde: einen, der ein Systemverzeichnis enthält (/, /var, /var/lib und dergleichen) oder innerhalb von /etc, /usr, /run oder eines anderen Systemverzeichnisses liegt (unter /var sind nur Ordner innerhalb von /var/backups offen). Geeignet ist ein Ordner innerhalb von /srv, /opt oder ein Mount unter /mnt oder /media, nicht diese Ordner selbst; auf einem Wechseldatenträger oder einem Netzwerkdateisystem kontrolliert, wer den Datenträger oder die Freigabe kontrolliert, die Ordner darauf, machen Sie also den Einhängepunkt selbst zum Stamm (der FUSE-Mount eines Benutzers sagt über seine Eigentümer und Links, was er will). Ein Stamm innerhalb eines anderen Stamms liegt durch diesen in der Sandbox. Ist /srv, /opt oder /mnt selbst ein Link nach /var, wie auf ostree-Systemen (Fedora Silverblue, CoreOS), nennt die Installation, wohin ein Stamm führt, und er wird dort abgelehnt: Wählen Sie einen Ordner innerhalb von /var/backups.
    • Ein Link wird danach beurteilt, wohin er führt, und die Unit nennt diesen Ort; ein Link, der ins Leere führt, wird ausgelassen: Legen Sie bei einem Link auf einen noch nicht angelegten Ordner diesen Ordner an und führen Sie dann erneut service install aus; wählen Sie bei einem Link, der im Kreis oder über eine Datei führt, einen anderen Ordner oder entfernen Sie den Link. Halten Sie jeden Ordner oberhalb eines Stamms sowie die Ordner, in denen die Links auf seinem Weg liegen (auch ein Link im Ziel eines Links), im Besitz von root und für Gruppe und andere gesperrt, sodass niemand dort einen Link an die Stelle eines Ordners setzen kann; lassen Sie in einem Ordner, in den andere schreiben dürfen (mit Sticky-Bit oder ohne), root den darin liegenden Ordner besitzen, und legen Sie den Stamm in diesen.
    • Ein Stamm unterhalb eines Ordners, den der Benutzer des Dienstes ändern könnte, an beliebiger Stelle bis hinauf zu / und entlang der Links auf seinem Pfad, wird ausgelassen: ein Ordner, den dieser Benutzer besitzt oder in den er über eine seiner Gruppen, eine ACL oder als beliebiger Benutzer schreiben darf, wo ein Prozess unter diesem Benutzer einen Link auf /etc an die Stelle eines Ordners setzen könnte. Das schließt einen Link in einem anderen Stamm ein, in den der Dienst schreibt. Installation und doctor, mit sudo ausgeführt, fragen zusätzlich das System: Mit setpriv führen sie test -w als dieser Benutzer aus, sodass der Kernel dessen Gruppen (die, die die Unit dem Dienst mit Group= oder SupplementaryGroups= gibt, auch aus einem Drop-in) und ACLs anwendet. Ohne setpriv oder ohne root werden nur die Modi der Ordner und die Gruppen des Benutzers gelesen, und beide weisen darauf hin. Was die Modi erlauben, zählt auch dort, wo eine ACL es entzieht, sodass ein solcher Ordner seine Stämme ebenfalls ausschließt.
    • Die Installation fragt systemd, wer den Dienst ausführt, wobei jedes Drop-in gelesen wird. Ein Drop-in, das ihn unter einem anderen Benutzer als --user (oder als root) ausführt, mit DynamicUser=yes und ohne Konto dieses Namens, mit einer Group=, die nicht die eigene des Benutzers ist, oder mit einer Gruppe, die das System nicht kennt (mit der systemd den Start verweigert), stoppt die Installation, bevor Datenverzeichnis und Konfiguration geändert werden; sie nennt den Grund und lässt den Dienst gestoppt und deaktiviert. Eine Gruppe, deren Abfrage fehlschlägt, oder ein systemd, das nicht gefragt werden kann, lässt jeden Stamm aus.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json prüft den installierten Dienst (das einfache mongo-manager doctor prüft Ihr eigenes Datenverzeichnis und weist darauf hin, dass der Dienst nicht das Geprüfte ist). Es prüft jeden Stamm: dass er existiert, ein Verzeichnis ist, in das der Server schreiben kann, innerhalb der Sandbox liegt und nicht innerhalb des Datenverzeichnisses; es nennt außerdem einen Ordner, in den die Sandbox den Dienst schreiben lässt und den kein Stamm mehr nennt oder der über einen Link, den jemand anderes als root ändern darf, zu einem Stamm oder zum Datenverzeichnis führt, und warnt vor einem Dienst, der als root läuft, vor einer Gruppe, die niemand hat oder deren Abfrage fehlschlägt, und vor DynamicUser=yes ohne Konto dieses Namens. Es prüft die Stämme, die die Konfigurations- und Env-Datei des Dienstes nennen, weshalb es sudo braucht: Nur root darf die Env-Datei lesen, in der auch der geheime Schlüssel des Dienstes steht. Es prüft den Schreibzugriff als der Benutzer, unter dem es läuft; als root ausgeführt, liest es stattdessen Eigentümer und Modus des Stamms für den Benutzer, dem das Datenverzeichnis gehört, und übernimmt die Auskunft des Systems, wo dieser Benutzer hineinschreiben darf. Die Ordner oberhalb der Stämme beurteilt es für den Benutzer, unter dem die Unit den Dienst ausführt (sein User=).
  • MM_BACKUP_PRIVATE_NETWORKS: private Bereiche, die Ziele erreichen dürfen, als durch Kommas getrennte Liste von höchstens 64 CIDRs (zum Beispiel 10.0.5.0/24); darin ist reines HTTP erlaubt. Standard: keine. Loopback-, 10/8-, 172.16/12-, 192.168/16-, CGNAT- (100.64.0.0/10) und Unique-Local-Bereiche (fc00::/7) werden akzeptiert. Ein öffentlicher Bereich stoppt den Server beim Start, ebenso ein Bereich innerhalb eines Link-Local- oder Cloud-Metadaten-Bereichs (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200) in jeder Form, einschließlich IPv4-gemappt und NAT64; die Meldung nennt den Bereich. Diese Adressen sind nie erreichbar, auch nicht innerhalb eines aufgeführten Bereichs.
  • MM_BACKUP_PROXY: ein HTTP(S)-Proxy, über den Ziele erreicht werden, etwa http://proxy.corp:3128 oder https://user:password@proxy.corp; kein Pfad und keine Abfrage. Standard: keiner (es wird nie eine Proxy-Umgebungsvariable gelesen). Mongo Manager löst die Adresse jedes Ziels weiterhin selbst auf, prüft sie und bittet den Proxy, zu dieser Adresse zu verbinden, sodass die obigen Adressregeln auch über den Proxy gelten; TLS läuft durchgehend bis zum Ziel, dessen Zertifikat wie ohne Proxy geprüft wird. Ziele innerhalb von MM_BACKUP_PRIVATE_NETWORKS werden direkt erreicht. Ein Proxy an einer Link-Local- oder Metadatenadresse stoppt den Server beim Start. Halten Sie das Passwort des Proxys aus gemeinsam genutzten Shell-Verläufen heraus: Es ist Teil der Adresse. Nur Backup-Ziele verwenden ihn: Warnungskanäle (E-Mail und Webhooks), KI-Anbieter und Plugins laufen nie darüber. Was Sie vor der Wahl eines Proxys wissen sollten: Ein http://-Proxy erhält Benutzername und Passwort im Klartext (Basic), bevorzugen Sie daher https:// oder einen Proxy in einem vertrauenswürdigen Netzwerk; ein Proxy, der CONNECT nur zu aufgelisteten Hostnamen erlaubt, lehnt diese Verbindungen ab, da er nach einer IP-Adresse gefragt wird; das Zertifikat eines https://-Proxys muss von einer Zertifizierungsstelle signiert sein, der Node.js vertraut (seine eingebaute Liste oder eine mit NODE_EXTRA_CA_CERTS hinzugefügte): Eine eigene CA kann nicht angegeben werden.
  • MM_BACKUP_DEST_PART_MB: die Größe der Upload-Teile, 16 bis 512 MiB (Standard 64).
  • MM_BACKUP_DRILL_MAX_MB: das Meiste, was ein Wiederherstellungstest schreibt, in MiB. Standard: keines – ein Test bleibt unter der Hälfte des freien Speicherplatzes, den MongoDB meldet (der des vollsten Shards, über einen mongos). Wo MongoDB ihn nicht meldet (Atlas Shared Tiers), laufen Tests nur mit dieser Einstellung.
  • MM_BACKUP_DEST_TRANSFERS: gleichzeitig laufende Sendungen und Downloads je Ziel, 1 bis 8 (Standard 2). Weitere warten, in der Auftragsliste als „Wartet auf“ dieses Ziel angezeigt.

Geplante Backups

  • MM_BACKUP_SCHEDULES: der Scheduler, standardmäßig ein. 0 schaltet ihn aus: Zeitpläne behalten ihre Einstellungen, nichts läuft, und der Tab Geplante Backups weist darauf hin, dass die Planung aus ist. Läufe, die ein gestoppter Server unfertig hinterlassen hat, werden beim Start abgeschlossen.
  • MM_BACKUP_SCHEDULE_CONCURRENCY: gleichzeitig arbeitende geplante Läufe, 1 bis 8 (Standard 2). Weitere fällige Läufe warten bis zu sechs Stunden.

Änderungen beobachten

  • MM_WATCH: Change-Stream-Feeds, standardmäßig ein. 0 schaltet sie aus: Die Abschnitte Beobachten weisen darauf hin, dass die Beobachtung aus ist, und in MongoDB wird nichts geöffnet.
  • MM_WATCH_MAX_FEEDS: gleichzeitig laufende Live-Feeds auf diesem Server, 1 bis 500 (Standard 50). Jeder Benutzer darf 5 haben und jedes Browserfenster 3. Jeder Feed hält einen Change-Stream-Cursor in MongoDB.
  • Das Beobachten erfordert ein Replica Set, einen Sharded Cluster oder ein Deployment mit Lastverteilung, und der Datenbankbenutzer der Verbindung benötigt changeStream und find auf das Beobachtete. Siehe Änderungen beobachten.

Live-Synchronisierung

  • MM_LIVE_SYNC: Live-Synchronisierungen zwischen Verbindungen, standardmäßig ein. 0 schaltet sie aus: Laufende Synchronisationen warten mit Angabe des Grundes, und es wird nichts gelesen oder geschrieben; neue werden abgelehnt. Nach dem erneuten Einschalten machen sie dort weiter, wo sie waren.
  • MM_LIVE_SYNC_MAX: Live-Synchronisierungen auf diesem Server, die nicht beendet sind, 1 bis 100 (Standard 10). Jeder Benutzer darf 3 haben. Jede laufende Synchronisation hält einen Change Stream auf ihrer Quelle und beide Verbindungen offen.
  • Die Quelle muss ein Replica Set, ein Sharded Cluster oder ein Deployment mit Lastverteilung sein (MongoDB 6.0 oder neuer); eine Kopie, die das Oplog der Quelle überdauern könnte, verlangt eine Bestätigung. Siehe Live-Synchronisierung.

Warnungen

  • MM_ALERTS (Konfigurationsdatei: alerts.enabled): Warnungen, standardmäßig ein. 0 schaltet sie aus: Nichts wird ausgewertet oder gesendet, und die Seite Warnungen weist darauf hin, dass Warnungen aus sind.
  • MM_ALERTS_PRIVATE_NETWORKS (Konfigurationsdatei: alerts.privateNetworks, eine Liste): Netzwerke, die die Mailserver und Webhooks der Warnungen zusätzlich zu öffentlichen Adressen erreichen dürfen, als durch Kommas getrennte Liste von höchstens 64 CIDRs (zum Beispiel 10.0.5.0/24). Standard: keine. Reines http zu einem Webhook ist nur innerhalb dieser Netzwerke erlaubt. Es werden dieselben Bereiche akzeptiert und abgelehnt wie bei MM_BACKUP_PRIVATE_NETWORKS: Link-Local- und Cloud-Metadatenadressen sind nie erreichbar.
  • In einer Konfigurationsdatei: "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. Siehe Serververwaltung.

Die erweiterte Shell

  • Deaktivieren Sie sie vollständig mit --no-shell (oder MM_SHELL_ENABLED=0).
  • Limits: MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. Eine Shell, die ihre Seite hält, bleibt offen, egal wie lange sie nicht benutzt wird, wie in Compass; eine, die keine Seite hält, schließt zwei Minuten, nachdem ihre Seite weg ist. Das Leerlauflimit ist aus (0), sofern Sie es nicht setzen (10000 bis 86400000 ms); eine Shell lebt höchstens 12 Stunden, sofern Sie keine andere Lebensdauer setzen (60000 bis 86400000 ms, oder 0 für keine). Offen gehaltene Shells zählen bis zum Schließen ihrer Seiten auf MM_SHELL_MAX_TOTAL; setzen Sie auf einem Server, den viele Personen teilen, MM_SHELL_IDLE_MS, damit offen gelassene, ungenutzte Shells freigegeben werden. Bei aktivierter Anmeldung endet eine Shell außerdem, wenn die Anmeldesitzung ihres Benutzers endet, sowie wenn sich die Rolle des Benutzers ändert oder das Konto deaktiviert wird.
  • MM_SHELL_RSS_MB: der Arbeitsspeicher, den der Prozess einer Shell belegen darf, 128 bis 16384 MB (Standard 384). Der Server misst ihn selbst über das Betriebssystem (unter Windows mit tasklist, unter macOS mit ps) und startet eine Shell neu, die ihn überschreitet; die Variablen der Shell gehen verloren. Eine Shell, die 15 Sekunden lang nicht antwortet, während kein Befehl läuft, wird ebenfalls neu gestartet. MM_SHELL_OUTPUT_MB: die Ausgabe eines Befehls, 1 bis 64 MB (Standard 5); der Rest wird abgeschnitten. MM_SHELL_COMMANDS_PER_SECOND: Befehle pro Shell und Sekunde, 1 bis 1000 (Standard 20).
  • Auf einem POSIX-Server mit root wechselt der Shell-Worker zu MM_SHELL_UID/MM_SHELL_GID (Standard 65534); führen Sie den Dienst nicht als root aus.

KI-Assistent

  • MM_AI: der KI-Assistent, standardmäßig ein; er wird erst angezeigt, wenn ein Administrator einen Anbieter hinzufügt (Einstellungen → KI-Assistent). 0 blendet ihn überall aus und lehnt Anfragen ab.
  • MM_AI_PRIVATE_NETWORKS: Netzwerke (CIDR, durch Kommas getrennt), in denen ein Anbieter zusätzlich zu öffentlichen Adressen stehen darf, zum Beispiel ein Ollama unter 10.0.0.5; nur dort reines http. Cloud-Metadaten- und Link-Local-Adressen sind nie erreichbar. Im Lokalen Modus ist dieser Rechner immer erlaubt.
  • MM_AI_PER_MINUTE (Standard 10, 1–120) und MM_AI_PER_DAY (Standard 200, 1–10.000): Anfragen pro Person. MM_AI_MAX_CONCURRENT (Standard 8, 1–64): gleichzeitige Anfragen auf dem Server; jede Person darf 2 haben. MM_AI_AGENT_PER_MINUTE (Standard 30, 1–120): weitere Anfragen eines Agents an den Anbieter innerhalb einer Nachricht, pro Person und Minute (sie zählen auch für den Tag).
  • MM_AI_CHAT_DAYS (Standard 30, 0–365): wie lange ein Chat nach seiner letzten Nachricht aufbewahrt wird. 0 hält Chats nur im Arbeitsspeicher (12 Stunden) und entfernt beim Start des Servers Chats, die unter einer früheren Einstellung gespeichert wurden.

Plugins

  • MM_PLUGINS: Plugins, standardmäßig ein. Jedes braucht nach seiner Sicherheitsprüfung weiterhin die Genehmigung eines Administrators. 0 findet, installiert und startet keine (siehe Plugins).
  • MM_PLUGINS_GITHUB: Installation eines Plugins aus dem Release eines öffentlichen GitHub-Repositorys, standardmäßig aus (Plugins werden per Upload oder aus einem Ordner installiert); 1 erlaubt sie. Der Server erreicht dann api.github.com, github.com und die Release-Asset-Hosts von GitHub über https, wobei er nichts von sich sendet. Bleibt sie aus, erreicht ein Server GitHub nie. Der Server verbindet sich direkt mit GitHub: HTTP-Proxy-Einstellungen werden nicht verwendet, sodass ein Server, der nur über einen Proxy nach außen kommt, Plugins per Upload installiert. Ein Systemdienst liest sie aus seiner config.json als "pluginsGithub": true (Linux /etc/mongo-manager/config.json, Windows %ProgramData%\Mongo Manager\config.json, macOS /Library/Application Support/Mongo Manager/config.json); starten Sie den Dienst danach neu.
