Plugins entwickeln

Ein Plugin ergänzt Mongo Manager um eine Ansicht, eine Aktion oder eine Seite: eine Karte der Orte einer Collection, ein Diagramm, eine Duplikatsuche, einen Übersetzer aus SQL. Dieser Leitfaden richtet sich an alle, die ein Plugin entwickeln. Er behandelt die Dateien, aus denen ein Plugin besteht, alles, was es von der App anfordern darf, die Regeln, welche die App durchsetzt, sowie das Paketieren, Testen und Veröffentlichen. Administratoren installieren und genehmigen Plugins auf der Seite Plugins; das Genehmigungsmodell steht unter Sicherheit. Diese Seite listet alle Plugins auf und schränkt die Liste auf aktivierte Plugins ein, auf solche, die einen Administrator brauchen (Genehmigung ausstehend, geändert oder defekt), oder auf deaktivierte, auf eine Quelle sowie auf Plugins, die eine Suche nach Name, Beschreibung, ID, Version, den angeforderten Berechtigungen oder dem, was sie hinzufügen, findet.

Was ein Plugin ist

Ein Plugin ist ein Ordner mit statischen Dateien: einer HTML-Seite, ihren Skripten, Stilen, Bildern und Schriften sowie einem Manifest namens mongo-manager-plugin.json, das angibt, was das Plugin hinzufügt und was es tun darf. Die App zeigt die Seite in einem Frame in einer Sandbox, und die Seite spricht mit der App ausschließlich über Nachrichten: Sie fordert Dokumente an, und die App antwortet als angemeldeter Benutzer, mit dessen Rechten und der Maskierung der App.

  • Kein Servercode. Auf dem Server läuft nichts von einem Plugin. Der Server speichert seine Dateien, prüft sie und liefert sie an den Frame aus.
  • Kein Netzwerk. Die Seite kann von keiner Adresse etwas abrufen, nicht einmal vom Server, von dem sie stammt. Sie hat keine Cookies, keinen Speicher und keinen Zugriff auf die Seite der App. Zwei Auswege bleiben dem Browser überlassen: WebRTC wird nur von Browsern blockiert, welche die Direktive webrtc der Richtlinie durchsetzen – Chromium-basierte Browser (Chrome, Edge) ignorieren sie ab Version 149, und auch bei Firefox sollten Sie sich nicht darauf verlassen –, sodass ein Plugin dort das Gelesene weiterhin über WebRTC nach außen senden kann; und ein Prefetch-Hinweis (dns-prefetch, preconnect) kann einen Namen auflösen lassen. Der Frame bittet den Browser, kein Prefetching durchzuführen, und der Scan stuft beides als hohes Risiko ein – er liest jedoch den Text der Dateien nach bekannten Mustern: Code, der darauf ausgelegt ist, ihm zu entgehen, wird nicht gefunden. Genehmigen Sie nur Plugins, denen Sie vertrauen.
  • Nichts ohne Genehmigung. Ein Plugin läuft erst, nachdem ein Administrator seine exakten Dateien und die angeforderten Berechtigungen genehmigt hat. Jede Änderung an seinen Dateien erfordert eine neue Genehmigung.
  • Änderungen laufen über den Benutzer. Ein Plugin, das Dokumente ändern darf, stellt eine Anfrage; die App zeigt die Änderung in einem eigenen Dialog, und der Benutzer entscheidet. Eine Abfrage oder Pipeline, die ein Plugin vorbereitet, wird in die eigenen Editoren des Benutzers eingetragen, wo nichts läuft, bis der Benutzer es ausführt.

Mongo Manager liefert mehrere eigene Plugins mit (Map, Charts, Schema health, Duplicate finder, Value search, References, Document diff, SQL to MongoDB, Time hints, Binary preview, Data dictionary, Local time, Log analyzer, Test data, Reshape, Anonymiser, Search playground, Shard key analyzer, Storage report, Validation check, Legacy UUIDs, Date filters, Index script, Expiry (TTL), Personal data finder, Document size). Sie laufen in derselben Sandbox, sprechen über dieselbe Bridge und werden auf dieselbe Weise gescannt wie Ihre; da es sich um den eigenen Code der App handelt, wird beim Genehmigen nie nach der ID gefragt (siehe Versionen und Genehmigung). Plugins lassen sich für einen ganzen Server mit MM_PLUGINS=0 abschalten (siehe Bereitstellung).

Schnellstart

Beginnen Sie mit der Starter-Vorlage: Wählen Sie auf der Seite Plugins unter Eigenes Plugin erstellen die Option Starter herunterladen (.zip) (sie liegt auch im Ordner packages/plugins/starter des Mongo-Manager-Quellcodes). Es ist ein vollständiges Plugin in reinem JavaScript, ohne Build-Schritt und ohne Abhängigkeiten: ein Collection-Tab und eine Seitenleistenseite, die die Dokumente einer Collection auflisten.

  1. Entpacken Sie sie oder kopieren Sie den Ordner in ein neues eigenes Repository.
  2. Ändern Sie in mongo-manager-plugin.json die Felder id, name, author und repository. Die ID muss eindeutig sein: Sie benennt den Ordner des Plugins auf jedem Server.
  3. Schreiben Sie Ihre Seite in main.js und style.css.
  4. Probieren Sie es auf Ihrem eigenen Server aus: node scripts/pack.mjs --folder ~/.mongo-manager/plugins, dann Plugins → Erneut scannen, den Scan ansehen und das Plugin genehmigen. Siehe Testen auf dem eigenen Server.
  5. Paketieren Sie es mit node scripts/pack.mjs, das <id>-<version>.tgz schreibt, und hängen Sie diese Datei an ein GitHub-Release an. Siehe Veröffentlichen auf GitHub.

Der Starter enthält außerdem Anweisungsdateien für KI-Coding-Assistenten (CLAUDE.md, AGENTS.md, GEMINI.md und .github/copilot-instructions.md); siehe Entwickeln mit einem KI-Assistenten.

Dateien und Ordnerstruktur

hello-documents/
  mongo-manager-plugin.json   the manifest (required, at the top)
  index.html                  the entry page every contribution opens
  main.js                     the page's script (an ES module)
  style.css                   the page's styles
  README.md                   shown to administrators on the plugin's details page
  README.tr.md, README.zh.md  the same in another language of the app (optional)
  scripts/pack.mjs            packaging (not part of the plugin: left out of the archive)
  CLAUDE.md, AGENTS.md, ...   AI assistant files (left out of the archive)

Die Regeln der App für die Dateien eines Plugins:

  • Höchstens 500 Dateien und insgesamt 25 MB; das Manifest höchstens 64 KB.
  • Jeder Pfad ist relativ und schlicht: Jeder Teil beginnt mit einem Buchstaben, einer Ziffer, _ oder - und enthält nur Buchstaben, Ziffern, ., _ und -, höchstens 100 Zeichen; höchstens 16 Ebenen tief und insgesamt 240 Zeichen. Keine versteckten Dateien oder Ordner (ein Name, der mit . beginnt), keine Leerzeichen, keine Gerätenamen (con, nul, com1 …), kein __proto__, constructor oder prototype.
  • Nur Dateien und Ordner: Links, Junctions und Spezialdateien machen das Plugin unbrauchbar.
  • Keine zwei Pfade, die sich nur in der Groß-/Kleinschreibung unterscheiden.
  • Dateien werden mit einem Typ ausgeliefert, der sich aus der Erweiterung ergibt: html, js, mjs, css, json, map, txt, svg, png, jpg, jpeg, gif, webp, avif, ico, woff, woff2, ttf, otf. Alles andere wird als Bytes ausgeliefert und nie ausgeführt.

Das Manifest

mongo-manager-plugin.json wird streng geprüft: Ein unbekanntes Feld, ein falscher Typ oder ein Wert außerhalb des zulässigen Bereichs macht das Plugin unbrauchbar, und die Seite Plugins nennt das fehlerhafte Feld. Texte, die ein Mensch liest (Namen, Titel, Hinweise), dürfen keine Steuerzeichen und keine Zeichen enthalten, die Text verbergen oder umkehren.

Feld Erforderlich Regeln
id ja Kleinbuchstaben und Ziffern, durch Bindestriche getrennt (geojson-map), höchstens 64 Zeichen. Sie muss dem Ordnernamen des Plugins entsprechen. Die ID eines mit Mongo Manager ausgelieferten Plugins darf nicht verwendet werden, ebenso wenig eine, die wie ein von der App reservierter Name gelesen wird (siehe unten).
name ja Lokalisierter Text, höchstens 60 Zeichen: { "en": "...", "tr": "..." }. Kein unsichtbares Zeichen (Zero-Width, Tag, Variation Selector – die eigenen eines Emojis sind zulässig) und nie ein Name, der wie die eigenen Meldungen der App wirkt: Mongo Manager (oder ein so beginnender Name), MongoDB, System, Session, Security, Admin, Server, Update und Ähnliches, in jeder Sprache der App, verglichen wie gelesen: unabhängig von Groß-/Kleinschreibung, Leerzeichen, Akzenten und ähnlich aussehenden Buchstaben. In jedem Wort sind die Buchstaben entweder alle lateinisch oder keiner (nie Griechisch und Kyrillisch zusammen), und keine Klammer enthält etwas, das wie eine ID gelesen wird ((value-search); (beta) ist zulässig). Die App zeigt die Meldungen und Fragen eines Plugins mit seiner ID neben seinem Namen an.
version ja Semantische Versionierung: major.minor.patch, optional mit einer Vorabversion (1.2.0-beta.1), höchstens 64 Zeichen.
description nein Lokalisierter Text, höchstens 300 Zeichen.
entry ja Die Seite, die jeder Erweiterungspunkt öffnet: ein schlichter Pfad zu einer .html-Datei des Plugins.
permissions nein Beliebige von documents:read, documents:write, collection:read, database:read, jede höchstens einmal. Standard: keine. Siehe Berechtigungen.
contributes nein collectionTabs, documentActions, sidebarPanels und cellRenderers: Listen mit jeweils höchstens 5 Einträgen, IDs innerhalb einer Liste eindeutig. Siehe Erweiterungspunkte.
settings nein Höchstens 10, nach Schlüssel (ein Buchstabe, dann Buchstaben und Ziffern, höchstens 32 Zeichen): { "type": "url" | "text" | "boolean", "title": lokalisierter Text mit höchstens 60 Zeichen }. Administratoren legen die Werte fest; die Seite liest sie im Kontext.
author nein { "name": Text mit höchstens 80 Zeichen, "url": eine https-Adresse (optional) }.
homepage, repository nein Eine https://-Adresse mit Host, höchstens 300 Zeichen, ohne Zugangsdaten, Leerzeichen oder Backslashes.
license nein Ein SPDX-Ausdruck, höchstens 40 Zeichen: MIT, Apache-2.0 OR MIT.
publishedAt nein Ein existierender Tag, YYYY-MM-DD, zwischen 1900 und 2100.
changelog nein Höchstens 50 Einträge { "version", "date": "YYYY-MM-DD", "notes": lokalisierter Text mit höchstens 1000 Zeichen }; jede Version höchstens einmal und keine nach der version des Manifests.

Lokalisierter Text ist ein Objekt mit en (erforderlich) und optional beliebigen weiteren Sprachen der App: tr, zh (Vereinfachtes Chinesisch), ja, es, pt (Brasilianisches Portugiesisch), ko, de, fr und ru; fehlt die Sprache des Lesers, wird Englisch angezeigt. Ein Erweiterungspunkt ist { "id", "title": lokalisierter Text mit höchstens 40 Zeichen, "icon" }: Seine ID ist ein Kleinbuchstabe, gefolgt von Kleinbuchstaben, Ziffern und Bindestrichen, höchstens 32 Zeichen, und sein Symbol eines von map, chart, table, file, image, globe, layers, puzzle, book, wand, shapes, scroll, code, calendar, hourglass, shield, fingerprint, ruler (die eigenen Symbole der App: Ein Plugin bringt keine mit). Ein Cell Renderer ist stattdessen { "id", "match" }, mit optionalem "display": inline (Standard) oder tooltip.

Eine url-Einstellung muss eine https-Adresse ohne Zugangsdaten sein (einfaches http nur für diesen Computer: localhost, 127.0.0.1 oder [::1]); ihr Schema, Host und Port werden zu den Bildern hinzugefügt, die der Frame laden darf (bei Kartenkacheln: Ein führendes {s}. steht für eine beliebige Subdomain, nur vor einem Namen aus zwei oder mehr Teilen, nie vor einer IP-Adresse). Die Adresse eines Bildes kann Daten tragen: Das Plugin kann das Gelesene an diesen Server senden, und die Genehmigung und die Einstellung weisen darauf hin. Eine text-Einstellung enthält höchstens 500 Zeichen. Jeder Benutzer des Plugins kann seine Einstellungen lesen: Fordern Sie nie ein Geheimnis an. Der Server speichert sie mit seinem Schlüssel verschlüsselt, wie jeden anderen gespeicherten Wert.

Erweiterungspunkte

Jeder Erweiterungspunkt öffnet dieselbe Einstiegsseite. Die Seite erfährt aus dem Fragment der Adresse, #<kind>=<id> (zum Beispiel #collectionTab=list), und aus contribution im Kontext, welcher es ist.

Art Wo er erscheint und wie er sich öffnet
collectionTabs Ein Tab jeder Collection nach den eigenen Tabs der App, auch bei Views. Der Frame füllt den Tab. Sein place ist diese Collection mit dem filter, den der Benutzer in Dokumente gesetzt hat. Die Seite wird bei jedem Anzeigen des Tabs neu geladen, es sei denn, sie hat mit ui.keepOpen darum gebeten, geladen zu bleiben: Dann bleibt sie geladen, während ein anderer Bereich des Tabs dieser Collection angezeigt wird (außer Sicht darf sie lesen, aber nicht handeln: not_visible).
documentActions Ein Eintrag im Aktionsmenü eines Dokuments unter Dokumente, nur für ein Plugin angezeigt, das für documents:read genehmigt ist. Er öffnet einen Dialog mit der Seite; place.documentId ist die _id dieses Dokuments. Der Dialog schließt sich, sobald das Plugin eine Abfrage oder eine Pipeline eingetragen hat (ui.useQuery, ui.useQueryIn, ui.useAggregation).
sidebarPanels Ein Eintrag in der Seitenleiste, der eine eigene Seite öffnet, einen Arbeitsbereich-Tab unter /plugin/<id>/<contribution>. Bei einem Klick, während der Tab einer Collection aktiv ist, öffnet sich die Seite für diese Collection (/plugin/<id>/<contribution>/<connection>/<db>/<collection>), und place benennt sie; von überall sonst ist place gleich null. Eine über einen Link geöffnete Seite fragt den Benutzer, bevor sie diese Collection liest, und der Benutzer kann auch ohne eine fortfahren. Die Seite bleibt geladen, während ein anderer Tab angezeigt wird; außer Sicht darf sie weiterhin lesen, aber nicht handeln (not_visible).
cellRenderers Ein kurzer Text zu Werten überall dort, wo Dokumente sie anzeigt (Tabelle, Baum, Karten, Dokumentseite, Details des Change Streams), etwa das Datum, an dem eine ObjectId erzeugt wurde: neben dem Wert ("display": "inline", der Standard) oder in einem Tooltip ("display": "tooltip"), den seine Zelle oder Zeile beim Überfahren oder Fokussieren zeigt, unter dem gesamten Wert und mit dem Namen des Plugins gekennzeichnet. Der Text eines Tooltips ist einfacher Text, sein tone bleibt ungenutzt; ein Screenreader liest ihn zusammen mit dem Wert vor. Ein Plugin liefert einen Text neben einem Wert und einen in seinem Tooltip: Maßgeblich ist sein erster Renderer, der für den jeweiligen Ort antwortet. Die Seite läuft in einem verborgenen Frame, einem pro Plugin, nur für ein Plugin, das für documents:read genehmigt ist; sie zeigt sich nie selbst. match ist eines von geojson, string, number, date, object, objectId, binary (keine UUID). Siehe Cell Renderer.

Cell Renderer

Die App fragt den verborgenen Frame in Stapeln von höchstens 200 mit einer Nachricht cells.render nach den Werten, die sie anzeigt. Mit dem Kit antworten Sie über client.onCells: 

client.onCells((renderer, values, locale, paths, place) =>
  values.map((v) => (typeof v?.$oid === 'string' ? { text: createdAt(v.$oid, locale), tone: 'info' } : null)),
)
  • renderer ist die ID des Erweiterungspunkts, values sind die Werte als kanonisches Extended JSON, locale ist die Sprache der App, paths der Feldpfad jedes Werts (oder null), place die Collection, aus der die Werte stammen (oder null).
  • Ein binary-Wert wird nur mit seinem Anfang gesendet, nie vollständig: { "$binaryHead": { "base64", "subType", "length" } } mit seinen ersten 2.048 Bytes – genug, um Art und Größe eines Bildes zu erkennen.
  • Antworten Sie mit einem Eintrag pro Wert, in derselben Reihenfolge: { "text", "tone" }, null für keinen Text oder { "retry": true }, um später erneut gefragt zu werden. Eine Liste anderer Länge wird ignoriert.
  • Der Text wird als einfacher Text angezeigt – höchstens 80 Zeichen neben dem Wert, 200 in einem Tooltip –, wobei Steuer- und verborgene Zeichen entfernt werden. tone ist eines von neutral, info, success, warning, danger.
  • Eine Antwort muss innerhalb von 3 Sekunden eintreffen; andernfalls bleibt der einfache Wert stehen, und der Wert wird nach 30 Sekunden erneut angefragt. Antworten werden pro Wert, Sprache und Einstellungen des Plugins aufbewahrt: Eine Änderung seiner Einstellungen fragt erneut an, und eine Antwort, die älter als eine Minute ist, wird beim nächsten Anzeigen ihres Werts erneut angefragt, wobei die alte Antwort bis zum Eintreffen der neuen stehen bleibt (und auch bleibt, wenn die erneute Anfrage fehlschlägt). Die Antwort auf einen binary-Wert wird unter seiner Länge, seinem Subtyp und einem Hash seines Anfangs aufbewahrt.
  • Ein Renderer darf lesen, bevor er antwortet (zum Beispiel Verweise auf andere Dokumente): Er übergibt den place, den er in seiner Anfrage erhalten hat, { place, filter, ... }, und darf nur dort lesen. Der place seines Kontexts ist null.

Der Kontext

context.get liefert, wo sich die Seite befindet und wie sie aussehen soll. Rufen Sie es zuerst auf; ist eine Collection geöffnet, kann die Antwort bis zu 3 Sekunden dauern, während die App prüft, ob es sich um eine View handelt. 

{
  "plugin": { "id": "hello-documents", "version": "0.1.0" },
  "contribution": { "kind": "collectionTab", "id": "list" },
  "locale": "en",
  "theme": "dark",
  "accent": "emerald",
  "place": {
    "connectionId": "6650...",
    "connectionName": "Production",
    "db": "shop",
    "coll": "orders",
    "view": false,
    "documentId": null,
    "filter": { "status": "open" }
  },
  "settings": { "tileUrl": "https://tile.example.org/{z}/{x}/{y}.png" }
}
  • kind ist collectionTab, documentAction, sidebarPanel oder cellRenderer.
  • locale ist die Sprache der App: en, tr, zh, ja, es, pt, ko, de, fr, ru.
  • theme ist light oder dark.
  • accent ist die Akzentfarbe des Benutzers: emerald, indigo, violet, ocean oder rose. Behandeln Sie jeden anderen Wert wie emerald.
  • place ist null, wenn die Seite ohne Collection geöffnet wurde (eine Seitenleistenseite, ein Cell Renderer). connectionName kann null sein. view ist true für eine View: Sie kann gelesen, aber nie geschrieben werden und hat keine Indizes. documentId ist das Dokument einer Dokumentaktion als kanonisches Extended JSON, sonst null. filter ist der Filter von Dokumente für einen Collection-Tab, sonst {}. Beide sind Daten: Ein Plugin ohne documents:read erhält null und {}.
  • hidden listet die Feldpfade auf, die Regeln für personenbezogene Daten in der Collection vor dem Benutzer verbergen, als Listen von Schlüsseln ([["contact", "phone"]]; "*" ein Schlüssel, "**" beliebig viele Schlüssel, in beliebiger Tiefe) – nur Namen, für ein Plugin mit documents:read; sonst []; null, wenn die App es nicht rechtzeitig (3 Sekunden) feststellen konnte. Die Werte eines solchen Felds kommen als "***" an: Halten Sie das nie für seinen Typ.
  • settings enthält die Werte, die ein Administrator festgelegt hat; eine nicht festgelegte Einstellung fehlt.

Wenn der Benutzer die Sprache, das Design oder die Akzentfarbe ändert, sendet die App context.changed mit locale, theme und accent (das client.onContext des Kits). Wenden Sie es sofort an: Die Seite darf nie das andere Design oder die andere Sprache zeigen. Ein Plugin, das Dokumente lesen darf, erhält außerdem context.changed, wenn sich der Filter von Dokumente ändert, während seine Seite geladen ist – ein Collection-Tab, der ui.keepOpen aufgerufen hat, erfährt von jedem Filter, den der Benutzer außer Sicht setzt. Fragen Sie context.get erneut nach dem neuen place.

Die Bridge-API

Das Protokoll

Die Seite und die App tauschen einfaches JSON per postMessage aus. Das Kit (packages/plugins/kit/src/client.ts) und die main.js des Starters implementieren es; die Regeln, falls Sie ein eigenes schreiben:

  1. Lesen Sie nur Nachrichten, deren event.source gleich window.parent ist und deren mm gleich 1 ist.
  2. Sobald die Seite geladen ist, begrüßt die App sie: { "mm": 1, "type": "hello", "token": "..." }. Behalten Sie das erste Token. Senden Sie vorher nichts.
  3. Eine Anfrage lautet { "mm": 1, "id": 1, "method": "documents.find", "params": { ... }, "token": "..." } und wird mit dem Ziel '*' an window.parent gesendet (der Origin des Frames ist opak). Die ID ist eine Zahl oder ein String mit höchstens 64 Zeichen; die App ignoriert eine Anfrage ohne das Token.
  4. Die Antwort trägt dieselbe ID: { "mm": 1, "id": 1, "result": ... } oder { "mm": 1, "id": 1, "error": { "code": "...", "message": "..." } }.
  5. Die App sendet { "mm": 1, "type": "context.changed", "locale", "theme", "accent" }, wenn der Benutzer diese ändert (und an ein Plugin mit documents:read den Filter von Dokumente), und fragt einen Cell Renderer mit { "mm": 1, "id": "h1", "method": "cells.render", "params": { ... } }, was mit { "mm": 1, "id": "h1", "token", "result": [...] } beantwortet wird.

Die Seite darf ihre Adresse nicht verlassen. Lädt sie eine andere Seite (ein Link, ein Formular, eine Änderung von location), schließt die App die Bridge und entfernt den Frame, und der Benutzer muss das Plugin erneut öffnen. Halten Sie alles auf einer Seite. 

import { createClient, askMessage, AskError } from './kit/client'

const client = createClient()                       // requests time out after 15 s ("timeout")
client.onContext((locale, theme, accent) => restyle(locale, theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  if (!context.place) return showNoCollection()
  try {
    const { documents, hasMore } = await client.ask('documents.find', { filter: context.place.filter, limit: 100 })
    show(documents, hasMore)
  } catch (e) {
    showError(askMessage(e, context.locale))         // the app's code, in the user's language
  }
})

Methoden

Werte sind in beide Richtungen kanonisches Extended JSON: Eine ObjectId ist { "$oid": "..." }, ein Datum { "$date": { "$numberLong": "..." } }, ein Int { "$numberInt": "3" }. Jeder Lesezugriff läuft als der Benutzer, mit dessen Rechten und der Maskierung der App. Mit „auf der eigenen Collection“ gekennzeichnete Methoden arbeiten auf der Collection in place und scheitern ohne eine mit no_collection.

Methode und Berechtigung Parameter → Ergebnis Regeln
context.get
keine		 keine → der Kontext Siehe Der Kontext.
documents.find
documents:read		 { filter?, projection?, sort?, limit? } → { documents, hasMore } Auf der eigenen Collection. limit 1 bis 1000, Standard 100. Höchstens 10 Sekunden. Ein Dokument, das der Benutzer nicht sehen darf, wird ausgelassen. Keine der letzten Abfragen des Benutzers.
documents.get
documents:read		 { id } → das Dokument oder null Auf der eigenen Collection. id ist der _id-Wert.
documents.aggregate
documents:read		 { pipeline, limit? } → { documents, truncated } Auf der eigenen Collection. Nur lesende Stages: $match, $group, $sort, $limit, $skip, $project, $addFields, $set, $unset, $count, $unwind, $sortByCount, $bucket, $bucketAuto, $facet (kein $facet darin), $replaceRoot, $replaceWith, $sample; höchstens 50 Stages. Mit database:read zusätzlich ein einfaches $lookup aus genau from, localField, foreignField und as, aus einer Collection derselben Datenbank. limit 1 bis 1000, Standard 100. Höchstens 10 Sekunden, nie mit Auslagerung auf den Datenträger, jeweils nur eine Pipeline gleichzeitig (busy: das serialAsk des Kits reiht sie ein).

Limits

  • Eine Nachricht ist in beide Richtungen höchstens 1 MB groß; eine größere Antwort scheitert mit too_large. Fordern Sie weniger Dokumente an oder projizieren Sie weniger Felder.
  • Höchstens 8 Anfragen warten gleichzeitig (too_many).
  • Höchstens 60 Lesezugriffe pro Minute und Frame (documents.find, .get, .aggregate, .findIn, collections.list, database.model) und davon getrennt 120 Lesezugriffe auf Definitionen (indexes.list, validation.get): Ein Datenwörterbuch mit 50 Collections sind ein Modell und 100 Definitionen.
  • Direkt nach einem Klick auf der Seite des Plugins. ui.copy, ui.useQuery, ui.useAggregation, ui.importSql, ui.exportSql, ui.openDocument, ui.download, ui.importDocuments und documents.update werden nur angenommen, solange der Klick oder Tastendruck des Benutzers auf der eigenen Seite des Plugins frisch ist: Der Frame muss den Fokus haben, ein Klick an anderer Stelle der App zählt also nie. Rufen Sie sie direkt im Klick-Handler auf, bevor Sie irgendetwas anderes abwarten; andernfalls scheitern sie mit no_activation. Jeder Versuch bei ui.copy, einer ui.use…-Methode, einer SQL-Seite oder ui.openDocument zählt zum Limit dieser Methode, ob abgelehnt oder nicht: Ein Plugin, das es immer wieder versucht und auf einen Klick wartet, verbraucht seine Minute (too_many); documents.update wird stattdessen durch seine eine Frage gleichzeitig und die zwei Ablehnungen begrenzt. Ein Frame kann den Fokus ohne Klick erhalten; ein ui.copy, ui.download oder ui.importDocuments, das innerhalb von 5 Sekunden nach einem Klick oder Tastendruck an anderer Stelle der App angefordert wird (so lange hält die Aktivierung des Browsers an), wird deshalb nicht auf Wort des Plugins ausgeführt: Die App fragt den Benutzer unter Nennung des Plugins und dessen Anliegens (wie viele Zeichen und wie der Text beginnt, verborgene Zeichen ausgeschrieben; Name und Größe der Datei; wie viele Dokumente für welche Collection) und führt es erst bei einem Klick auf ihren eigenen Button Kopieren, Speichern oder Öffnen aus; die Antwort des Plugins wartet darauf (declined, wenn der Benutzer es verwirft, unanswered, wenn es unbeantwortet bleibt, busy, solange eine wartet). Jede Frage, welche die App für ein Plugin stellt – diese, eine Änderung, eingetragene Stages –, endet nach 150 Sekunden, selbst wenn der Zeiger darauf zeigt; das Kit wartet bei diesen Anfragen 180 Sekunden, sodass eine Seite die Antwort der App hört, nie ihren eigenen Timeout.
  • In Sicht. documents.update, ui.openDocument und die obigen Methoden scheitern mit not_visible aus einem Cell Renderer oder von einer Seite, die geladen bleibt, während ein anderer Tab angezeigt wird.

Berechtigungen

Ein Administrator genehmigt ein Plugin für die Berechtigungen, die es auflistet, so wie die Seite Plugins sie benennt. Fordern Sie so wenige an, wie nötig: Jede einzelne ist für einen Administrator ein Grund, abzulehnen.

Berechtigung Was der Administrator liest Was sie erlaubt
documents:read Dokumente lesen documents.find, .get, .aggregate; Dokumentaktionen und Cell Renderer werden nur mit ihr angeboten.
documents:write Dokumente ändern (jede Änderung wird bestätigt) documents.update, jede Änderung vom Benutzer bestätigt. Sie anzufordern ist immer ein eigener mittlerer Scanbefund.
collection:read Indizes dieser Collection lesen indexes.list.
database:read die anderen Collections derselben Datenbank lesen (Namen und Dokumente) collections.list, documents.findIn, ein einfaches $lookup.

Ein Plugin ohne Berechtigung darf dennoch eine Seite anzeigen, seinen Kontext und seine Einstellungen lesen und die ui.*-Methoden verwenden. Eine Berechtigung geht nie über das eigene Recht des Benutzers hinaus: Ein Benutzer, der eine Collection nicht lesen darf, kann sie auch nicht über ein Plugin lesen.

Die Sandbox

Die Seite wird in einem iframe mit sandbox="allow-scripts" geladen, von einer signierten Adresse, die das Plugin, seine Version, seine genehmigten Dateien und die Sitzung des Benutzers benennt und versiegelt ist (ein Ticket: Die Seite muss innerhalb von 10 Minuten geladen werden, ihre übrigen Dateien, solange die Sitzung dauert, höchstens 12 Stunden – eine an Ort und Stelle erneuerte Sitzung, durch eine Anmeldung in einem anderen Tab oder eine Passwortänderung, wird mitgeführt; nach dem Abmelden liefert die Adresse nichts mehr aus, und der Browser behält keine ihrer Dateien). Jede ausgelieferte Datei wird gegen ihren genehmigten SHA-256 geprüft. Ihre Richtlinie (Content-Security-Policy), mit X-DNS-Prefetch-Control: off: 

default-src 'none'; script-src <its files>; style-src <its files>;
img-src <its files> data: blob: <the origins of its url settings>; font-src <its files>;
connect-src 'none'; webrtc 'block'; frame-ancestors 'self'; base-uri 'none'; form-action 'none';
sandbox allow-scripts

Was das für Ihren Code bedeutet:

  • Überhaupt kein Netzwerk. Keine Anfrage an irgendeine Adresse, auch nicht an die eigenen Dateien des Plugins: Legen Sie Daten in ein Skriptmodul (data.js), statt eine .json-Datei zu laden. Verwenden Sie auch kein WebRTC und keine Prefetch-Hinweise: Nicht jeder Browser blockiert sie, und der Scan stuft sie als hohes Risiko ein.
  • Kein Inline-Code und kein Inline-Stil. Skripte und Stile stammen nur aus den Dateien des Plugins. Kein Inline-<script>, kein <style>-Element, kein style-Attribut, kein Inline-Event-Handler, kein eval. Das Setzen einer Eigenschaft im Skript (el.style.width = '40px') funktioniert.
  • Ein opaker Origin. Keine Cookies, kein localStorage, keine IndexedDB: Sie schlagen fehl. Halten Sie den Zustand im Arbeitsspeicher; Einstellungen, die ein Administrator wählt, kommen aus den settings des Manifests.
  • Keine Popups, Dialoge, Formulare oder Downloads. window.open, alert, confirm und das Absenden von Formularen bewirken nichts. Kopieren Sie mit ui.copy; übergeben Sie dem Benutzer Dateien über den eigenen Import und Export der App.
  • Kein Zugriff auf die App. Die Seite kann die Seite der App, ihre Sitzung und ihren Speicher nicht lesen. Sie tauscht nur Nachrichten mit ihr aus.
  • Schriften und Bilder sind eigene Dateien (oder data:- und blob:-Bilder).

Der Sicherheitsscan

Die Dateien jedes Plugins werden gescannt, wenn sie gefunden oder installiert werden, bevor ein Administrator sie genehmigt. Der Scan liest Skript- (.js, .mjs, .cjs), Markup- (.html, .htm, .svg) und Stildateien (.css) Zeile für Zeile, Kommentare eingeschlossen, und listet jeden Befund mit Schweregrad, Regel, Datei, Zeile und einem Auszug auf. Markup-Dateien werden auch als Ganzes gelesen, sodass auch ein über mehrere Zeilen verteiltes <script>-Tag oder ein Inline-Handler gefunden wird. In das Plugin eingebundene Bibliotheken werden wie Ihr eigener Code gescannt. Der Scan ist eine Heuristik: Er sucht im Text nach bekannten Mustern, sodass Code, der darauf ausgelegt ist, sich ihm zu entziehen (etwa ein aus Teilen zusammengesetzter Name), nicht gefunden wird – ein sauberer Scan ist kein Beweis. Ein Plugin mit einem Befund mit Schweregrad hoch kann erst genehmigt werden, nachdem der Administrator seine ID eingetippt hat, um das Risiko zu akzeptieren; der Server erzwingt das, und das Audit-Protokoll hält die Anzahl der Befunde des Scans fest sowie, ob ein Risiko akzeptiert wurde. Vermeiden Sie jeden hohen Befund, und beschränken Sie mittlere auf solche, die Sie erklären können.

So bestehen Sie ihn:

  • Schreiben Sie Text mit textContent, append('text') oder dem Helfer h() des Kits; bauen Sie Elemente mit document.createElement. Zum Leeren eines Elements verwenden Sie replaceChildren(). Nichts davon wird je gemeldet; das Zuweisen oder Anhängen von Markup (innerHTML = oder innerHTML +=) wird immer gemeldet.
  • Binden Sie Handler mit addEventListener an, nie im Markup.
  • Übergeben Sie setTimeout und setInterval Funktionen. Erreichen Sie die App nur über window.parent.postMessage.
  • Speichern Sie jede Datei als UTF-8, ohne NUL-Bytes (nie als UTF-16).
  • Liefern Sie keinen Code aus, der nach außen greift, auch nicht ungenutzt: Prüfen Sie, was eine Bibliothek mitbringt. Bevorzugen Sie einen Build, der nicht minifiziert ist, oder erklären Sie den Befund minified in Ihrer README, und halten Sie große Datenmengen aus Base64-Strings heraus.
  • Bedenken Sie, dass auch Kommentare gescannt werden: Ein Kommentar, der eval( oder innerHTML = nennt, ist ein Befund.
  • Erklären Sie in Ihrer README, warum jeder verbleibende Befund unbedenklich ist: welche Bibliothek, welche Zeile, warum er nie ausgeführt wird oder warum die Sandbox ihn stoppt.

Gescannt werden nur Skript-, Markup- und Stildateien; das Manifest wird auf documents:write gelesen (immer ein mittlerer Befund: Fordern Sie es nur an, wenn das Plugin Dokumente ändert). Pro Regel und Datei werden höchstens 10 Befunde und insgesamt höchstens 200 Befunde aufgelistet (die schwersten zuerst); die Zählungen erfassen stets jeden Befund. Jedes Muster läuft in linearer Zeit, sodass der Scan bei jeder Datei schnell fertig wird. Schlägt der Scan selbst fehl, wird das Plugin nicht als defekt markiert: Es hat keinen Scan und kann (sofern es nicht mit Mongo Manager ausgeliefert wird) nur mit eingetippter ID genehmigt werden, wie bei einem hohen Befund. Der Scan eines mit Mongo Manager ausgelieferten Plugins wird ebenfalls angezeigt, aber beim Genehmigen wird nie nach seiner ID gefragt.

Oberfläche und Design

Ein Plugin sollte wie ein Teil der App aussehen: ihre Farben, ihre Schrift, ihre Abstände, im Design und in der Akzentfarbe des Benutzers. Die eigenen Plugins von Mongo Manager verwenden das Plugin-Kit in packages/plugins/kit:

  • kit/src/ui.css: die Design-Tokens der App (--ds-surface, --ds-fg, --ds-accent …) für hell und dunkel sowie jede Akzentfarbe, und Komponenten (mm-btn, mm-table, mm-empty, mm-callout …). Ihre Schriften sind Dateien der @fontsource-Pakete: Bündeln Sie sie mit Ihrem Plugin, oder entfernen Sie die @font-face-Regeln, um die Systemschrift zu verwenden.
  • kit/src/ui.ts: applyLook(theme, accent) setzt html.dark und html[data-accent]; h(tag, props, ...children) baut Elemente, bei denen Text immer Text ist; und icon, button, segmented, switchControl, chip, badge, pageHeader, emptyState, skeleton, callout, table, valueView, describeValue, formatNumber, statusLine, setBusy, serialAsk.
  • kit/src/client.ts: createClient, AskError, askMessage.

Das Kit ist TypeScript und zum Bündeln gedacht: Kopieren Sie kit/src in Ihr Projekt und bauen Sie mit Vite (oder einem anderen Bundler) zu relativen Pfaden ohne Inline-Skript, wie die vite.config.ts der Plugins von Mongo Manager: base: './', modulePreload: { polyfill: false }, assetsInlineLimit: 0. Paketieren Sie die Build-Ausgabe, nicht Ihre Quellen. Der Starter enthält stattdessen eine kurze Kopie des Clients und der Farben in reinem JavaScript und CSS. 

import './kit/ui.css'
import { createClient } from './kit/client'
import { applyLook, h, pageHeader, emptyState, button } from './kit/ui'

const client = createClient()
client.onContext((locale, theme, accent) => applyLook(theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  applyLook(context.theme, context.accent)
  document.body.append(
    h('div', { class: 'mm-page' },
      pageHeader({ icon: 'table', title: 'Hello', description: context.place?.coll ?? '' }),
      emptyState({ icon: 'search', title: 'Nothing yet', action: button({ label: 'Load', variant: 'primary' }) }),
    ),
  )
})

Gestalten Sie für den Ort, an dem die Seite erscheint: Ein Collection-Tab ist breit, eine Dokumentaktion ist ein Dialog, eine Seitenleistenseite füllt den Arbeitsbereich. Zeigen Sie einen leeren Zustand, wenn es nichts anzuzeigen gibt und place gleich null ist, einen Skeleton während des Lesens und die Worte der App für eine Ablehnung. Verwenden Sie Buttons und echte Bedienelemente, damit die Seite mit der Tastatur funktioniert.

Sprachen

Die App spricht Englisch, Türkisch, Vereinfachtes Chinesisch, Japanisch, Spanisch, Brasilianisches Portugiesisch, Koreanisch, Deutsch, Französisch und Russisch: context.locale ist eines von en, tr, zh, ja, es, pt, ko, de, fr und ru. Ein Plugin sollte so viele davon sprechen, wie es kann, und immer Englisch:

  • Geben Sie im Manifest in jedem lokalisierten Text jede Sprache an, die Sie neben en haben.
  • Halten Sie auf der Seite Ihre Texte in einer Tabelle nach Sprache, wählen Sie nach context.locale (Englisch für eine Sprache, die Sie nicht haben), setzen Sie document.documentElement.lang auf die Sprache, in der Ihre Texte tatsächlich vorliegen – en, wenn Sie auf Englisch zurückgefallen sind – (zh-CN und pt-BR für Chinesisch und Portugiesisch, damit die richtigen Glyphen erscheinen), formatieren Sie Zahlen in derselben Sprache und rendern Sie bei context.changed erneut.
  • Ein Cell Renderer antwortet in der locale, in der jeder Stapel angefragt wird.
  • Formatieren Sie Zahlen und Datumsangaben für die Sprache (Intl.NumberFormat, Intl.DateTimeFormat).
  • Fügen Sie für jede Sprache README.<language>.md neben README.md hinzu (README.tr.md, README.zh.md, …) sowie Versionshinweise in jeder.

README und Versionshinweise

Die README.md auf oberster Ebene des Plugins wird auf seiner Detailseite angezeigt, wo Administratoren sie lesen, bevor sie das Plugin genehmigen; README.<language>.md (README.tr.md, README.ja.md, …) wird stattdessen jemandem angezeigt, der die App in dieser Sprache verwendet. Die lokalisierte README wird nur angezeigt, wenn auch README.md existiert. Sie wird als sicheres Markdown angezeigt: Überschriften, Absätze, Listen (eine Ebene), Fettdruck, Kursivschrift, Inline-Code und Codeblöcke. Links, Bilder, Tabellen und HTML werden als einfacher Text angezeigt. Angezeigt werden höchstens 64 KB.

Eine gute README sagt, in dieser Reihenfolge:

  1. Was das Plugin tut, in zwei oder drei Sätzen.
  2. Wo es erscheint: welcher Tab, welche Aktion, Seite oder welcher Zelltext.
  3. Wie es verwendet wird, Schritt für Schritt, mit einem Beispiel.
  4. Jede Berechtigung und warum sie nötig ist.
  5. Seine Einstellungen, falls vorhanden.
  6. Seine Grenzen: wie viele Dokumente es liest, was es nicht verarbeitet.
  7. Jeden verbleibenden Scanbefund und warum er unbedenklich ist.

Versionshinweise stehen im changelog des Manifests, die neuesten zuerst, ein Eintrag pro Version mit ihrem Tag und den Hinweisen auf Englisch und in jeder Ihrer Sprachen. Die Detailseite zeigt sie an; nach einer Aktualisierung werden die Versionen seit der letzten als neu markiert.

Versionen und Genehmigung

  • Eine Genehmigung gilt für exakte Dateien: ihren Digest, den SHA-256 aus Pfad und SHA-256 jeder Datei. Der Administrator sieht ihn vor der Genehmigung.
  • Jede Änderung an irgendeiner Datei eines hochgeladenen Plugins oder eines Plugin-Ordners (eine neue Version, ein korrigierter Tippfehler in der README) deaktiviert es, bis ein Administrator es erneut genehmigt. Erhöhen Sie version und fügen Sie für jedes Release einen Changelog-Eintrag hinzu, damit Administratoren wissen, was sie genehmigen.
  • Das Hochladen eines Plugins, dessen ID installiert ist, ersetzt es; es bleibt nur aktiviert, wenn die Dateien genau die genehmigten sind. Seine Einstellungen bleiben erhalten, solange das neue Manifest sie weiterhin mit demselben Typ deklariert.
  • Ein von Hand abgelegter Plugin-Ordner wird von Hand verwaltet: Ein Upload derselben ID wird abgelehnt, und das Entfernen in der App vergisst ihn, ohne den Ordner zu löschen.
  • Nur mit Mongo Manager ausgelieferte Plugins behalten ihre Genehmigung über eine Aktualisierung hinweg, und nur, solange sie aktiviert sind und die Aktualisierung keine neue Berechtigung anfordert; dann wird von einem Administrator nichts verlangt, und die Detailseite des Plugins gibt an, dass es seine Genehmigung behalten hat. Bei einer Aktualisierung, die ein Administrator von Hand genehmigt hat, steht, dass sie von einem Administrator genehmigt wurde.

Paketieren

Ein Plugin wird als gzip-komprimiertes tar-Archiv (.tgz) transportiert, dessen Dateien im Stammverzeichnis des Archivs liegen, darunter mongo-manager-plugin.json. Ein einziger oberster Ordner, der alles enthält (wie das package/ von npm pack), wird akzeptiert und entfernt. Das Archiv darf nur reguläre Dateien enthalten (Ordner ergeben sich implizit); Links, Geräte, Spezialeinträge, Pfade, die nicht schlicht sind, und doppelt angegebene Pfade werden abgelehnt; entpackt höchstens 500 Dateien und 25 MB, hochgeladen höchstens 30 MB.

Veröffentlichen auf GitHub

Administratoren können ein Plugin direkt aus einem öffentlichen GitHub-Repository installieren, auf einem Server, der das erlaubt (MM_PLUGINS_GITHUB=1; standardmäßig ist es aus). Auf der Seite Plugins fügen sie eine dieser Adressen ein:

  • https://github.com/<owner>/<repo>, …/releases oder …/releases/latest für das neueste Release;
  • https://github.com/<owner>/<repo>/releases/tag/<tag> für ein bestimmtes. Das Tag darf Schrägstriche enthalten (höchstens 4 Teile).

Die Adresse enthält nichts weiter: keine Abfrage, kein Fragment, keinen Port, keine Zugangsdaten. Einem umbenannten Repository wird gefolgt: Die eigene Seitenadresse des Releases benennt sein Repository. Die App lädt das Plugin-Archiv dieses Releases herunter, sein einziges Asset, dessen Name auf .tgz oder .tar.gz endet. Ein Release ohne ein solches Asset oder mit mehreren wird abgelehnt. Tag- und Asset-Namen müssen druckbares ASCII sein. Das Asset muss zu den Releases dieses Repositorys gehören und darf nicht größer sein als ein Upload (30 MB), sowohl wie angegeben als auch wie gelesen.

Die App spricht nur mit github.com, api.github.com, objects.githubusercontent.com und release-assets.githubusercontent.com, über https, nur an öffentlichen Adressen, und sendet nichts vom Server mit (kein Cookie, kein Token, keine Zugangsdaten). Sie folgt höchstens 4 Weiterleitungen, nur zwischen diesen Hosts, liest die Beschreibung des Releases bis zu 5 MB und gibt der gesamten Installation 4 Minuten. Das Plugin wird deaktiviert installiert, mit seinem Scan, und wartet wie ein Upload auf die Genehmigung. Es merkt sich, woher es stammt (Repository, Release und Archiv), was auf seiner Detailseite angezeigt wird.

Schlägt die Installation fehl, nennt die Seite Plugins den Grund: Das Repository hat kein veröffentlichtes Release, das Ratenlimit von GitHub wurde erreicht, GitHub hat abgelehnt (das Repository ist nicht öffentlich), GitHub ist vom Server aus nicht erreichbar, eine Weiterleitung ging an einen nicht erlaubten Host, es gab zu viele Weiterleitungen, das Release hat kein Archiv oder mehrere, oder das Archiv gehört nicht zu den Releases dieses Repositorys.

  1. Erhöhen Sie version, fügen Sie einen changelog-Eintrag hinzu und setzen Sie publishedAt.
  2. Führen Sie node scripts/pack.mjs aus.
  3. Erstellen Sie ein GitHub-Release (zum Beispiel mit dem Tag v0.1.0) und hängen Sie hello-documents-0.1.0.tgz als dessen Asset an. Hängen Sie keine andere .tgz- oder .tar.gz-Datei an.
  4. Markieren Sie es als neuestes Release. Tragen Sie den von pack.mjs ausgegebenen Digest in die Release-Notes ein, damit Administratoren ihn mit dem vergleichen können, was die App anzeigt.

Installationen von GitHub sind aus, solange MM_PLUGINS_GITHUB=1 nicht gesetzt ist; ein Server kann GitHub außerdem möglicherweise nicht erreichen oder nur über einen Proxy nach außen gelangen (die Installation verbindet sich direkt mit GitHub und verwendet keine HTTP-Proxy-Einstellungen); seine Administratoren laden dann die .tgz herunter und laden sie mit Plugin hochladen hoch.

Damit andere es finden, tragen Sie Ihr Plugin in Awesome Mongo Manager ein (github.com/mongo-manager/awesome-mongo-manager): Öffnen Sie dort einen Pull Request, der seiner README eine Zeile hinzufügt. Dessen Prüfungen laden Ihr neuestes Release herunter und prüfen es mit dem eigenen Code der App, wie eine Installation von GitHub; danach liest ein Maintainer das Plugin, bevor er es aufnimmt.

Testen auf dem eigenen Server

  1. Führen Sie Mongo Manager mit aktivierten Plugins aus (Standard) und melden Sie sich als Administrator an. Suchen Sie sein Datenverzeichnis: ~/.mongo-manager, sofern MM_DATA_DIR nichts anderes angibt.
  2. Kopieren Sie das Plugin nach <data-dir>/plugins/<id>: node scripts/pack.mjs --folder ~/.mongo-manager/plugins. Der Name des Ordners muss die ID sein, und er darf keine versteckten Dateien enthalten (weshalb das Skript nur die Dateien des Plugins kopiert). ~/ ist in jeder Shell Ihr Home-Verzeichnis; ~\ in cmd und PowerShell oder in Anführungszeichen (bash und zsh lassen einen Backslash ohne Anführungszeichen fallen, und das Skript lehnt dann ab, was übrig bleibt). Das Skript ersetzt nur einen Ordner dieses Plugins, der ausschließlich Dateien und Ordner enthält, die es hätte kopieren können (keine Skripte, versteckten Dateien, Links, Pipes oder Sockets), und in dem oder an dem kein Dateisystem eingehängt ist; dabei tauscht es die neue Kopie so ein, dass ein abgebrochener Kopiervorgang den Ordner so belässt, wie er war. Es lehnt ein Ziel ab, das der eigene Ordner des Plugins ist, in ihm liegt oder ihn enthält, egal wie der Pfad es benennt (ein symbolischer Link, eine Junction oder eine Freigabe); dann wird nichts geschrieben.
  3. Öffnen Sie Plugins und klicken Sie auf Erneut scannen. Ein Plugin, das nicht verwendet werden kann, nennt den Grund (ein Manifest-Feld, ein Pfad). Öffnen Sie seine Details: Lesen Sie die Scanbefunde, die Berechtigungen und die README, wie es ein Administrator täte.
  4. Klicken Sie auf Genehmigen und aktivieren, öffnen Sie dann eine Collection und probieren Sie jeden Erweiterungspunkt aus.
  5. Kopieren Sie nach jeder Änderung erneut, klicken Sie auf Erneut scannen und genehmigen Sie erneut (die Dateien haben sich geändert), und öffnen Sie dann den Tab, die Seite oder den Dialog erneut. Probieren Sie mehrere Sprachen, beide Designs, eine View, eine Collection ohne Dokumente und eine ohne Collection geöffnete Seitenleistenseite aus.
  6. Laden Sie schließlich die .tgz selbst mit Plugin hochladen auf einen sauberen Server hoch, so wie Ihre Benutzer es tun werden.

Die Entwicklertools des Browsers funktionieren im Frame: Wählen Sie in der Konsole den Frame des Plugins aus, um seine Fehler und Nachrichten zu sehen. Eine Richtlinienverletzung in der Konsole bedeutet, dass die Seite etwas versucht hat, was die Sandbox verbietet.

Entwickeln mit einem KI-Assistenten

Der Starter enthält Anweisungsdateien, die einem KI-Coding-Assistenten alles auf dieser Seite beibringen: die Regeln des Manifests, die Bridge-Methoden und Berechtigungen, die Sandbox, den Scan, Sprachen, README, Paketieren und Veröffentlichen. Behalten Sie sie auf oberster Ebene des Repositorys Ihres Plugins; pack.mjs lässt sie aus dem Archiv aus. Die Seite Plugins speichert den Starter als .zip und jede Datei einzeln unter Anweisungen für Ihren KI-Assistenten, um sie einem bereits vorhandenen Plugin hinzuzufügen; die für Copilot wird als copilot-instructions.md gespeichert, für den Ordner .github Ihres Repositorys.

  • CLAUDE.md: Claude Code.
  • AGENTS.md: OpenAI Codex und andere Agents, die AGENTS.md lesen.
  • GEMINI.md: Gemini CLI.
  • .github/copilot-instructions.md: GitHub Copilot.

Bitten Sie den Assistenten um das, was Ihr Plugin tun soll; er sollte mit Code antworten, der den Scan und die folgende Checkliste besteht. Lesen Sie, was er schreibt, bevor Sie es veröffentlichen: Sie sind derjenige, dem Administratoren vertrauen.

Checkliste vor der Veröffentlichung

  • Die ID ist eindeutig und entspricht dem Ordnernamen; die Version ist erhöht und hat einen Changelog-Eintrag mit dem heutigen Tag.
  • Jeder lokalisierte Text hat en und tr; die Seite folgt locale und context.changed.
  • Die Berechtigungen sind die wenigsten, mit denen es funktioniert, und die README sagt, warum jede nötig ist.
  • Der Scan zeigt keinen hohen Befund, und die README erklärt jeden anderen.
  • Text wird mit textContent oder h() geschrieben; es wird kein Markup aus Text gebaut.
  • Nichts greift auf das Netzwerk zu (kein fetch, WebRTC oder Prefetch-Hinweis), verwendet Speicher, öffnet Popups oder verlässt die Seite.
  • Kein Inline-Skript, -Stil oder -Event-Handler; jeder Pfad ist relativ (./main.js).
  • Jede Datei ist als UTF-8 gespeichert, ohne NUL-Bytes.
  • Die Seite folgt dem Design und der Akzentfarbe und funktioniert mit der Tastatur.
  • Sie behandelt, dass place gleich null ist, eine View, eine leere Collection und jeden Fehlercode, auf den sie stoßen kann.
  • Aufrufe, die einen Klick benötigen, erfolgen direkt im Klick-Handler.
  • Große Lesezugriffe sind begrenzt: ein limit, eine Projektion, jeweils eine Pipeline gleichzeitig.
  • README.md und ihre Übersetzungen beschreiben das Plugin; license, author und repository sind gesetzt.
  • Die .tgz wurde auf einen sauberen Server hochgeladen, gescannt, genehmigt und dort ausprobiert.
  • Das GitHub-Release enthält genau ein Plugin-Archiv, benannt <id>-<version>.tgz.
