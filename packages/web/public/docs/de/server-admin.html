Serververwaltung

Über Ihre Daten hinaus verwaltet Mongo Manager den MongoDB-Server selbst: seine Datenbankbenutzer und Rollen, das Sharding eines Clusters, Warnungen bei Problemen und den Zustand jeder Verbindung auf einen Blick.

Benutzer und Rollen

Die Seite einer Verbindung → Benutzer und Rollen verwaltet die eigenen Konten von MongoDB, ähnlich wie Database Access in Atlas. Dies sind die Konten, mit denen sich Anwendungen und Personen bei MongoDB anmelden, nicht die Benutzer von Mongo Manager.

Wer es verwenden darf

  • Benutzer mit der App-Berechtigung databases:admin für die Verbindung: App-Administratoren oder ein Benutzer, dem Administratorrechte für diese Verbindung gewährt wurden. Ein Benutzer, dem ein Administrator personenbezogene Daten verbirgt, sieht diesen Bereich nie; wer sie vor sich selbst verbirgt, sieht ihn.
  • Auch die eigenen Rechte von MongoDB gelten: Das Konto, mit dem sich die Verbindung anmeldet, benötigt userAdmin für die Datenbank oder userAdminAnyDatabase (viewUser und viewRole genügen zum Auflisten). Wenn MongoDB ablehnt, sagt die Seite, dass MongoDB abgelehnt hat und bei welchem Befehl — nicht die App.
  • Bei einer schreibgeschützten Verbindung werden Benutzer und Rollen aufgelistet, aber nie geändert.

Die Liste

Benutzer aller Datenbanken oder einer einzelnen (der Datenbankfilter), mit Suche. Die Rollen jedes Benutzers erscheinen als Chips, zum Beispiel „readWrite on shop“. Das Konto, mit dem sich die Verbindung selbst anmeldet, ist mit Diese Verbindung gekennzeichnet.

Einen Benutzer hinzufügen

  • Authentifizierungsdatenbank: wo sich der Benutzer anmeldet. Empfohlen wird admin (Benutzer dort können Rollen für jede Datenbank haben), aber jede Datenbank funktioniert. $external ist für x.509-, LDAP-, Kerberos- und AWS-IAM-Benutzer, die kein Passwort haben: Der Name muss genau dem entsprechen, was diese Quelle sendet.
  • Benutzername.
  • Passwort: Geben Sie eines ein oder wählen Sie Generieren für 24 zufällige Zeichen, die in Ihrem Browser aus der Zufallsquelle des Systems erzeugt werden, in einer Verbindungszeichenfolge unbedenklich sind und angezeigt werden, damit Sie sie kopieren können.
  • Rollen: integrierte Rollen, jeweils mit dem, was sie erlauben, oder Ihre benutzerdefinierten Rollen, jeweils für eine Datenbank. Rollen, die nur in admin existieren (clusterMonitor, backup, root und ähnliche), sind daran gebunden.

Passwörter verwenden SCRAM-SHA-256 und müssen mindestens 12 Zeichen lang sein. Ein Passwort wird einmal an MongoDB gesendet; Mongo Manager speichert es nie, protokolliert es nie und schreibt es nie in das Audit-Protokoll. Kopieren Sie ein generiertes Passwort, bevor Sie das Formular schließen. Das Gewähren weitreichender Rechte verlangt zuvor eine Bestätigung, und der Server lehnt sie unbestätigt ab: die integrierten Rollen root, userAdminAnyDatabase, userAdmin, dbOwner, clusterAdmin, clusterManager, hostManager, backup, restore, readWriteAnyDatabase und dbAdminAnyDatabase, jede andere integrierte Rolle der Datenbank admin (readAnyDatabase, clusterMonitor, enableSharding), jede Rolle von local (sie enthält das Oplog, jeden ausgeführten Schreibvorgang) oder config (die Sharding-Metadaten) und jede benutzerdefinierte Rolle, die eine davon erbt oder eine Berechtigung für den Cluster, eine beliebige Ressource, alle Datenbanken auf einmal oder local und config enthält, oder die Benutzer oder Rollen erstellt (createUser, grantRole, changePassword und ähnliche). Solche benutzerdefinierten Rollen sind als weitreichend gekennzeichnet, und auch ihr Erstellen wird bestätigt.

Benutzer ändern und verwerfen

  • Bearbeiten legt ein neues Passwort, neue Rollen oder beides fest. Die Rollen, die Sie speichern, ersetzen die Liste des Benutzers.
  • Beim Ändern oder Verwerfen des eigenen Kontos der Verbindung erscheint eine Warnung, dass die Verbindung dadurch ausgesperrt werden kann, und es ist eine Bestätigung nötig. Dasselbe gilt für das Ändern oder Verwerfen einer benutzerdefinierten Rolle, die dieses Konto besitzt. Welches Konto es ist, sagt MongoDB selbst (nicht die Einstellungen der Verbindung, die ein SRV-Eintrag oder ein Zertifikat ändern können). Bearbeiten Sie nach einem neuen Passwort auch die Verbindung.
  • Zum Verwerfen eines Benutzers oder einer Rolle müssen Sie deren Namen eingeben.

Benutzerdefinierte Rollen

Benutzerdefinierte Rollen geben einem Team genau die Aktionen, die es braucht, und nicht mehr. Eine Rolle hat eine Datenbank, einen Namen, Berechtigungen und geerbte Rollen.

  • Jede Berechtigung gilt für eine Datenbank und eine Collection (bei leerem Feld für jede Datenbank oder jede Collection), für den Cluster oder für eine beliebige Ressource.
  • Ihre Aktionen werden aus der Liste von MongoDB ausgewählt, gruppiert nach Abfragen und Schreiben, Datenbankverwaltung, Benutzer und Rollen, Deployment, Replikation und Sharding.
  • Eine Rolle außerhalb von admin erbt nur Rollen ihrer eigenen Datenbank (Regel von MongoDB); eine Rolle in admin darf Rollen jeder Datenbank erben.

Jede Änderung steht im Audit-Protokoll als mongo.users.create, mongo.users.update, mongo.users.grant, mongo.users.revoke, mongo.users.drop, mongo.roles.create, mongo.roles.update und mongo.roles.drop, mit den Namen und Rollenlisten, nie mit einem Passwort.

Sharding

Die Seite einer Verbindung → Sharding erscheint, wenn die Verbindung zu einem mongos besteht. Alle, die den Server beobachten dürfen, sehen den Zustand des Balancers, die Chunk-Verteilung und die Cluster-Übersicht. Änderungen erfordern databases:admin und eine Verbindung, die nicht schreibgeschützt ist.

Chunk-Verteilung

Ein Balken pro geshardeter Collection, eine Farbe pro Shard, mit den Zahlen auch in Worten für Screenreader.

Der Balancer

  • Starten oder stoppen Sie ihn; vor dem Stoppen wird nachgefragt. Solange er gestoppt ist, werden keine Chunks zwischen Shards verschoben; eine laufende Migration wird zuerst abgeschlossen. Stoppen Sie ihn für ein Backup oder Wartungsarbeiten und starten Sie ihn danach wieder.
  • Aktives Zeitfenster: von–bis, nach der Uhr des Config-Servers. Chunks werden dann nur innerhalb dieser Stunden verschoben. Jederzeit hebt es auf.

Eine Collection shardieren

  1. Wählen Sie die Datenbank und die Collection.
  2. Bauen Sie den Shard-Schlüssel Feld für Feld auf. Jedes Feld ist bereichsbasiert oder gehasht, mit höchstens einem gehashten Feld. Die Reihenfolge zählt: Verschieben Sie Felder nach oben und unten.
  3. Diesen Schlüssel prüfen: Der Server nimmt eine Stichprobe von 1000 Dokumenten und antwortet nur mit Zahlen, sodass kein Wert MongoDB verlässt: der Anteil der Dokumente, die das jeweilige Feld haben, die Anzahl verschiedener Werte, der Anteil des häufigsten Werts, ob die Werte mit der Zeit wachsen (ObjectId, Datumswerte) und ob ein Index mit den Feldern des Schlüssels beginnt. Das Urteil lautet gut, mittel oder schlecht.
  4. Optionen: eindeutig (nur bereichsbasierte Schlüssel); Chunks vorab erstellen (ein gehashter Schlüssel auf einer leeren Collection, MongoDB 6.0 und früher, 1 bis 8192 Chunks); Chunks für jede Zone erstellen (ein gehashter Schlüssel, bei bereits definierten Zonen).
  5. Sharding kann nicht rückgängig gemacht werden: Bestätigen Sie durch Eingabe des Namespace.

Ein Feld, das mit der Zeit wächst und als bereichsbasierter Schlüssel verwendet wird, sendet jedes neue Dokument an einen Shard: Hashen Sie es oder stellen Sie ein anderes Feld voran. Eine Collection mit Daten benötigt einen Index, der mit den Feldern des Schlüssels beginnt, bevor sie geshardet werden kann. Die eigenen und die System-Namespaces von MongoDB (admin, config, local, system.*) werden abgelehnt.

Zonen

  • Jeder Shard listet seine Zonen auf; fügen Sie einem Shard eine Zone hinzu oder entfernen Sie eine.
  • Schlüsselbereiche pro Collection: Die Grenzen sind Extended JSON der Felder des Shard-Schlüssels, mit {"$minKey":1} und {"$maxKey":1} für offene Enden, zum Beispiel {"region": "eu"} bis {"region": "us"}. Operatoren werden abgelehnt. Der Anfang ist eingeschlossen, das Ende nicht.
  • Entfernen Sie einen Bereich, wenn seine Dokumente wieder auf jedem Shard liegen dürfen.

Das Audit-Protokoll verzeichnet sharding.collection.shard, sharding.zone.shard, sharding.zone.range (den Namespace und die Zone, nie die Grenzwerte), sharding.balancer und sharding.balancer.window. Die Tests von Mongo Manager lassen diese Bildschirme gegen aufgezeichnete Antworten von mongos laufen.

Warnungen

Warnungen informieren Sie, wenn ein Server einen Schwellenwert überschreitet oder einer der eigenen Aufträge der App fehlschlägt: in der Glocke, per E-Mail oder an einen Webhook.

Schwellenwerte

Die Seite einer Verbindung → Warnungen, für App-Administratoren (settings:manage). Ein Schwellenwert überwacht eine Metrik:

  • Verbindungen: offene Clientverbindungen (eine Anzahl).
  • Operationen: Operationen pro Sekunde, alle Arten zusammen.
  • Replikationsverzögerung: Sekunden, die der am weitesten zurückliegende Sekundärknoten im Rückstand ist (Replica Sets).
  • WiredTiger-Cache: wie voll der Cache ist, in Prozent.
  • Datenträgernutzung: Prozent des Datenträgers der Datendateien, die belegt sind (MongoDB 4.4 und höher).
  • Langsame Operationen: die Anzahl der Operationen, die länger als die von Ihnen gewählten Sekunden laufen (erfordert clusterMonitor).

Der Server wertet sie einmal pro Minute aus derselben serverStatus-Abtastung aus wie den Metrikverlauf. Warnungen tasten eine Verbindung auch dann ab, wenn ihr Verlauf ausgeschaltet ist; Messwerte werden nur gespeichert, wenn der Verlauf eingeschaltet ist. Höchstens 50 Verbindungen werden abgetastet, für Verlauf und Warnungen zusammen.

Kein Flattern: Eine Warnung wird ausgelöst, sobald der Wert die von Ihnen gewählten Minuten (1 bis 60, Standard 2) über dem Schwellenwert geblieben ist, und wird erst behoben, nachdem er ebenso lange bei oder unter 90 % des Schwellenwerts geblieben ist. Ein Schwellenwert von 80 % Cache-Füllung wird bei 72 % oder weniger behoben.

Ereigniswarnungen

Auf der Seite „Warnungen“, für alle Verbindungen oder eine, oder im Bereich einer Verbindung:

  • Backup fehlgeschlagen: Ein Auftrag zum Sichern, Senden oder Abrufen eines Backups ist fehlgeschlagen.
  • Geplantes Backup fehlgeschlagen: Ein Lauf ist fehlgeschlagen oder hat nur einige seiner Ziele erreicht.
  • Live-Synchronisierung gestoppt: Sie ist fehlgeschlagen, wurde gestoppt oder braucht von sich aus Aufmerksamkeit — nicht, wenn eine Person sie gestoppt hat.
  • Auftrag fehlgeschlagen: jeder andere Auftrag (eine Wiederherstellungsübung hat ihr eigenes Ereignis).
  • Wiederherstellungsübung fehlgeschlagen: Eine geplante Wiederherstellungsübung konnte ihr Backup nicht wiederherstellen, hat abweichende Daten gefunden oder konnte ihre temporäre Datenbank nicht verwerfen (eine Warnung: Die Daten stimmten überein). Eine bestandene Übung steht im Verlauf des Zeitplans, nicht in einer Warnung.
  • Bidirektionale Synchronisierung hat Konflikte aufgelöst: Beide Seiten einer bidirektionalen Live-Synchronisierung haben dieselben Dokumente geändert; der letzte Schreibende hat gewonnen (die _ids stehen in der Aktivität der Synchronisierung).
  • Beobachtung hat ihren Warnungsfilter getroffen: Ein Beobachten-Feed, dessen Eigentümer Warnungen angefordert hat, hat Änderungen durch seinen Filter gelassen (höchstens alle 10 Sekunden, solange der Feed läuft).

Benachrichtigungen enthalten nur Namen und Zahlen: nie Dokumentwerte, Fehlertexte, Verbindungszeichenfolgen oder Hosts.

Geplante Berichte

Auf der Seite „Warnungen“ (App-Administratoren): Ein Bericht nennt nach einem Zeitplan einige Zahlen einer Verbindung — jeden Morgen, jeden Montag, bis hin zu stündlich — in der Glocke, per E-Mail oder an Webhooks, so wie Warnungen gesendet werden. Jede Zahl hat ihre Bezeichnung, eine Collection und einen optionalen Filter (JSON; ohne Filter werden alle Dokumente gezählt, nach der Schätzung der Collection); eine Zahl über einer Million wird als „mindestens“ angegeben. Führen Sie einen Bericht über seine Zeile sofort aus, ändern, deaktivieren oder löschen Sie ihn; die Zahlen seines letzten Laufs werden dort angezeigt.

Nur Zahlen, nie ein Wert. Ein Filter, der ein personenbezogenes Feld nennt — oder einer, den die Regeln für personenbezogene Daten anders lesen würden —, wird beim Speichern des Berichts abgelehnt und weggelassen, mit Angabe des Grundes, wenn sich Regeln danach ändern; ebenso die eigenen Namespaces von MongoDB, JavaScript auf dem Server, Views und Time-Series-Collections (die Pipeline einer View könnte nach einem personenbezogenen Feld auswählen). Ein Bericht gilt als die eigenen Anmeldedaten der Verbindung: Eine Verbindung, bei der sich jede Person einzeln anmeldet, wird abgelehnt, ebenso ein Filter bei einer Verbindung, die Felder auf dem Client verschlüsselt (er würde nichts treffen, was sie lesen kann). In der Glocke und im Verlauf sehen Administratoren die Zahlen eines Laufs mit ihren Bezeichnungen; andere sehen, dass ein Bericht gelaufen ist, aber nicht seine Zahlen. Die letzten 30 Läufe jedes Berichts bleiben im Verlauf erhalten; ein Bericht, dessen Zeitplan nicht mehr berechnet werden kann, wird deaktiviert, mit Angabe des Grundes.

Kanäle

  • Die Glocke. Jeder Benutzer schaltet Warnungen in der Glocke anzeigen für sich selbst ein, in den Präferenzen oder auf der Seite „Warnungen“. Er sieht Warnungen nur für Verbindungen, deren Server er beobachten darf (server:monitor).
  • E-Mail. Der SMTP-Server, der Port und TLS von Anfang an (meist 465) oder STARTTLS (meist 587): Ein Server, der keines von beiden anbietet, wird abgelehnt, E-Mails werden nie im Klartext gesendet. Ein Benutzername und ein Passwort (versiegelt), die Absenderadresse und bis zu 20 Empfänger. Ein neuer Server, Port, eine neue Verschlüsselung oder ein neuer Benutzername erfordert die erneute Eingabe des Passworts: Das gespeicherte wird nie an einen anderen Server gesendet. Testnachricht senden sendet mit den gespeicherten Einstellungen. Eine Sitzung, die ihren TLS-Handshake oder ihren Austausch nicht rechtzeitig abschließt, wird aufgegeben. E-Mails laufen über den eigenen Client von Mongo Manager und dessen Egress-Schutz: öffentliche Adressen, und private nur innerhalb von MM_ALERTS_PRIVATE_NETWORKS.
  • Webhooks. Eine https-Adresse; einfaches http nur an Adressen innerhalb von MM_ALERTS_PRIVATE_NETWORKS. Keine Anmeldedaten in der Adresse, Cloud-Metadaten- und Link-Local-Adressen nie, und Weiterleitungen werden nicht befolgt. Der Server erzeugt das Signaturgeheimnis jedes Webhooks und zeigt es einmal an; Neues Geheimnis erstellen ersetzt es, und das alte funktioniert sofort nicht mehr.

Jede Regel wählt, wohin sie gesendet wird; eine Regel ohne Kanal wird nur aufgezeichnet.

Webhook-Zustellungen

Jede Zustellung ist ein POST mit einem JSON-Body:

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type ist alert.firing, alert.resolved, alert.event oder alert.test (ein Test enthält nur type und at). Ereigniswarnungen setzen event (backup.failed, schedule.failed, liveSync.stopped, job.failed) anstelle von metric. Die Header:

  • x-mm-event: noch einmal der Typ.
  • x-mm-delivery: eine eindeutige ID der Zustellung, bei jedem erneuten Versuch dieselbe.
  • x-mm-timestamp: Unix-Sekunden, zu denen dieser Versuch signiert wurde.
  • x-mm-signature: sha256= gefolgt vom hexadezimalen HMAC-SHA256 mit dem Geheimnis des Webhooks über den Zeitstempel, einen Punkt und den Body.

Prüfen Sie die Signatur über den rohen Body, bevor Sie ihn parsen, und lehnen Sie Zeitstempel ab, die älter als 5 Minuten sind. In Node.js: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

In Python:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

Eine Zustellung wird bis zu dreimal erneut versucht, nach 2 Sekunden, 10 Sekunden und 60 Sekunden, bei einem Netzwerkfehler, einer 5xx-Antwort, 408 oder 429; nie bei einem anderen 4xx und nie an eine Adresse, die der Schutz ablehnt. Jeder Versuch wird mit einem neuen Zeitstempel erneut signiert. Nutzen Sie x-mm-delivery, um eine bereits verarbeitete Zustellung zu ignorieren.

Zurückstellen, Pausieren und Bestätigen

  • Zurückstellen einer Regel für 1 Stunde, 8 Stunden oder 1 Tag: Warnungen werden weiterhin aufgezeichnet, es wird nichts gesendet. Jetzt reaktivieren beendet die Zurückstellung vorzeitig.
  • Pausieren und fortsetzen Sie eine Regel mit ihrem Schalter.
  • Administratoren bestätigen eine Warnung für alle, die dann sehen, wer es getan hat; alle anderen blenden sie aus ihrer eigenen Glocke aus. Außerhalb der Administratoren zeigt die Glocke, was geschehen ist (die Codes), aber nicht, welche Synchronisierung, welcher Auftrag, welcher Zeitplan oder welcher Namespace betroffen ist.
  • Zustellungen erfolgen einige wenige gleichzeitig aus einer Warteschlange, egal wie viele Kanäle und Warnungen zusammen ausgelöst werden.
  • Der Verlauf, auf der Seite „Warnungen“ und im Bereich jeder Verbindung, behält 90 Tage (höchstens 20.000 Einträge), mit dem Ergebnis jeder Zustellung und der Anzahl ihrer Versuche.

MM_ALERTS=0 schaltet Warnungen auf dem Server aus: Nichts wird ausgewertet oder gesendet (siehe Bereitstellung). Das Audit-Protokoll verzeichnet alerts.rule.create, alerts.rule.update, alerts.rule.delete, alerts.rule.snooze, alerts.email.update, alerts.email.test, alerts.webhook.create, alerts.webhook.update, alerts.webhook.delete, alerts.webhook.test und alerts.acknowledge — nie das SMTP-Passwort oder ein Webhook-Geheimnis.

Live-Zustand

Die Verbindungskarten in der Übersicht zeigen die Ping-Latenz, die MongoDB-Version und die Topologie jeder Verbindung sowie die auf ihr ausgelösten Warnungen. Die Seite einer Verbindung zeigt dasselbe in ihrer Kopfzeile, mit einem Statuspunkt.

  • Der Server behält jede Antwort 30 Sekunden lang.
  • Die Liste stellt nie von selbst eine Verbindung her: Eine nicht geöffnete Verbindung zeigt Nicht verbunden. Das Öffnen der Seite einer Verbindung prüft sie, ebenso wie das Auflisten ihrer Datenbanken.
  • Die Anzahl der Warnungen wird nur für Verbindungen angezeigt, deren Server Sie beobachten dürfen.
