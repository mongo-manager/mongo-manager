Live-Synchronisierung

Eine Live-Synchronisierung kopiert eine Collection oder eine Datenbank von einer Verbindung auf eine andere und wendet dann jede Änderung an der Quelle an, sobald sie erfolgt. Sie läuft auf dem Server, übersteht Neustarts und läuft weiter, bis Sie sie stoppen oder beenden. Sie können sie auf zwei Arten nutzen:

  • Als Spiegel: eine Staging-, Reporting- oder Standby-Kopie, die monatelang aktuell bleibt.
  • Zum Verschieben von Daten: kopieren, aufholen lassen, prüfen, dann zu einem von Ihnen gewählten Zeitpunkt beenden (die Umschaltung) und Ihre Anwendungen auf das Ziel ausrichten.

Öffnen Sie Live-Synchronisierungen über das Kontomenü oder die Befehlspalette (Ctrl+K). Starten Sie eine über das Menü einer Collection oder einer Datenbank in der Baumansicht (Live-Synchronisierung…), über die Palette, während eine Collection geöffnet ist („Diese Collection synchron halten…“), oder über die Zusammenfassung des Kopier-Assistenten (Kopieren und synchron halten…).

Was synchronisiert werden kann

  • Eine Collection auf eine Collection oder eine Datenbank auf eine Datenbank (alle ihre Collections oder die, die Sie ankreuzen).
  • Die Quelle muss ein Replica Set, ein Sharded Cluster oder ein Load-Balanced-Deployment mit MongoDB 6.0 oder neuer sein (MongoDB Atlas ist es immer): Eine Live-Synchronisierung liest die Change Streams von MongoDB. Für die Entwicklung genügt ein Replica Set mit einem einzigen Knoten. Das Ziel kann jedes Deployment sein.
  • Eine Datenbanksynchronisierung aller Collections kann auch später erstellten Collections folgen: Sie werden mit den Optionen der Quelle auf dem Ziel erstellt, und ihre Dokumente folgen. Views werden nur mit der anfänglichen Kopie kopiert.
  • Eine Collection-Synchronisierung kann nur die Dokumente übertragen, die ein Filter trifft (Nur die Dokumente, die ein Filter trifft, geschrieben wie in der Shell). Ein Änderungsereignis allein kann nicht sagen, dass eine Aktualisierung ein Dokument aus dem Filter heraus verschoben hat, daher entscheidet die Quelle: Für jeden Stapel wird sie gefragt, welche der geänderten Dokumente jetzt zutreffen; diese werden so geschrieben, wie sie jetzt sind, und die anderen werden vom Ziel entfernt. Die anfängliche Kopie übernimmt nur die passenden Dokumente. Eine maskierte oder anonyme Synchronisierung lehnt einen Filter ab, der ein verborgenes Feld oder ein darüberliegendes Feld liest oder einen Ausdruck verwendet. Ein Filter, der JavaScript auf dem MongoDB-Server ausführt ($where, $function), wird nur akzeptiert, solange der Server es erlaubt; er wird bei jedem Start und vor jedem Stapel erneut beurteilt, und die Synchronisierung wartet („Der Filter führt JavaScript auf dem MongoDB-Server aus …“), sobald die Einstellung ausgeschaltet wird. Eine Datenbanksynchronisierung überträgt ganze Collections.
  • Mit Begründung abgelehnt: admin, local, config und system.* als Quelle oder Ziel; eine Time-Series-Quelle; ein View als Quelle (er hat keinen eigenen Change Stream: synchronisieren Sie die Collection dahinter); ein Capped-Ziel (es kann keine Löschvorgänge aufnehmen); ein Ziel, das die Quelle selbst ist oder sein könnte; und eine Synchronisierung, die eine Schleife schließen würde (A nach B, während B nach A geht, oder eine längere Kette). Ein Deployment, das sich nicht von einem anderen unterscheiden lässt, gilt für diese Prüfungen als dasselbe.

Starten

Der Assistent fragt, wie die Synchronisierung startet:

  • Zuerst kopieren (Standard): Das Ziel muss fehlen oder leer sein; alles wird kopiert, dann folgen die Änderungen.
  • Ziel ersetzen: Das Ziel wird daneben neu aufgebaut und eingetauscht (Sie geben zur Bestätigung seinen Namen ein). Es benötigt das Recht, Collections zu erstellen und zu verwerfen, und wird für ein Sharded-Ziel abgelehnt.
  • Mit dem Ziel zusammenführen: Dokumente werden per Upsert über _id auf das vorhandene Material angewendet.
  • Ab jetzt: Das Ziel hat die Daten bereits; es werden nur Änderungen ab jetzt angewendet.

Die anfängliche Kopie läuft als Kopierauftrag (sie erscheint in der Auftragsleiste). Zwischen Kopie und Änderungen geht nichts verloren: Bevor die Kopie beginnt, vermerkt die Synchronisierung die Cluster-Zeit der Quelle, und sobald die Kopie fertig ist, wendet sie jede seither erfolgte Änderung an. Das Anwenden ist idempotent, sodass ein Dokument, das nach einer Änderung kopiert oder später erneut geändert wurde, am Ende der Quelle entspricht.

Später starten

Zu einem von mir gewählten Zeitpunkt starten plant den Start eine Minute bis 30 Tage im Voraus (etwa eine ruhige Nacht). Die Synchronisierung wird sofort mit der von Ihnen bestätigten Zusammenfassung erstellt und wartet als Pausiert – Startet …; bis dahin wird nichts kopiert oder gelesen. Zu ihrem Zeitpunkt wird sie als ihr Besitzer neu geplant (Rechte, Regeln, Schleifen, das Ziel, Maskierung, mit den von Ihnen gegebenen Bestätigungen), ihre Cluster-Zeit wird gelesen und ihre Kopie beginnt. Gilt der Plan nicht mehr – das Ziel wurde inzwischen gefüllt, ein Recht ging verloren –, wartet sie mit den Gründen unter Handlungsbedarf, und Neu starten plant sie neu. Ihr Besitzer kann mit Jetzt starten früher starten; ein Administrator kann sie stoppen, aber nicht starten (sie startet als ihr Besitzer). Ein Neustart hält sie weiter wartend.

Zu ihrem Zeitpunkt und bei Jetzt starten wird zuerst alles geprüft, was eine laufende Synchronisierung vor jedem Stapel prüft: Ihr Besitzer muss weiterhin von der Quelle lesen und exportieren können, die Verbindungen müssen unverändert sein, und die Regeln für personenbezogene Daten müssen die sein, unter denen sie geplant wurde. Seither hinzugekommene Regeln halten sie für eine Prüfung an (Prüfen…): Sie startet, sobald ihr Besitzer sie bestätigt hat. Eine Synchronisierung, die kopieren muss, wartet außerdem auf Platz unter den laufenden Übertragungen ihres Besitzers: Zu ihrem Zeitpunkt versucht sie es etwas später erneut; Jetzt starten sagt es. Sobald die Ursache behoben ist, startet Erneut versuchen eine geplante Synchronisierung, die nie gestartet ist (sie wird dann geplant).

Das Oplog-Fenster

Während der Kopie vorgenommene Änderungen warten im Änderungsverlauf der Quelle (ihrem Oplog). Die Zusammenfassung schätzt, wie lange die Kopie dauert und, wo der Benutzer der Verbindung es lesen darf, wie lange die Quelle ihre Änderungen aufbewahrt. Eine Kopie, die voraussichtlich mehr als die Hälfte dieses Fensters benötigt, muss bestätigt werden: Geht der Verlauf aus, bevor die Kopie endet, kann die Synchronisierung nicht aufholen und endet Fehlgeschlagen mit „Neu starten“. Lässt sich das Fenster nicht lesen, sagt die Zusammenfassung es.

Wie Änderungen angewendet werden

  • Ein Einfügen, Aktualisieren oder Ersetzen schreibt das Dokument so, wie es jetzt in der Quelle ist (über _id, bei Bedarf angelegt); ein Löschen löscht über _id. Innerhalb eines Stapels (höchstens 1.000 Änderungen oder 8 MB) wird nur die letzte Änderung jedes Dokuments geschrieben.
  • Nach jedem vom Ziel akzeptierten Stapel speichert die Synchronisierung ihre Position. Ein Neustart setzt direkt danach fort; höchstens der letzte Stapel wird erneut angewendet, was nichts ändert.
  • Eine Live-Synchronisierung ist unidirektional. Schreibvorgänge anderer auf dem Ziel werden nicht erkannt: Die nächste Änderung dieses Dokuments in der Quelle überschreibt sie. Der Assistent bittet Sie, dies zu bestätigen.
  • Neue und verworfene Indizes folgen. Neue Collection-Optionen oder Validatoren nicht: Die Synchronisierung wartet mit „Die Optionen oder der Validator der Quell-Collection haben sich geändert“, und Sie wählen Optionen der Quelle anwenden (ihr Validator und ihre Validierungseinstellungen werden auf dem Ziel gesetzt) oder Ignorieren.
  • Eine verworfene oder umbenannte Quell-Collection verwirft nie das Ziel: Die Synchronisierung wartet auf Sie, und Sie stoppen oder starten sie neu.

Prüfen

Prüfen vergleicht Quelle und Ziel Dokument für Dokument, während die Synchronisierung weiterläuft. Als verschieden, fehlend oder überzählig gefundene Dokumente werden erneut gelesen, sobald die Synchronisierung alles bis zum Ende des Vergleichs angewendet hat, sodass noch unterwegs befindliche Änderungen nicht als Unterschiede gemeldet werden (bis zu 10.000 solcher Dokumente pro Collection; darüber hinaus sagt der Bericht, wie viele nicht erneut geprüft wurden). Die Karte zeigt das Ergebnis, zum Beispiel „Geprüft 12:40 — 1.204.331 gleich, 0 verschieden“; die Details listen die weiterhin abweichenden _ids auf. Eine maskierte Synchronisierung wird gegen die maskierte Quelle geprüft.

Unterschiede anzeigen in den Details öffnet den Vergleich so, wie die Vergleichsansicht ihn zeigt: für jede Gruppe (verschieden, nur in der Quelle, nur im Ziel) bis zu 10 Dokumente pro Collection und für ein verschiedenes die Felder, die sich vom Ziel zur Quelle geändert haben. Die Stichproben gehören allein dem Besitzer der Synchronisierung (ein Administrator sieht die Zahlen), werden nur gegeben, solange der Besitzer beide Seiten lesen darf und ihm dort seither nichts verborgen ist, und nicht mehr, nachdem sich die Regeln für personenbezogene Felder geändert haben: Prüfen Sie dann erneut.

Beenden (die Umschaltung)

  1. Stoppen Sie die Anwendungen, die in die Quelle schreiben. Mongo Manager kann andere Clients nicht stoppen.
  2. Wählen Sie Beenden… und bestätigen Sie. Die Synchronisierung vermerkt in diesem Moment die Cluster-Zeit der Quelle, wendet jede davor erfolgte Änderung an und endet dann. Eine Änderung danach kann trotzdem noch angewendet werden (sie kann im selben Stapel eintreffen), weshalb zuerst die Schreibvorgänge gestoppt werden.
  3. Sie prüft (standardmäßig an; Sie können das Häkchen entfernen).
  4. Sie endet Abgeschlossen mit ihren endgültigen Zahlen. Hat die Prüfung Unterschiede gefunden, zeigt der Bericht sie: Die Daten zu beurteilen, ist Ihre Sache.

Bidirektionale Synchronisierung

Bidirektional (eine Collection-Synchronisierung) bringt auch die Änderungen des Ziels zur Quelle zurück. Es sind zwei verknüpfte Synchronisierungen, je eine pro Richtung, dargestellt als zwei Karten (dieser Weg und der Rückweg), die gemeinsam pausieren, fortsetzen, stoppen und gelöscht werden; es gibt keine Umschaltung. Setzen Sie sie mit Bedacht ein: Sie eignet sich für zwei Standorte, die in dieselbe Collection schreiben, nicht für eine Migration.

  • Sie startet ab jetzt: Beide Collections müssen bereits dieselben Dokumente enthalten (kopieren Sie sie oder beenden Sie zuerst eine unidirektionale Synchronisierung). Sie überträgt ganze Collections (kein Filter), kann nicht maskieren (beide Seiten benötigen dieselben Regeln für personenbezogene Felder, und auf keiner Seite darf jemand eingeschränkt sein), benötigt nicht gesharte Collections und pausiert bei einem abgelehnten Dokument. Zwei Synchronisierungen zählen auf die Limits.
  • Beide Collections benötigen Pre- und Post-Images (changeStreamPreAndPostImages, MongoDB 6.0+): Pre- und Post-Images auf beiden Collections aktivieren erledigt das beim Start der Synchronisierung mit collMod. Sie kosten Speicherplatz auf beiden Servern.
  • Nichts kommt dorthin zurück, woher es kam. Jede Seite schreibt die Änderungen der anderen in Transaktionen einer eigenen Sitzung; MongoDB kennzeichnet die Änderungsereignisse dieser Schreibvorgänge mit der Sitzung, und der Rückweg überspringt sie. Die Dokumente werden dafür nicht verändert.
  • Konflikte: Der letzte Schreiber gewinnt. Eine Änderung wird nur angewendet, wo die andere Seite noch das hält, was die Änderung vorfand (ihr Pre-Image). Haben beide Seiten dasselbe Dokument geändert, bevor eine der Änderungen ankam, gewinnt auf beiden Seiten die Änderung mit der späteren Wanduhrzeit; die andere geht verloren. Jeder Konflikt wird in der Aktivität aufgelistet (seine _id und welche Seite gewann, nie ein Wert), auf der Karte gezählt und als App-Ereignis für Warnungen ausgelöst. Hält die andere Seite etwas anderes und trifft keine eigene Änderung ein, wird die Änderung angewendet und als solche aufgelistet – nur dort geschrieben, wo die andere Seite noch das hält, was sie beim Lesen hielt; hat sie sich inzwischen erneut geändert, wird auf diese neuere Änderung gewartet und sie als Konflikt beigelegt. Dokumente werden mit den Typen ihrer Werte verglichen und geschrieben: Ein Double, das eine ganze Zahl enthält, ist nicht der Int32, und jede Synchronisierung (auch die unidirektionale) schreibt ein Double, ein Long oder ein Decimal128 so, wie die Quelle es speichert.
  • Uhren. Ob eine Änderung der anderen Seite noch aussteht, wird anhand der eigenen Cluster-Zeit dieser Seite entschieden: Die Abweichung wird in einem Snapshot dessen gelesen, was die Mehrheit ihrer Mitglieder hält, und die Änderung wartet, bis der Change Stream des Rückwegs über diesen Zeitpunkt hinaus gelesen hat. Die Uhr des Computers, auf dem Mongo Manager läuft, spielt keine Rolle, ebenso wenig ein langsamer Majority Commit: Eine Änderung wartet, statt eine noch nicht eingetroffene zu überschreiben. Welche von zwei in Konflikt stehenden Änderungen gewinnt, vergleicht weiterhin die Wanduhren der beiden Server: Halten Sie beide im Takt (NTP). Laufen sie auseinander, gewinnt die Seite, deren Uhr vorgeht, Konflikte, die sie hätte verlieren müssen – beide Seiten halten am Ende weiterhin dasselbe Dokument, aber es kann die ältere Änderung sein. Auf einem ruhigen Server rückt der Stream des Rückwegs etwa alle 10 Sekunden weiter, sodass eine Änderung, in der sich die andere Seite lediglich unterschied, so lange dauern kann.
  • Wenn eine Richtung stoppt, stoppt auch die andere. Eine Richtung, die für eine Person stoppt (ein abgelehntes Dokument, verlorene Rechte, eine Änderung der Optionen) oder fehlschlägt, pausiert die andere („Pausiert, weil die andere Richtung gestoppt wurde“): Sich selbst überlassen, würde sie ihre Änderungen zurückhalten und auf einen Stream warten, der sich nicht bewegt, während ihre Position und das benötigte Oplog zurückfielen. Das Fortsetzen einer Richtung setzt beide fort. Eine Richtung stoppt auch („Zu viele ihrer Änderungen warten …“), wenn mehr als 10.000 ihrer Änderungen auf die andere Seite warten oder wenn das fast volle Oplog der Quelle über die Position hinwegzurollen droht, die sie hält. Das Fortsetzen startet dann zuerst die andere Richtung; diese wartet („Wartet darauf, dass die andere Richtung … aufholt“) und läuft von selbst weiter, sobald jene live ist.
  • Ein abgelehntes Dokument. Lehnt eine Seite eine Änderung ab (ein Validator, ein eindeutiger Index), stoppt die Richtung und nennt die _id des Dokuments. Beheben Sie die Ursache und wählen Sie Erneut versuchen oder Dieses Dokument überspringen: Diese Änderung wird endgültig ausgelassen und als verloren vermerkt, sodass beide Seiten bei diesem Dokument abweichen können, bis es sich wieder ändert; prüfen Sie es und kopieren Sie es bei Bedarf von Hand.
  • Werden Pre- und Post-Images auf einer der Collections ausgeschaltet, stoppt ihre Richtung („Pre- und Post-Images wurden deaktiviert“): Ohne sie würde jede Änderung die andere Seite ungeprüft überschreiben. Schalten Sie sie wieder ein (die Seite Beobachten bietet es an), übergehen Sie die Änderung der Optionen, dann Erneut versuchen.
  • Ein Neustart mittendrin liest erneut von vor jeder noch beizulegenden Änderung; bereits angewendete Änderungen werden erkannt, und eine Änderung, die verloren hat, kommt nicht zurück.

Zustände und was zu tun ist

  • Kopiert: Die anfängliche Kopie läuft; die Karte zeigt ihren Fortschritt.
  • Holt auf: Änderungen werden angewendet, mehr als 2 Sekunden im Rückstand; die Karte sagt, wie weit.
  • Live: weniger als 2 Sekunden im Rückstand. Die Karte zeichnet, wie weit sie in den letzten 10 Minuten im Rückstand war; der Server bewahrt diesen Verlauf einen Tag auf (der größte Rückstand je 10 Sekunden), sodass er ein Neuladen und einen Neustart übersteht, und die Details der Synchronisierung stellen die letzte Stunde, 6 Stunden oder 24 Stunden dar.
  • Pausiert: durch ihren Besitzer oder einen Administrator. Ihre Position bleibt erhalten; Fortsetzen macht weiter.
  • Handlungsbedarf: Sie hat aus einem Grund gestoppt, den eine Person ansehen muss – das Ziel hat ein Dokument abgelehnt (Dieses Dokument überspringen oder Erneut versuchen nach der Korrektur), neue Optionen an der Quelle, eine verworfene Quelle, geänderte Regeln für personenbezogene Daten oder eine bearbeitete Verbindung (Zusammenfassung prüfen), verlorene Rechte, schreibgeschützter Modus, der ausgeschaltete Schalter oder ein Change-Stream-Fehler, den Warten nicht behebt (eine Änderung größer als 16 MB, ein Recht, das der Benutzer der Quelle verloren hat: beheben Sie es, dann Erneut versuchen). Eine hinter der Synchronisierung verworfene Ziel-Collection oder eine Bearbeitung, die eine Verbindung auf einen anderen Server zeigen lässt, bittet um Neu starten. Die Pause eines Administrators wird von einem Administrator aufgehoben.
  • Neuer Versuch: Eine Verbindung ist nicht erreichbar; sie versucht es nach 1 Sekunde erneut, dann in längeren Abständen, bis zu 5 Minuten.
  • Wird abgeschlossen, dann Abgeschlossen: die Umschaltung.
  • Fehlgeschlagen: Sie kann von ihrer Position aus nicht fortfahren, meist weil der Änderungsverlauf der Quelle sie nicht mehr erreicht. Neu starten erstellt anstelle der alten eine neue Synchronisierung mit denselben Einstellungen, die in das zusammenführt, was das Ziel bereits enthält (die alte zählt dann nicht mehr auf die Limits).
  • Gestoppt: durch ihren Besitzer oder einen Administrator. Das Ziel behält, was es hat.

Lehnt das Ziel ein Dokument ab (ein doppelter Schlüssel in einem anderen eindeutigen Index, Validierung, Größe), gilt die Wahl des Assistenten: Pausieren und nachfragen (Standard) nennt die _id des Dokuments und den Fehler; Überspringen und protokollieren überspringt es, listet es im Aktivitätsprotokoll auf (seine _id und den Fehlercode, nie seinen Inhalt) und pausiert nach 1.000.

Unter Überspringen und protokollieren werden die abgelehnten Dokumente selbst in einer Datei aufbewahrt, eines pro Zeile in Extended JSON, genau so, wie die Synchronisierung sie zu schreiben versuchte (maskiert, wenn die Synchronisierung maskiert); die Details der Synchronisierung bieten sie ihrem Besitzer als Abgelehnte Dokumente herunterladen an. Ein Serverneustart erhält sie, und sie wächst weiter, wenn die Synchronisierung erneut läuft. Die Datei zählt auf den Übertragungsspeicher des Besitzers; ist dieser voll, werden Dokumente weiterhin übersprungen und protokolliert, aber nicht mehr aufbewahrt, und das Aktivitätsprotokoll sagt es. Sie wird nur gegeben, solange der Besitzer weiterhin von der Quelle lesen und exportieren darf: nicht mehr, wenn personenbezogene Werte dort vor ihm verborgen sind (bei einer Synchronisierung, die nicht maskierte), und nicht nach einer Änderung der Regeln der Quelle (bei einer, die maskierte). Das Löschen der Synchronisierung löscht sie.

Personenbezogene Daten

  • Dürfen Sie personenbezogene Daten auf der Quelle nicht sehen oder kreuzen Sie Personenbezogene Daten maskieren an, wird jedes Dokument, das die Synchronisierung schreibt – die Kopie und jede Änderung –, mit den Regeln der Quelle maskiert (***). Eindeutige Indizes über maskierte Felder werden nicht aufgebaut.
  • Dürfen Sie personenbezogene Daten auf dem Ziel nicht sehen und hat es Regeln, wird die Synchronisierung abgelehnt: Sie schreibt ganze Dokumente, die Ihre Regeln nicht Feld für Feld einhalten können.
  • Eine unmaskierte Synchronisierung auf ein Ziel ohne dieselben Regeln benötigt Ihre Bestätigung oder „Diese Regeln zuerst zum Ziel hinzufügen“ (für Administratoren der Zielverbindung). Beides wird im Audit-Protokoll festgehalten.
  • Ändern sich die Regeln auf einer der beiden Seiten, wartet die Synchronisierung: Bereits geschriebene Werte können jetzt personenbezogen sein. Prüfen Sie die Zusammenfassung, um fortzufahren, oder starten Sie neu.

Rechte, Limits und Einstellungen

  • Sie benötigen das Recht, von der Quelle zu exportieren, und auf dem Ziel Dokumente zu schreiben, Collections und Indizes zu erstellen und Aufträge auszuführen. Diese Rechte werden vor jedem Stapel erneut gelesen: Der Verlust eines davon oder Ihres Kontos stoppt die Synchronisierung sofort. Das Abmelden tut es nicht.
  • Das Bearbeiten einer Verbindung, die eine Synchronisierung verwendet, stoppt sie, bis Sie die Zusammenfassung prüfen (die Verbindung zeigt möglicherweise jetzt auf einen anderen Server); das Löschen der Verbindung stoppt sie endgültig.
  • Jeder Benutzer darf 3 Live-Synchronisierungen haben, die nicht beendet sind; ein Server führt höchstens MM_LIVE_SYNC_MAX aus (standardmäßig 10). MM_LIVE_SYNC=0 schaltet die Funktion aus: Laufende Synchronisierungen warten und machen weiter, wenn sie wieder eingeschaltet wird. Siehe Bereitstellung.
  • Administratoren sehen jede Synchronisierung und dürfen sie pausieren, fortsetzen, prüfen, stoppen und löschen; nur der Besitzer beendet sie oder bestätigt eine Prüfung.
