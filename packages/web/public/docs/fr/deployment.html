Déploiement

Comme service système

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

Le service s’exécute sous son propre compte sans privilèges, depuis un dossier de programme que seuls les administrateurs peuvent modifier, en mode équipe sur 127.0.0.1:4321. Au premier démarrage, le jeton de configuration à usage unique est conservé dans setup-token, dans le dossier de données, que seuls le compte du service et les administrateurs peuvent lire ; service install indique comment le lire. Le jeton n’est jamais écrit dans le journal, et le fichier est supprimé dès que le premier administrateur existe.

Installé en mode local (--no-auth), le service ne s’ouvre que depuis un lien de lancement à usage unique : service install en affiche un, et service open en affiche un nouveau chaque fois que vous en avez besoin (en tant qu’administrateur : il est produit à partir de launch.key, dans le dossier de données). Ouvrez-le dans votre propre navigateur, et non dans un navigateur élevé ; ce navigateur reste ensuite connecté tant qu’il conserve les données de ce site, six mois au plus après sa dernière utilisation.

Docker

L’image s’exécute sous un utilisateur sans privilèges, sur un système de fichiers racine en lecture seule, en mode équipe. Les données se trouvent dans le volume /data. Les machines hors ligne peuvent charger une archive d’image avec docker load -i. Le jeton de configuration du premier démarrage : docker exec <container> cat /data/setup-token. Le fichier compose publie le port sur la boucle locale de l’hôte uniquement (127.0.0.1:4321) ; pour servir d’autres machines, placez devant un proxy inverse HTTPS plutôt que de publier du HTTP en clair. Un proxy situé sur l’hôte atteint le conteneur depuis la passerelle du réseau compose : faites confiance à MM_TRUSTED_PROXIES=172.31.240.1, et non à 127.0.0.1.

À l’intérieur du conteneur, le serveur écoute sur toutes les adresses ; sans MM_ALLOWED_HOSTS, il ne répond donc qu’aux adresses IP et à localhost (chaque démarrage le signale). Tout ce qui l’atteint par un nom — un proxy qui transmet le nom public, un autre conteneur par le nom du service (un Prometheus qui interroge mongo-manager:4321), un service Kubernetes — reçoit une erreur 403 tant que ce nom n’est pas listé : MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

En mode local (MM_AUTH=0), le journal du conteneur nomme la commande qui affiche un lien, jamais un lien : docker exec <container> node /app/dist/cli.cjs open --no-open. Elle indique le port sur lequel le serveur écoute à l’intérieur du conteneur : s’il est publié sur un autre port de l’hôte (-p 127.0.0.1:8080:4321), remplacez le port du lien par celui de l’hôte avant de l’ouvrir.

Sur un serveur, placez devant un proxy inverse HTTPS qui le sert sous le nom mongo.example.com, et démarrez-le ainsi ; la dernière ligne lit le jeton de configuration. Terminez la configuration sans attendre : tant que le premier administrateur n’existe pas, quiconque détient le jeton peut le devenir. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES est l’adresse depuis laquelle un proxy situé sur l’hôte atteint le conteneur : la passerelle du réseau Docker, en général 172.17.0.1 sur le réseau bridge par défaut (docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}' l’affiche). Sans elle, chaque requête semble venir de la passerelle, si bien que le journal d’audit et les bannissements de connexion ne distinguent plus les utilisateurs. Une fois MM_ALLOWED_HOSTS défini, seuls les noms qu’il liste sont acceptés : ajoutez-y 127.0.0.1 pour continuer à ouvrir http://127.0.0.1:4321 sur l’hôte. --read-only, --tmpfs /tmp, --cap-drop ALL et no-new-privileges sont le durcissement qu’applique le fichier compose.

Joindre MongoDB depuis le conteneur

Dans un conteneur, localhost désigne le conteneur lui-même : mongodb://localhost:27017 échoue donc avec ECONNREFUSED, même si MongoDB tourne sur la même machine.

  • MongoDB dans un autre conteneur : placez les deux sur un même réseau Docker (docker network create mm, puis docker network connect mm mongo-manager et docker network connect mm my-mongodb, ou --network mm au démarrage) et connectez-vous à mongodb://my-mongodb:27017.
  • MongoDB sur l’hôte, Docker Desktop (Windows, macOS) : mongodb://host.docker.internal:27017.
  • MongoDB sur l’hôte, Linux : lancez Mongo Manager avec --network host (localhost est alors l’hôte ; gardez-le privé avec -e MM_HOST=127.0.0.1, derrière le proxy, approuvé en tant que 127.0.0.1), ou ajoutez --add-host=host.docker.internal:host-gateway. Cette seconde option n’atteint qu’un MongoDB qui écoute sur l’adresse de la passerelle du bridge : ni un MongoDB lié au 127.0.0.1 de l’hôte, ni un conteneur publié là seulement (-p 127.0.0.1:27018:27017) ; pour ceux-là, utilisez un réseau partagé ou le réseau de l’hôte.
  • Un jeu de réplicas dont les membres s’appellent localhost:27017 renvoie le pilote vers localhost : ajoutez ?directConnection=true.

Mises à jour

Un administrateur voit la version installée sur la page À propos de Mongo Manager, dans le menu du compte. Vérifier maintenant demande à GitHub la dernière version publiée ; Rechercher les mises à jour automatiquement le fait une fois par jour. La vérification quotidienne est désactivée jusqu’à ce qu’un administrateur l’active, et rien sur vous, votre serveur ou vos données ne l’accompagne : seul le numéro de la dernière version revient. Les brouillons et les préversions ne sont jamais proposés.

Une version n’est proposée que si son SHA256SUMS porte la signature de Mongo Manager (Ed25519) et que son release.json y figure. Mettre à jour télécharge la version dans app/ du répertoire de données, vérifie chaque octet avec les sommes de contrôle signées, copie la base de données, puis redémarre. À chaque démarrage, chaque fichier de la version qui s’exécute est vérifié à nouveau. Une version trouvée modifiée ne s’exécute pas : elle est téléchargée à nouveau (sauf si les mises à jour sont désactivées), ou la version à partir de laquelle elle a été installée s’exécute, et la page À propos de Mongo Manager le dit. Rien d’autre n’est téléchargé au démarrage. Une nouvelle version qui ne démarre pas en une minute est annulée : la copie de la base de données est remise en place, la version précédente fonctionne à nouveau, et la page À propos de Mongo Manager le dit.

  • Paquet npm, binaire autonome, service système : le programme installé reste tel quel et démarre la version vérifiée la plus récente conservée dans app/. Un service installé par une version antérieure est réinstallé une fois (mongo-manager service install) : son unité démarre alors avec --isolate-account, afin que les autres processus du compte du service soient arrêtés avant qu’une version mise à jour soit vérifiée et démarre. Sous Linux et macOS, cela ne se fait que pour le compte que crée service install, jamais en root ; sous Windows, où LocalService est partagé avec d’autres services, seuls les programmes de cette installation et les processus propres au programme précédent sont arrêtés.
  • Docker : la nouvelle version est conservée dans le volume /data et s’exécute dans l’image que vous avez. Avant qu’elle soit vérifiée et démarre, les autres processus de son utilisateur dans le conteneur sont arrêtés (jamais quand le conteneur s’exécute en root ou partage les processus de l’hôte). Quand une version a besoin d’une image plus récente (son Node.js ou ses paquets système ont changé), la page À propos de Mongo Manager affiche plutôt les commandes : docker pull ghcr.io/mongo-manager/mongo-manager:<version>, ou docker compose pull && docker compose up -d. Une image de plus de 90 jours est aussi signalée : récupérez-en une plus récente pour les correctifs de sécurité de Node.js et du système.
  • Depuis le code source : mettez à jour avec git.
  • La première version qui se met à jour elle-même s’installe à la main.
  • MM_UPDATES : off (ou 0, false) désactive entièrement les mises à jour : ni vérification, ni réglage, ni bouton, ni requête, et la page À propos de Mongo Manager le dit. Par défaut : activé, la vérification quotidienne restant désactivée jusqu’à ce qu’un administrateur l’active.
  • MM_UPDATE_PROXY : un proxy HTTP(S) par lequel GitHub est joint, comme MM_BACKUP_PROXY. Par défaut : aucun.

Derrière un proxy inverse

  • Ne faites confiance qu’au proxy : --trusted-proxies 127.0.0.1. Sans cela, le serveur ne peut pas savoir qu’une requête est arrivée en HTTPS, et les cookies de session ne sont donc pas marqués Secure ; un démarrage en mode équipe le signale, et signale aussi lorsque des connexions traverseraient le réseau en HTTP non chiffré.
  • Nommez l’hôte public : --allowed-hosts mm.example.com.
  • Servez l’application sous un sous-chemin avec --base-path /mm/.
  • Chaque adresse cliente peut effectuer 600 requêtes d’API par minute ; relevez cette limite avec MM_API_RATE_LIMIT (60–100000) lorsque beaucoup de personnes partagent une même adresse.
  • Au plus 1000 connexions peuvent être ouvertes à la fois (MM_MAX_CONNECTIONS, 16–100000), dont 256 au plus depuis une même adresse (MM_MAX_CONNECTIONS_PER_IP, 2–100000) ; une connexion au-delà est fermée, et le journal le signale une fois par minute et par adresse. Un navigateur garde environ six connexions ouvertes : lorsque beaucoup de personnes atteignent Mongo Manager depuis une même adresse — derrière un NAT, un VPN ou Docker Desktop —, relevez MM_MAX_CONNECTIONS_PER_IP. Derrière des proxys de confiance, seul le total s’applique : toutes les connexions viennent du proxy, qui doit limiter lui-même ses propres clients.
  • Les fichiers importés et exportés se trouvent sous <data directory>/transfer : MM_TRANSFER_MAX_UPLOAD est le plus gros envoi en Mio (1024 par défaut, 1–65536), MM_TRANSFER_QUOTA l’espace que chaque utilisateur peut occuper en Mio (5120 par défaut, 16–1048576), MM_TRANSFER_TOTAL_QUOTA ce que tous les utilisateurs ensemble peuvent occuper en Mio (51200 par défaut, ou MM_TRANSFER_QUOTA lorsqu’il est plus grand ; 16–16777216), MM_TRANSFER_TTL_HOURS la durée de conservation d’un fichier (24 par défaut, 1–720), et MM_TRANSFER_MAX_JOB_HOURS la durée maximale d’un import ou d’un export (6 par défaut, 1–72). Prévoyez sur ce disque la place du total, ou du quota multiplié par le nombre de personnes qui transfèrent des fichiers si ce produit est plus petit.

Paramètres et variables d’environnement

Chaque paramètre du serveur peut être donné comme option de ligne de commande, comme variable d’environnement ou dans un fichier de configuration JSON indiqué par --config ou MM_CONFIG. La ligne de commande l’emporte sur l’environnement, et l’environnement sur le fichier. Un interrupteur accepte 1/0, true/false, yes/no ou on/off. Les paramètres de chaque fonctionnalité figurent dans sa propre section ci-dessous.

Variable Option Rôle
MM_WEB_PORT -p, --web-port Port de l’interface web (4321 par défaut).
MM_HOST --host Adresse d’écoute (127.0.0.1 par défaut). Une adresse réseau exige le mode équipe, ou MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Mode équipe : utilisateurs, rôles et connexion (désactivé par défaut).
MM_DATA_DIR --data-dir Le répertoire de données (~/.mongo-manager par défaut).
MM_CONFIG --config Un fichier de configuration JSON. Sous Linux et macOS, un fichier qui contient un secret ne doit pas être lisible par les autres utilisateurs, sinon le serveur le refuse.
MM_SECRET_KEY La clé de chiffrement, à la place du fichier secret.key du répertoire de données.
MM_OPEN --open Ouvre le navigateur au démarrage (activé par défaut) : en mode local, sur une adresse de bouclage, lorsque le démarrage se fait depuis un terminal.
MM_URI --uri Une connexion créée uniquement au tout premier démarrage. Utilisez la variable pour une chaîne de connexion contenant un mot de passe : les autres utilisateurs peuvent voir les lignes de commande.
MM_READ_ONLY --read-only Aucune connexion ne peut modifier les données, quel que soit son propre paramètre.
MM_TRUSTED_PROXIES --trusted-proxies Adresses ou plages CIDR de proxys dont les en-têtes X-Forwarded-* sont crus.
MM_ALLOWED_HOSTS --allowed-hosts Les seuls noms d’hôte auxquels le serveur répond. Sans ce paramètre, il répond aux noms de bouclage lorsqu’il écoute sur la boucle locale, et sinon aux seuls noms de bouclage et adresses IP, jamais à un autre nom (protection contre le DNS rebinding ; le démarrage l’indique). Indiquez ici chaque nom d’hôte par lequel les utilisateurs l’ouvrent.
MM_BASE_PATH --base-path Sert l’application sous un sous-chemin, tel que /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Autorise une adresse réseau sans mode équipe. Quiconque l’atteint dispose d’un accès complet.
MM_LOG_LEVEL --log-level fatal, error, warn, info (par défaut), debug, trace ou silent.
MM_LOG_FILE --log-file Ajoute le journal JSON à ce fichier au lieu de la sortie standard. Le fichier est rendu privé (mode 0600 ; sous Windows, l’accès de tous les utilisateurs est retiré : ce compte, SYSTEM et Administrators le conservent) et renouvelé à 10 Mio, la partie précédente étant conservée sous <file>.1. Un chemin qui est un lien, un fichier portant d’autres noms (liens physiques) ou qui n’est pas un fichier ordinaire est refusé, et le démarrage échoue en le disant : supprimez-le ou renommez-le, ou indiquez un autre fichier de journal. Une ligne qui ne peut pas être écrite (disque plein) est abandonnée et signalée une fois sur la sortie d’erreur standard. Les requêtes sont journalisées par leur chemin, chaque valeur de requête et l’id d’un fichier GridFS étant écrits ***.
MM_REQUIRE_ADMIN_2FA Chaque administrateur doit configurer la connexion à deux facteurs avant toute autre chose ; elle ne peut ensuite plus être désactivée dans l’application. Sans ce paramètre, un administrateur peut exiger la même chose dans l’application.
MM_REQUIRE_2FA Chaque utilisateur, quel que soit son rôle, doit configurer la connexion à deux facteurs avant toute autre chose ; elle ne peut ensuite plus être désactivée dans l’application. Sans ce paramètre, un administrateur peut exiger la même chose dans l’application.
MM_METRICS_TOKEN Active les métriques Prometheus à l’adresse <base path>metrics, lues avec ce jeton comme jeton bearer (32 caractères au moins). Les chiffres ne nomment aucun utilisateur, aucune connexion, aucune base de données ni aucune collection.
MM_GRIDFS_MAX_MB Le plus gros fichier envoyé vers GridFS, en Mo (512 par défaut, 1–10240).
MM_MODEL_MAX_DOCS Le nombre total de documents qu’un modèle de données (la section Modèle d’une base de données) peut échantillonner (20000 par défaut, 100–1000000) : avec beaucoup de collections, l’échantillon de chacune est réduit, et la section l’indique.
MM_ALLOW_KERBEROS Mode équipe : autorise les connexions Kerberos (GSSAPI) (désactivé par défaut). Elles se connectent avec le ticket Kerberos du compte sous lequel le serveur s’exécute — chaque utilisateur d’une telle connexion se connecte sous ce compte. Voir Sécurité.
MM_ALLOW_WORKLOAD_IDENTITY Mode équipe : autorise les connexions OIDC à utiliser l’identité de charge de travail de la machine (Azure, GCP, Kubernetes) lorsqu’elle est choisie sur la connexion (désactivé par défaut).
MM_OIDC_DEVICE_FLOW Connexion OIDC avec un code (le device flow), pour les fournisseurs d’identité qui ne peuvent pas renvoyer le navigateur vers ce serveur. Celui qui approuve le code se connecte : ce mode est donc désactivé en mode équipe tant qu’il n’est pas activé ici ; il est activé en mode local.
MM_OIDC_PRIVATE_NETWORKS Réseaux privés (CIDR séparés par des virgules) sur lesquels les fournisseurs d’identité OIDC peuvent se trouver ; le http en clair n’y est autorisé que là. Sans ce paramètre, ils doivent être des adresses https publiques.
MM_CRYPT_SHARED_LIB_PATH Le chemin absolu de la bibliothèque crypt_shared (mongo_crypt_v1) pour le chiffrement côté client. En mode équipe, c’est la seule qui soit chargée.
MM_KMS_PRIVATE_NETWORKS Réseaux privés (CIDR séparés par des virgules) sur lesquels les services de gestion de clés (un serveur KMIP sur site) peuvent se trouver. Sans ce paramètre, ils doivent être des adresses publiques.
MM_KMS_ALLOWED_HOSTS Hôtes de services de gestion de clés (séparés par des virgules, host ou host:port, port 443 par défaut) qu’une connexion peut atteindre en plus de ceux des fournisseurs eux-mêmes (AWS KMS, Azure Key Vault et Managed HSM avec la connexion Microsoft, Google Cloud KMS) et des points de terminaison que nomment ses paramètres : un point de terminaison VPC, un serveur KMIP. Tout autre hôte, ou un autre port, est refusé — la clé maître d’une clé de données ne peut pas envoyer le jeton KMS ailleurs.

Kerberos et chiffrement côté client (paquet npm)

Kerberos (GSSAPI) et le chiffrement côté client au niveau des champs / Queryable Encryption nécessitent des paquets natifs que Mongo Manager n’installe pas lui-même : son installation n’exécute le script d’installation d’aucun paquet. Pour les utiliser, installez les paquets à côté du paquet npm, puis redémarrez : 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager ne les charge que depuis le dossier global node_modules qui contient mongo-manager lui-même (vérifié par son chemin réel, jamais un dossier situé au-dessus), et seulement lorsqu’une connexion en a besoin pour la première fois ; le formulaire de connexion indique lequel manque et comment l’installer. Les binaires autonomes, l’image Docker (qui définit MM_DISTRIBUTION=docker) et la copie à partir de laquelle s’exécute un service Windows ne contiennent aucun module natif : ces deux fonctionnalités y indiquent qu’elles ne sont pas disponibles dans ce paquet — utilisez à la place le paquet npm, exécuté au premier plan. Le chiffrement automatique de Queryable Encryption exige aussi la bibliothèque crypt_shared (MM_CRYPT_SHARED_LIB_PATH) ou mongocryptd, ainsi que MongoDB Enterprise ou Atlas ; MongoDB Community ne fait que déchiffrer. MONGODB-OIDC n’exige aucun paquet : le fournisseur d’identité doit avoir <address><base path>oidc/callback de ce serveur comme adresse de redirection (ou une autre que nomme la connexion), et les utilisateurs peuvent se connecter avec un code là où cela n’est pas possible.

Installer comme application

Dans Chrome ou Edge, choisissez Installer Mongo Manager dans la barre d’adresse pour l’ouvrir dans sa propre fenêtre depuis votre bureau ou votre menu Démarrer.

Destinations de sauvegarde

  • MM_BACKUP_FOLDER_ROOTS : les dossiers que les destinations de type dossier du serveur peuvent utiliser, sous forme de chemins absolus séparés par le séparateur de chemins du système (: sous Linux et macOS, ; sous Windows), 16 au plus. Par défaut : aucun, si bien qu’aucune destination de type dossier ne peut être créée. Un chemin relatif arrête le serveur au démarrage. Donnez au compte du service l’accès en écriture à chaque racine, et gardez les racines en dehors du répertoire de données : une destination de type dossier située à l’intérieur est refusée. Chaque démarrage journalise une racine dans laquelle le serveur ne peut pas écrire. Pour le service Linux :
    • Son bac à sable ne lui permet d’écrire que dans son répertoire de données et dans les racines que nomment sa configuration et son fichier d’environnement au moment de l’installation : après les avoir modifiés, exécutez de nouveau sudo mongo-manager service install (il conserve les données, la configuration et la clé), et redémarrez le service après avoir créé une racine qui manquait. Les racines définies ailleurs, par exemple un Environment= dans un drop-in, l’installation ne les voit pas : leurs dossiers restent en lecture seule pour le service.
    • L’installation écarte une racine située sous /home, /root, /run/user, /tmp, /var/tmp ou /dev, que le service ne peut pas atteindre, et toute racine qui annulerait le bac à sable : celle qui contient un répertoire système (/, /var, /var/lib et analogues) ou qui se trouve dans /etc, /usr, /run ou un autre répertoire système (sous /var, seuls les dossiers situés dans /var/backups sont ouverts). Un dossier situé dans /srv, /opt ou un point de montage sous /mnt ou /media convient, pas ces dossiers eux-mêmes ; sur un système de fichiers amovible ou réseau, celui qui contrôle le disque ou le partage contrôle les dossiers qu’il contient, faites donc du point de montage lui-même la racine (un montage FUSE d’utilisateur dit ce qu’il veut de ses propriétaires et de ses liens). Une racine située dans une autre racine est dans le bac à sable par celle-ci. Lorsque /srv, /opt ou /mnt est lui-même un lien vers /var, comme sur les systèmes ostree (Fedora Silverblue, CoreOS), l’installation indique où mène une racine, et elle y est refusée : choisissez un dossier situé dans /var/backups.
    • Un lien est jugé d’après l’endroit où il mène, et l’unité nomme cet endroit ; un lien qui ne mène nulle part est écarté : pour un lien vers un dossier qui n’existe pas encore, créez ce dossier, puis exécutez de nouveau service install ; pour un lien qui tourne en boucle ou passe par un fichier, choisissez un autre dossier ou supprimez le lien. Gardez chaque dossier situé au-dessus d’une racine, ainsi que les dossiers où se trouvent les liens de son chemin (un lien dans la cible d’un lien compris), détenus par root et fermés à son groupe et aux autres, afin que personne ne puisse y placer un lien à la place d’un dossier ; dans un dossier où d’autres peuvent écrire, avec sticky bit ou non, faites détenir par root le dossier qu’il contient, et placez la racine à l’intérieur de celui-ci.
    • Une racine située sous un dossier que l’utilisateur du service pourrait modifier, n’importe où jusqu’à / et le long des liens de son chemin, est écartée : un dossier que cet utilisateur possède, ou dans lequel il peut écrire par l’un de ses groupes, une ACL ou en tant que n’importe qui, là où un processus s’exécutant sous cet utilisateur pourrait placer un lien vers /etc à la place d’un dossier. Cela comprend un lien situé dans une autre racine, dans laquelle le service écrit. L’installation, et doctor exécuté avec sudo, interrogent aussi le système : avec setpriv, ils exécutent test -w sous cet utilisateur, si bien que le noyau applique ses groupes (ceux que l’unité donne au service avec Group= ou SupplementaryGroups=, ceux d’un drop-in compris) et ses ACL. Sans setpriv, ou sans root, seuls les modes des dossiers et les groupes de l’utilisateur sont lus, et les deux commandes le disent. Ce que permettent les modes compte même là où une ACL le retire, si bien qu’un tel dossier écarte aussi ses racines.
    • L’installation demande à systemd sous quel compte s’exécute le service, tous les drop-ins étant lus. Un drop-in qui l’exécute sous un utilisateur autre que --user (ou sous root), avec DynamicUser=yes et aucun compte de ce nom, avec un Group= autre que celui de l’utilisateur, ou avec un groupe que le système ne connaît pas (systemd refuse alors de le démarrer) arrête l’installation avant toute modification du répertoire de données et de la configuration ; elle en donne la raison et laisse le service arrêté et désactivé. Un groupe dont la recherche échoue, ou un systemd qui ne peut pas être interrogé, écarte toutes les racines.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json vérifie le service installé (mongo-manager doctor seul vérifie votre propre répertoire de données, et indique que le service n’est pas ce qu’il a vérifié). Il vérifie chaque racine : qu’elle existe, qu’elle est un dossier dans lequel le serveur peut écrire, qu’elle se trouve dans le bac à sable, et qu’elle ne se trouve pas dans le répertoire de données ; il nomme aussi un dossier dans lequel le bac à sable permet au service d’écrire et qu’aucune racine ne nomme plus, ou qui mène à une racine ou au répertoire de données par un lien que quelqu’un d’autre que root peut modifier, et il avertit d’un service qui s’exécute sous root, d’un groupe que personne n’a ou dont la recherche échoue, et de DynamicUser=yes sans compte de ce nom. Il vérifie les racines que nomment la configuration et le fichier d’environnement du service, ce qui explique qu’il exige sudo : seul root peut lire le fichier d’environnement, où se trouve aussi la clé secrète du service. Il vérifie l’accès en écriture sous l’utilisateur du service ; exécuté sous root, il lit à la place le propriétaire et le mode de la racine pour l’utilisateur qui possède le répertoire de données, et s’en remet au système lorsque cet utilisateur peut y écrire. Les dossiers situés au-dessus des racines sont jugés pour l’utilisateur sous lequel l’unité exécute le service (son User=).
  • MM_BACKUP_PRIVATE_NETWORKS : les plages privées que les destinations peuvent atteindre, sous forme d’une liste de 64 CIDR au plus séparés par des virgules (par exemple 10.0.5.0/24) ; le HTTP en clair y est autorisé. Par défaut : aucune. Les plages de bouclage, 10/8, 172.16/12, 192.168/16, CGNAT (100.64.0.0/10) et unique-local (fc00::/7) sont acceptées. Une plage publique arrête le serveur au démarrage, tout comme une plage située dans une plage de lien local ou de métadonnées cloud (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200), sous quelque forme que ce soit, IPv4 mappée et NAT64 compris ; le message nomme la plage. Ces adresses ne peuvent jamais être atteintes, même à l’intérieur d’une plage listée.
  • MM_BACKUP_PROXY : un proxy HTTP(S) par lequel les destinations sont atteintes, tel que http://proxy.corp:3128 ou https://user:password@proxy.corp ; ni chemin ni requête. Par défaut : aucun (aucune variable de proxy d’environnement n’est jamais lue). Mongo Manager résout et vérifie toujours lui-même l’adresse de chaque destination et demande au proxy de se connecter à cette adresse, si bien que les règles d’adresses ci-dessus s’appliquent à travers le proxy ; TLS s’exécute de bout en bout jusqu’à la destination, dont le certificat est vérifié comme sans proxy. Les destinations situées dans MM_BACKUP_PRIVATE_NETWORKS sont atteintes directement. Un proxy situé à une adresse de lien local ou de métadonnées arrête le serveur au démarrage. Gardez le mot de passe du proxy hors des historiques de shell partagés : il fait partie de l’adresse. Seules les destinations de sauvegarde l’utilisent : les canaux d’alerte (e-mail et webhooks), les fournisseurs d’IA et les plug-ins ne passent jamais par lui. À savoir avant de choisir un proxy : un proxy http:// reçoit en clair son nom d’utilisateur et son mot de passe (Basic), préférez donc https:// ou un proxy situé dans un réseau de confiance ; un proxy qui n’autorise CONNECT que vers des noms d’hôte listés refuse ces connexions, puisqu’on lui demande une adresse IP ; le certificat d’un proxy https:// doit être signé par une autorité que Node.js reconnaît (sa liste intégrée, ou une autorité ajoutée avec NODE_EXTRA_CA_CERTS) : aucune autorité propre ne peut être indiquée.
  • MM_BACKUP_DEST_PART_MB : la taille des parties d’envoi, de 16 à 512 Mio (64 par défaut).
  • MM_BACKUP_DRILL_MAX_MB : le maximum qu’un test de restauration écrit, en Mio. Par défaut : aucun — un test reste sous la moitié de l’espace disque libre que MongoDB indique (celui du shard le plus plein, à travers un mongos). Là où MongoDB ne l’indique pas (niveaux partagés d’Atlas), les tests ne s’exécutent que si ce paramètre est défini.
  • MM_BACKUP_DEST_TRANSFERS : les envois et téléchargements simultanés sur chaque destination, de 1 à 8 (2 par défaut). Les suivants attendent, ce qu’affiche « En attente de » cette destination dans la liste des tâches.

Sauvegardes planifiées

  • MM_BACKUP_SCHEDULES : le planificateur, activé par défaut. 0 le désactive : les planifications conservent leurs paramètres, rien ne s’exécute, et l’onglet Sauvegardes planifiées indique que la planification est désactivée. Les exécutions qu’un serveur arrêté a laissées inachevées sont clôturées au démarrage.
  • MM_BACKUP_SCHEDULE_CONCURRENCY : les exécutions planifiées simultanées, de 1 à 8 (2 par défaut). Les exécutions suivantes attendent jusqu’à six heures.

Suivi des modifications

  • MM_WATCH : les flux de modifications (change streams), activés par défaut. 0 les désactive : les sections Suivi indiquent que le suivi est désactivé, et rien n’est ouvert sur MongoDB.
  • MM_WATCH_MAX_FEEDS : les flux en direct simultanés sur ce serveur, de 1 à 500 (50 par défaut). Chaque utilisateur peut en avoir 5 et chaque fenêtre de navigateur 3. Chaque flux détient un curseur de flux de modifications sur MongoDB.
  • Le suivi exige un jeu de réplicas, un cluster partitionné ou un déploiement à charge équilibrée, et l’utilisateur de base de données de la connexion a besoin de changeStream et de find sur ce qui est suivi. Voir Suivi des modifications.

Synchronisation en continu

  • MM_LIVE_SYNC : les synchronisations en continu entre connexions, activées par défaut. 0 les désactive : les synchronisations en cours attendent en indiquant la raison, et rien n’est lu ni écrit ; les nouvelles sont refusées. Une fois réactivées, elles reprennent là où elles en étaient.
  • MM_LIVE_SYNC_MAX : les synchronisations en continu non terminées sur ce serveur, de 1 à 100 (10 par défaut). Chaque utilisateur peut en avoir 3. Chaque synchronisation en cours détient un flux de modifications sur sa source et garde les deux connexions ouvertes.
  • La source doit être un jeu de réplicas, un cluster partitionné ou un déploiement à charge équilibrée (MongoDB 6.0 ou ultérieur) ; une copie susceptible de durer plus longtemps que l’oplog de la source demande une confirmation. Voir Synchronisation en continu.

Alertes

  • MM_ALERTS (fichier de configuration : alerts.enabled) : les alertes, activées par défaut. 0 les désactive : rien n’est évalué ni envoyé, et la page Alertes indique que les alertes sont désactivées.
  • MM_ALERTS_PRIVATE_NETWORKS (fichier de configuration : alerts.privateNetworks, une liste) : les réseaux que les serveurs de messagerie et les webhooks des alertes peuvent atteindre en plus des adresses publiques, sous forme d’une liste de 64 CIDR au plus séparés par des virgules (par exemple 10.0.5.0/24). Par défaut : aucun. Le http en clair vers un webhook n’est autorisé qu’à l’intérieur de ces réseaux. Les mêmes plages sont acceptées et refusées que pour MM_BACKUP_PRIVATE_NETWORKS : les adresses de lien local et de métadonnées cloud ne peuvent jamais être atteintes.
  • Dans un fichier de configuration : "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. Voir Administration du serveur.

Le shell avancé

  • Désactivez-le entièrement avec --no-shell (ou MM_SHELL_ENABLED=0).
  • Limites : MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. Un shell que sa page retient reste ouvert aussi longtemps qu’il n’est pas utilisé, comme dans Compass ; un shell qu’aucune page ne retient se ferme deux minutes après le départ de sa page. La limite d’inactivité est désactivée (0) tant que vous ne la définissez pas (10000 à 86400000 ms) ; un shell vit 12 heures au plus, sauf si vous définissez une autre durée de vie (60000 à 86400000 ms, ou 0 pour aucune). Les shells maintenus ouverts comptent dans MM_SHELL_MAX_TOTAL jusqu’à la fermeture de leurs pages ; sur un serveur que beaucoup de personnes partagent, définissez MM_SHELL_IDLE_MS afin que les shells laissés ouverts et inutilisés soient libérés. Lorsque la connexion est activée, un shell prend aussi fin avec la session de son utilisateur, ainsi que lorsque le rôle de l’utilisateur change ou que son compte est désactivé.
  • MM_SHELL_RSS_MB : la mémoire que peut détenir le processus d’un shell, de 128 à 16384 Mo (384 par défaut). Le serveur la mesure lui-même auprès du système d’exploitation (sous Windows avec tasklist, sous macOS avec ps) et redémarre un shell qui la dépasse ; les variables du shell sont perdues. Un shell qui ne répond plus pendant 15 secondes alors qu’aucune commande ne s’exécute est lui aussi redémarré. MM_SHELL_OUTPUT_MB : la sortie d’une commande, de 1 à 64 Mo (5 par défaut) ; le reste est coupé. MM_SHELL_COMMANDS_PER_SECOND : les commandes par shell et par seconde, de 1 à 1000 (20 par défaut).
  • Sur un serveur POSIX exécuté sous root, le processus du shell passe à MM_SHELL_UID/MM_SHELL_GID (65534 par défaut) ; n’exécutez pas le service sous root.

Assistant IA

  • MM_AI : l’assistant IA, activé par défaut ; il n’apparaît qu’une fois qu’un administrateur a ajouté un fournisseur (Paramètres → Assistant IA). 0 le masque partout et refuse les requêtes.
  • MM_AI_PRIVATE_NETWORKS : les réseaux (CIDR, séparés par des virgules) sur lesquels un fournisseur peut se trouver en plus des adresses publiques, par exemple un Ollama à 10.0.0.5 ; le http en clair uniquement là. Les adresses de métadonnées cloud et de lien local ne sont jamais atteignables. En mode local, cette machine est toujours autorisée.
  • MM_AI_PER_MINUTE (10 par défaut, 1–120) et MM_AI_PER_DAY (200 par défaut, 1–10 000) : les requêtes par personne. MM_AI_MAX_CONCURRENT (8 par défaut, 1–64) : les requêtes simultanées sur le serveur ; chaque personne peut en avoir 2. MM_AI_AGENT_PER_MINUTE (30 par défaut, 1–120) : les requêtes supplémentaires d’un agent vers le fournisseur au sein d’un même message, par personne et par minute (elles comptent aussi pour la journée).
  • MM_AI_CHAT_DAYS (30 par défaut, 0–365) : la durée de conservation d’une conversation après son dernier message. 0 ne garde les conversations qu’en mémoire (12 heures) et supprime, au démarrage du serveur, les conversations enregistrées sous un paramètre antérieur.

Plug-ins

  • MM_PLUGINS : les plug-ins, activés par défaut. Chacun a encore besoin de l’approbation d’un administrateur, après son analyse de sécurité. 0 n’en trouve, n’en installe et n’en exécute aucun (voir Plug-ins).
  • MM_PLUGINS_GITHUB : l’installation d’un plug-in depuis la version publiée d’un dépôt GitHub public, désactivée par défaut (les plug-ins s’installent par envoi ou depuis un dossier) ; 1 l’autorise. Le serveur contacte alors api.github.com, github.com et les hôtes de ressources de versions de GitHub, en https, sans rien envoyer qui lui soit propre. Désactivé, un serveur ne contacte jamais GitHub. Le serveur se connecte directement à GitHub : les paramètres de proxy HTTP ne sont pas utilisés, si bien qu’un serveur qui ne peut sortir que par un proxy installe les plug-ins par envoi. Un service système le lit dans son fichier config.json sous la forme "pluginsGithub": true (Linux /etc/mongo-manager/config.json, Windows %ProgramData%\Mongo Manager\config.json, macOS /Library/Application Support/Mongo Manager/config.json) ; redémarrez ensuite le service.
