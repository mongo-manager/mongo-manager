Créer des plug-ins

Un plug-in ajoute une vue, une action ou une page à Mongo Manager : une carte des lieux d’une collection, un graphique, un détecteur de doublons, un traducteur depuis SQL. Ce guide s’adresse à celles et ceux qui en développent un. Il décrit les fichiers qui composent un plug-in, tout ce qu’il peut demander à l’application, les règles qu’elle applique, ainsi que la manière de l’empaqueter, de le tester et de le publier. Les administrateurs installent et approuvent les plug-ins sur la page Plug-ins ; consultez Sécurité pour le modèle d’approbation. Cette page les liste tous et permet de restreindre la liste aux plug-ins activés, à ceux qui nécessitent un administrateur (en attente d’approbation, modifiés ou inutilisables) ou aux plug-ins désactivés, à une source, ainsi qu’à ceux que trouve une recherche par nom, description, identifiant, version, autorisations demandées ou ce qu’ils ajoutent.

Ce qu’est un plug-in

Un plug-in est un dossier de fichiers statiques : une page HTML, ses scripts, ses styles, ses images et ses polices, ainsi qu’un manifeste nommé mongo-manager-plugin.json qui indique ce qu’il ajoute et ce qu’il peut faire. L’application affiche la page dans un cadre isolé (sandbox) et la page ne communique avec l’application que par messages : elle demande des documents et l’application répond en tant qu’utilisateur connecté, avec les droits de cet utilisateur et le masquage de l’application.

  • Aucun code serveur. Rien d’un plug-in ne s’exécute sur le serveur. Le serveur stocke ses fichiers, les vérifie et les sert au cadre.
  • Aucun accès réseau. La page ne peut rien récupérer à aucune adresse, pas même du serveur dont elle provient. Elle n’a ni cookies, ni stockage, ni accès à la page de l’application. Deux issues restent du ressort du navigateur : WebRTC n’est bloqué que par les navigateurs qui appliquent la directive webrtc de la politique — les navigateurs basés sur Chromium (Chrome, Edge) l’ignorent à partir de la version 149, et il ne faut pas compter non plus sur Firefox — si bien que, sur ces navigateurs, un plug-in peut encore envoyer ce qu’il lit via WebRTC ; et une directive de préchargement (dns-prefetch, preconnect) peut déclencher la résolution d’un nom. Le cadre demande au navigateur de ne rien précharger et l’analyse signale ces deux cas comme des risques élevés — mais l’analyse lit le texte des fichiers à la recherche de motifs connus : un code écrit pour lui échapper n’est pas détecté. N’approuvez que des plug-ins de confiance.
  • Rien sans approbation. Un plug-in ne s’exécute qu’après qu’un administrateur a approuvé ses fichiers exacts et les autorisations qu’il demande. Toute modification de ses fichiers exige une nouvelle approbation.
  • Les modifications passent par l’utilisateur. Un plug-in qui peut modifier des documents le demande ; l’application présente la modification dans sa propre boîte de dialogue et l’utilisateur décide. Une requête ou un pipeline préparé par un plug-in est placé dans les éditeurs de l’utilisateur, où rien ne s’exécute tant que l’utilisateur ne le lance pas.

Mongo Manager est livré avec plusieurs plug-ins qui lui sont propres (Map, Charts, Schema health, Duplicate finder, Value search, References, Document diff, SQL to MongoDB, Time hints, Binary preview, Data dictionary, Local time, Log analyzer, Test data, Reshape, Anonymiser, Search playground, Shard key analyzer, Storage report, Validation check, Legacy UUIDs, Date filters, Index script, Expiry (TTL), Personal data finder, Document size). Ils s’exécutent dans le même bac à sable, communiquent par le même bridge et sont analysés de la même manière que les vôtres ; faisant partie du code de l’application, leur approbation ne demande jamais leur identifiant (voir Versions et approbation). Les plug-ins peuvent être désactivés pour tout un serveur avec MM_PLUGINS=0 (voir Déploiement).

Démarrage rapide

Partez du modèle de départ : sur la page Plug-ins, sous Créer votre propre plug-in, choisissez Télécharger le modèle de départ (.zip) (c’est aussi le dossier packages/plugins/starter du code source de Mongo Manager). Il s’agit d’un plug-in complet en JavaScript simple, sans étape de compilation ni dépendances : un onglet de collection et une page de la barre latérale qui listent les documents d’une collection.

  1. Décompressez-le, ou copiez le dossier, dans un nouveau dépôt qui vous appartient.
  2. Dans mongo-manager-plugin.json, modifiez id, name, author et repository. L’identifiant doit être unique : il nomme le dossier du plug-in sur chaque serveur.
  3. Écrivez votre page dans main.js et style.css.
  4. Essayez-le sur votre propre serveur : node scripts/pack.mjs --folder ~/.mongo-manager/plugins, puis Plug-ins → Analyser à nouveau, examinez l’analyse et approuvez-le. Voir Test sur votre propre serveur.
  5. Empaquetez-le avec node scripts/pack.mjs, qui écrit <id>-<version>.tgz, et joignez ce fichier à une release GitHub. Voir Publication sur GitHub.

Le modèle de départ contient aussi des fichiers d’instructions pour les assistants de programmation IA (CLAUDE.md, AGENTS.md, GEMINI.md et .github/copilot-instructions.md) ; voir Développer avec un assistant IA.

Fichiers et arborescence

hello-documents/
  mongo-manager-plugin.json   the manifest (required, at the top)
  index.html                  the entry page every contribution opens
  main.js                     the page's script (an ES module)
  style.css                   the page's styles
  README.md                   shown to administrators on the plugin's details page
  README.tr.md, README.zh.md  the same in another language of the app (optional)
  scripts/pack.mjs            packaging (not part of the plugin: left out of the archive)
  CLAUDE.md, AGENTS.md, ...   AI assistant files (left out of the archive)

Les règles de l’application pour les fichiers d’un plug-in :

  • Au plus 500 fichiers et 25 Mo au total ; le manifeste, au plus 64 Ko.
  • Chaque chemin est relatif et simple : chaque segment commence par une lettre, un chiffre, _ ou - et ne contient que des lettres, des chiffres, ., _ et -, sur 100 caractères au plus ; 16 niveaux de profondeur au plus et 240 caractères au total. Aucun fichier ni dossier caché (un nom commençant par .), aucune espace, aucun nom de périphérique (con, nul, com1...), ni __proto__, constructor ou prototype.
  • Uniquement des fichiers et des dossiers : les liens, les jonctions et les fichiers spéciaux rendent le plug-in inutilisable.
  • Pas deux chemins qui ne diffèrent que par la casse.
  • Les fichiers sont servis avec un type déduit de leur extension : html, js, mjs, css, json, map, txt, svg, png, jpg, jpeg, gif, webp, avif, ico, woff, woff2, ttf, otf. Tout le reste est servi comme des octets et ne s’exécute jamais.

Le manifeste

mongo-manager-plugin.json est vérifié strictement : un champ inconnu, un type incorrect ou une valeur hors limites rend le plug-in inutilisable, et la page Plug-ins indique quel champ est en cause. Les textes lus par une personne (noms, titres, notes) ne peuvent contenir ni caractères de contrôle, ni caractères qui masquent ou inversent le texte.

  "entry": "index.html",

  "author": { "name": "Your Name", "url": "https://example.com" },

Champ Obligatoire Règles
id oui Lettres minuscules et chiffres, séparés par des tirets (geojson-map), 64 caractères au plus. Il doit être identique au nom du dossier du plug-in. L’identifiant d’un plug-in livré avec Mongo Manager ne peut pas être utilisé, pas plus qu’un identifiant qui se lit comme un nom réservé par l’application (voir ci-dessous).
name oui Texte localisé, 60 caractères au plus : { "en": "...", "tr": "..." }. Aucun caractère invisible (largeur nulle, balise, sélecteur de variante — ceux propres à un emoji sont acceptés), et jamais un nom qui se lit comme les messages propres de l’application : Mongo Manager (ou un nom qui commence ainsi), MongoDB, System, Session, Security, Admin, Server, Update et similaires, dans n’importe quelle langue de l’application, comparés tels qu’ils se lisent, sans tenir compte de la casse, des espaces, des accents ni des lettres qui se ressemblent. Dans chaque mot, les lettres sont toutes latines ou aucune ne l’est (jamais du grec et du cyrillique ensemble), et aucune parenthèse ne contient ce qui se lit comme un identifiant ((value-search) ; (beta) est accepté). L’application affiche les messages et les questions d’un plug-in avec son identifiant à côté de son nom.
version oui Gestion sémantique des versions : major.minor.patch, éventuellement avec une préversion (1.2.0-beta.1), 64 caractères au plus.
description non Texte localisé, 300 caractères au plus.
entry oui La page que toute contribution ouvre : un chemin simple vers un fichier .html du plug-in.
permissions non Parmi documents:read, documents:write, collection:read, database:read, chacune au plus une fois. Par défaut : aucune. Voir Autorisations.
contributes non collectionTabs, documentActions, sidebarPanels et cellRenderers : des listes de 5 éléments au plus chacune, aux identifiants uniques dans une liste. Voir Points de contribution.
settings non 10 au plus, par clé (une lettre, puis des lettres et des chiffres, 32 caractères au plus) : { "type": "url" | "text" | "boolean", "title": localized text of at most 60 }. Les administrateurs définissent les valeurs ; la page les lit dans le contexte.
author non { "name": text of at most 80, "url": an https address (optional) }.
homepage, repository non Une adresse https:// avec un hôte, 300 caractères au plus, sans identifiants, sans espaces ni barres obliques inverses.
license non Une expression SPDX, 40 caractères au plus : MIT, Apache-2.0 OR MIT.
publishedAt non Un jour qui existe, YYYY-MM-DD, entre 1900 et 2100.
changelog non 50 entrées au plus { "version", "date": "YYYY-MM-DD", "notes": localized text of at most 1000 } ; chaque version au plus une fois et aucune postérieure à la version du manifeste.

Un texte localisé est un objet contenant en (obligatoire) et, facultativement, l’une des autres langues de l’application : tr, zh (chinois simplifié), ja, es, pt (portugais brésilien), ko, de, fr et ru ; l’anglais s’affiche lorsque la langue du lecteur manque. Une contribution est { "id", "title": localized text of at most 40, "icon" } : son identifiant est une lettre minuscule suivie de lettres minuscules, de chiffres et de tirets, 32 caractères au plus, et son icône l’une des suivantes : map, chart, table, file, image, globe, layers, puzzle, book, wand, shapes, scroll, code, calendar, hourglass, shield, fingerprint, ruler (les icônes propres à l’application : un plug-in n’en apporte aucune). Un moteur de rendu de cellule est plutôt { "id", "match" }, avec un "display" facultatif : inline (par défaut) ou tooltip.

Un paramètre url doit être une adresse https sans identifiants (http simple uniquement pour cet ordinateur : localhost, 127.0.0.1 ou [::1]) ; son schéma, son hôte et son port sont ajoutés aux images que le cadre peut charger (pour des tuiles de carte : un {s}. en tête devient n’importe quel sous-domaine, uniquement devant un nom d’au moins deux parties, jamais devant une adresse IP). L’adresse d’une image peut transporter des données : le plug-in peut envoyer ce qu’il lit à ce serveur, et l’approbation ainsi que le paramètre le signalent. Un paramètre text contient 500 caractères au plus. Tous les utilisateurs du plug-in peuvent lire ses paramètres : ne demandez jamais de secret. Le serveur les stocke chiffrés avec sa clé, comme toute autre valeur enregistrée.

Points de contribution

Chaque contribution ouvre la même page d’entrée. La page apprend laquelle elle est grâce au fragment de l’adresse, #<kind>=<id> (par exemple #collectionTab=list), et grâce à contribution dans le contexte.

Type Où il apparaît et comment il s’ouvre
collectionTabs Un onglet de chaque collection, après les onglets propres à l’application, y compris pour les vues. Le cadre remplit l’onglet. Son place est cette collection, avec le filter de Documents défini par l’utilisateur. La page se recharge à chaque affichage de l’onglet, sauf si elle a demandé à rester avec ui.keepOpen : elle reste alors chargée tant qu’une autre section de l’onglet de cette collection est affichée (hors de vue, elle peut lire mais pas agir : not_visible).
documentActions Une entrée du menu d’actions d’un document dans Documents, affichée uniquement pour un plug-in approuvé pour documents:read. Elle ouvre une boîte de dialogue contenant la page ; place.documentId est le _id de ce document. La boîte de dialogue se ferme une fois que le plug-in a placé une requête ou un pipeline (ui.useQuery, ui.useQueryIn, ui.useAggregation).
sidebarPanels Une entrée de la barre latérale qui ouvre une page à part entière, un onglet de l’espace de travail à l’adresse /plugin/<id>/<contribution>. Si l’on clique alors que l’onglet d’une collection est actif, la page s’ouvre sur cette collection (/plugin/<id>/<contribution>/<connection>/<db>/<collection>) et place la désigne ; de partout ailleurs, place vaut null. Une page ouverte depuis un lien demande à l’utilisateur avant de lire cette collection, et l’utilisateur peut continuer sans elle. La page reste chargée tant qu’un autre onglet est affiché ; hors de vue, elle peut encore lire mais pas agir (not_visible).
cellRenderers Un court texte sur les valeurs partout où Documents les affiche (tableau, arborescence, cartes, page du document, détails du flux de modifications), comme la date de création d’un ObjectId : à côté de la valeur ("display": "inline", par défaut) ou dans une info-bulle ("display": "tooltip") que sa cellule ou sa ligne affiche au survol ou à la prise de focus, sous la valeur entière et marquée du nom du plug-in. Le texte d’une info-bulle est brut, sa tone n’est pas utilisée ; un lecteur d’écran le lit avec la valeur. Un plug-in fournit un texte à côté d’une valeur et un dans son info-bulle : son premier moteur de rendu qui répond pour chaque emplacement. La page s’exécute dans un cadre masqué, un par plug-in, uniquement pour un plug-in approuvé pour documents:read ; elle ne s’affiche jamais. match est l’une des valeurs geojson, string, number, date, object, objectId, binary (pas un UUID). Voir Moteurs de rendu de cellule.

Moteurs de rendu de cellule

L’application interroge le cadre masqué sur les valeurs qu’elle affiche, par lots de 200 au plus, avec un message cells.render. Avec le kit, répondez via client.onCells : 

client.onCells((renderer, values, locale, paths, place) =>
  values.map((v) => (typeof v?.$oid === 'string' ? { text: createdAt(v.$oid, locale), tone: 'info' } : null)),
)
  • renderer est l’identifiant de la contribution, values les valeurs en Extended JSON canonique, locale la langue de l’application, paths le chemin de champ de chaque valeur (ou null), place la collection d’où proviennent les valeurs (ou null).
  • Une valeur binary n’est envoyée que par son début, jamais en entier : { "$binaryHead": { "base64", "subType", "length" } } avec ses 2 048 premiers octets — de quoi reconnaître le genre et la taille d’une image.
  • Répondez par un élément par valeur, dans l’ordre : { "text", "tone" }, null pour aucun texte, ou { "retry": true } pour être interrogé de nouveau plus tard. Une liste d’une autre longueur est ignorée.
  • Le texte est affiché en texte brut — 80 caractères au plus à côté de la valeur, 200 dans une info-bulle — après suppression des caractères de contrôle et des caractères cachés. tone est l’une des valeurs neutral, info, success, warning, danger.
  • Une réponse doit arriver en moins de 3 secondes ; sinon la valeur brute reste affichée et la valeur est redemandée après 30 secondes. Les réponses sont conservées par valeur, par langue et par paramètres du plug-in : une modification de ses paramètres redemande les réponses, et une réponse de plus d’une minute est redemandée la prochaine fois que sa valeur est affichée, l’ancienne réponse restant en place jusqu’à l’arrivée de la nouvelle (et restant si la nouvelle demande échoue). La réponse pour une valeur binary est conservée sous sa longueur, son sous-type et un condensat de son début.
  • Un moteur de rendu peut lire avant de répondre (des références à d’autres documents, par exemple) : il transmet le place reçu dans sa demande, { place, filter, ... }, et ne peut lire que là. Le place de son contexte est null.

Le contexte

context.get indique où se trouve la page et à quoi elle doit ressembler. Appelez-le en premier ; lorsqu’une collection est ouverte, la réponse peut prendre jusqu’à 3 secondes, le temps que l’application vérifie s’il s’agit d’une vue. 

{
  "plugin": { "id": "hello-documents", "version": "0.1.0" },
  "contribution": { "kind": "collectionTab", "id": "list" },
  "locale": "en",
  "theme": "dark",
  "accent": "emerald",
  "place": {
    "connectionId": "6650...",
    "connectionName": "Production",
    "db": "shop",
    "coll": "orders",
    "view": false,
    "documentId": null,
    "filter": { "status": "open" }
  },
  "settings": { "tileUrl": "https://tile.example.org/{z}/{x}/{y}.png" }
}
  • kind est collectionTab, documentAction, sidebarPanel ou cellRenderer.
  • locale est la langue de l’application : en, tr, zh, ja, es, pt, ko, de, fr, ru.
  • theme est light ou dark.
  • accent est la couleur d’accent de l’utilisateur : emerald, indigo, violet, ocean ou rose. Traitez toute autre valeur comme emerald.
  • place vaut null lorsque la page a été ouverte sans collection (une page de la barre latérale, un moteur de rendu de cellule). connectionName peut valoir null. view est vrai pour une vue : elle peut être lue, jamais modifiée, et n’a pas d’index. documentId est le document d’une action de document, en Extended JSON canonique, sinon null. filter est le filtre de Documents pour un onglet de collection, sinon {}. Ce sont tous deux des données : un plug-in sans documents:read reçoit null et {}.
  • hidden liste les chemins de champs que les règles de données personnelles masquent à l’utilisateur dans la collection, sous forme de listes de clés ([["contact", "phone"]] ; "*" pour une clé, "**" pour un nombre quelconque de clés, à n’importe quelle profondeur) — les noms seulement, pour un plug-in disposant de documents:read ; [] sinon ; null lorsque l’application n’a pas pu le déterminer à temps (3 secondes). Les valeurs d’un tel champ arrivent sous la forme "***" : ne les prenez jamais pour son type.
  • settings contient les valeurs définies par un administrateur ; un paramètre non défini est absent.

Lorsque l’utilisateur change de langue, de thème ou de couleur d’accent, l’application envoie context.changed avec locale, theme et accent (le client.onContext du kit). Appliquez-le immédiatement : la page ne doit jamais afficher l’autre thème ni l’autre langue. Un plug-in autorisé à lire des documents reçoit aussi context.changed lorsque le filtre de Documents change pendant que sa page est chargée — un onglet de collection qui a appelé ui.keepOpen est informé de chaque filtre défini par l’utilisateur pendant qu’il est hors de vue. Redemandez context.get pour obtenir le nouveau place.

L’API de communication (bridge)

Le protocole

La page et l’application échangent du JSON simple avec postMessage. Le kit (packages/plugins/kit/src/client.ts) et le main.js du modèle de départ l’implémentent ; voici les règles, si vous écrivez le vôtre :

  1. Ne lisez que les messages dont event.source est window.parent et dont mm vaut 1.
  2. Une fois la page chargée, l’application la salue : { "mm": 1, "type": "hello", "token": "..." }. Conservez le premier jeton. N’envoyez rien avant.
  3. Une requête est { "mm": 1, "id": 1, "method": "documents.find", "params": { ... }, "token": "..." }, envoyée à window.parent avec la cible '*' (l’origine du cadre est opaque). L’identifiant est un nombre ou une chaîne de 64 caractères au plus ; l’application ignore une requête sans jeton.
  4. La réponse porte le même identifiant : { "mm": 1, "id": 1, "result": ... } ou { "mm": 1, "id": 1, "error": { "code": "...", "message": "..." } }.
  5. L’application envoie { "mm": 1, "type": "context.changed", "locale", "theme", "accent" } lorsque l’utilisateur les modifie (et, à un plug-in disposant de documents:read, le filtre de Documents), et interroge un moteur de rendu de cellule avec { "mm": 1, "id": "h1", "method": "cells.render", "params": { ... } }, auquel on répond par { "mm": 1, "id": "h1", "token", "result": [...] }.

La page ne doit pas quitter son adresse. Si elle charge une autre page (un lien, un formulaire, un changement de location), l’application ferme le bridge et supprime le cadre, et l’utilisateur doit rouvrir le plug-in. Gardez tout sur une seule page. 

import { createClient, askMessage, AskError } from './kit/client'

const client = createClient()                       // requests time out after 15 s ("timeout")
client.onContext((locale, theme, accent) => restyle(locale, theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  if (!context.place) return showNoCollection()
  try {
    const { documents, hasMore } = await client.ask('documents.find', { filter: context.place.filter, limit: 100 })
    show(documents, hasMore)
  } catch (e) {
    showError(askMessage(e, context.locale))         // the app's code, in the user's language
  }
})

Méthodes

Les valeurs sont en Extended JSON canonique dans les deux sens : un ObjectId est { "$oid": "..." }, une date { "$date": { "$numberLong": "..." } }, un entier { "$numberInt": "3" }. Chaque lecture s’exécute en tant qu’utilisateur, avec ses droits et le masquage de l’application. Les méthodes marquées « sur sa collection » agissent sur la collection de place et échouent avec no_collection s’il n’y en a pas.

Méthode et autorisation Paramètres → résultat Règles
context.get
aucune		 aucun → le contexte Voir Le contexte.
documents.find
documents:read		 { filter?, projection?, sort?, limit? } → { documents, hasMore } Sur sa collection. limit de 1 à 1 000, 100 par défaut. 10 secondes au plus. Un document que l’utilisateur n’a pas le droit de voir est omis. Ne compte pas parmi les requêtes récentes de l’utilisateur.
documents.get
documents:read		 { id } → le document, ou null Sur sa collection. id est la valeur de _id.
documents.aggregate
documents:read		 { pipeline, limit? } → { documents, truncated } Sur sa collection. Uniquement des étapes de lecture : $match, $group, $sort, $limit, $skip, $project, $addFields, $set, $unset, $count, $unwind, $sortByCount, $bucket, $bucketAuto, $facet (pas de $facet à l’intérieur), $replaceRoot, $replaceWith, $sample ; 50 étapes au plus. Avec database:read, aussi un $lookup simple comportant exactement from, localField, foreignField et as, depuis une collection de la même base de données. limit de 1 à 1 000, 100 par défaut. 10 secondes au plus, sans jamais déborder sur le disque, un seul pipeline à la fois (busy : le serialAsk du kit les met en file).
documents.update

Limites

  • Un message pèse 1 Mo au plus dans les deux sens ; une réponse plus volumineuse échoue avec too_large. Demandez moins de documents ou projetez moins de champs.
  • 8 requêtes au plus attendent en même temps (too_many).
  • 60 lectures par minute au plus et par cadre (documents.find, .get, .aggregate, .findIn, collections.list, database.model), et, en plus, 120 lectures de définitions (indexes.list, validation.get) : un dictionnaire de 50 collections représente un modèle et 100 définitions.
  • Juste après un clic dans la page du plug-in. ui.copy, ui.useQuery, ui.useAggregation, ui.importSql, ui.exportSql, ui.openDocument, ui.download, ui.importDocuments et documents.update ne sont acceptés que tant que le clic ou l’appui sur une touche de l’utilisateur dans la page propre du plug-in est récent : le cadre doit avoir le focus, si bien qu’un clic ailleurs dans l’application ne compte jamais. Appelez-les directement dans le gestionnaire de clic, avant d’attendre quoi que ce soit d’autre ; sinon elles échouent avec no_activation. Chaque tentative de ui.copy, d’un ui.use…, d’une page SQL ou de ui.openDocument compte dans la limite de cette méthode, refusée ou non : un plug-in qui réessaie sans cesse en attendant un clic épuise sa minute (too_many) ; documents.update est limitée à la place par sa seule question à la fois et par les deux refus. Un cadre peut prendre le focus sans clic, si bien qu’un ui.copy, un ui.download ou un ui.importDocuments demandé dans les 5 secondes qui suivent un clic ou un appui sur une touche ailleurs dans l’application (la durée de l’activation par le navigateur) n’est pas exécuté sur la seule parole du plug-in : l’application interroge l’utilisateur en nommant le plug-in et ce qu’il veut (combien de caractères et comment le texte commence, caractères cachés écrits en toutes lettres ; le nom et la taille du fichier ; combien de documents pour quelle collection), et l’exécute sur un clic de son propre bouton Copier, Enregistrer ou Ouvrir ; la réponse du plug-in l’attend (declined lorsque l’utilisateur la ferme, unanswered lorsqu’elle reste sans réponse, busy tant qu’une est en attente). Chaque question que l’application pose pour un plug-in — celles-ci, une modification, des étapes mises en place — prend fin après 150 secondes, même si le pointeur est dessus ; le kit attend 180 secondes pour ces requêtes, si bien qu’une page entend la réponse de l’application, jamais son propre délai.
  • À l’écran. documents.update, ui.openDocument et les méthodes ci-dessus échouent avec not_visible depuis un moteur de rendu de cellule ou depuis une page conservée pendant qu’un autre onglet est affiché.

Un administrateur approuve un plug-in pour les autorisations qu’il liste, telles que la page Plug-ins les nomme. Demandez le strict nécessaire : chacune est une raison pour un administrateur de refuser.

Le bac à sable

La page est chargée dans une iframe avec sandbox="allow-scripts", à partir d’une adresse signée qui nomme le plug-in, sa version, ses fichiers approuvés et la session de l’utilisateur, scellée (un ticket : la page doit se charger dans les 10 minutes, ses autres fichiers tant que cette session dure, 12 heures au plus — une session renouvelée sur place, par une connexion dans un autre onglet ou un changement de mot de passe, est suivie ; une fois déconnecté, l’adresse ne sert plus rien, et le navigateur n’en conserve aucun fichier). Chaque fichier servi est comparé à son SHA-256 approuvé. Sa politique (Content-Security-Policy), avec X-DNS-Prefetch-Control: off : 

default-src 'none'; script-src <its files>; style-src <its files>;
img-src <its files> data: blob: <the origins of its url settings>; font-src <its files>;
connect-src 'none'; webrtc 'block'; frame-ancestors 'self'; base-uri 'none'; form-action 'none';
sandbox allow-scripts

Ce que cela signifie pour votre code :

  • Aucun accès réseau. Aucune requête vers aucune adresse, y compris vers les fichiers du plug-in lui-même : placez les données dans un module de script (data.js) plutôt que dans un fichier .json que vous chargeriez. N’utilisez pas non plus WebRTC ni les directives de préchargement : tous les navigateurs ne les bloquent pas, et l’analyse les signale comme des risques élevés.
  • Aucun code ni style en ligne. Les scripts et les styles proviennent uniquement des fichiers du plug-in. Pas de <script> en ligne, pas d’élément <style>, pas d’attribut style, pas de gestionnaire d’événement en ligne, pas de eval. Définir une propriété dans un script (el.style.width = '40px') fonctionne.
  • Une origine opaque. Ni cookies, ni localStorage, ni IndexedDB : ils échouent. Conservez l’état en mémoire ; les paramètres choisis par un administrateur viennent de settings dans le manifeste.
  • Ni fenêtres contextuelles, ni boîtes de dialogue, ni formulaires, ni téléchargements. window.open, alert, confirm et l’envoi de formulaire ne font rien. Copiez avec ui.copy ; remettez les fichiers à l’utilisateur par l’import et l’export propres à l’application.
  • Aucun accès à l’application. La page ne peut lire ni la page de l’application, ni sa session, ni son stockage. Elle ne fait qu’échanger des messages avec elle.
  • Les polices et les images sont ses propres fichiers (ou des images data: et blob:).

L’analyse de sécurité

Les fichiers de chaque plug-in sont analysés lorsqu’ils sont trouvés ou installés, avant qu’un administrateur ne les approuve. L’analyse lit ligne par ligne les fichiers de script (.js, .mjs, .cjs), de balisage (.html, .htm, .svg) et de style (.css), commentaires compris, et liste chaque résultat avec sa gravité, sa règle, son fichier, sa ligne et un extrait. Les fichiers de balisage sont aussi lus en entier, si bien qu’une balise <script> ou un gestionnaire en ligne répartis sur plusieurs lignes sont également trouvés. Les bibliothèques intégrées au plug-in sont analysées comme votre propre code. L’analyse est heuristique : elle cherche des motifs connus dans le texte, si bien qu’un code écrit pour lui échapper (un nom construit à partir de morceaux, par exemple) n’est pas détecté — une analyse sans résultat ne prouve rien. Un plug-in ayant un résultat de gravité élevée ne peut être approuvé qu’après que l’administrateur a saisi son identifiant pour accepter le risque ; le serveur l’impose, et le journal d’audit enregistre les décomptes de l’analyse et si un risque a été accepté. Évitez tout résultat de gravité élevée et limitez les résultats de gravité moyenne à ce que vous pouvez expliquer.

Comment la réussir :

  • Écrivez le texte avec textContent, append('text') ou l’assistant h() du kit ; construisez les éléments avec document.createElement. Pour vider un élément, utilisez replaceChildren(). Aucun de ces appels n’est jamais signalé ; affecter ou ajouter du balisage (innerHTML = ou innerHTML +=) l’est toujours.
  • Attachez les gestionnaires avec addEventListener, jamais dans le balisage.
  • Passez des fonctions à setTimeout et setInterval. N’atteignez l’application que par window.parent.postMessage.
  • Enregistrez chaque fichier en UTF-8, sans octets NUL (jamais en UTF-16).
  • N’expédiez pas de code qui sort vers l’extérieur, même inutilisé : vérifiez ce qu’apporte une bibliothèque. Préférez une compilation non minifiée, ou expliquez le résultat minified dans votre README, et gardez les grosses données hors des chaînes base64.
  • N’oubliez pas que les commentaires sont aussi analysés : un commentaire qui nomme eval( ou innerHTML = est un résultat.
  • Dites dans votre README pourquoi chaque résultat restant est sans danger : quelle bibliothèque, quelle ligne, pourquoi il ne s’exécute jamais ou pourquoi le bac à sable l’arrête.

Seuls les fichiers de script, de balisage et de style sont analysés ; le manifeste est lu pour documents:write (toujours un résultat de gravité moyenne : ne le demandez que si le plug-in modifie des documents). 10 résultats d’une même règle dans un même fichier au plus, et 200 résultats au total au plus (les plus graves d’abord), sont listés ; les décomptes couvrent toujours tous les résultats. Chaque motif s’exécute en temps linéaire, si bien que l’analyse se termine rapidement sur n’importe quel fichier. Si l’analyse elle-même échoue, le plug-in n’est pas marqué comme inutilisable : il n’a pas d’analyse et (sauf s’il est livré avec Mongo Manager) il ne peut être approuvé qu’en saisissant son identifiant, comme pour un résultat de gravité élevée. L’analyse d’un plug-in livré avec Mongo Manager est également affichée, mais son approbation ne demande jamais son identifiant.

Interface et thèmes

Un plug-in doit ressembler à une partie de l’application : ses couleurs, ses polices, ses espacements, dans le thème et la couleur d’accent de l’utilisateur. Les plug-ins propres à Mongo Manager utilisent le kit de plug-ins de packages/plugins/kit :

  • kit/src/ui.css : les jetons de conception de l’application (--ds-surface, --ds-fg, --ds-accent...) pour le clair et le sombre et chaque couleur d’accent, ainsi que les composants (mm-btn, mm-table, mm-empty, mm-callout...). Ses polices sont des fichiers des paquets @fontsource : intégrez-les à votre plug-in, ou supprimez les règles @font-face pour utiliser la police du système.
  • kit/src/ui.ts : applyLook(theme, accent) définit html.dark et html[data-accent] ; h(tag, props, ...children) construit des éléments dont le texte est toujours du texte ; et icon, button, segmented, switchControl, chip, badge, pageHeader, emptyState, skeleton, callout, table, valueView, describeValue, formatNumber, statusLine, setBusy, serialAsk.
  • kit/src/client.ts : createClient, AskError, askMessage.

Le kit est écrit en TypeScript et destiné à être empaqueté : copiez kit/src dans votre projet et compilez avec Vite (ou un autre outil d’empaquetage) vers des chemins relatifs sans script en ligne, comme le vite.config.ts des plug-ins officiels : base: './', modulePreload: { polyfill: false }, assetsInlineLimit: 0. Empaquetez le résultat de la compilation, pas vos sources. Le modèle de départ embarque plutôt une courte copie du client et des couleurs, en JavaScript et CSS simples. 

import './kit/ui.css'
import { createClient } from './kit/client'
import { applyLook, h, pageHeader, emptyState, button } from './kit/ui'

const client = createClient()
client.onContext((locale, theme, accent) => applyLook(theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  applyLook(context.theme, context.accent)
  document.body.append(
    h('div', { class: 'mm-page' },
      pageHeader({ icon: 'table', title: 'Hello', description: context.place?.coll ?? '' }),
      emptyState({ icon: 'search', title: 'Nothing yet', action: button({ label: 'Load', variant: 'primary' }) }),
    ),
  )
})

Concevez la page en fonction de l’endroit où elle apparaît : un onglet de collection est large, une action de document est une boîte de dialogue, une page de la barre latérale remplit l’espace de travail. Affichez un état vide lorsqu’il n’y a rien à montrer et que place vaut null, un squelette pendant la lecture, et les mots de l’application pour un refus. Utilisez de vrais boutons et de vrais contrôles, afin que la page fonctionne au clavier.

Langues

L’application parle anglais, turc, chinois simplifié, japonais, espagnol, portugais brésilien, coréen, allemand, français et russe : context.locale vaut en, tr, zh, ja, es, pt, ko, de, fr ou ru. Un plug-in doit parler autant de ces langues qu’il le peut, et toujours l’anglais :

  • Dans le manifeste, donnez chaque langue dont vous disposez à côté de en dans chaque texte localisé.
  • Dans la page, conservez vos textes dans une table par langue, choisissez selon context.locale (l’anglais pour une langue que vous n’avez pas), définissez document.documentElement.lang sur la langue dans laquelle vos textes sont réellement écrits — en si vous êtes revenu à l’anglais — (zh-CN et pt-BR pour le chinois et le portugais, afin que les bons glyphes s’affichent), formatez les nombres dans cette même langue, et réaffichez lors de context.changed.
  • Un moteur de rendu de cellule répond dans la langue (locale) dans laquelle chaque lot est demandé.
  • Formatez les nombres et les dates selon la langue (Intl.NumberFormat, Intl.DateTimeFormat).
  • Ajoutez README.<language>.md à côté de README.md pour chaque langue (README.tr.md, README.zh.md, …), ainsi que des notes de version dans chacune.

README et notes de version

Le README.md situé à la racine du plug-in est affiché sur sa page de détails, où les administrateurs le lisent avant d’approuver le plug-in ; README.<language>.md (README.tr.md, README.ja.md, …) est affiché à la place pour une personne qui utilise l’application dans cette langue. Le README localisé n’est affiché que si README.md existe aussi. Il est affiché comme du Markdown sûr : titres, paragraphes, listes (sur un niveau), gras, italique, code en ligne et blocs de code. Les liens, les images, les tableaux et le HTML sont affichés en texte brut. 64 Ko au plus sont affichés.

Un bon README dit, dans cet ordre :

  1. Ce que fait le plug-in, en deux ou trois phrases.
  2. Où il apparaît : quel onglet, quelle action, quelle page ou quel texte de cellule.
  3. Comment l’utiliser, pas à pas, avec un exemple.
  4. Chaque autorisation et pourquoi elle est nécessaire.
  5. Ses paramètres, le cas échéant.
  6. Ses limites : combien de documents il lit, ce qu’il ne gère pas.
  7. Chaque résultat d’analyse qui subsiste, et pourquoi il est sans danger.

Les notes de version vont dans le changelog du manifeste, de la plus récente à la plus ancienne, une entrée par version avec son jour et ses notes en anglais et dans chacune de vos langues. La page de détails les affiche ; après une mise à jour, les versions parues depuis la précédente sont marquées comme nouvelles.

Versions et approbation

  • Une approbation porte sur des fichiers exacts : leur condensat, c’est-à-dire le SHA-256 du chemin et du SHA-256 de chaque fichier. L’administrateur le voit avant d’approuver.
  • Toute modification de n’importe quel fichier d’un plug-in téléversé ou d’un dossier de plug-in (une nouvelle version, une faute corrigée dans le README) le désactive jusqu’à ce qu’un administrateur l’approuve de nouveau. Augmentez version et ajoutez une entrée de changelog à chaque version, afin que les administrateurs sachent ce qu’ils approuvent.
  • Téléverser un plug-in dont l’identifiant est déjà installé le remplace ; il reste activé seulement si les fichiers sont exactement ceux qui ont été approuvés. Ses paramètres sont conservés tant que le nouveau manifeste les déclare toujours avec le même type.
  • Un dossier de plug-in placé à la main est géré à la main : un téléversement du même identifiant est refusé, et le supprimer dans l’application l’oublie sans supprimer le dossier.
  • Seuls les plug-ins livrés avec Mongo Manager conservent leur approbation lors d’une mise à jour, et seulement tant qu’ils sont activés et que la mise à jour ne demande aucune nouvelle autorisation ; rien n’est alors demandé à un administrateur, et la page de détails du plug-in indique qu’il a conservé son approbation. Une mise à jour qu’un administrateur a approuvée à la main indique qu’elle a été approuvée par un administrateur.

Empaquetage

Un plug-in voyage sous la forme d’une archive tar compressée en gzip (.tgz) dont les fichiers se trouvent à la racine, mongo-manager-plugin.json compris. Un seul dossier de premier niveau contenant tout (comme le package/ de npm pack) est accepté et retiré. L’archive ne doit contenir que des fichiers ordinaires (les dossiers sont implicites) ; les liens, les périphériques, les entrées spéciales, les chemins qui ne sont pas simples et les chemins donnés deux fois sont refusés ; 500 fichiers et 25 Mo au plus une fois décompressée, et 30 Mo au plus téléversée.

Il vérifie les chemins et les limites comme le fait l’application, laisse de côté ce qui ne fait pas partie du plug-in (fichiers cachés, scripts/, node_modules/, fichiers des assistants IA, fichiers de paquet et archives ; modifiez sa liste SKIP à votre convenance), écrit <id>-<version>.tgz et affiche le condensat que l’administrateur verra. Si vous compilez avec un outil d’empaquetage, empaquetez plutôt le dossier de sortie de la compilation, avec son manifeste à la racine.

Publication sur GitHub

Les administrateurs peuvent installer un plug-in directement depuis un dépôt GitHub public, sur un serveur configuré pour l’autoriser (MM_PLUGINS_GITHUB=1 ; désactivé par défaut). Sur la page Plug-ins, ils collent l’une de ces adresses :

  • https://github.com/<owner>/<repo>, …/releases ou …/releases/latest pour sa dernière release ;
  • https://github.com/<owner>/<repo>/releases/tag/<tag> pour une release donnée. Le tag peut contenir des barres obliques (4 segments au plus).

L’adresse ne contient rien d’autre : ni requête, ni fragment, ni port, ni identifiants. Un dépôt renommé est suivi : l’adresse de la page propre à la release nomme son dépôt. L’application télécharge l’archive de plug-in de cette release, son unique fichier joint dont le nom se termine par .tgz ou .tar.gz. Une release sans un tel fichier, ou avec plusieurs, est refusée. Les noms du tag et du fichier joint doivent être en ASCII imprimable. Le fichier joint doit appartenir aux releases de ce dépôt, et il ne peut pas dépasser la taille d’un téléversement (30 Mo), tant d’après ce qui est déclaré que d’après ce qui est lu.

L’application ne communique qu’avec github.com, api.github.com, objects.githubusercontent.com et release-assets.githubusercontent.com, en https, uniquement à des adresses publiques, et n’envoie rien du serveur (ni cookie, ni jeton, ni identifiants). Elle suit 4 redirections au plus, uniquement entre ces hôtes, lit la description de la release jusqu’à 5 Mo, et accorde 4 minutes à l’ensemble de l’installation. Le plug-in est installé désactivé, avec son analyse, et attend son approbation comme un téléversement. Il se souvient de son origine (dépôt, release et archive), affichée sur sa page de détails.

Lorsque l’installation échoue, la page Plug-ins en donne la raison : le dépôt n’a pas de release publiée, la limite de débit de GitHub a été atteinte, GitHub a refusé (le dépôt n’est pas public), GitHub est inaccessible depuis le serveur, une redirection est allée vers un hôte non autorisé, il y avait trop de redirections, la release n’a pas d’archive ou en a plusieurs, ou l’archive ne figure pas parmi les releases de ce dépôt.

  1. Augmentez version, ajoutez une entrée changelog et définissez publishedAt.
  2. Exécutez node scripts/pack.mjs.
  3. Créez une release GitHub (tag v0.1.0, par exemple) et joignez-y hello-documents-0.1.0.tgz comme fichier. Ne joignez aucun autre fichier .tgz ou .tar.gz.
  4. Marquez-la comme dernière release. Mettez le condensat affiché par pack.mjs dans les notes de la release, afin que les administrateurs puissent le comparer à ce que montre l’application.

Les installations depuis GitHub sont désactivées sauf si MM_PLUGINS_GITHUB=1 est défini ; un serveur peut aussi ne pas pouvoir joindre GitHub, ou ne le joindre que par un proxy (l’installation se connecte directement à GitHub et n’utilise pas les paramètres de proxy HTTP) ; ses administrateurs téléchargent alors le .tgz et le téléversent avec Téléverser un plug-in.

Pour que d’autres le trouvent, inscrivez votre plug-in dans Awesome Mongo Manager (github.com/mongo-manager/awesome-mongo-manager) : ouvrez-y une pull request qui ajoute une ligne à son README. Ses vérifications téléchargent votre dernière version et la contrôlent avec le code même de l’application, comme une installation depuis GitHub ; un mainteneur lit ensuite le plug-in avant de l’inscrire.

Test sur votre propre serveur

  1. Exécutez Mongo Manager avec les plug-ins activés (par défaut) et connectez-vous en tant qu’administrateur. Trouvez son répertoire de données : ~/.mongo-manager sauf si MM_DATA_DIR indique autre chose.
  2. Copiez le plug-in dans <data-dir>/plugins/<id> : node scripts/pack.mjs --folder ~/.mongo-manager/plugins. Le nom du dossier doit être l’identifiant, et il ne peut contenir aucun fichier caché (c’est pourquoi le script ne copie que les fichiers du plug-in). ~/ désigne votre dossier personnel dans tous les shells ; ~\ dans cmd et PowerShell, ou entre guillemets (bash et zsh suppriment une barre oblique inverse sans guillemets, et le script refuse alors ce qui reste). Le script ne remplace qu’un dossier de ce plug-in qui ne contient que des fichiers et des dossiers qu’il aurait pu copier (pas de scripts, de fichiers cachés, de liens, de tubes ni de sockets) et où aucun système de fichiers n’est monté, ni dessus ni à l’intérieur, en mettant la nouvelle copie en place de façon qu’une copie interrompue laisse le dossier tel qu’il était. Il refuse une cible qui est le dossier propre du plug-in, qui se trouve dedans ou qui le contient, quelle que soit la manière dont le chemin la désigne (un lien symbolique, une jonction ou un partage) ; rien n’est alors écrit.
  3. Ouvrez Plug-ins et cliquez sur Analyser à nouveau. Un plug-in qui ne peut pas être utilisé en indique la raison (un champ du manifeste, un chemin). Ouvrez ses détails : lisez les résultats de l’analyse, les autorisations et le README comme le ferait un administrateur.
  4. Cliquez sur Approuver et activer, puis ouvrez une collection et essayez chaque contribution.
  5. Après chaque modification, copiez de nouveau, cliquez sur Analyser à nouveau et approuvez de nouveau (les fichiers ont changé), puis rouvrez l’onglet, la page ou la boîte de dialogue. Essayez plusieurs langues, les deux thèmes, une vue, une collection sans documents et une page de la barre latérale ouverte sans collection.
  6. Enfin, téléversez le .tgz lui-même avec Téléverser un plug-in sur un serveur vierge, comme le feront vos utilisateurs.

Les outils de développement du navigateur fonctionnent dans le cadre : choisissez le cadre du plug-in dans la console pour voir ses erreurs et ses messages. Une violation de politique dans la console signifie que la page a tenté quelque chose que le bac à sable interdit.

Développer avec un assistant IA

Le modèle de départ contient des fichiers d’instructions qui enseignent à un assistant de programmation IA tout ce que décrit cette page : les règles du manifeste, les méthodes du bridge et les autorisations, le bac à sable, l’analyse, les langues, le README, l’empaquetage et la publication. Gardez-les à la racine du dépôt de votre plug-in ; pack.mjs les laisse hors de l’archive. La page Plug-ins enregistre le modèle de départ sous forme de .zip, et chaque fichier séparément, sous Instructions pour votre assistant IA, à ajouter à un plug-in que vous avez déjà ; celui de Copilot est enregistré sous le nom copilot-instructions.md, pour le dossier .github de votre dépôt.

  • CLAUDE.md : Claude Code.
  • AGENTS.md : OpenAI Codex et les autres agents qui lisent AGENTS.md.
  • GEMINI.md : Gemini CLI.
  • .github/copilot-instructions.md : GitHub Copilot.

Demandez à l’assistant ce que votre plug-in doit faire ; il doit répondre par du code qui passe l’analyse et la liste de contrôle ci-dessous. Relisez ce qu’il écrit avant de le publier : c’est vous à qui les administrateurs font confiance.

Liste de contrôle avant publication

  • L’identifiant est unique et identique au nom du dossier ; la version est augmentée et possède une entrée de changelog datée du jour.
  • Chaque texte localisé contient en et tr ; la page suit locale et context.changed.
  • Les autorisations sont le strict minimum qui fonctionne, et le README dit pourquoi chacune est nécessaire.
  • L’analyse ne montre aucun résultat de gravité élevée, et le README explique tous les autres.
  • Le texte est écrit avec textContent ou h() ; aucun balisage n’est construit à partir de texte.
  • Rien n’accède au réseau (ni fetch, ni WebRTC, ni directive de préchargement), n’utilise le stockage, n’ouvre de fenêtres contextuelles ni ne quitte la page.
  • Aucun script, style ni gestionnaire d’événement en ligne ; chaque chemin est relatif (./main.js).
  • Chaque fichier est enregistré en UTF-8, sans octets NUL.
  • La page suit le thème et la couleur d’accent, et fonctionne au clavier.
  • Elle gère un place valant null, une vue, une collection vide et chaque code d’erreur qu’elle peut rencontrer.
  • Les appels qui exigent un clic sont faits directement dans le gestionnaire de clic.
  • Les lectures volumineuses sont bornées : une limit, une projection, un pipeline à la fois.
  • README.md et ses traductions décrivent le plug-in ; license, author et repository sont renseignés.
  • Le .tgz a été téléversé sur un serveur vierge, analysé, approuvé et essayé là.
  • La release GitHub contient exactement une archive de plug-in, nommée <id>-<version>.tgz.
