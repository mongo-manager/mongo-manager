Backup and restore

Back up a collection, a database or the whole server, then download the file or keep it on the server for a while. Restore any of your backups, a mongodump archive or a zip of a mongodump folder into the namespaces you choose. Both run as background jobs you can follow in the jobs list.

Start from a collection's or database's menu in the sidebar, the connection's menu, a connection's Backups tab, a database's or a collection's Backups section, or the command palette ("Back up…", "Restore a backup…").

Taking a backup

The backup opens on one screen with the recommended choice for what you opened it from: an encrypted backup when the data holds personal fields, a compressed archive otherwise. The checks beside it update as you change anything: the expected size and time, your free backup space, personal fields that would be readable in the file, and anything left out. Each check that can be fixed has a button for it. "Customize…" opens the steps: scope, engine, content, protection and a summary.

The backup runs in the background: close the dialog when you like. Once it starts, the Backups section of what it backs up opens: the collection's, the database's or the connection's. While it runs, the Backups section and the jobs list show each namespace with its own progress (how many of them are done, the one being read, and the phase). When it finishes, its notice offers "Download" and "Open report".

A backup and a restore need the connection's server, and are shown only while Mongo Manager is connected to it (its databases were read). While it connects, or while it cannot (a timeout, a network, DNS or TLS failure, a sign-in refused, a server not available), the connection's page shows only its overview with the error, Retry and Edit: no Performance, Watch, Users and roles, Alerts, Personal data or Backups, no New database or shell; a database's page shows no Model, Watch or Backups. The menus of the tree and of these pages leave out backing up, restoring, live sync, the shell, creating, renaming and dropping, and the command palette's commands for the server say there is no connection. A backup or restore opened another way says so, with Retry, and starts nothing. An answer that is not about reaching the server (all its connections busy for a moment, a query that ran past its time limit) hides nothing. Everything comes back once the databases are read: Retry, Refresh, a connection test that passes, or by itself when the cause passes by itself (the network, a timeout, DNS, a server not available): an open page tries again every 15 seconds while the browser shows it. A sign-in the server refused (a username or password, an SSH sign-in, an SSH host key that changed) is kept for five minutes, or until the connection is edited, its person signs in again (a connection each person signs in to) or a connection test passes: meanwhile nothing in Mongo Manager (pages, widgets, the health check, jobs, the shell) signs in again for it, and while it is kept only the connection's administrators can test it again, so a directory's lockout rules do not lock the account out, and the error says how to try again.

Formats

  • .archive: a mongodump archive; it opens with mongorestore --archive.
  • .archive.gz: the same archive compressed with gzip; mongorestore --archive --gzip.
  • .mmbak: compressed with Zstandard, then sealed with AES-256-GCM in parts that are each verified when read. The password needs at least 12 characters; "Generate a strong password" makes one for you. The password is stored nowhere and cannot be recovered: without it, the backup cannot be opened. Open it in Mongo Manager, or turn it into a plain archive with mongo-manager backup decrypt <file> -o <file.archive> (the password is asked without echo, or read from a pipe with --password-stdin). mongo-manager backup inspect <file> lists what any backup holds.

Engines

  • Built-in: reads through Mongo Manager, so personal-field rules and masking apply. It works on every installation, and its archives open with mongorestore.
  • mongodump and mongorestore: MongoDB's own tools, which can be faster on very large data. They are offered to administrators of the connection who see personal values, not through SSH tunnels. Install the MongoDB Database Tools 100.9 or later (100.16 or later for MongoDB 8.3 and later, which the Docker image's own tools are not yet: there it uses the built-in engine) and set MM_MONGODB_TOOLS_PATH, or use the Docker image, which includes them. Credentials reach the tools in a private, temporary configuration file that is deleted when they finish, never on the command line.

Time series

A time series is kept as mongodump keeps it for the server's version: from MongoDB 8.3 under its own name, read and written through it with rawData; before 8.3 under system.buckets.<name>. The built-in engine restores either kind, Mongo Manager's or mongodump's, into any supported version, an 8.3 backup into an older server too. mongorestore needs 100.16 or later for a backup or a target of 8.3 or later, and finds the time series of an 8.3 backup only when mongodump 100.16 or later, or this version of Mongo Manager, made it: for one made otherwise the plan offers the built-in engine instead. A server that does not say its version is never guessed at: its time series is left out of a backup, with the reason, a restore of one is refused in its plan, and a drill of one stops before writing any of its documents, its scratch database dropped. With sign-in on MongoDB 8.3 and later, the account that backs up or restores a time series also needs the performRawDataOperations privilege (MongoDB's backup role has it; for a restore, grant it alongside restore).

Personal data

  • A user who may not see personal values backs up *** in their place: such a backup is always anonymous. Anyone can choose an anonymous backup.
  • Time series with personal fields, and views whose definition holds a value that would be masked, are left out of a masked backup. A collection whose validator holds such a value keeps its masked data, without the validator. The report says what was left out and why.
  • A masked backup can no longer be downloaded or restored once the personal-field rules change.
  • Restoring a masked backup over existing documents needs a confirmation, since *** replaces the stored values.

Restoring

  1. Drop a file, choose one, or pick one of your kept backups. Large files go up in parts and resume after a lost connection; what the file holds is shown while it is still uploading. An encrypted backup asks for its password.
  2. Choose what to restore and where: rename the database for every namespace at once, add _restored to the names, or "Into a new database" (named after the backed-up database and the date, never one the target already has; a backup of several databases gets one new database for each, so collections of the same name never meet). Targets that already exist are marked with their document count. "Restore here…" on a collection restores into it: a backup of one collection goes into that collection whatever its name was.
  3. Choose how to write: add (a document whose _id is already there is refused and listed), upsert by key fields, or replace. A replace restores into a staging collection and puts it in place only when everything arrived, so a failed or cancelled restore leaves the target as it was. With the built-in engine, what a replace does not take from the backup (its indexes, or its options and validator, when those are left out) stays the target's own: if one of its own indexes cannot be rebuilt, or its own cap would keep fewer documents than were written, nothing is replaced. mongorestore cannot keep them. A time series cannot be replaced, in the backup or on the target; restore it into a new collection. A restore run again finds the documents it already wrote as they were, and counts them as already there instead of refusing them, a dry run too.
  4. Confirm what needs confirming: the TTL indexes and collection expiry the written collection will have, the backup's or the target's own kept by a replace (the report, and a dry run, count the documents deleted as soon as they are written, their dates already past expiry, the target's own TTL included), personal-field rules the target lacks (an administrator can add them), and the name of each non-empty target a replace overwrites, typed.
  5. Run a dry run to see what would happen, then "Restore now with these settings", or start the restore. Every namespace's checksum is verified; a mismatch fails the restore. Its progress is shown per namespace, then the indexes and views it builds; when it finishes, its notice and its row in the jobs list open what it wrote ("Open collection", or "Open database" for several) and its report.

Kept backups

The Backups section of a connection, database or collection lists your backups (a collection's, those that hold it) with their protection, size, age and when they expire, and your use of the backup space. A backup's "…" menu downloads, sends or restores it, or deletes it (with five seconds to undo). Backups are yours only; they are withdrawn when you lose access to their connection or when personal values become hidden from you there.

Destinations

A backup can also be sent somewhere else: a folder on the server, S3-compatible storage, Google Drive or a WebDAV server. Administrators define destinations under Account menu → Backup destinations and choose who may use each one; everyone else sees only a destination's name, never its address or keys. The keys are stored encrypted and can only be replaced, never read back.

  • Server folder: an absolute path inside one of the folders listed in MM_BACKUP_FOLDER_ROOTS, outside the data directory. Without that setting no folder destination can be made.
  • S3-compatible storage: an endpoint, region, bucket, access key id and secret. Presets fill in what they can for Amazon S3, MinIO, Cloudflare R2 (your account id), Backblaze B2, DigitalOcean Spaces, DigitalOcean Spaces Cold Storage, Wasabi, or any other S3 service.
  • Google Drive: your own Google Cloud OAuth client, connected with a code shown on screen, or a service account writing into a Shared Drive (see below).
  • WebDAV: the server's address, a user name and an app password (Nextcloud, ownCloud or any WebDAV server). Nextcloud and ownCloud take large backups in resumable chunks.
  • Google Cloud Storage: a bucket, an optional prefix, the storage class backups are written in (Standard, Nearline, Coldline or Archive — every class is read at once; colder ones bill a minimum time) and the JSON key of a service account with the Storage Object User role (enough: it reads, writes, lists and deletes objects) on the bucket. The key is sealed on the server; only the account's address is shown. Uploads resume after a lost connection, and each copy is checked against Google's MD5.
  • Azure Blob Storage: a storage account, a container, an optional prefix and the access tier backups are written in (the account's default, Hot, Cool, Cold or Archive), signed with a SAS token or the account key. A SAS token for the container alone, allowed to read, add, create, write, delete and list, is the narrowest grant; it stops working at its end date. Only the fields a SAS token may hold are accepted, and only the credential the chosen way of signing uses is kept. A small backup is checked whole against its MD5. Large backups go up in blocks, each checked by Azure against its MD5, and the finished blob is compared by its size (Azure keeps no checksum of a blob made of blocks); an interrupted upload resumes from its own blocks only — every upload marks its blocks, so blocks another attempt left are never taken for this one's. A blob in the Archive tier is shown as archived: Thaw… rehydrates it to Cool (it stays there) at standard or high priority. Manifests are never written to Archive. Advanced takes another Azure cloud's endpoint and a CA certificate.
  • SFTP: a server, its port, a user name, an optional folder (the login folder when empty; it must exist) and a password or a private key (with its passphrase). The server's host key is pinned by its SHA-256 fingerprint: leave the fingerprint empty, run Test the connection, compare the key it shows with the server's own (for example ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the server) and choose Trust this key and test again. Nothing is sent to a server whose key is not the trusted one; a changed key asks for the password or key again. Backups are written as .part files, renamed when whole, and an interrupted upload continues where it stopped — once what the part file holds has been read back and found to be the backup's beginning (even with reading back off); a part file that is not starts again. SFTP keeps no checksum, so each copy is read back whole unless Verify by reading back is turned off. A manifest written again replaces the old one at once where the server offers posix-rename@openssh.com (OpenSSH does). A download that receives nothing for a minute is given up. The connection goes through the same address checks and proxy as the other destinations.

Under Access, choose who else may use the destination: Send lets a user send their own backups there and restore the ones they sent; Browse everything lets them read every backup there, other users' included. Administrators can always use every destination.

Testing a destination

The last step of the editor, Test and save, runs Test the connection on the real destination and shows each step with its time: Find the address, Connect securely, Sign in, Write a test file, Read it back and Delete it. For a server folder the first two read On this server. A step that fails says why; the steps after it show Not run. A setting changed after the test calls for a new one. Save after a failed test asks Save without a passing test? first; Save anyway keeps the destination as it is, to be fixed later. Test now in a destination's menu tests a saved one again. Its card shows the result: Healthy, Needs attention, Reconnect needed (Google Drive, see below) or Not tested yet.

Google Drive

Mongo Manager signs in to Drive with your own Google Cloud OAuth client, or with a service account in Google Workspace. It asks only for the drive.file scope: it sees the files and folders it created itself and nothing else in that Drive.

With your Google account (My Google account in the editor):

  1. In the Google Cloud console, choose or create a project. Under APIs & Services → Library, enable the Google Drive API.
  2. Configure the OAuth consent screen first (in newer consoles it is Google Auth Platform, with Branding and Audience). In Google Workspace, choose the user type Internal: only your organisation's accounts can connect. Otherwise choose External and then Publish app so that its status is In production; drive.file is a non-sensitive scope, so publishing needs no review by Google. Do not leave an External app in Testing: Google lets its sign-ins expire after 7 days, and the destination then shows Reconnect needed.
  3. Go to Credentials → Create credentials → OAuth client ID and choose the type TVs and Limited Input devices. No redirect address is needed. Keep the client id and the client secret.
  4. In the editor, enter the OAuth client id and the OAuth client secret and choose Connect Google account. Open the address shown (google.com/device) and enter the code with the Google account that should hold the backups, before the countdown ends. The editor then shows Connected as that account. Backups go into a folder the app creates (Folder name, "Mongo Manager backups" unless you change it).
  5. When Google no longer accepts the connection (its access was removed in the Google account, it was not used for six months, or the app stayed in Testing), the destination shows Reconnect needed. Open Edit…, choose Reconnect, enter the new code, and save. The stored client secret is used for this: you do not enter it again, and it never comes back to the browser.

With a service account (Google Workspace, Service account in the editor):

  1. In the same project, under IAM & Admin → Service accounts, create a service account (it needs no role). Under its Keys, choose Add key → Create new key of type JSON.
  2. In Google Drive, open the Shared drive that should hold the backups, choose Manage members, and add the service account's address as Content manager (a service account has no storage of its own). The Shared drive's id is the last part of its address (drive.google.com/drive/folders/<id>).
  3. In the editor, paste the key or drop its file on Service account key (JSON), and enter the Shared Drive id. Only the account's address stays on screen.

Sending a backup

Choose destinations under Where when you take a backup, or use Send… on a kept backup. Each copy shows on the backup's row: Sending to a destination with its progress, On a destination once it is verified, or Not sent to one with the reason.

  • A destination accepts encrypted backups only unless an administrator turns that off (the change is audited).
  • A backup of data with personal-field rules goes to a destination only when it is encrypted or masked, whatever the destination's setting.
  • A copy counts as sent only once it is verified. Every destination compares the size. S3-compatible storage also checks each uploaded part against its SHA-256 as it arrives, and Google Drive compares the checksum it reports. A server folder reads the whole file back and compares its SHA-256; so does WebDAV when Verify each upload by reading it back is on (it doubles the traffic). Without it, WebDAV checks the size only, and the dialog says so. A copy that fails verification is removed from the destination.
  • Delete the local copy after a verified upload relies on that verification: the server's copy is deleted only when every chosen destination verified its copy. If any fails, the local copy is kept for 7 days, the time a send can be retried in, and the job says so; a cancelled send never deletes it.
  • Each destination runs a limited number of transfers at once (MM_BACKUP_DEST_TRANSFERS, 2 by default, for sends and downloads together). Further ones wait, and the job shows Waiting for that destination until a slot is free.
  • Retry on a copy that was not sent sends it again and keeps its Delete the local copy choice: once it and the other copies sent with that choice are verified, the local copy goes. Discard drops the failed copy and abandons its unfinished upload.
  • A send cut off by a server restart becomes a copy that was not sent, with the reason "The server restarted while it was being sent."; Retry continues it from the parts already uploaded where the provider keeps them (S3 multipart uploads, Nextcloud chunks).

What is stored there

Files go under mongo-manager/<year>/<month>/ in the destination's folder or prefix, named by date, time and a short id, next to a small .json manifest with the size, format and checksum, written last, once the file is verified. Neither the names nor the manifest contain database or collection names.

Restoring from a destination

Choose the destination's tab in the Backups card, or From a destination in the restore sheet, and pick a backup. Restoring needs the right to write to the target connection. The file is downloaded to the server and previewed while it arrives; the restore can start once the download is complete and its checksum matches the one recorded when it was sent, or the manifest's. A file whose checksum differs is removed. A file without a manifest (put there by another tool, or by hand) is listed as From another installation: it can be restored, but nothing can verify it first, and the restore sheet says so.

A download that fails keeps what it received: choosing the same backup again resumes it. A cancelled download is dropped, and so is one whose received part is of no use (its checksum differs, or the file is gone). The part already received counts against your backup space until it is resumed, discarded, or expires (MM_BACKUP_TTL_HOURS).

On a new installation, define the destination again with the same settings: the same folder; the same endpoint, bucket and prefix; the same WebDAV address and folder. For Google Drive, use the same OAuth client (or the same service account and Shared drive) and the same folder name: with drive.file, a client sees only the files it created itself. Administrators then see every backup there, those of the old installation included. Anyone else needs Browse everything: Send shows only the backups that user sent from this installation.

Cold Storage and archive storage classes

DigitalOcean Spaces Cold Storage keeps backups cheaply and they stay readable at once, but every object is billed for at least 30 days, and the provider may charge for retrievals beyond an allowance: deleting or restoring soon after sending costs money.

An S3 destination's Storage class (under Advanced, STANDARD by default) applies to the backup files; manifests stay in STANDARD. Files in GLACIER or DEEP_ARCHIVE are not readable until they are thawed: the destination's list shows them as archived with a Thaw… action, which asks how long the thawed copy stays readable (1 to 30 days) and how fast the provider works (Standard, Bulk — cheapest and slowest — or Expedited, not for Deep Archive). The provider bills the thaw and those days. While it runs the copy shows as thawing; once thawed it can be restored from the list until the days run out. Anyone who may restore from the destination may thaw (a sender, their own copies), at most 10 thaws a minute, each one audited. GLACIER_IR, STANDARD_IA, ONEZONE_IA and INTELLIGENT_TIERING are read at once.

Scheduled backups

A schedule takes the same backup again and again, sends each one to the destinations you choose and keeps as many as its retention rule says. Open Account menu → Scheduled backups, the command palette ("Open scheduled backups") or Schedule… in the Backups section of a connection or database, which starts a schedule for it. The editor has six steps: what, when, protection, where, retention and a summary with the server's checks.

Who may schedule

  • Anyone who may back up the connection may schedule it (read documents, run jobs and export there). Each run takes the owner's rights as they are at that moment, never as they were when the schedule was saved.
  • A right that is gone pauses the schedule before any data is read, with the reason on its card: the owner's account is disabled, the owner can no longer back up the connection or send to a destination, a destination was deleted, the backup key is not active, the scope now holds personal data for an unencrypted schedule, a destination now takes encrypted backups only, this server cannot read its cadence or time zone (a time zone another build knew), or the copies it keeps on this server fill your backup space. Resume it once the reason is gone.
  • Administrators see every schedule and may pause, resume, run and delete it; they do not edit another user's schedule. A schedule an administrator paused is resumed by an administrator. A user may hold at most 10 schedules.

When it runs

  • Every N hours (1 to 24), at a chosen minute of the hour.
  • Daily, at up to four times of day.
  • Weekly, on the days you choose, at a time.
  • Monthly, on a day from 1 to 28 or on the last day of the month, at a time.
  • Advanced: a five-field cron expression (minute, hour, day of month, month, day of week), read back in words as you type. It follows the classic Vixie rules: when both the day of month and the day of week are restricted, either one matching is enough; a field that starts with * counts as unrestricted. There are no @ shortcuts, no seconds and no L, W or #.

Runs must be at least an hour apart, and a cadence must run within the next five years; the editor shows the next runs in the schedule's time zone and says when either rule is broken.

Time zones and daylight saving

Each schedule has its own time zone (yours by default); times are wall-clock times there. When the clocks go forward, a time that does not exist that day runs at the first minute after the change. When they go back, a time that happens twice runs once, at its first occurrence. An hourly schedule loses one run in the hour that repeats rather than running twice within an hour.

Missed runs, overlap and the queue

  • When the server was stopped at a due time, the next start runs one catch-up backup if the latest missed time is no older than the schedule's own interval (at most a day). Every other missed time is recorded as missed; there is never more than one catch-up.
  • A run that comes due while the previous one is still running, or still waiting for its turn, is skipped and recorded as skipped, with which of the two it was.
  • At most MM_BACKUP_SCHEDULE_CONCURRENCY scheduled runs work at once (default 2). The others wait in due order for up to six hours; a run that waits longer is skipped.
  • A clock that jumps forward gives at most one catch-up; a clock that goes back runs nothing twice.

Run now and the run history

Run now starts a run at once without moving the next one; a schedule runs one at a time. Each card shows its last runs as a strip: green succeeded, amber partial (a destination failed), red failed, grey skipped, a dashed outline missed, and a pulsing mark for the run in progress. The run history lists each run with its outcome, duration and size, where each copy went, what retention removed and, for a run that did not succeed, why. The last 200 runs of each schedule are kept. A card whose last finished run failed or was partial says so, with the reason. Jobs started by a schedule carry its name in the jobs list, and a paused or failing schedule of yours marks the account menu.

Protection and where it goes

  • By default each run is an encrypted .mmbak sealed with your backup key (see Backup keys): no password to type, and its recovery kit opens it anywhere. Create a key under Account settings → Backup keys first.
  • A plain format (.archive or .archive.gz) is allowed only when the scope holds no personal data and every chosen destination accepts unencrypted backups; both are checked again before each run.
  • Each run goes to the destinations shared with you that you choose, then the copy on this server is deleted once every destination has a verified copy. Keep on the server too keeps it here as well, under the same retention and in your backup space; the editor says about how much space they will take. Turning it off gives the copies kept so far the normal time to live.

Restore drills

A backup is only as good as its restore. "Test that backups restore" (in the retention step) runs a restore drill every so many runs (1 to 30): the run's backup, opened with your backup key, is restored into a new scratch database on the same connection (mm_drill_ and 12 random characters), each namespace is read back and compared with the backup — the number of documents, and every document byte for byte — and the scratch database is dropped, whatever the outcome. While it exists it is closed to everyone, administrators included: it is not listed in the tree, the Performance page, the slow queries or the running operations (nor counted in the databases' total size), and no page, request, shell command, assistant, change feed, live sync, copy, compare, backup or restore reads it or writes to it — a request that names it is refused. Two things remain outside the app's reach: the listDatabases answer in a connection admin's shell still shows its name (it cannot be opened), and what the drill writes appears, like every write, in the oplog (local.oplog.rs, admins only) and in a whole-deployment change stream opened in an admin's shell. It also carries the personal-data rules of what it holds (the backup's, and the connection's for those namespaces), so its values are hidden from anyone who may not see them; these rules are not added to the connection's list and go with the database. Collections are restored without their options (a validator or a cap would make it a test of the target), and views are not checked. The run keeps its server copy until the drill is done, then lets it go as usual. The run history says whether each drill passed or failed (and in which namespaces), the drill's report is in the jobs list, and a failed drill raises an alert. A drill needs the right to create databases on the connection; without it (or on a read-only connection) the drill is skipped, never the backup. It writes as much as the backup holds, and writes go to the primary whatever member the connection names: choose a quiet time. Before it writes anything it checks that the connection's MongoDB user may drop databases (a drill that cannot clean up fails at once), picks a scratch name no database has, and keeps what it writes under half the server's free disk space — the fullest shard's through a mongos, and under MM_BACKUP_DRILL_MAX_MB when that is set, which a server that does not report its free space (Atlas shared tiers) needs — a larger backup fails the drill, said as such. A right to drop that cannot be read is not assumed: the drill does not start. If the scratch database cannot be dropped at the end, the drill fails, a warning alert is raised and the report names the database: the connection's administrators see it on the connection's page and drop it there by typing its name (not while any drill runs). It is closed to everyone meanwhile, and a restart drops it.

Retention

Retention decides which backups a schedule keeps at each location (each destination, and this server when it keeps copies). Four tiers, counted in the schedule's time zone; a backup stays when any tier keeps it:

  • Newest: the N most recent backups (1 to 100).
  • Daily: the newest backup of each calendar day, for that many days (0 to 90).
  • Weekly: the newest of each ISO week (Monday to Sunday), for that many weeks (0 to 52).
  • Monthly: the newest of each calendar month, for that many months (0 to 60).

Presets: Daily for 30 days (the 7 newest and one a day for 30 days), Standard (the 7 newest, 14 days, 8 weeks and 12 months), Long (the 7 newest, 30 days, 26 weeks and 60 months) and Custom. The editor draws what stays on a timeline.

  • Only the schedule's own complete and verified copies at a location are ever removed; a copy sent by hand, even of a scheduled backup, never is. Nothing is removed at a destination its owner may no longer use.
  • The newest backup is never removed, and a run that fails removes nothing.
  • Removal at a location happens after this run's copy there is complete, at most 100 removals per location and run; a removal that fails is tried again after the next run. Every removal is in the audit log with the file's name.
  • A change of rule, time zone, destinations or keeping that would remove more than ten backups at once asks you to confirm the number first.
  • DigitalOcean Spaces Cold Storage bills every object for at least 30 days: the editor warns when a rule would keep backups there for less.

Opening a scheduled backup

  • On this server, restore it as any other backup: it opens with your backup key, retired keys included, and the restore says which key opened it.
  • Elsewhere, or when none of your keys opens it, the restore asks for the backup's recovery kit (paste it or choose its file). The kit is used for that restore and not kept, unless you tick Import this key, which adds the key to your backup keys.
  • Without the app: mongo-manager backup decrypt <file.mmbak> --key-file <kit.txt> -o <file.archive> writes the plain archive, which opens with mongorestore --archive. Without --key-file, a file that opens only with its backup key says so before asking anything.

Limits and settings

  • MM_BACKUP_QUOTA: backup space per user, in MiB (default 20 480).
  • MM_BACKUP_TOTAL_QUOTA: backup space for all users, in MiB (default 102 400).
  • MM_BACKUP_MAX_UPLOAD: the largest file to restore, in MiB (default 20 480).
  • MM_BACKUP_TTL_HOURS: how long backups and uploads are kept (default 24).
  • MM_BACKUP_MAX_JOB_HOURS: the longest a backup or restore may run (default 12).
  • MM_BACKUP_CHUNK_MB: the default part size of encrypted backups (default 64).
  • MM_MONGODB_TOOLS_PATH: the folder of mongodump and mongorestore.
  • At most 10 000 namespaces in one archive; a zip of a mongodump folder must be under 4 GiB.
  • MM_BACKUP_SCHEDULES and MM_BACKUP_SCHEDULE_CONCURRENCY: scheduling on or off, and scheduled runs at once (see Deployment).

Not covered

Users and roles, the oplog and point-in-time restore. A backup reads collection after collection, not one moment: documents written meanwhile may be partly in it. For a copy of one moment, back up a replica set member that writes have stopped on, or use MongoDB's own snapshots.
