Развертывание

Как системная служба

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

Служба работает от отдельной непривилегированной учетной записи, из папки программы, которую могут изменять только администраторы, в командном режиме на 127.0.0.1:4321. При первом запуске одноразовый установочный токен сохраняется в файле setup-token в папке данных, который могут читать только учетная запись службы и администраторы; service install выводит подсказку, как его прочитать. Токен никогда не записывается в журнал, а файл удаляется, как только появляется первый администратор.

Если служба установлена в локальном режиме (--no-auth), она открывается только по одноразовой ссылке для запуска: service install выводит такую ссылку, а service open выводит новую, когда она вам нужна (от имени администратора: она создается из launch.key в папке данных). Откройте ее в своем обычном браузере, а не в браузере с повышенными правами; после этого браузер остается в системе, пока хранит данные этого сайта, но не дольше шести месяцев после последнего использования.

Docker

Образ работает от непривилегированного пользователя на корневой файловой системе только для чтения, в командном режиме. Данные хранятся в томе /data. На компьютерах без доступа к сети можно загрузить архив образа командой docker load -i. Установочный токен первого запуска: docker exec <container> cat /data/setup-token. Файл compose публикует порт только на loopback-адресе хоста (127.0.0.1:4321); чтобы обслуживать другие компьютеры, поставьте перед ним обратный прокси с HTTPS, а не публикуйте обычный HTTP. Прокси на хосте обращается к контейнеру со шлюза сети compose: доверяйте MM_TRUSTED_PROXIES=172.31.240.1, а не 127.0.0.1.

Внутри контейнера сервер слушает все адреса, поэтому без MM_ALLOWED_HOSTS он отвечает только на IP-адреса и localhost (каждый запуск сообщает об этом). Все, что обращается к нему по имени — прокси, пересылающий публичное имя, другой контейнер по имени службы (Prometheus, опрашивающий mongo-manager:4321), служба Kubernetes, — получает 403, пока это имя не внесено в список: MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

В локальном режиме (MM_AUTH=0) журнал контейнера указывает команду, которая выводит ссылку, но не саму ссылку: docker exec <container> node /app/dist/cli.cjs open --no-open. В ней указан порт, который сервер слушает внутри контейнера: если он опубликован на другом порту хоста (-p 127.0.0.1:8080:4321), замените порт в ссылке на порт хоста, прежде чем открывать ее.

На сервере поставьте перед ним обратный прокси с HTTPS, который обслуживает его как mongo.example.com, и запустите контейнер так; последняя строка читает установочный токен. Завершите настройку сразу: пока нет первого администратора, им может стать любой, у кого есть токен. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES — адрес, с которого прокси на хосте обращается к контейнеру: шлюз сети Docker, в стандартной сети bridge обычно 172.17.0.1 (его показывает docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}'). Без него каждый запрос выглядит пришедшим со шлюза, и журнал аудита и блокировки входа не различают пользователей. Если задан MM_ALLOWED_HOSTS, принимаются только перечисленные в нем имена: добавьте 127.0.0.1, чтобы по-прежнему открывать http://127.0.0.1:4321 на хосте. --read-only, --tmpfs /tmp, --cap-drop ALL и no-new-privileges — то же усиление защиты, что применяет файл compose.

Доступ к MongoDB из контейнера

Внутри контейнера localhost — это сам контейнер, поэтому mongodb://localhost:27017 завершается ошибкой ECONNREFUSED, даже если MongoDB работает на той же машине.

  • MongoDB в другом контейнере: подключите оба к одной сети Docker (docker network create mm, затем docker network connect mm mongo-manager и docker network connect mm my-mongodb или --network mm при запуске) и подключайтесь к mongodb://my-mongodb:27017.
  • MongoDB на хосте, Docker Desktop (Windows, macOS): mongodb://host.docker.internal:27017.
  • MongoDB на хосте, Linux: запустите Mongo Manager с --network host (тогда localhost — это хост; закройте его от сети с помощью -e MM_HOST=127.0.0.1, поставьте перед ним прокси и доверяйте ему как 127.0.0.1) или добавьте --add-host=host.docker.internal:host-gateway. Второй способ достает только до MongoDB, который слушает адрес шлюза bridge: ни до MongoDB, привязанного только к 127.0.0.1 хоста, ни до контейнера, опубликованного только там (-p 127.0.0.1:27018:27017); для них используйте общую сеть или сеть хоста.
  • Набор реплик, участники которого названы localhost:27017, отправляет драйвер обратно на localhost: добавьте ?directConnection=true.

Обновление

Администратор видит установленную версию на странице «О программе Mongo Manager» в меню учетной записи. Проверить сейчас запрашивает у GitHub последний опубликованный выпуск; Проверять обновления автоматически делает это раз в день. Ежедневная проверка выключена, пока ее не включит администратор, и вместе с ней не отправляется ничего о вас, вашем сервере или ваших данных: возвращается только номер последней версии. Черновики и предварительные выпуски никогда не предлагаются.

Выпуск предлагается, только если его SHA256SUMS подписан ключом Mongo Manager (Ed25519) и в нем указан release.json. Обновить загружает выпуск в app/ в каталоге данных, сверяет каждый байт с подписанными контрольными суммами, копирует базу данных и перезапускается. При каждом запуске каждый файл работающей версии проверяется снова. Версия, в которой найдены изменения, не запускается: она загружается заново (если обновления не выключены), или работает версия, из которой она была установлена, и страница «О программе Mongo Manager» сообщает об этом. Больше при запуске ничего не загружается. Новая версия, не запустившаяся за минуту, откатывается: копия базы данных возвращается на место, снова работает предыдущая версия, и страница «О программе Mongo Manager» сообщает об этом.

  • Пакет npm, автономный исполняемый файл, системная служба: установленная программа остается как есть и запускает самую новую проверенную версию из app/. Службу, установленную более ранним выпуском, нужно один раз установить заново (mongo-manager service install): тогда ее юнит запускается с --isolate-account, чтобы перед проверкой и запуском обновленной версии завершались другие процессы учетной записи службы. В Linux и macOS это делается только для учетной записи, которую создает service install, и никогда от root; в Windows, где LocalService используется и другими службами, завершаются только программы этой установки и собственные процессы предыдущей программы.
  • Docker: новая версия хранится в томе /data и работает в вашем образе. Перед ее проверкой и запуском завершаются другие процессы ее пользователя в контейнере (никогда, если контейнер работает от root или видит процессы хоста). Выпуску нужен более новый образ, только если приложение не может работать в вашем (нужен более новый Node.js); тогда страница «О программе Mongo Manager» вместо обновления объясняет, как его получить. Более новый образ, который лишь приносит исправления безопасности системы, никогда не мешает обновлению: страница советует его рядом с кнопкой обновления. С Docker Compose: docker compose pull && docker compose up -d. С docker run: docker pull ghcr.io/mongo-manager/mongo-manager:<version>, затем удалите контейнер и запустите его снова из нового образа с теми же параметрами и тем же томом /data (данные остаются в томе). Об образе старше 90 дней тоже сообщается: загрузите более новый, чтобы получить исправления безопасности Node.js и системы.
  • Из исходного кода: обновляйте через git.
  • Первая версия, которая обновляет себя сама, устанавливается вручную.
  • MM_UPDATES: off (или 0, false) полностью выключает обновления: нет ни проверки, ни настройки, ни кнопки, ни запроса, и страница «О программе Mongo Manager» сообщает об этом. По умолчанию: включено, а ежедневная проверка выключена, пока ее не включит администратор.
  • MM_UPDATE_PROXY: прокси HTTP(S), через который выполняется обращение к GitHub, как MM_BACKUP_PROXY. По умолчанию: нет.

За обратным прокси

  • Доверяйте только прокси: --trusted-proxies 127.0.0.1. Без этого сервер не может определить, что запрос пришел по HTTPS, поэтому cookie сеанса не помечаются как Secure; запуск в командном режиме сообщает об этом, а также о том, что вход пойдет по сети через обычный HTTP.
  • Укажите публичный хост: --allowed-hosts mm.example.com.
  • Обслуживайте приложение по вложенному пути с помощью --base-path /mm/.
  • Каждый клиентский адрес может делать 600 запросов к API в минуту; увеличьте лимит с помощью MM_API_RATE_LIMIT (60–100000), если много людей работают с одного адреса.
  • Одновременно открыто не более 1000 соединений (MM_MAX_CONNECTIONS, 16–100000) и не более 256 с одного адреса (MM_MAX_CONNECTIONS_PER_IP, 2–100000); соединение сверх лимита закрывается, а журнал сообщает об этом раз в минуту для каждого адреса. Браузер держит открытыми около шести соединений, поэтому, если многие люди обращаются к Mongo Manager с одного адреса — за NAT, через VPN или Docker Desktop, — увеличьте MM_MAX_CONNECTIONS_PER_IP. За доверенными прокси действует только общий лимит: все соединения приходят от прокси, который должен ограничивать собственных клиентов.
  • Импортированные и экспортированные файлы хранятся в <data directory>/transfer: MM_TRANSFER_MAX_UPLOAD — наибольший размер загрузки в МиБ (по умолчанию 1024, 1–65536), MM_TRANSFER_QUOTA — объем хранилища, который может занимать каждый пользователь, в МиБ (по умолчанию 5120, 16–1048576), MM_TRANSFER_TOTAL_QUOTA — объем, который могут занимать все пользователи вместе, в МиБ (по умолчанию 51200 или MM_TRANSFER_QUOTA, если оно больше; 16–16777216), MM_TRANSFER_TTL_HOURS — срок хранения файла (по умолчанию 24, 1–720), а MM_TRANSFER_MAX_JOB_HOURS — как долго может выполняться один импорт или экспорт (по умолчанию 6, 1–72). Выделите диску место под общий объем или под квоту, умноженную на число людей, передающих файлы, если это меньше.

Настройки и переменные окружения

Каждую настройку сервера можно задать параметром командной строки, переменной окружения или в конфигурационном файле JSON, указанном через --config или MM_CONFIG. Командная строка приоритетнее окружения, а окружение — файла. Переключатель принимает 1/0, true/false, yes/no или on/off. Настройки каждой функции описаны в ее собственном разделе ниже.

Переменная Параметр Что делает
MM_WEB_PORT -p, --web-port Порт веб-интерфейса (по умолчанию 4321).
MM_HOST --host Адрес, который слушает сервер (по умолчанию 127.0.0.1). Для сетевого адреса нужен командный режим или MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Командный режим: пользователи, роли и вход (по умолчанию выключен).
MM_DATA_DIR --data-dir Папка данных (по умолчанию ~/.mongo-manager).
MM_CONFIG --config Конфигурационный файл JSON. В Linux и macOS файл, содержащий секрет, не должен быть доступен для чтения другим пользователям, иначе сервер его отклонит.
MM_SECRET_KEY Ключ шифрования вместо файла secret.key из папки данных.
MM_OPEN --open Открывает браузер при запуске (по умолчанию включено): в локальном режиме, на loopback-адресе, при запуске из терминала.
MM_URI --uri Подключение, создаваемое только при самом первом запуске. Для строки подключения с паролем используйте переменную: командные строки могут видеть другие пользователи.
MM_READ_ONLY --read-only Ни одно подключение не может изменять данные, независимо от его собственной настройки.
MM_TRUSTED_PROXIES --trusted-proxies Адреса прокси или диапазоны CIDR, заголовкам X-Forwarded-* которых верят.
MM_ALLOWED_HOSTS --allowed-hosts Единственные имена хостов, на которые отвечает сервер. Если не задано, он отвечает на loopback-имена, когда слушает loopback-адрес, а в остальных случаях — только на loopback-имена и IP-адреса, но никогда на другое имя (защита от DNS rebinding; запуск сообщает об этом). Перечислите здесь все имена хостов, по которым люди открывают приложение.
MM_BASE_PATH --base-path Обслуживает приложение по вложенному пути, например /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Разрешает сетевой адрес без командного режима. Любой, кто до него дотянется, получает полный доступ.
MM_LOG_LEVEL --log-level fatal, error, warn, info (по умолчанию), debug, trace или silent.
MM_LOG_FILE --log-file Дописывает журнал JSON в этот файл вместо стандартного вывода. Файл делается закрытым (режим 0600; в Windows доступ для всех пользователей отбирается: остается у этой учетной записи, SYSTEM и Administrators) и ротируется при достижении 10 МиБ, предыдущая часть сохраняется как <file>.1. Путь, который является ссылкой, файл с несколькими именами (жесткие ссылки) или не обычный файл отклоняется, и запуск завершается ошибкой с пояснением: удалите или переименуйте его либо укажите другой файл журнала. Строка, которую не удалось записать (диск заполнен), отбрасывается, и об этом один раз сообщается в стандартный вывод ошибок. Запросы записываются по их пути, а каждое значение запроса и идентификатор файла GridFS заменяются на ***.
MM_REQUIRE_ADMIN_2FA Каждый администратор должен настроить двухфакторный вход прежде всего остального; после этого его нельзя отключить в приложении. Без этой переменной администратор может включить такое же требование в приложении.
MM_REQUIRE_2FA Каждый пользователь независимо от роли должен настроить двухфакторный вход прежде всего остального; после этого его нельзя отключить в приложении. Без этой переменной администратор может включить такое же требование в приложении.
MM_METRICS_TOKEN Включает метрики Prometheus по адресу <base path>metrics, которые читаются с этим токеном как bearer-токеном (не менее 32 символов). В числах нет имен пользователей, подключений, баз данных и коллекций.
MM_GRIDFS_MAX_MB Наибольший файл, загружаемый в GridFS, в МБ (по умолчанию 512, 1–10240).
MM_MODEL_MAX_DOCS Сколько документов в сумме может быть выбрано для одной модели данных (раздел «Модель» базы данных) (по умолчанию 20000, 100–1000000): при большом числе коллекций выборка каждой из них уменьшается, и раздел сообщает об этом.
MM_ALLOW_KERBEROS Командный режим: разрешает подключения Kerberos (GSSAPI) (по умолчанию выключено). Они входят с билетом Kerberos той учетной записи, от имени которой работает сервер, — каждый пользователь такого подключения входит от имени этой учетной записи. См. «Безопасность».
MM_ALLOW_WORKLOAD_IDENTITY Командный режим: позволяет подключениям OIDC использовать идентификатор рабочей нагрузки машины (Azure, GCP, Kubernetes), если он выбран в подключении (по умолчанию выключено).
MM_OIDC_DEVICE_FLOW Вход OIDC с помощью кода (device flow) для поставщиков удостоверений, которые не могут вернуть браузер на этот сервер. Входит тот, кто подтверждает код, поэтому в командном режиме эта возможность выключена, пока ее не включат здесь; в локальном режиме она включена.
MM_OIDC_PRIVATE_NETWORKS Частные сети (CIDR через запятую), в которых могут находиться поставщики удостоверений OIDC; обычный http разрешен только там. Без этой переменной они должны быть публичными адресами https.
MM_CRYPT_SHARED_LIB_PATH Абсолютный путь к библиотеке crypt_shared (mongo_crypt_v1) для шифрования на стороне клиента. В командном режиме загружается только она.
MM_KMS_PRIVATE_NETWORKS Частные сети (CIDR через запятую), в которых могут находиться службы управления ключами (KMIP- сервер в собственной инфраструктуре). Без этой переменной они должны быть публичными адресами.
MM_KMS_ALLOWED_HOSTS Хосты служб управления ключами (через запятую, host или host:port, порт по умолчанию 443), к которым подключение может обращаться помимо собственных адресов провайдеров (AWS KMS, Azure Key Vault и Managed HSM со входом Microsoft, Google Cloud KMS) и конечных точек, названных в его настройках: конечная точка VPC, KMIP-сервер. Любой другой хост или другой порт отклоняется — главный ключ ключа данных не может отправить токен KMS в другое место.

Kerberos и шифрование на стороне клиента (пакет npm)

Для Kerberos (GSSAPI) и шифрования на уровне полей на стороне клиента / Queryable Encryption нужны нативные пакеты, которые Mongo Manager не устанавливает сам: при его установке скрипты установки пакетов не запускаются. Чтобы ими пользоваться, установите пакеты рядом с пакетом npm и перезапустите приложение: 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager загружает их только из глобальной папки node_modules, в которой лежит сам mongo-manager (проверяется по ее реальному пути, никогда не по папке выше), и только когда подключению впервые понадобится один из них; форма подключения сообщает, какого пакета не хватает и как его установить. Автономные исполняемые файлы, образ Docker (который задает MM_DISTRIBUTION=docker) и копия, из которой работает служба Windows, не содержат нативных модулей: там эти две возможности сообщают, что в данной сборке они недоступны, — используйте пакет npm и запускайте приложение на переднем плане. Автоматическому шифрованию Queryable Encryption также нужна библиотека crypt_shared (MM_CRYPT_SHARED_LIB_PATH) или mongocryptd, а также MongoDB Enterprise или Atlas; MongoDB Community умеет только расшифровывать. MONGODB-OIDC не требует пакета: у поставщика удостоверений адресом перенаправления должен быть <address><base path>oidc/callback этого сервера (или другой адрес, указанный в подключении), а там, где это невозможно, люди могут входить с помощью кода.

Установка как приложения

В Chrome или Edge выберите Install Mongo Manager в адресной строке, чтобы открывать его в отдельном окне с рабочего стола или из меню «Пуск».

Места хранения резервных копий

  • MM_BACKUP_FOLDER_ROOTS: папки, которые могут использовать места хранения типа «папка на сервере», — абсолютные пути, разделенные разделителем путей системы (: в Linux и macOS, ; в Windows), не более 16. По умолчанию: нет, поэтому создать место хранения типа «папка» нельзя. Относительный путь останавливает сервер при запуске. Предоставьте учетной записи службы доступ на запись к каждому корню и держите корни вне папки данных: место хранения типа «папка» внутри нее отклоняется. При каждом запуске в журнал записывается корень, в который сервер не может писать. Для службы Linux:
    • Ее песочница позволяет писать только в папку данных и в корни, названные в ее конфигурации и файле env на момент установки: после их изменения снова выполните sudo mongo-manager service install (данные, конфигурация и ключ сохраняются) и перезапустите службу после создания отсутствовавшего корня. Корни, заданные где-либо еще, например через Environment= в drop-in, установка не видит: их папки остаются для службы доступными только для чтения.
    • Установка исключает корень в /home, /root, /run/user, /tmp, /var/tmp или /dev, до которых служба не может добраться, и такой, который свел бы песочницу на нет: содержащий системный каталог (/, /var, /var/lib и подобные) либо находящийся внутри /etc, /usr, /run или другого системного каталога (в /var открыты только папки внутри /var/backups). Подходит папка внутри /srv, /opt или точки монтирования в /mnt или /media, но не сами эти папки; на съемной или сетевой файловой системе тот, кто управляет диском или общим ресурсом, управляет и папками на нем, поэтому сделайте корнем саму точку монтирования (монтирование FUSE пользователя заявляет о своих владельцах и ссылках что угодно). Корень внутри другого корня попадает в песочницу вместе с тем корнем. Если /srv, /opt или /mnt сам является ссылкой в /var, как в системах ostree (Fedora Silverblue, CoreOS), установка сообщает, куда ведет корень, и там он отклоняется: выберите папку внутри /var/backups.
    • Ссылка оценивается по тому, куда она ведет, и юнит называет это место; ссылка, которая никуда не ведет, исключается: для ссылки на еще не созданную папку создайте эту папку и снова выполните service install; для ссылки, образующей цикл или ведущей через файл, выберите другую папку или удалите ссылку. Каждая папка выше корня и папки, в которых лежат ссылки на его пути (включая ссылку в цели ссылки), должны принадлежать root и быть закрыты для его группы и остальных, чтобы никто не мог подставить там ссылку вместо папки; в папке, в которую могут писать другие (с sticky-битом или без него), пусть папка внутри нее принадлежит root, а корень находится внутри этой папки.
    • Корень ниже папки, которую мог бы изменить пользователь службы, на любом уровне до / и вдоль ссылок на его пути, исключается: папка, которой этот пользователь владеет или в которую может писать через одну из своих групп, ACL или как любой пользователь, где процесс от имени этого пользователя мог бы подставить ссылку на /etc вместо папки. Сюда входит и ссылка в другом корне, в который пишет служба. Установка, а также doctor, запущенный с sudo, дополнительно спрашивают систему: с помощью setpriv они выполняют test -w от имени этого пользователя, так что ядро применяет его группы (те, что юнит дает службе через Group= или SupplementaryGroups=, включая drop-in) и ACL. Без setpriv или без root читаются только режимы папок и группы пользователя, и обе команды сообщают об этом. То, что разрешают режимы, учитывается, даже если ACL это отнимает, поэтому такая папка тоже исключает свои корни.
    • Установка спрашивает у systemd, кто запускает службу, прочитав все drop-in. Drop-in, который запускает ее от пользователя, отличного от --user (или от root), с DynamicUser=yes без учетной записи с таким именем, с Group=, отличной от собственной группы пользователя, или с группой, неизвестной системе (в этом случае systemd отказывается ее запускать), останавливает установку до изменения папки данных и конфигурации; она сообщает причину и оставляет службу остановленной и отключенной. Группа, поиск которой завершился ошибкой, или systemd, у которого нельзя спросить, исключают все корни.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json проверяет установленную службу (обычный mongo-manager doctor проверяет вашу собственную папку данных и сообщает, что проверил не службу). Он проверяет каждый корень: что он существует, является папкой, в которую сервер может писать, находится внутри песочницы и не находится внутри папки данных; он также называет папку, в которую песочница позволяет писать службе, но которую уже не называет ни один корень или которая ведет к корню или к папке данных по ссылке, которую может изменить не только root, и предупреждает о службе, работающей от root, о группе, которой нет ни у кого или поиск которой не удался, и о DynamicUser=yes без учетной записи с таким именем. Он проверяет корни, названные в конфигурации службы и файле env, поэтому ему нужен sudo: читать файл env, в котором лежит и секретный ключ службы, может только root. Доступ на запись он проверяет от имени пользователя, от которого работает; будучи запущенным от root, он вместо этого читает владельца и режим корня для пользователя, владеющего папкой данных, и принимает ответ системы там, где этот пользователь может в нее писать. Папки выше корней он оценивает для пользователя, от имени которого юнит запускает службу (его User=).
  • MM_BACKUP_PRIVATE_NETWORKS: частные диапазоны, к которым могут обращаться места хранения, — список не более чем из 64 CIDR через запятую (например, 10.0.5.0/24); внутри них разрешен обычный HTTP. По умолчанию: нет. Принимаются диапазоны loopback, 10/8, 172.16/12, 192.168/16, CGNAT (100.64.0.0/10) и unique-local (fc00::/7). Публичный диапазон останавливает сервер при запуске, так же как и диапазон внутри link-local или диапазона метаданных облака (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200) в любой форме, включая IPv4-mapped и NAT64; в сообщении назван диапазон. Эти адреса недостижимы никогда, даже внутри указанного диапазона.
  • MM_BACKUP_PROXY: прокси HTTP(S), через который достигаются места хранения, например http://proxy.corp:3128 или https://user:password@proxy.corp; без пути и запроса. По умолчанию: нет (переменные окружения прокси не читаются никогда). Mongo Manager по- прежнему сам определяет и проверяет адрес каждого места хранения и просит прокси подключиться к этому адресу, поэтому приведенные выше правила для адресов действуют и через прокси; TLS работает сквозным образом до места хранения, сертификат которого проверяется так же, как без прокси. Места хранения внутри MM_BACKUP_PRIVATE_NETWORKS достигаются напрямую. Прокси по адресу link-local или метаданных останавливает сервер при запуске. Не оставляйте пароль прокси в общих историях командной оболочки: он входит в адрес. Его используют только места хранения резервных копий: каналы оповещений (электронная почта и вебхуки), ИИ-провайдеры и плагины через него не ходят никогда. Что нужно знать перед выбором прокси: прокси http:// получает имя пользователя и пароль открытым текстом (Basic), поэтому лучше https:// или прокси внутри доверенной сети; прокси, разрешающий CONNECT только к перечисленным именам хостов, отклонит эти подключения, так как ему передается IP-адрес; сертификат прокси https:// должен быть подписан центром, которому доверяет Node.js (его встроенный список или центр, добавленный через NODE_EXTRA_CA_CERTS): указать собственный центр сертификации нельзя.
  • MM_BACKUP_DEST_PART_MB: размер части при загрузке, от 16 до 512 МиБ (по умолчанию 64).
  • MM_BACKUP_DRILL_MAX_MB: наибольший объем, который записывает проверочное восстановление, в МиБ. По умолчанию: нет — проверочное восстановление укладывается в половину свободного места на диске, о котором сообщает MongoDB (для самого заполненного шарда — через mongos). Там, где MongoDB этого не сообщает (общие тарифы Atlas), проверочное восстановление работает только при заданной переменной.
  • MM_BACKUP_DEST_TRANSFERS: число одновременных отправок и загрузок на каждое место хранения, от 1 до 8 (по умолчанию 2). Остальные ждут; в списке заданий они показываются как «Ожидание» этого места хранения.

Резервное копирование по расписанию

  • MM_BACKUP_SCHEDULES: планировщик, по умолчанию включен. 0 выключает его: расписания сохраняют свои настройки, ничего не выполняется, а вкладка «Резервное копирование по расписанию» сообщает, что планирование выключено. Запуски, которые остановленный сервер оставил незавершенными, закрываются при запуске.
  • MM_BACKUP_SCHEDULE_CONCURRENCY: число одновременно выполняемых запусков по расписанию, от 1 до 8 (по умолчанию 2). Остальные наступившие запуски ждут до шести часов.

Отслеживание изменений

  • MM_WATCH: ленты потоков изменений, по умолчанию включены. 0 выключает их: разделы «Наблюдение» сообщают, что отслеживание выключено, и в MongoDB ничего не открывается.
  • MM_WATCH_MAX_FEEDS: число одновременно работающих живых лент на этом сервере, от 1 до 500 (по умолчанию 50). У каждого пользователя может быть 5, у каждого окна браузера — 3. Каждая лента держит один курсор потока изменений в MongoDB.
  • Для отслеживания нужен набор реплик, шардированный кластер или развертывание с балансировкой нагрузки, а пользователю базы данных подключения нужны changeStream и find для отслеживаемых объектов. См. «Отслеживание изменений».

Живая синхронизация

  • MM_LIVE_SYNC: живая синхронизация между подключениями, по умолчанию включена. 0 выключает ее: работающие синхронизации ждут с указанием причины, ничего не читается и не записывается; новые отклоняются. После повторного включения они продолжаются с того места, где остановились.
  • MM_LIVE_SYNC_MAX: число не завершенных живых синхронизаций на этом сервере, от 1 до 100 (по умолчанию 10). У каждого пользователя может быть 3. Каждая работающая синхронизация держит один поток изменений на источнике и оба подключения открытыми.
  • Источником должен быть набор реплик, шардированный кластер или развертывание с балансировкой нагрузки (MongoDB 6.0 или новее); копия, которая может пережить oplog источника, запрашивает подтверждение. См. «Живая синхронизация».

Оповещения

  • MM_ALERTS (в конфигурационном файле: alerts.enabled): оповещения, по умолчанию включены. 0 выключает их: ничего не вычисляется и не отправляется, а страница «Оповещения» сообщает, что оповещения выключены.
  • MM_ALERTS_PRIVATE_NETWORKS (в конфигурационном файле: alerts.privateNetworks, список): сети, к которым почтовые серверы и вебхуки оповещений могут обращаться помимо публичных адресов, — список не более чем из 64 CIDR через запятую (например, 10.0.5.0/24). По умолчанию: нет. Обычный http для вебхука разрешен только внутри них. Принимаются и отклоняются те же диапазоны, что и для MM_BACKUP_PRIVATE_NETWORKS: адреса link-local и метаданных облака недостижимы никогда.
  • В конфигурационном файле: "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. См. «Администрирование сервера».

Расширенная оболочка

  • Полностью отключите ее с помощью --no-shell (или MM_SHELL_ENABLED=0).
  • Ограничения: MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. Оболочка, которую удерживает ее страница, остается открытой сколько угодно долго без использования, как в Compass; оболочка, которую не удерживает ни одна страница, закрывается через две минуты после ухода страницы. Ограничение простоя выключено (0), пока вы его не зададите (от 10000 до 86400000 мс); оболочка живет не дольше 12 часов, пока вы не зададите другой срок жизни (от 60000 до 86400000 мс или 0 — без ограничения). Удерживаемые открытыми оболочки учитываются в MM_SHELL_MAX_TOTAL, пока их страницы не закроются; на сервере, которым пользуется много людей, задайте MM_SHELL_IDLE_MS, чтобы открытые и неиспользуемые оболочки освобождались. Если включен вход, оболочка также завершается, когда заканчивается сеанс ее пользователя, а также когда меняется роль пользователя или его учетная запись отключается.
  • MM_SHELL_RSS_MB: объем памяти, который может занимать процесс оболочки, от 128 до 16384 МБ (по умолчанию 384). Сервер сам измеряет его через операционную систему (в Windows с помощью tasklist, в macOS с помощью ps) и перезапускает оболочку, превысившую его; переменные оболочки при этом теряются. Оболочка, которая 15 секунд не отвечает, пока не выполняется ни одна команда, тоже перезапускается. MM_SHELL_OUTPUT_MB: вывод одной команды, от 1 до 64 МБ (по умолчанию 5); остальное обрезается. MM_SHELL_COMMANDS_PER_SECOND: число команд в секунду на оболочку, от 1 до 1000 (по умолчанию 20).
  • На сервере POSIX, работающем от root, рабочий процесс оболочки понижает права до MM_SHELL_UID/MM_SHELL_GID (по умолчанию 65534); не запускайте службу от root.

ИИ-помощник

  • MM_AI: ИИ-помощник, по умолчанию включен; он появляется, только когда администратор добавит провайдера (Настройки → ИИ-ассистент). 0 скрывает его везде и отклоняет запросы.
  • MM_AI_PRIVATE_NETWORKS: сети (CIDR через запятую), в которых помимо публичных адресов может находиться провайдер, например Ollama по адресу 10.0.0.5; обычный http только там. Метаданные облака и адреса link-local недостижимы никогда. В локальном режиме этот компьютер разрешен всегда.
  • MM_AI_PER_MINUTE (по умолчанию 10, 1–120) и MM_AI_PER_DAY (по умолчанию 200, 1–10 000): запросов на человека. MM_AI_MAX_CONCURRENT (по умолчанию 8, 1–64): одновременных запросов на сервере; у каждого человека может быть 2. MM_AI_AGENT_PER_MINUTE (по умолчанию 30, 1–120): дополнительные запросы агента к провайдеру в рамках одного сообщения, на человека в минуту (они учитываются и в дневном лимите).
  • MM_AI_CHAT_DAYS (по умолчанию 30, 0–365): как долго чат хранится после последнего сообщения. 0 хранит чаты только в памяти (12 часов) и удаляет чаты, сохраненные при прежней настройке, когда запускается сервер.

Плагины

  • MM_PLUGINS: плагины, по умолчанию включены. Каждому по-прежнему требуется одобрение администратора после проверки безопасности. 0 ничего не ищет, не устанавливает и не запускает (см. «Плагины»).
  • MM_PLUGINS_GITHUB: установка плагина из релиза публичного репозитория GitHub, по умолчанию выключена (плагины устанавливаются загрузкой или из папки); 1 разрешает ее. Тогда сервер обращается к api.github.com, github.com и хостам ресурсов релизов GitHub по https, не отправляя ничего от себя. Если выключено, сервер к GitHub не обращается никогда. Сервер подключается к GitHub напрямую: настройки HTTP-прокси не используются, поэтому сервер, который может выходить наружу только через прокси, устанавливает плагины загрузкой. Системная служба читает эту настройку из своего config.json как "pluginsGithub": true (Linux — /etc/mongo-manager/config.json, Windows — %ProgramData%\Mongo Manager\config.json, macOS — /Library/Application Support/Mongo Manager/config.json); после этого перезапустите службу.
