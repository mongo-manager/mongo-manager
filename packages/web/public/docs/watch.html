Watching changes

The Watch section shows the changes MongoDB makes to your data as they happen: every insert, update, replace and delete, and, when you ask for them, schema changes such as new indexes. It uses MongoDB's change streams. Nothing is stored: a feed starts when you open it and shows what happens from then on.

Where to find it

  • A collection tab → Watch: the changes of that collection.
  • A database tab → Watch: the changes of every collection in the database.
  • A connection tab → Watch: the changes of every database of the connection.
  • The command palette (Ctrl+K): "Watch changes…" opens the Watch section of the tab you are on.

Change streams need a replica set, a sharded cluster or a load-balanced deployment (MongoDB Atlas is always one of these). A standalone server cannot be watched; the section says so. A single-node replica set is enough for development: start mongod --replSet rs0 and run rs.initiate() once. Views cannot be watched: a view's Watch section offers the collection the view reads from. A collection that does not exist yet can be watched; its changes appear once it is created.

Who may watch

Anyone who may read documents on the connection may watch it, in every scope. The connection's database user needs the changeStream and find privileges on what is watched (the built-in read role has both). Credential collections such as system.users are shown to the connection's administrators only.

The feed

The bar above the feed shows its state: Live, Paused, Behind (more than two seconds behind, with how far), Reconnecting or Ended, and how many changes arrived and how fast. Newest changes are at the top. Each row shows the kind of change (in words and colour), the collection in database and connection feeds, the document's _id, the changed field names for updates, and how long ago it happened (the exact time on hover). When you scroll down, new changes wait behind a "new events" button instead of moving what you read. The latest 2,000 changes are kept; older ones leave the list.

Select a change to see it on the right: the fields that changed, the whole document for inserts and replaces, or the event as JSON. "Open document" opens the collection's Documents section filtered by that document's _id. "Copy as EJSON" copies the change in Extended JSON.

Pause, resume and reconnects

Pause stops the list without losing your place: MongoDB keeps the changes on the server's side. Resume with "Catch up" to see what happened while paused, or "From now" to skip it. Space on the feed's toolbar pauses and resumes. A paused feed stays paused when you switch sections or tabs, until you close its tab; a running one stops a few seconds after you leave its section.

When the connection to the app drops, the feed reconnects by itself. Within two minutes it resumes right after the last change your browser received, with nothing missed and nothing repeated, and says so; a paused feed comes back paused. If it can no longer resume from there (after a very long burst), it resumes from where the server was and says some changes may be missing; after two minutes it starts again from now and says that instead. The place a feed resumes from (MongoDB's resume token) stays on the server.

Filters

The chips choose the kinds of change: insert, update, replace and delete. "Include schema changes" adds changes such as created or dropped collections and indexes and changed options. "Show the whole document after updates" reads the document after each update, which costs one read per update.

"Edit filter" takes a $match on each change event, written like a query, for example:

  • { 'updateDescription.updatedFields.status': 'paid' }: updates that set the status to paid.
  • { 'fullDocument.total': { $gt: 1000 } }: inserts and replaces of large orders.
  • { 'documentKey._id': ObjectId('…') }: one document.
  • { 'ns.coll': 'orders' }: one collection, in a database or connection feed.

A filter may be up to 12 KB and 20 levels deep. Operators that run JavaScript on the server ($where, $function, $accumulator) are never accepted. Changing any filter starts the feed again from now, and the feed says so.

Seeing the values before a change

MongoDB reports which fields an update changed and their new values. To also see the values before, turn on pre-images for the collection; the feed then shows a full before/after comparison for updates and the document as it was for deletes. On a collection's Watch page, someone who may change the collection's options (validation rules, for example) sees Turn on pre- and post-images while they are off; it says what they cost, then runs the same command (audited). Or in the shell: 

db.runCommand({ collMod: 'orders', changeStreamPreAndPostImages: { enabled: true } })

Pre-images are kept in the server's storage for as long as its change stream settings say, so they cost disk space on busy collections. Without them the feed shows the updated values, the removed field names and how arrays were shortened.

Recording, replaying and alerts

Record to a file (in the filters, for those who may export from the connection) keeps the feed's events on the server, exactly as you were sent them — masked where they were masked — one event per line. A recording is your own transfer file: it counts against your transfer space, holds 64 MB at most (then recording stops and the feed goes on, and the Watch page says so), and is kept for the transfer files' time once its feed ends. A reconnect that records starts a new file. A server restart ends a recording: what reached the disk is kept, as a finished recording. A file is marked masked or not as its events were sent: when your masking changes during the feed (personal values hidden from you now, or no longer, or the rules changed), the file ends there and a new one begins under the new marking — the recordings list shows both. Recordings on the toolbar lists yours for this connection: Replay shows one in place of the live feed (with the same list and details) — the first 500 events, then 500 more each time you choose Load more events, up to 5,000 (the file has the rest) — Download gives the file (NDJSON), and they can be deleted. Nobody else, administrators included, can read them. A recording is not given once personal values are hidden from you on the connection (when it was recorded unmasked), nor once its rules changed (when it was recorded masked).

Raise an alert on matches tells the app's alerts (the watch.matched event) that events passed the feed's filter: at most every 10 seconds, with how many and the kind of the last one, never a value. It works while the feed runs.

Personal data

For a user who may not see personal data, every change is shown with personal fields as ***: the document, its key, the values before and the updated values, by field path, array positions included. A filter on a hidden field is refused, and in database and connection feeds such a user may filter on the kind of change, the namespace and the time only. Exports of the feed hold what was shown, hidden values included as ***.

Limits and settings

  • 3 live feeds per browser window, 5 per user, and 50 on the server (MM_WATCH_MAX_FEEDS).
  • A document larger than 256 KB is not sent in the feed; "Open document" shows it.
  • At most 200 changes a second reach the browser per feed; when more happen, the feed shows how far behind it is and catches up.
  • MM_WATCH=0 turns watching off on the server.
  • Starting and stopping a feed is recorded in the audit log, with the filter's fingerprint but never its values.

When a feed ends

  • The collection was dropped or renamed: the feed ends; "Start again from now" watches the collection by that name again.
  • The server's history (oplog) no longer reaches the feed's place, for example after a long time away: start again from now.
  • Your access, the connection or its settings changed: the feed ends and says why.
