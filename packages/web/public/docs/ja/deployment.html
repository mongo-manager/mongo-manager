デプロイメント

システムサービスとして

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

サービスは、専用の非特権アカウントとして、管理者だけが変更できるプログラムフォルダーから、チームモードで 127.0.0.1:4321 上で動作します。初回起動時のワンタイムセットアップトークンは、データフォルダー内の setup-token に保存されます。このファイルを読めるのはサービスアカウントと管理者だけで、読み方は service install が表示します。トークンがログに書き込まれることはなく、最初の管理者が作成されるとファイルは削除されます。

ローカルモード（--no-auth）でインストールした場合、サービスはワンタイムの起動リンクからしか開けません。service install が 1 つ表示し、service open は必要なときにいつでも新しいリンクを表示します（管理者として実行します。リンクはデータフォルダー内の launch.key から作られます）。管理者権限ではない、ご自身のブラウザーで開いてください。そのブラウザーは、このサイトのデータを保持している間はサインインしたままになり、最後に使ってから最長 6 か月間続きます。

Docker

イメージは、読み取り専用のルートファイルシステム上で、非特権ユーザーとして、チームモードで動作します。データは /data ボリュームに保存されます。オフラインのマシンでは、docker load -i でイメージアーカイブを読み込めます。初回起動時のセットアップトークンは docker exec <container> cat /data/setup-token で確認します。compose ファイルは、ポートをホストのループバックにのみ公開します（127.0.0.1:4321）。ほかのマシンに提供する場合は、平文の HTTP を公開せず、前段に HTTPS のリバースプロキシを置いてください。ホスト上のプロキシは、compose ネットワークのゲートウェイからコンテナーに到達します。127.0.0.1 ではなく MM_TRUSTED_PROXIES=172.31.240.1 を信頼してください。

コンテナー内では、サーバーはすべてのアドレスで待ち受けます。そのため MM_ALLOWED_HOSTS がないと、IP アドレスと localhost にしか応答しません（起動のたびにその旨が表示されます）。名前でアクセスするもの（公開名を転送するプロキシ、サービス名を使う別のコンテナー（mongo-manager:4321 をスクレイピングする Prometheus など）、Kubernetes のサービス）は、その名前を登録するまで 403 になります。例：MM_ALLOWED_HOSTS=mongo-manager,mm.example.com

ローカルモード（MM_AUTH=0）では、コンテナーのログにはリンクではなく、リンクを表示するコマンドが示されます。 docker exec <container> node /app/dist/cli.cjs open --no-open。ここに示されるのは、コンテナー内でサーバーが待ち受けているポートです。ホストの別のポートで公開している場合（-p 127.0.0.1:8080:4321）は、リンクを開く前に、リンク内のポートをホストのポートに書き換えてください。

サーバーでは、mongo.example.com として公開する HTTPS のリバースプロキシを前段に置き、次のように起動します。最後の行でセットアップトークンを読み取ります。セットアップはすぐに完了させてください。最初の管理者ができるまでは、トークンを持つ人なら誰でも管理者になれます。 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES は、ホスト上のプロキシがコンテナーに到達するときのアドレス、つまり Docker ネットワークのゲートウェイです。デフォルトの bridge ネットワークでは通常 172.17.0.1 です（docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}' で確認できます）。これがないと、すべてのリクエストがゲートウェイから来たように見え、監査ログとサインインの禁止でユーザーを区別できません。MM_ALLOWED_HOSTS を設定すると、そこに挙げた名前しか受け付けません。ホスト上で http://127.0.0.1:4321 を引き続き開くには、127.0.0.1 も加えてください。--read-only、--tmpfs /tmp、--cap-drop ALL、no-new-privileges は、compose ファイルが適用しているのと同じ強化設定です。

コンテナーから MongoDB に接続する

コンテナー内の localhost はコンテナー自身です。そのため、MongoDB が同じマシンで動いていても、mongodb://localhost:27017 は ECONNREFUSED で失敗します。

  • 別のコンテナー内の MongoDB: 両方を同じ Docker ネットワークに入れ（docker network create mm のあと docker network connect mm mongo-manager と docker network connect mm my-mongodb、または起動時に --network mm）、mongodb://my-mongodb:27017 に接続します。
  • ホスト上の MongoDB（Docker Desktop、Windows・macOS）: mongodb://host.docker.internal:27017。
  • ホスト上の MongoDB（Linux）: Mongo Manager を --network host で実行するか（このとき localhost はホストです。-e MM_HOST=127.0.0.1 で外部に公開しないようにし、前段にプロキシを置いて 127.0.0.1 として信頼します）、--add-host=host.docker.internal:host-gateway を追加します。後者で到達できるのは、bridge のゲートウェイアドレスで待ち受けている MongoDB だけです。ホストの 127.0.0.1 にだけバインドされた MongoDB にも、そこにだけ公開されたコンテナー（-p 127.0.0.1:27018:27017）にも到達できません。その場合は共有ネットワークかホストネットワークを使ってください。
  • メンバー名が localhost:27017 のレプリカセットでは、ドライバーが localhost に戻されてしまいます。?directConnection=true を付けてください。

リバースプロキシの背後で

  • 信頼するのはプロキシだけにします：--trusted-proxies 127.0.0.1。これがないと、サーバーはリクエストが HTTPS で届いたかどうかを判断できず、セッション Cookie に Secure が付きません。チームモードの起動時にはその旨が表示され、サインインが平文の HTTP でネットワークを通る場合にもそのことが表示されます。
  • 公開ホスト名を指定します：--allowed-hosts mm.example.com。
  • サブパスで提供するには --base-path /mm/ を使います。
  • クライアントアドレスごとに、1 分あたり 600 件の API リクエストまで可能です。多くの人が 1 つのアドレスを共有する場合は、MM_API_RATE_LIMIT（60～100000）で引き上げてください。
  • 同時に開ける接続は最大 1000 件（MM_MAX_CONNECTIONS、16～100000）、1 つのアドレスからは最大 256 件（MM_MAX_CONNECTIONS_PER_IP、2～100000）です。これを超えた接続は閉じられ、ログには 1 アドレスにつき 1 分に 1 回その旨が記録されます。ブラウザーは約 6 本の接続を開いたままにするため、NAT、VPN、Docker Desktop の背後など、多くの人が 1 つのアドレスから Mongo Manager にアクセスする環境では、MM_MAX_CONNECTIONS_PER_IP を引き上げてください。信頼するプロキシの背後では総数だけが適用されます。すべての接続がプロキシから来るため、クライアントの制限はプロキシ側で行ってください。
  • インポートとエクスポートのファイルは <data directory>/transfer に置かれます。 MM_TRANSFER_MAX_UPLOAD は最大アップロードサイズ（MiB、既定 1024、1～65536）、 MM_TRANSFER_QUOTA は各ユーザーが保持できるストレージ（MiB、既定 5120、16～1048576）、 MM_TRANSFER_TOTAL_QUOTA は全ユーザーの合計で保持できる量（MiB、既定 51200。MM_TRANSFER_QUOTA のほうが大きい場合はその値。16～16777216）、 MM_TRANSFER_TTL_HOURS はファイルの保持時間（既定 24、1～720）、 MM_TRANSFER_MAX_JOB_HOURS は 1 回のインポートまたはエクスポートが実行できる時間（既定 6、1～72）です。ディスクには、合計値分の空き容量を確保してください。ファイルを転送する人数に割り当てを掛けた値のほうが小さい場合は、その値で構いません。

設定と環境変数

サーバーの各設定は、コマンドラインオプション、環境変数、または --config もしくは MM_CONFIG で指定した JSON 設定ファイルで指定できます。優先順位は、コマンドライン、環境変数、ファイルの順です。スイッチには 1/0、 true/false、yes/no、 on/off のいずれかを指定できます。各機能の設定は、以下のそれぞれのセクションにあります。

変数 オプション 説明
MM_WEB_PORT -p, --web-port Web インターフェースのポート（既定は 4321）。
MM_HOST --host 待ち受けるアドレス（既定は 127.0.0.1）。ネットワークアドレスにはチームモード、または MM_UNSAFE_NO_AUTH が必要です。
MM_AUTH --auth チームモード：ユーザー、ロール、サインイン（既定はオフ）。
MM_DATA_DIR --data-dir データディレクトリ（既定は ~/.mongo-manager）。
MM_CONFIG --config JSON 設定ファイル。Linux と macOS では、シークレットを含むファイルがほかのユーザーから読める状態だと、サーバーはそのファイルを拒否します。
MM_SECRET_KEY 暗号化キー。データディレクトリの secret.key の代わりに使います。
MM_OPEN --open 起動時にブラウザーを開きます（既定はオン）。ローカルモードで、ループバックアドレスを使い、ターミナルから起動した場合に限ります。
MM_URI --uri ごく最初の起動時にだけ作成される接続。パスワードを含む接続文字列には変数を使ってください。コマンドラインはほかのユーザーから見えます。
MM_READ_ONLY --read-only 各接続自体の設定にかかわらず、どの接続でもデータを変更できません。
MM_TRUSTED_PROXIES --trusted-proxies プロキシのアドレスまたは CIDR 範囲。ここからの X-Forwarded-* ヘッダーが信頼されます。
MM_ALLOWED_HOSTS --allowed-hosts サーバーが応答するホスト名の一覧（これ以外には応答しません）。未設定の場合、ループバックで待ち受けているときはループバック名に、それ以外のときはループバック名と IP アドレスにのみ応答し、ほかの名前には応答しません（DNS リバインディング対策。起動時にその旨が表示されます）。人々がアクセスに使うホスト名はすべてここに指定してください。
MM_BASE_PATH --base-path アプリを /mm/ などのサブパスで提供します。
MM_UNSAFE_NO_AUTH --unsafe-no-auth チームモードなしでネットワークアドレスを許可します。到達できる人は誰でも完全なアクセス権を持ちます。
MM_LOG_LEVEL --log-level fatal、error、warn、info（既定）、 debug、trace、silent。
MM_LOG_FILE --log-file JSON ログを標準出力ではなく、このファイルに追記します。ファイルは非公開になり（モード 0600。Windows では全ユーザーへのアクセスが取り消され、このアカウント、SYSTEM、Administrators だけが保持します）、10 MiB でローテーションされ、直前の分は <file>.1 として残ります。リンクであるパス、ほかの名前を持つファイル（ハードリンク）、通常のファイルではないパスは拒否され、起動はその旨を示して失敗します。削除または名前を変更するか、別のログファイルを指定してください。書き込めない行（ディスクの空き容量不足など）は破棄され、標準エラーに一度だけ通知されます。リクエストはパスで記録され、すべてのクエリ値と GridFS ファイルの ID は *** と書かれます。
MM_REQUIRE_ADMIN_2FA すべての管理者は、ほかの操作より先に二要素サインインを設定する必要があります。その後、アプリ内でオフにすることはできません。この変数がなくても、管理者はアプリ内で同じ要件を設定できます。
MM_REQUIRE_2FA ロールにかかわらず、すべてのユーザーは、ほかの操作より先に二要素サインインを設定する必要があります。その後、アプリ内でオフにすることはできません。この変数がなくても、管理者はアプリ内で同じ要件を設定できます。
MM_METRICS_TOKEN <base path>metrics で Prometheus メトリクスを有効にします。このトークンをベアラートークンとして読み取ります（32 文字以上）。数値にはユーザー、接続、データベース、コレクションの名前は含まれません。
MM_GRIDFS_MAX_MB GridFS にアップロードできる最大ファイルサイズ（MB、既定 512、1～10240）。
MM_MODEL_MAX_DOCS 1 つのデータモデル（データベースのモデルセクション）が合計でサンプリングできるドキュメント数（既定 20000、100～1000000）。コレクションが多い場合は各コレクションのサンプルが小さくなり、セクションにその旨が表示されます。
MM_ALLOW_KERBEROS チームモード：Kerberos（GSSAPI）接続を許可します（既定はオフ）。サーバーを実行しているアカウントの Kerberos チケットでサインインするため、そのような接続のユーザー全員が、そのアカウントとしてサインインします。セキュリティを参照してください。
MM_ALLOW_WORKLOAD_IDENTITY チームモード：接続側で選択した場合に、OIDC 接続がマシンのワークロードアイデンティティ（Azure、GCP、Kubernetes）を使えるようにします（既定はオフ）。
MM_OIDC_DEVICE_FLOW コードによる OIDC サインイン（デバイスフロー）。ブラウザーをこのサーバーに戻せない ID プロバイダー向けです。コードを承認した人がサインインするため、チームモードではここでオンにしない限りオフで、ローカルモードではオンです。
MM_OIDC_PRIVATE_NETWORKS OIDC の ID プロバイダーが存在してよいプライベートネットワーク（カンマ区切りの CIDR）。そこでは平文の http のみが許可されます。これがない場合、ID プロバイダーは公開された https アドレスである必要があります。
MM_CRYPT_SHARED_LIB_PATH クライアント側暗号化に使う crypt_shared ライブラリ（mongo_crypt_v1）の絶対パス。チームモードでは、これだけが読み込まれます。
MM_KMS_PRIVATE_NETWORKS 鍵管理サービス（オンプレミスの KMIP サーバーなど）が存在してよいプライベートネットワーク（カンマ区切りの CIDR）。これがない場合、鍵管理サービスは公開アドレスである必要があります。
MM_KMS_ALLOWED_HOSTS 接続が、各プロバイダー自身のもの（AWS KMS、Microsoft サインインを使う Azure Key Vault と Managed HSM、Google Cloud KMS）と設定で指定されたエンドポイントに加えて到達できる、鍵管理サービスのホスト（カンマ区切り。host または host:port、ポートの既定は 443）。VPC エンドポイントや KMIP サーバーなどが該当します。これ以外のホストやポートは拒否されます。データキーのマスターキーが、KMS トークンをほかへ送ることはできません。

Kerberos とクライアント側暗号化（npm パッケージ）

Kerberos（GSSAPI）と、クライアント側のフィールドレベル暗号化 / Queryable Encryption にはネイティブパッケージが必要です。Mongo Manager はこれらを自動ではインストールせず、インストール時にパッケージのインストールスクリプトも実行しません。使用するには、npm パッケージと同じ場所にこれらのパッケージをインストールし、再起動してください。 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager は、mongo-manager 自体が置かれているグローバルな node_modules フォルダー（実パスで確認し、その上位のフォルダーは対象外）からのみ、接続が最初にそれを必要としたときに限って読み込みます。接続フォームには、どちらが足りないか、どうインストールするかが表示されます。スタンドアロンのバイナリ、Docker イメージ（MM_DISTRIBUTION=docker を設定しています）、Windows サービスが実行元とするコピーにはネイティブモジュールが含まれないため、これらでは、この 2 つの機能はこのパッケージでは利用できないと表示されます。その場合は、npm パッケージをフォアグラウンドで実行してください。Queryable Encryption の自動暗号化には、crypt_shared ライブラリ（MM_CRYPT_SHARED_LIB_PATH）または mongocryptd と、MongoDB Enterprise または Atlas も必要です。MongoDB Community は復号のみ可能です。MONGODB-OIDC にはパッケージは不要です。ただし ID プロバイダー側で、このサーバーの <address><base path>oidc/callback をリダイレクトアドレス（または接続で指定した別のアドレス）として登録しておく必要があり、それが使えない環境では、コードを使ってサインインできます。

アプリとしてインストール

Chrome または Edge では、アドレスバーの Mongo Manager をインストールを選ぶと、デスクトップやスタートメニューから専用のウィンドウで開けるようになります。

バックアップ先

  • MM_BACKUP_FOLDER_ROOTS：サーバーフォルダーのバックアップ先が使えるフォルダー。絶対パスをシステムのパス区切り文字（Linux と macOS では :、Windows では ;）で区切って指定し、最大 16 件です。既定は指定なしで、この場合はフォルダーのバックアップ先を作成できません。相対パスを指定すると、サーバーは起動時に停止します。各ルートにはサービスアカウントの書き込み権限を付与し、ルートはデータディレクトリの外に置いてください。データディレクトリ内のフォルダーのバックアップ先は拒否されます。起動のたびに、サーバーが書き込めないルートがログに記録されます。Linux サービスの場合：
    • サンドボックスは、データディレクトリと、インストール時に設定ファイルと env ファイルで指定されたルートにしか書き込めません。これらを変更したあとは、sudo mongo-manager service install をもう一度実行し（データ、設定、キーは保持されます）、存在しなかったルートを作成したあとはサービスを再起動してください。ドロップインの Environment= など、ほかの場所で設定したルートはインストール時に認識されず、そのフォルダーはサービスから読み取り専用のままになります。
    • インストールは、サービスが到達できない /home、/root、/run/user、 /tmp、/var/tmp、/dev 配下のルートと、サンドボックスを無効にしてしまうルートを除外します。システムディレクトリ（/、 /var、/var/lib など）を含むルートや、/etc、 /usr、/run などのシステムディレクトリの内側にあるルートがこれに当たります（/var の下では、/var/backups 内のフォルダーだけが開放されています）。/srv、 /opt、または /mnt や /media 配下のマウント内のフォルダーは適していますが、それらのフォルダー自体は適していません。リムーバブルまたはネットワークのファイルシステムでは、ディスクや共有を管理する人がその上のフォルダーも管理できるため、マウントポイント自体をルートにしてください（ユーザーの FUSE マウントは、その所有者やリンクについて任意の内容を返せます）。別のルートの内側にあるルートは、その別のルートによってサンドボックスに含まれます。/srv、/opt、/mnt 自体が、ostree システム（Fedora Silverblue、CoreOS）のように /var へのリンクになっている場合、インストールはルートがどこに通じているかを示し、そこでは拒否されます。/var/backups 内のフォルダーを選んでください。
    • リンクは、それが指す先で判断され、ユニットにはその場所が記録されます。どこにも通じていないリンクは除外されます。まだ作られていないフォルダーへのリンクの場合は、そのフォルダーを作成してから service install をもう一度実行してください。ループになっているリンクやファイルを経由するリンクの場合は、別のフォルダーを選ぶか、リンクを削除してください。ルートより上位の各フォルダーと、途中のリンクが含まれるフォルダー（リンクの指す先にあるリンクも含む）は、所有者を root にし、グループとその他のユーザーに対して閉じておいてください。これにより、誰もそこにあるフォルダーの代わりにリンクを置けなくなります。他のユーザーが書き込める（スティッキーかどうかは問いません）フォルダーでは、その中のフォルダーの所有者を root にし、ルートはそのさらに内側に作成してください。
    • サービスのユーザーが変更できるフォルダー（/ までのどこか、およびそのパス上のリンクを辿った先も含む）の下にあるルートは除外されます。具体的には、そのユーザーが所有している場合、グループ、ACL、または誰でも書き込める権限を通じて書き込める場合です。そのユーザーとして動作するプロセスが、フォルダーの代わりに /etc へのリンクを置けてしまうためです。サービスが書き込む別のルート内のリンクも同様です。インストールと、sudo で実行した doctor は、システムにも問い合わせます。setpriv があれば、そのユーザーとして test -w を実行し、カーネルがそのグループ（ユニットが Group= や SupplementaryGroups= でサービスに与えるもので、ドロップインのものも含む）と ACL を適用します。setpriv がない場合や root でない場合は、フォルダーのモードとユーザーのグループだけを読み取り、どちらの場合もその旨が表示されます。モードが許可していれば、ACL がそれを取り消していても許可として扱われるため、そのようなフォルダーもルートから除外されます。
    • インストールは、すべてのドロップインを読み込んだうえで、systemd にサービスの実行ユーザーを問い合わせます。--user 以外のユーザー（または root）としてサービスを実行するドロップイン、DynamicUser=yes で同名のアカウントがない場合、ユーザー自身のものとは異なる Group= がある場合、システムに存在しないグループがある場合（その場合 systemd は起動を拒否します）は、データディレクトリと設定が変更される前にインストールが停止します。理由が表示され、サービスは停止し無効のままになります。グループの検索に失敗した場合や、systemd に問い合わせられない場合は、すべてのルートが除外されます。
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json は、インストールされたサービスを検査します（単なる mongo-manager doctor は、ご自身のデータディレクトリを検査し、サービスを検査したわけではないと表示します）。各ルートについて、存在すること、サーバーが書き込めるディレクトリであること、サンドボックス内にあること、データディレクトリの内側にないことを確認します。また、サンドボックスがサービスに書き込みを許可しているのに、どのルートにも指定されなくなったフォルダー、あるいは root 以外が変更できるリンクを通じてルートやデータディレクトリに通じているフォルダーを示します。さらに、root として動作しているサービス、誰も所有していない、または検索に失敗するグループ、同名のアカウントがない DynamicUser=yes について警告します。検査するのはサービスの設定ファイルと env ファイルで指定されたルートで、env ファイルは root だけが読め、サービスのシークレットキーもそこにあるため、sudo が必要です。書き込み権限は、サービスの実行ユーザーとして確認します。root として実行した場合は、データディレクトリを所有するユーザーについて、root の所有者とモードを読み取り、そのユーザーが書き込めるかどうかはシステムの判断に従います。ルートより上位のフォルダーは、ユニットがサービスを実行するユーザー（その User=）の立場で判定されます。
  • MM_BACKUP_PRIVATE_NETWORKS：バックアップ先が到達してよいプライベート範囲。カンマ区切りで最大 64 個の CIDR を指定します（例：10.0.5.0/24）。その範囲内では平文の HTTP が許可されます。既定は指定なしです。ループバック、10/8、172.16/12、192.168/16、CGNAT（100.64.0.0/10）、ユニークローカル（fc00::/7）の範囲を指定できます。パブリックな範囲を指定するとサーバーは起動時に停止し、リンクローカルまたはクラウドメタデータの範囲（169.254.0.0/16、fe80::/10、169.254.169.254、fd00:ec2::254、100.100.100.200）の内側にある範囲も、IPv4 マップや NAT64 を含むどのような形式でも同様に停止します。メッセージにはその範囲が示されます。これらのアドレスには、指定した範囲の内側であっても到達できません。
  • MM_BACKUP_PROXY：バックアップ先に接続するときに経由する HTTP(S) プロキシ。http://proxy.corp:3128 や https://user:password@proxy.corp のように指定し、パスやクエリは付けません。既定は指定なしです（環境のプロキシ変数は一切読み込まれません）。Mongo Manager は引き続き各バックアップ先のアドレスを自分で解決して確認し、そのアドレスへ接続するようプロキシに依頼するため、上記のアドレスのルールはプロキシを経由しても適用されます。TLS はバックアップ先までエンドツーエンドで動作し、証明書はプロキシがない場合と同様に検証されます。 MM_BACKUP_PRIVATE_NETWORKS 内のバックアップ先には直接接続します。リンクローカルまたはメタデータのアドレスにあるプロキシを指定すると、サーバーは起動時に停止します。プロキシのパスワードはアドレスの一部なので、共有のシェル履歴に残さないでください。このプロキシを使うのはバックアップ先だけで、アラートチャンネル（メールと Webhook）、AI プロバイダー、プラグインがプロキシを経由することはありません。プロキシを選ぶ前に知っておくべきこと：http:// のプロキシはユーザー名とパスワードを平文で受け取る（Basic）ため、https:// または信頼できるネットワーク内のプロキシを推奨します。CONNECT を、一覧にあるホスト名にだけ許可しているプロキシは、IP アドレスを指定されるためこれらの接続を拒否します。https:// のプロキシの証明書は、Node.js が信頼する認証局（組み込みの一覧、または NODE_EXTRA_CA_CERTS で追加したもの）によって署名されている必要があり、独自の CA は指定できません。
  • MM_BACKUP_DEST_PART_MB：アップロードのパートサイズ。16～512 MiB（既定 64）。
  • MM_BACKUP_DRILL_MAX_MB：リストアドリルが書き込む最大量（MiB）。既定は指定なしで、ドリルは MongoDB が報告する空きディスク容量の半分未満に収まります（mongos 経由では最も使用量の多いシャードの値）。MongoDB が空き容量を報告しない環境（Atlas の共有ティア）では、この設定がある場合にのみドリルが実行されます。
  • MM_BACKUP_DEST_TRANSFERS：各バックアップ先で同時に実行される送信とダウンロードの数。1～8（既定 2）。それ以降は待機し、ジョブ一覧でそのバックアップ先を「待機先」として表示します。

スケジュールバックアップ

  • MM_BACKUP_SCHEDULES：スケジューラー。既定でオンです。0 でオフになります。スケジュールの設定は保持されますが何も実行されず、スケジュールバックアップタブにスケジュールがオフであることが表示されます。停止したサーバーが未完了のまま残した実行は、起動時に終了処理されます。
  • MM_BACKUP_SCHEDULE_CONCURRENCY：同時に実行されるスケジュール実行の数。1～8（既定 2）。実行時刻を迎えたそれ以外の実行は最大 6 時間待機します。

変更の監視

  • MM_WATCH：チェンジストリームのフィード。既定でオンです。0 でオフになり、監視セクションに監視がオフであることが表示され、MongoDB 上では何も開かれません。
  • MM_WATCH_MAX_FEEDS：このサーバー上で同時に存在できるライブフィードの数。1～500（既定 50）。1 ユーザーあたり 5 件、ブラウザーウィンドウあたり 3 件までです。各フィードは MongoDB 上で 1 つのチェンジストリームカーソルを保持します。
  • 監視にはレプリカセット、シャーディングされたクラスター、またはロードバランサー経由のデプロイメントが必要で、接続のデータベースユーザーには、監視対象に対する changeStream と find が必要です。変更の監視を参照してください。

ライブ同期

  • MM_LIVE_SYNC：接続間のライブ同期。既定でオンです。0 でオフになります。実行中の同期は理由を示して待機し、何も読み書きされず、新規の同期は拒否されます。再びオンにすると、停止した場所から再開します。
  • MM_LIVE_SYNC_MAX：このサーバー上で終了していないライブ同期の数。1～100（既定 10）。1 ユーザーあたり 3 件までです。実行中の各同期は、同期元で 1 つのチェンジストリームを保持し、両方の接続を開いたままにします。
  • 同期元は、レプリカセット、シャーディングされたクラスター、またはロードバランサー経由のデプロイメントである必要があります（MongoDB 6.0 以降）。同期元の oplog より長く残る可能性があるコピーでは、確認が求められます。ライブ同期を参照してください。

アラート

  • MM_ALERTS（設定ファイル：alerts.enabled）：アラート。既定でオンです。 0 でオフになり、何も評価も送信もされず、アラートページにアラートがオフであることが表示されます。
  • MM_ALERTS_PRIVATE_NETWORKS（設定ファイル：alerts.privateNetworks、リスト）：パブリックアドレスに加えて、アラートのメールサーバーと Webhook が到達してよいネットワーク。カンマ区切りで最大 64 個の CIDR を指定します（例：10.0.5.0/24）。既定は指定なしです。Webhook への平文の http は、この範囲内でのみ許可されます。指定できる範囲と拒否される範囲は MM_BACKUP_PRIVATE_NETWORKS と同じで、リンクローカルとクラウドメタデータのアドレスには到達できません。
  • 設定ファイルでは： "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }。サーバー管理を参照してください。

高度なシェル

  • 完全に無効にするには、--no-shell（または MM_SHELL_ENABLED=0）を指定します。
  • 制限：MM_SHELL_MAX_PER_USER、MM_SHELL_MAX_TOTAL、 MM_SHELL_COMMAND_TIMEOUT_MS、MM_SHELL_IDLE_MS、 MM_SHELL_LIFETIME_MS。ページが保持しているシェルは、Compass と同様に、使われなくなってもいつまでも開いたままです。どのページも保持していないシェルは、ページが閉じてから 2 分後に閉じられます。アイドル制限は、設定しない限りオフ（0）です（設定する場合は 10000～86400000 ms）。シェルの寿命は、別の値を設定しない限り最長 12 時間です（60000～86400000 ms、または制限なしの 0）。開いたままのシェルは、そのページが閉じるまで MM_SHELL_MAX_TOTAL に数えられます。多くの人が共有するサーバーでは、開いたまま使われていないシェルが解放されるよう、MM_SHELL_IDLE_MS を設定してください。サインインがオンの場合、シェルは、そのユーザーのサインインセッションが終了したとき、ユーザーのロールが変更されたとき、アカウントが無効になったときにも終了します。
  • MM_SHELL_RSS_MB：シェルのプロセスが保持できるメモリ。128～16384 MB（既定 384）。サーバーはオペレーティングシステムから自分で測定し（Windows では tasklist、macOS では ps）、これを超えたシェルを再起動します。シェルの変数は失われます。コマンドが実行されていない間に 15 秒間応答しないシェルも再起動されます。 MM_SHELL_OUTPUT_MB：1 つのコマンドの出力。1～64 MB（既定 5）。それを超えた分は切り捨てられます。 MM_SHELL_COMMANDS_PER_SECOND：シェルごとの 1 秒あたりのコマンド数。1～1000（既定 20）。
  • root の POSIX サーバーでは、シェルワーカーは MM_SHELL_UID/MM_SHELL_GID（既定 65534）に権限を下げます。サービスを root で実行しないでください。

AI アシスタント

  • MM_AI：AI アシスタント。既定でオンですが、管理者がプロバイダーを追加するまで表示されません（設定 → AI アシスタント）。0 にすると、あらゆる場所で非表示になり、リクエストは拒否されます。
  • MM_AI_PRIVATE_NETWORKS：パブリックアドレスに加えて、プロバイダーが存在してよいネットワーク（CIDR、カンマ区切り）。たとえば 10.0.0.5 の Ollama などです。平文の http はそこでのみ許可されます。クラウドメタデータとリンクローカルのアドレスには到達できません。ローカルモードでは、このマシンは常に許可されます。
  • MM_AI_PER_MINUTE（既定 10、1～120）と MM_AI_PER_DAY（既定 200、1～10,000）：1 人あたりのリクエスト数。MM_AI_MAX_CONCURRENT（既定 8、1～64）：サーバー全体での同時リクエスト数。1 人あたり 2 件までです。MM_AI_AGENT_PER_MINUTE（既定 30、1～120）：1 件のメッセージ内でエージェントがプロバイダーに送る追加のリクエストの、1 人あたり 1 分間の上限です（1 日の上限にも数えられます）。
  • MM_AI_CHAT_DAYS（既定 30、0～365）：最後のメッセージからチャットを保持する日数。 0 にすると、チャットはメモリ上にのみ保持され（12 時間）、以前の設定で保存されたチャットはサーバーの起動時に削除されます。

プラグイン

  • MM_PLUGINS：プラグイン。既定でオンです。各プラグインは、セキュリティスキャンのあとに管理者の承認が必要です。0 にすると、プラグインの検索、インストール、実行は一切行われません（プラグインを参照）。
  • MM_PLUGINS_GITHUB：公開 GitHub リポジトリのリリースからのプラグインのインストール。既定ではオフです（プラグインはアップロードまたはフォルダーからインストールします）。1 で許可されます。その場合、サーバーは自分では何も送信せずに、https で api.github.com、github.com、GitHub のリリースアセットのホストに接続します。オフのままなら、サーバーが GitHub に接続することはありません。サーバーは GitHub に直接接続します。HTTP プロキシの設定は使われないため、プロキシ経由でしか外部に接続できないサーバーでは、プラグインをアップロードでインストールしてください。システムサービスは、config.json の "pluginsGithub": true から読み取ります（Linux は /etc/mongo-manager/config.json、Windows は %ProgramData%\Mongo Manager\config.json、macOS は /Library/Application Support/Mongo Manager/config.json）。変更後はサービスを再起動してください。
