サーバー管理

Mongo Manager は、データだけでなく MongoDB サーバー自体も管理します。データベースユーザーとロール、クラスターのシャーディング、問題が起きたときのアラート、各接続の状態を一目で確認できるヘルス表示です。

ユーザーとロール

接続のページ → ユーザーとロール では、Atlas の Database Access のように、MongoDB 自体のアカウントを管理します。これらはアプリケーションやユーザーが MongoDB にサインインするためのアカウントであり、Mongo Manager のユーザーではありません。

使用できるユーザー

  • その接続に対してアプリの権限 databases:admin を持つユーザー: アプリの管理者、またはその接続の管理権限を付与されたユーザーです。管理者によって個人データを非表示にされているユーザーには、このセクションは表示されません。自分で非表示にしているユーザーには表示されます。
  • MongoDB 自体の権限も適用されます。接続がサインインに使うアカウントには、データベースに対する userAdmin、または userAdminAnyDatabase が必要です (一覧表示には viewUser と viewRole で足ります)。MongoDB が拒否した場合、ページには、アプリではなく MongoDB が拒否したこと、およびどのコマンドかが表示されます。
  • 読み取り専用の接続では、ユーザーとロールは一覧表示されますが、変更はできません。

一覧

すべてのデータベース、または 1 つのデータベース (データベースフィルター) のユーザーを、検索付きで表示します。各ユーザーのロールはチップで表示されます (たとえば「readWrite on shop」)。接続自体がサインインに使っているアカウントには この接続 と表示されます。

ユーザーを追加する

  • 認証データベース: ユーザーがサインインする場所です。admin を推奨します (そこのユーザーは任意のデータベースのロールを持てます) が、どのデータベースでも使えます。$external は x.509、LDAP、Kerberos、AWS IAM のユーザー用で、これらにはパスワードがありません。名前は、その認証元が送信する内容と完全に一致している必要があります。
  • ユーザー名。
  • パスワード: 入力するか、生成 を押して 24 文字のランダムな文字列を作成します。この文字列はブラウザー内でシステムの乱数源から作られ、接続文字列でも安全に使え、コピーできるよう表示されます。
  • ロール: 許可内容が併記された組み込みロール、またはデータベースごとのカスタムロールです。admin にのみ存在するロール (clusterMonitor、backup、root など) は、そこに固定されます。

パスワードには SCRAM-SHA-256 が使われ、12 文字以上が必要です。パスワードは MongoDB に一度だけ送信され、Mongo Manager が保存、ログ出力、監査ログへの書き込みを行うことは一切ありません。生成されたパスワードは、フォームを閉じる前にコピーしてください。広範な権限を付与するときは事前に確認が求められ、確認なしの場合はサーバーが拒否します。対象は次のとおりです。組み込みロールの root、userAdminAnyDatabase、userAdmin、dbOwner、clusterAdmin、clusterManager、hostManager、backup、restore、readWriteAnyDatabase、dbAdminAnyDatabase。admin データベースのその他すべての組み込みロール (readAnyDatabase、clusterMonitor、enableSharding)。local (oplog、つまりすべての書き込みを保持) または config (シャーディングのメタデータ) の任意のロール。そして、これらのいずれかを継承するカスタムロール、クラスター、任意のリソース、すべてのデータベース全体、または local や config に対する権限を持つカスタムロール、あるいはユーザーやロールを作成するカスタムロール (createUser、grantRole、changePassword など) です。このようなカスタムロールには「広範」というマークが付き、作成時にも確認が求められます。

ユーザーの変更と削除

  • 編集 では、新しいパスワード、新しいロール、またはその両方を設定します。保存したロールは、ユーザーのロール一覧を置き換えます。
  • 接続自身のアカウントを変更または削除すると、接続からロックアウトされる可能性があるという警告が表示され、確認が必要です。そのアカウントが持つカスタムロールを変更または削除する場合も同様です。どのアカウントがそれにあたるかは、(SRV レコードや証明書によって変わりうる接続の設定ではなく) MongoDB 自体が判断します。新しいパスワードを設定したら、接続も編集してください。
  • ユーザーまたはロールを削除するときは、その名前の入力が求められます。

カスタムロール

カスタムロール を使うと、チームに必要なアクションだけを正確に与えることができます。ロールには、データベース、名前、権限、継承するロールがあります。

  • 各権限は、データベースとコレクション (空にすると任意のデータベースまたは任意のコレクション)、クラスター、または任意のリソースに適用されます。
  • アクションは MongoDB の一覧から選択します。クエリと書き込み、データベース管理、ユーザーとロール、デプロイメント、レプリケーション、シャーディングに分類されています。
  • admin 以外のロールは、自身のデータベースのロールのみを継承できます (MongoDB の規則)。admin のロールは、任意のデータベースのロールを継承できます。

すべての変更は、mongo.users.create、mongo.users.update、mongo.users.grant、mongo.users.revoke、mongo.users.drop、mongo.roles.create、mongo.roles.update、mongo.roles.drop として監査ログに記録されます。名前とロールの一覧は記録されますが、パスワードは記録されません。

シャーディング

接続のページ → シャーディング は、接続先が mongos の場合に表示されます。サーバーを監視できるユーザーなら誰でも、バランサーの状態、チャンクの分布、クラスターの概要を確認できます。変更には databases:admin と、読み取り専用ではない接続が必要です。

チャンクの分布

シャーディングされたコレクションごとに 1 本のバーを表示し、シャードごとに色分けします。件数は、スクリーンリーダー向けに文字でも提供されます。

バランサー

  • 開始と停止ができ、停止する前に確認が求められます。停止中は、シャード間でチャンクが移動しません。進行中の移行は先に完了します。バックアップやメンテナンスの際は停止し、その後に再び開始してください。
  • アクティブな時間帯: 開始から終了まで、config サーバーの時計を基準にします。チャンクはその時間内にのみ移動します。常時 を選ぶと解除されます。

コレクションをシャーディングする

  1. データベースとコレクションを選びます。
  2. シャードキーをフィールドごとに組み立てます。各フィールドは範囲またはハッシュで、ハッシュのフィールドは最大 1 つです。順序が重要です。フィールドを上下に移動して調整します。
  3. このキーを確認: サーバーが 1000 件のドキュメントをサンプリングし、件数のみを返すため、MongoDB から値が外に出ることはありません。各フィールドを持つドキュメントの割合、異なる値の数、最も多い値の割合、値が時間とともに増加するか (ObjectId、日付)、キーのフィールドで始まるインデックスがあるか、が分かります。判定は良好、普通、不良のいずれかです。
  4. オプション: 一意 (範囲キーのみ)、チャンクを事前に作成 (空のコレクション上のハッシュキー、MongoDB 6.0 以前、1 から 8192 個のチャンク)、ゾーンごとにチャンクを作成 (ハッシュキー。ゾーンが定義済みの場合)。
  5. シャーディングは元に戻せません。名前空間を入力して確認します。

時間とともに増加するフィールドを範囲キーとして使うと、新しいドキュメントがすべて 1 つのシャードに送られます。そのフィールドをハッシュにするか、別のフィールドを先頭にしてください。データのあるコレクションは、シャーディングする前に、キーのフィールドで始まるインデックスが必要です。MongoDB 自体の名前空間とシステムの名前空間 (admin、config、local、system.*) は拒否されます。

ゾーン

  • 各シャードにそのゾーンが一覧表示されます。シャードにゾーンを追加したり、削除したりできます。
  • コレクションごとのキー範囲: 境界は、シャードキーのフィールドの Extended JSON で指定し、開いた端には {"$minKey":1} と {"$maxKey":1} を使います。たとえば {"region": "eu"} から {"region": "us"} です。演算子は拒否されます。開始は含まれ、終了は含まれません。
  • 範囲を削除すると、そのドキュメントは再び任意のシャードに置けるようになります。

監査ログには、sharding.collection.shard、sharding.zone.shard、sharding.zone.range (名前空間とゾーンのみで、境界の値は記録されません)、sharding.balancer、sharding.balancer.window が記録されます。Mongo Manager のテストでは、これらの画面を記録済みの mongos の応答に対して実行しています。

アラート

アラートは、サーバーがしきい値を超えたとき、またはアプリ自体のジョブが失敗したときに、ベルアイコン、メール、または Webhook で通知します。

しきい値

接続のページ → アラート。アプリの管理者 (settings:manage) が使用できます。しきい値は 1 つのメトリクスを監視します。

  • 接続: 開いているクライアント接続 (件数)。
  • 操作数: 1 秒あたりの操作数 (すべての種類の合計)。
  • レプリケーションラグ: 最も遅れているセカンダリの遅延秒数 (レプリカセット)。
  • WiredTiger キャッシュ: キャッシュの使用率 (パーセント)。
  • ディスク使用率: データファイルのディスクの使用率 (パーセント。MongoDB 4.4 以降)。
  • 低速な操作: 指定した秒数より長く実行されている操作の件数 (clusterMonitor が必要)。

サーバーは、メトリクス履歴と同じ serverStatus のサンプリングを使って、これらを 1 分に 1 回評価します。アラートは、履歴がオフの接続でもサンプリングします。サンプルが保存されるのは、履歴がオンのときだけです。サンプリングされる接続は、履歴とアラートを合わせて最大 50 件です。

フラッピングは起こりません。値が指定した分数 (1 から 60、既定は 2) の間しきい値を超え続けた場合にアラートが発生し、同じ時間だけしきい値の 90% 以下にとどまった後でのみ解決されます。キャッシュ使用率のしきい値が 80% の場合、72% 以下で解決されます。

イベントアラート

アラートページで、すべての接続または 1 つの接続に対して、あるいは接続のセクションで設定します。

  • バックアップの失敗: バックアップ、送信、取得のジョブが失敗しました。
  • スケジュールバックアップの失敗: 実行が失敗したか、一部のバックアップ先にしか届きませんでした。
  • ライブ同期の停止: 同期が失敗した、停止した、または自身で対応が必要になった場合です。ユーザーが停止した場合は対象外です。
  • ジョブの失敗: その他のジョブ (リストアドリルには専用のイベントがあります)。
  • リストアドリルの失敗: スケジュールされたリストアドリルが、バックアップをリストアできなかった、差異のあるデータを検出した、またはスクラッチデータベースをドロップできなかった場合です (最後は警告で、データは一致していました)。成功したドリルはアラートではなく、スケジュールの履歴に記録されます。
  • 双方向同期で競合を解決: 双方向ライブ同期の両側が同じドキュメントを変更しました。最後に書き込んだ側が優先されました (_id は同期のアクティビティに記録されます)。
  • ウォッチがアラートフィルターに一致: 所有者がアラートを要求した監視フィードで、変更がそのフィルターを通過しました (フィードの実行中、最大で 10 秒に 1 回)。

通知に含まれるのは名前と数値のみです。ドキュメントの値、エラーのテキスト、接続文字列、ホストが含まれることはありません。

スケジュールレポート

アラートページ (アプリの管理者向け): レポートは、1 つの接続のいくつかの件数を、毎朝、毎週月曜日、最短で 1 時間ごとなどのスケジュールで知らせます。アラートと同様に、ベルアイコン、メール、または Webhook で送信されます。各件数には、ラベル、コレクション、任意のフィルター (JSON。指定しない場合はすべてのドキュメント、つまりコレクションの推定値を数えます) があります。100 万件を超える件数は「少なくとも」と表示されます。行から、今すぐ実行、変更、オフにする、削除ができ、直近の実行の件数がそこに表示されます。

数値のみで、値は一切含まれません。個人フィールドを指定するフィルター (または、個人データのルールによって別の解釈になるフィルター) は、レポートの保存時に拒否されます。ルールがその後に変更された場合は、フィルターが除外され、その理由が表示されます。MongoDB 自体の名前空間、サーバーの JavaScript、ビュー、時系列コレクションも同様です (ビューのパイプラインは個人フィールドで選択できてしまうため)。レポートは接続自身の認証情報として扱われます。ユーザーごとにサインインする接続では拒否されます。また、接続がクライアント側でフィールドを暗号化している場合のフィルターも拒否されます (読み取れるものに一致しないため)。ベルアイコンと履歴では、管理者には実行の件数がラベルとともに表示されます。それ以外のユーザーには、レポートが実行されたことだけが表示され、件数は表示されません。各レポートの直近 30 回の実行が履歴に保持されます。スケジュールを算出できなくなったレポートはオフになり、その理由が表示されます。

通知チャネル

  • ベルアイコン。 各ユーザーが、環境設定またはアラートページで、自分用に ベルアイコンにアラートを表示 をオンにします。表示されるのは、サーバーを監視できる接続 (server:monitor) のアラートだけです。
  • メール。 SMTP サーバー、ポート、そして最初から TLS (通常は 465) または STARTTLS (通常は 587) を指定します。どちらも提供しないサーバーは拒否され、メールが平文で送信されることはありません。ユーザー名とパスワード (暗号化して保存)、送信元アドレス、最大 20 件の宛先を設定します。サーバー、ポート、暗号化、ユーザー名のいずれかを新しくする場合は、パスワードを再入力する必要があります。保存済みのパスワードが別のサーバーに送られることはありません。テストメッセージを送信 は、保存済みの設定で送信します。TLS ハンドシェイクややり取りが時間内に完了しないセッションは破棄されます。メールは Mongo Manager 自身のクライアントとそのエグレスガードを経由して送信されます。パブリックアドレスは許可され、プライベートアドレスは MM_ALERTS_PRIVATE_NETWORKS の範囲内のみ許可されます。
  • Webhook。 https のアドレスです。プレーンな http は MM_ALERTS_PRIVATE_NETWORKS 内のアドレスにのみ使えます。アドレスに認証情報を含めることはできず、クラウドのメタデータアドレスとリンクローカルアドレスは常に拒否され、リダイレクトにも従いません。各 Webhook の署名シークレットはサーバーが作成し、一度だけ表示します。新しいシークレットを作成 で置き換えると、古いシークレットはすぐに使えなくなります。

各ルールで送信先を選びます。チャネルのないルールは記録されるだけです。

Webhook の配信

各配信は、JSON 本文を持つ POST です。

{
  "type": "alert.firing",
  "id": "…",
  "at": "2026-10-16T09:30:00.000Z",
  "alert": {
    "metric": "cacheFill",
    "event": null,
    "state": "firing",
    "value": 91,
    "threshold": 80,
    "unit": "percent",
    "startedAt": "2026-10-16T09:28:00.000Z",
    "resolvedAt": null,
    "connection": { "id": "…", "name": "Production" },
    "detail": {}
  }
}

type は alert.firing、alert.resolved、alert.event、alert.test のいずれかです (テストには type と at のみが含まれます)。イベントアラートでは、metric の代わりに event (backup.failed、schedule.failed、liveSync.stopped、job.failed) が設定されます。ヘッダーは次のとおりです。

  • x-mm-event: type と同じ値。
  • x-mm-delivery: 配信の一意な ID。再試行しても同じ値です。
  • x-mm-timestamp: この試行に署名した時刻 (Unix 秒)。
  • x-mm-signature: sha256= に続けて、Webhook のシークレットを使い、タイムスタンプ、ドット、本文を対象にした HMAC-SHA256 の 16 進文字列。

署名は、本文をパースする前に生の本文に対して検証し、5 分より古いタイムスタンプは拒否してください。Node.js の例: 

const crypto = require('node:crypto')

function verify(secret, headers, rawBody) {
  const timestamp = headers['x-mm-timestamp']
  const signature = headers['x-mm-signature'] ?? ''
  if (!/^\d+$/.test(timestamp ?? '')) return false
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected =
    'sha256=' + crypto.createHmac('sha256', secret).update(timestamp + '.' + rawBody).digest('hex')
  const a = Buffer.from(signature)
  const b = Buffer.from(expected)
  return a.length === b.length && crypto.timingSafeEqual(a, b)
}

Python の例:

import hashlib, hmac, time

def verify(secret: bytes, headers, raw_body: bytes) -> bool:
    timestamp = headers.get("x-mm-timestamp", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret, timestamp.encode() + b"." + raw_body, hashlib.sha256)
    expected = "sha256=" + mac.hexdigest()
    return hmac.compare_digest(headers.get("x-mm-signature", ""), expected)

配信は、ネットワークエラー、5xx 応答、408、429 の場合に、2 秒後、10 秒後、60 秒後の最大 3 回まで再試行されます。それ以外の 4xx や、ガードが拒否したアドレスへの配信では再試行されません。各試行は、新しいタイムスタンプで改めて署名されます。すでに処理した配信を無視するには、x-mm-delivery を使用してください。

スヌーズ、一時停止、確認済み

  • ルールを 1 時間、8 時間、または 1 日 スヌーズ できます。アラートは記録されますが、何も送信されません。今すぐ解除 で早めに終了できます。
  • ルールのスイッチで、一時停止と再開ができます。
  • 管理者はアラートを全員に対して 確認済みにする ことができ、他のユーザーには誰が確認したかが表示されます。それ以外のユーザーは、自分のベルアイコンからアラートを 閉じる ことができます。管理者以外のベルアイコンには、何が起きたか (そのコード) は表示されますが、どの同期、ジョブ、スケジュール、名前空間かは表示されません。
  • 配信は、同時に発生するチャネルやアラートの数にかかわらず、1 つのキューから少しずつ行われます。
  • 履歴 は、アラートページと各接続のセクションにあり、90 日間 (最大 20,000 件) を保持し、各配信の結果と試行回数も記録します。

MM_ALERTS=0 を設定すると、サーバーでアラートが無効になり、評価も送信も行われません (デプロイを参照)。監査ログには、alerts.rule.create、alerts.rule.update、alerts.rule.delete、alerts.rule.snooze、alerts.email.update、alerts.email.test、alerts.webhook.create、alerts.webhook.update、alerts.webhook.delete、alerts.webhook.test、alerts.acknowledge が記録されます。SMTP パスワードや Webhook のシークレットは記録されません。

ライブヘルス

概要の接続カードには、各接続の ping レイテンシ、MongoDB のバージョン、トポロジー、発生中のアラートが表示されます。接続のページでは、同じ内容がステータスドット付きでヘッダーに表示されます。

  • サーバーは、各応答を 30 秒間保持します。
  • 一覧が自動的に接続することはありません。開いていない接続には 未接続 と表示されます。接続のページを開くと、データベースの一覧を取得するときと同様に、その接続が確認されます。
  • アラートの件数は、サーバーを監視できる接続についてのみ表示されます。
