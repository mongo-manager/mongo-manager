Building plugins

A plugin adds a view, an action or a page to Mongo Manager: a map of a collection's places, a chart, a duplicate finder, a translator from SQL. This guide is for people who build one. It covers the files a plugin is made of, everything it may ask the app, the rules the app enforces, and how to package, test and publish it. Administrators install and approve plugins on the Plugins page; see Security for the approval model. That page lists them all, and narrows the list to the enabled ones, those that need an administrator (waiting for an approval, changed or broken) or the disabled ones, to one source, and to those a search finds by name, description, id, version, the permissions they ask for or what they add.

What a plugin is

A plugin is a folder of static files: an HTML page, its scripts, styles, images and fonts, and a manifest named mongo-manager-plugin.json that says what it adds and what it may do. The app shows the page in a sandboxed frame and the page talks to the app only by messages: it asks for documents, the app answers as the signed-in user, with that user's rights and the app's masking.

  • No server code. Nothing of a plugin runs on the server. The server stores its files, checks them, and serves them to the frame.
  • No network. The page cannot fetch from any address, not even the server it came from. It has no cookies, no storage and no access to the app's page. Two ways out are left to the browser: WebRTC is blocked only by browsers that enforce the policy's webrtc directive — Chromium-based browsers (Chrome, Edge) ignore it as of version 149, and do not count on Firefox either — so on those a plugin can still send what it reads out over WebRTC; and a prefetch hint (dns-prefetch, preconnect) can have a name looked up. The frame asks the browser not to prefetch, and the scan flags both as high risks — but the scan reads the files' text for known patterns: code written to slip past it is not found. Approve only plugins you trust.
  • Nothing without approval. A plugin runs only after an administrator approved its exact files and the permissions it asks for. Every change to its files needs a new approval.
  • Changes go through the user. A plugin that may change documents asks; the app shows the change in its own dialog and the user decides. A query or a pipeline a plugin prepares is put in the user's own editors, where nothing runs until the user runs it.

Mongo Manager ships several plugins of its own (Map, Charts, Schema health, Duplicate finder, Value search, References, Document diff, SQL to MongoDB, Time hints, Binary preview, Data dictionary, Local time, Log analyzer, Test data, Reshape, Anonymiser, Search playground, Shard key analyzer, Storage report, Validation check, Legacy UUIDs, Date filters, Index script, Expiry (TTL), Personal data finder, Document size). They run in the same sandbox, talk through the same bridge and are scanned the same way as yours; being the app's own code, approving one never asks for its id (see Versions and approval). Plugins can be turned off for a whole server with MM_PLUGINS=0 (see Deployment).

Quick start

Start from the starter template: on the Plugins page, under Build your own plugin, choose Download the starter (.zip) (it is also the packages/plugins/starter folder of the Mongo Manager source code). It is a complete plugin in plain JavaScript, with no build step and no dependencies: a collection tab and a sidebar page that list the documents of a collection.

  1. Unpack it, or copy the folder, into a new repository of your own.
  2. In mongo-manager-plugin.json, change id, name, author and repository. The id must be unique: it names the plugin's folder on every server.
  3. Write your page in main.js and style.css.
  4. Try it on your own server: node scripts/pack.mjs --folder ~/.mongo-manager/plugins, then Plugins → Scan again, look at the scan, and approve it. See Testing on your own server.
  5. Package it with node scripts/pack.mjs, which writes <id>-<version>.tgz, and attach that file to a GitHub release. See Publishing on GitHub.

The starter also holds instruction files for AI coding assistants (CLAUDE.md, AGENTS.md, GEMINI.md and .github/copilot-instructions.md); see Building with an AI assistant.

Files and folder layout

hello-documents/
  mongo-manager-plugin.json   the manifest (required, at the top)
  index.html                  the entry page every contribution opens
  main.js                     the page's script (an ES module)
  style.css                   the page's styles
  README.md                   shown to administrators on the plugin's details page
  README.tr.md, README.zh.md  the same in another language of the app (optional)
  scripts/pack.mjs            packaging (not part of the plugin: left out of the archive)
  CLAUDE.md, AGENTS.md, ...   AI assistant files (left out of the archive)

The app's rules for the files a plugin holds:

  • At most 500 files and 25 MB in all; the manifest at most 64 KB.
  • Every path is relative and plain: each part starts with a letter, a digit, _ or - and holds only letters, digits, ., _ and -, at most 100 characters; at most 16 levels deep and 240 characters in all. No hidden files or folders (a name starting with .), no spaces, no device names (con, nul, com1...), no __proto__, constructor or prototype.
  • Files and folders only: links, junctions and special files make the plugin unusable.
  • No two paths that differ only in letter case.
  • Files are served with a type taken from their extension: html, js, mjs, css, json, map, txt, svg, png, jpg, jpeg, gif, webp, avif, ico, woff, woff2, ttf, otf. Anything else is served as bytes and never runs.

The manifest

mongo-manager-plugin.json is checked strictly: an unknown field, a wrong type or a value out of range makes the plugin unusable, and the Plugins page says which field is wrong. Text a person reads (names, titles, notes) may not hold control characters or characters that hide or reverse text. 

{
  "id": "hello-documents",
  "name": { "en": "Hello documents", "tr": "Merhaba belgeler" },
  "version": "0.1.0",
  "description": { "en": "Lists the documents of a collection.", "tr": "Bir koleksiyonun belgelerini listeler." },
  "entry": "index.html",
  "permissions": ["documents:read"],
  "contributes": {
    "collectionTabs": [{ "id": "list", "title": { "en": "Hello", "tr": "Merhaba" }, "icon": "table" }],
    "sidebarPanels": [{ "id": "page", "title": { "en": "Hello documents" }, "icon": "puzzle" }]
  },
  "settings": {},
  "author": { "name": "Your Name", "url": "https://example.com" },
  "homepage": "https://example.com/hello-documents",
  "repository": "https://github.com/your-name/hello-documents",
  "license": "MIT",
  "publishedAt": "2026-10-11",
  "changelog": [
    { "version": "0.1.0", "date": "2026-10-11", "notes": { "en": "First release.", "tr": "İlk sürüm." } }
  ]
}
Field Required Rules
id yes Lowercase letters and digits, dash-separated (geojson-map), at most 64 characters. It must equal the plugin's folder name. The id of a plugin shipped with Mongo Manager cannot be used, nor one that reads as a name the app keeps (below).
name yes Localized text, at most 60 characters: { "en": "...", "tr": "..." }. No invisible character (zero-width, tag, variation selector — an emoji's own are fine), and never a name that reads as the app's own messages: Mongo Manager (or one starting so), MongoDB, System, Session, Security, Admin, Server, Update and the like, in any language of the app, compared as read: case, spaces, accents and lookalike letters aside. In each word, the letters are all Latin or none of them (never Greek and Cyrillic together), and no bracket holds what reads as an id ((value-search); (beta) is fine). The app shows a plugin's messages and questions with its id beside its name.
version yes Semantic versioning: major.minor.patch, optionally a pre-release (1.2.0-beta.1), at most 64 characters.
description no Localized text, at most 300 characters.
entry yes The page every contribution opens: a plain path to an .html file of the plugin.
permissions no Any of documents:read, documents:write, collection:read, database:read, each at most once. Default: none. See Permissions.
contributes no collectionTabs, documentActions, sidebarPanels and cellRenderers: lists of at most 5 each, ids unique within a list. See Contribution points.
settings no At most 10, by key (a letter, then letters and digits, at most 32 characters): { "type": "url" | "text" | "boolean", "title": localized text of at most 60 }. Administrators set the values; the page reads them in the context.
author no { "name": text of at most 80, "url": an https address (optional) }.
homepage, repository no An https:// address with a host, at most 300 characters, with no credentials, spaces or backslashes.
license no An SPDX expression, at most 40 characters: MIT, Apache-2.0 OR MIT.
publishedAt no A day that exists, YYYY-MM-DD, between 1900 and 2100.
changelog no At most 50 entries { "version", "date": "YYYY-MM-DD", "notes": localized text of at most 1000 }; each version at most once and none after the manifest's version.

Localized text is an object with en (required) and, optionally, any of the app's other languages: tr, zh (Simplified Chinese), ja, es, pt (Brazilian Portuguese), ko, de, fr and ru; English is shown where the reader's language is missing. A contribution is { "id", "title": localized text of at most 40, "icon" }: its id is a lowercase letter, then lowercase letters, digits and dashes, at most 32 characters, and its icon one of map, chart, table, file, image, globe, layers, puzzle, book, wand, shapes, scroll, code, calendar, hourglass, shield, fingerprint, ruler (the app's own icons: a plugin brings none). A cell renderer is { "id", "match" } instead, with an optional "display": inline (the default) or tooltip.

A url setting must be an https address with no credentials (plain http only for this computer: localhost, 127.0.0.1 or [::1]); its scheme, host and port are added to the images the frame may load (for map tiles: a leading {s}. becomes any subdomain, only before a name of two parts or more, never an address). An image's address can carry data: the plugin may send what it reads to that server, and the approval and the setting say so. A text setting holds at most 500 characters. Every user of the plugin can read its settings: never ask for a secret. The server stores them encrypted with its key, like every other saved value.

Contribution points

Every contribution opens the same entry page. The page learns which one it is from the address's fragment, #<kind>=<id> (for example #collectionTab=list), and from contribution in the context.

Kind Where it appears and how it opens
collectionTabs A tab of every collection, after the app's own tabs, on views too. The frame fills the tab. Its place is that collection, with the Documents filter the user has set. The page loads again each time the tab is shown, unless it asked to stay with ui.keepOpen: then it stays loaded while another section of that collection's tab shows (out of sight, it may read but not act: not_visible).
documentActions An entry in a document's actions menu in Documents, shown only for a plugin approved for documents:read. It opens a dialog with the page; place.documentId is that document's _id. The dialog closes once the plugin put a query or a pipeline in place (ui.useQuery, ui.useQueryIn, ui.useAggregation).
sidebarPanels An entry in the sidebar that opens a page of its own, a workspace tab at /plugin/<id>/<contribution>. Clicked while a collection's tab is active, the page opens on that collection (/plugin/<id>/<contribution>/<connection>/<db>/<collection>) and place names it; from anywhere else place is null. A page opened from a link asks the user before it reads that collection, and the user may go on without one. The page stays loaded while another tab shows; out of sight, it may still read but not act (not_visible).
cellRenderers A short text about values wherever Documents shows them (table, tree, cards, the document page, change stream details), such as the date an ObjectId was made: beside the value ("display": "inline", the default) or in a tooltip ("display": "tooltip") that its cell or row shows when hovered or focused, under the whole value and marked with the plugin's name. A tooltip's text is plain, its tone unused; a screen reader reads it with the value. A plugin says one text beside a value and one in its tooltip: its first renderer for each place that answers. The page runs in a hidden frame, one per plugin, only for a plugin approved for documents:read; it never shows itself. match is one of geojson, string, number, date, object, objectId, binary (not a UUID). See Cell renderers.

Cell renderers

The app asks the hidden frame about the values it shows, in batches of at most 200, with a cells.render message. With the kit, answer through client.onCells: 

client.onCells((renderer, values, locale, paths, place) =>
  values.map((v) => (typeof v?.$oid === 'string' ? { text: createdAt(v.$oid, locale), tone: 'info' } : null)),
)
  • renderer is the contribution's id, values the values as canonical Extended JSON, locale the app's language, paths each value's field path (or null), place the collection the values come from (or null).
  • A binary value is sent as its head only, never whole: { "$binaryHead": { "base64", "subType", "length" } } with its first 2,048 bytes — enough to tell an image's kind and size.
  • Answer one item per value, in order: { "text", "tone" }, null for no text, or { "retry": true } to be asked again later. A list of another length is ignored.
  • Text is shown as plain text — at most 80 characters beside the value, 200 in a tooltip — with control and hidden characters removed. tone is one of neutral, info, success, warning, danger.
  • An answer must come within 3 seconds; otherwise the plain value stays and the value is asked again after 30 seconds. Answers are kept per value, language and the plugin's settings: a change of its settings asks again, and an answer over a minute old is asked for again the next time its value is shown, the old answer staying until the new one comes (and staying when asking again fails). A binary value's answer is kept under its length, subtype and a hash of its head.
  • A renderer may read before it answers (references to other documents, for example): it passes the place it was given in its request, { place, filter, ... }, and may read only there. Its context's place is null.

The context

context.get answers where the page is and how it should look. Call it first; when a collection is open, the answer may take up to 3 seconds while the app checks whether it is a view. 

{
  "plugin": { "id": "hello-documents", "version": "0.1.0" },
  "contribution": { "kind": "collectionTab", "id": "list" },
  "locale": "en",
  "theme": "dark",
  "accent": "emerald",
  "place": {
    "connectionId": "6650...",
    "connectionName": "Production",
    "db": "shop",
    "coll": "orders",
    "view": false,
    "documentId": null,
    "filter": { "status": "open" }
  },
  "settings": { "tileUrl": "https://tile.example.org/{z}/{x}/{y}.png" }
}
  • kind is collectionTab, documentAction, sidebarPanel or cellRenderer.
  • locale is the app's language: en, tr, zh, ja, es, pt, ko, de, fr, ru.
  • theme is light or dark.
  • accent is the user's accent: emerald, indigo, violet, ocean or rose. Treat any other value as emerald.
  • place is null when the page was opened on no collection (a sidebar page, a cell renderer). connectionName may be null. view is true for a view: it can be read, never written, and has no indexes. documentId is the document of a document action, as canonical Extended JSON, else null. filter is the Documents filter for a collection tab, else {}. Both are data: a plugin without documents:read gets null and {}.
  • hidden lists the field paths personal-data rules hide from the user in the collection, as lists of keys ([["contact", "phone"]]; "*" one key, "**" any number of keys, at any depth) — names only, for a plugin with documents:read; [] otherwise; null when the app could not tell in time (3 seconds). Such a field's values arrive as "***": never take that for its type.
  • settings holds the values an administrator set; a setting not set is absent.

When the user changes the language, the theme or the accent, the app sends context.changed with locale, theme and accent (the kit's client.onContext). Apply it at once: the page should never show the other theme or language. A plugin that may read documents is also sent context.changed when the Documents filter changes while its page is loaded — a collection tab that called ui.keepOpen hears of every filter the user sets while it is out of sight. Ask context.get again for the new place.

The bridge API

The protocol

The page and the app exchange plain JSON with postMessage. The kit (packages/plugins/kit/src/client.ts) and the starter's main.js implement it; the rules, should you write your own:

  1. Read only messages whose event.source is window.parent and whose mm is 1.
  2. Once the page has loaded, the app greets it: { "mm": 1, "type": "hello", "token": "..." }. Keep the first token. Send nothing before it.
  3. A request is { "mm": 1, "id": 1, "method": "documents.find", "params": { ... }, "token": "..." }, posted to window.parent with the target '*' (the frame's origin is opaque). The id is a number or a string of at most 64 characters; the app ignores a request without the token.
  4. The answer carries the same id: { "mm": 1, "id": 1, "result": ... } or { "mm": 1, "id": 1, "error": { "code": "...", "message": "..." } }.
  5. The app sends { "mm": 1, "type": "context.changed", "locale", "theme", "accent" } as the user changes them (and, to a plugin with documents:read, the Documents filter), and asks a cell renderer { "mm": 1, "id": "h1", "method": "cells.render", "params": { ... } }, which is answered { "mm": 1, "id": "h1", "token", "result": [...] }.

The page must not leave its address. If it loads another page (a link, a form, a change of location), the app closes the bridge and removes the frame, and the user has to open the plugin again. Keep everything on one page. 

import { createClient, askMessage, AskError } from './kit/client'

const client = createClient()                       // requests time out after 15 s ("timeout")
client.onContext((locale, theme, accent) => restyle(locale, theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  if (!context.place) return showNoCollection()
  try {
    const { documents, hasMore } = await client.ask('documents.find', { filter: context.place.filter, limit: 100 })
    show(documents, hasMore)
  } catch (e) {
    showError(askMessage(e, context.locale))         // the app's code, in the user's language
  }
})

Methods

Values are canonical Extended JSON both ways: an ObjectId is { "$oid": "..." }, a date { "$date": { "$numberLong": "..." } }, an int { "$numberInt": "3" }. Every read runs as the user, with the user's rights and the app's masking. Methods marked "on its collection" work on the collection in place and fail with no_collection without one.

Method and permission Parameters → result Rules
context.get
none		 none → the context See The context.
documents.find
documents:read		 { filter?, projection?, sort?, limit?, fit? } → { documents, hasMore, cut? } On its collection. limit 1 to 1000, default 100. At most 10 seconds. A document the user may not see is left out. Not one of the user's recent queries.
documents.get
documents:read		 { id } → the document, or null On its collection. id is the _id value.
documents.aggregate
documents:read		 { pipeline, limit?, fit? } → { documents, truncated, cut? } On its collection. Reading stages only: $match, $group, $sort, $limit, $skip, $project, $addFields, $set, $unset, $count, $unwind, $sortByCount, $bucket, $bucketAuto, $facet (no $facet inside it), $replaceRoot, $replaceWith, $sample; at most 50 stages. With database:read, also a plain $lookup of exactly from, localField, foreignField and as, from a collection of the same database. limit 1 to 1000, default 100. At most 10 seconds, never spilling to disk, one pipeline at a time (busy: the kit's serialAsk queues them).
documents.update
documents:write		 { id, set?, unset? } → { modified } On its collection, in sight only, right after a click in the plugin's page only. set is an object of fields and values, unset a list of field names; at least one change; a field name with a control, line-break or direction character is refused (bad_params). The app shows the user every changed field, each quoted, on the question's first line, then the whole change, every hidden or invisible character spelled out, and applies it only if the user agrees; its Confirm takes a click only after a moment with no press, once the pointer moved onto it. Refused on a view (read_only), for a change too long to show (over 2000 characters: too_large), while another question waits (busy), and after the user declined twice (blocked, until the plugin is opened again). A decline is declined.
indexes.list
collection:read		 { coll? } → [{ name, key, options, usage }] On its collection, or another of its database (coll, one that collections.list names), which needs database:read too. A view has none: [].
collections.list
database:read		 none → [{ name, type }] The collections and views of its database, system. ones left out, at most 500, kept for 30 seconds.
documents.findIn
database:read		 { coll, filter?, projection?, limit?, fit? } → { documents } Another collection of the same database, one that collections.list names. limit 1 to 200, default 50. At most 10 seconds.
ui.toast
none		 { message, kind? } → true A short message in the app, after the plugin's name and id. kind: info (default), success or error. At most 200 characters shown, without control, direction or invisible characters; at most 5 messages a minute, shared with ui.copy. In sight only.
ui.openDocument
none		 { id } → true On its collection, in sight only. Shows that document in Documents. id must be an _id value, never a query. Right after a click in the plugin's page only; at most 30 a minute.
ui.resize
none		 { height } → true The frame's height in pixels, kept between 80 and 2000.
ui.keepOpen
none		 – → true / false A collection tab's page stays loaded while another section shows (false anywhere else). Ask it only when the page reads context.get again on context.changed; out of sight it may read but not act.
ui.copy
none		 { text } → true Copies text (at most 100,000 characters) to the clipboard. Right after a click in its page only; at most 5 a minute, shared with ui.toast.
ui.useQuery
none		 { filter?, projection?, sort? } → true On its collection. Puts the query in Documents of the collection's tab, as if the user had typed it. Right after a click in its page only; at most 10 a minute, shared with the other ui.use… and SQL methods.
ui.useQueryIn
database:read		 { coll, filter?, projection?, sort? } → true On another collection of its database, one collections.list gives. Puts the query in Documents of that collection's tab, as ui.useQuery does in its own (References uses it to show the documents referring to one); the tab runs it as a query the user typed. One at a time (busy while one is put in place), while its page is in sight, right after a click in it only; at most 10 a minute, shared with the other ui.use… and SQL methods.
ui.suggestPersonalData
documents:read		 { fields: string[] } → true Fields of its collection suggested as personal data: 1 to 50 paths of plain names (contact.phone; no *, no $ starting a key). Nothing is saved: the collection's Personal data section opens with them listed, named by the plugin; it offers only those a sample of the collection holds, and an administrator adds each there (or all at once, in one save). No hidden character and no space around a name; for the connection's administrators, on a collection (not a view, not system.*), right after a click in its page only; counted with the ui.use… methods.
ui.useAggregation
none		 { stages } → true On its collection. Puts the stages in Aggregations as cards; asks the user before replacing a pipeline that is there; nothing runs until the user runs it. At most 50 stages; any stage but ones that write or run code. Right after a click in its page only; declined, busy and blocked as for documents.update.
ui.importSql
none		 none → true On its collection. Opens the app's SQL ↔ MongoDB page on the import, in the collection's database. The plugin passes nothing and sees nothing of the import; the user chooses the file and starts it. Right after a click in its page only; not_permitted when the user may not write documents and run jobs there, or for a system database.
ui.exportSql
none		 none → true On its collection. Opens the app's SQL ↔ MongoDB page on the export, in the collection's database, with that collection chosen. The user chooses the options and starts it. Right after a click in its page only; not_permitted when the user may not export from the connection.
validation.get
collection:read		 { coll? } → { validator, validationLevel, validationAction } or null The collection's validation rules, as the Validation section reads them (validator is null when it has none); null for a view. Another collection of the database (coll) needs database:read too. What a rule says of a field hidden from the user (its type, pattern or bounds) is left out — its schema is {}, a query rule or $expr naming it is dropped — and its name is kept (in required, for one); failed when what is hidden could not be told.
database.model
database:read		 none → the data model The database's model as the Database tab draws it: { db, sampleSize, collections, references, skipped, at } — each collection's fields with their types and shares (a field hidden from the user named only, masked: true, without types), the references found between collections. Up to 200 sampled documents a collection. One read for the frame, kept for 60 seconds; requests made while it runs share it (for 90 seconds: the server ends a model at 60), and a failed one is not kept.
storage.stats
database:read		 none → { collections, more } The database's storage, as its Storage report reads it: each collection's { name, type, count, size, storageSize, freeBytes, indexSize, indexFreeBytes, indexes } (each index's { name, size, freeBytes }), up to 500 by name (more when there are more). A figure MongoDB would not tell is null (unread), and so are the sizes personal data rules hide (sizesHidden). One read kept 30 seconds a database, for every frame, forgotten after a compact there.
storage.compactEstimate
collection:read		 { coll? } → { available, estimatedBytes } or { available: false, reason } What compact would give back (MongoDB 8.0 and later), for its collection or, with database:read, another of its database. reason is version, mongos or timeseries; read_only on a view.
ui.compact
collection:read		 { coll? } → { bytesFreed } Compacts the collection in the app's own dialog, which names the plugin and the collection and runs only when the user types the collection's name. For a user who may administer databases, on a connection that is not read-only, never a time series, a view or a collection personal data rules reach; one compact of a collection at a time (busy). Right after a click in its page only; counted with the ui.use… methods; declined or unanswered when the user does not go on, blocked after two noes.
shardKey.analyze
documents:read		 { key } → the analysis, or { available: false, reason } A candidate shard key's characteristics (analyzeShardKey): key is one to five fields, each 1 or "hashed" (one at most). Answers { numDocsTotal, numDocsSampled, numDistinctValues, avgDocSizeBytes, isUnique, mostCommonValues, monotonicity } — its common values are data, as canonical Extended JSON; reason is version, standalone or no_index. read_only on a view.
searchIndexes.list
collection:read		 none → { supported, reason?, indexes } The collection's search indexes (Atlas Search, vector search): each { name, type, status, queryable, dynamic, fields }, a field { path, type, numDimensions?, similarity? }. A field hidden from the user is left out, as by validation.get; failed when what is hidden could not be told.
ui.download
none		 { name, type, text? | base64? | html? } → true A file the plugin made, saved by the app (the frame cannot download). type is markdown, mermaid, csv, json, text (with text), png (with base64, which must be a PNG) or html (with { title, css, body }): the app assembles the page — a policy that runs no script and loads nothing first, the title as text (at most 200 characters), a style that may hold no markup, escape (\), @import, @font-face, image set, src(), expression or address but a data: one, and the body through an allowlist of structural elements (no script, form, frame, image, svg, MathML, template, link other than #anchor, comment or on… attribute). A text, a style and a body are each at most 1,000,000 characters. In a CSV, a cell that starts like a formula (=, +, -, @, a tab or a carriage return, and is not a number) is written with a leading '. The name loses any path, reserved device name (CON, COM¹, CONIN$…), hidden or reversing character, and its dots (_): its one extension is the type's. Right after a click in its page only; counted with the ui.use… methods; asked first after a press elsewhere in the app (see Limits).
ui.importDocuments
none		 { ndjson } → true On its collection. Opens the app's Import wizard with these documents as its file — one JSON object a line, at most 1,000,000 characters, and the whole message at most 1 MB as JSON (a quote or a backslash in it counts twice). The user checks them, maps them and starts the import, with their own rights. Right after a click in its page only; counted with the ui.use… methods; asked first after a press elsewhere in the app; busy while a dialog is open in the app; not_permitted when the user may not write documents and run jobs there, or for a system database; read_only on a view.

In the filters, projections and sorts of documents.find, documents.findIn and ui.useQuery, and in documents.aggregate, the operators $where, $function, $accumulator, $out, $merge, $lookup, $graphLookup and $unionWith are refused at any depth (except the plain top-level $lookup above). The stages of ui.useAggregation may read other collections, since the user runs them with their own rights, but never hold $where, $function, $accumulator, $out or $merge. Reads run at once; ui.useQuery and ui.useAggregation only hand work to the user.

Limits

  • A message is at most 1 MB either way; a bigger answer fails with too_large. Ask for fewer documents or project fewer fields, or pass fit: true to documents.find, documents.findIn or documents.aggregate: the app then answers as many whole documents, in order, as fit, and cut: true says it left the rest out (hasMore or truncated is then true). A sample can take what came; a pager goes on after the last document it got. If not even one document fits, it is still too_large.
  • At most 8 requests wait at once (too_many).
  • At most 60 reads a minute per frame (documents.find, .get, .aggregate, .findIn, collections.list, database.model), and apart from them 120 reads of definitions (indexes.list, validation.get): a dictionary of 50 collections is one model and 100 definitions.
  • Right after a click in the plugin's page. ui.copy, ui.useQuery, ui.useAggregation, ui.importSql, ui.exportSql, ui.openDocument, ui.download, ui.importDocuments and documents.update are taken only while the user's click or key press in the plugin's own page is fresh: the frame must have the focus, so a click elsewhere in the app never counts. Call them directly in the click handler, before awaiting anything else; otherwise they fail with no_activation. Every attempt at ui.copy, a ui.use…, an SQL page or ui.openDocument counts toward that method's limit, refused or not: a plugin that tries again and again, waiting for a click, spends its minute (too_many); documents.update is bounded by its one question at a time and the two noes instead. A frame can take the focus without a click, so a ui.copy, ui.download or ui.importDocuments asked within 5 seconds of a click or key press elsewhere in the app (the time the browser's activation of it lasts) is not done on the plugin's word: the app asks the user, naming the plugin and what it wants (how many characters and how the text starts, hidden characters spelled out; the file's name and size; how many documents for which collection), and does it on a click of its own Copy, Save or Open; the plugin's answer waits for it (declined when the user dismisses it, unanswered when it goes unanswered, busy while one waits). Every question the app asks for a plugin — these, a change, stages put in place — ends after 150 seconds even while pointed at; the kit waits 180 seconds for these requests, so a page hears the app's answer, never its own timeout.
  • In sight. documents.update, ui.openDocument and the methods above fail with not_visible from a cell renderer or from a page kept while another tab shows.

unknown_method No such method.

Permissions

An administrator approves a plugin for the permissions it lists, as the Plugins page names them. Ask for the fewest you need: each one is a reason for an administrator to say no.

Permission What the administrator reads What it allows
documents:read read documents documents.find, .get, .aggregate; document actions and cell renderers are offered only with it.
documents:write change documents (each change confirmed) documents.update, each change confirmed by the user. Asking for it is always a medium scan finding of its own.
collection:read read this collection's indexes indexes.list.
database:read read the other collections of the same database (names and documents) collections.list, documents.findIn, a plain $lookup.

A plugin with no permission may still show a page, read its context and settings, and use the ui.* methods. A permission is never more than the user's own right: a user who may not read a collection cannot read it through a plugin either.

The sandbox

The page is loaded in an iframe with sandbox="allow-scripts", from a signed address that names the plugin, its version, its approved files and the user's session, sealed (a ticket: the page must load within 10 minutes, its other files while that session lasts, at most 12 hours — a session renewed in place, by a sign-in in another tab or a password change, is followed; signed out, the address serves nothing more, and the browser keeps none of its files). Every file served is checked against its approved SHA-256. Its policy (Content-Security-Policy), with X-DNS-Prefetch-Control: off: 

default-src 'none'; script-src <its files>; style-src <its files>;
img-src <its files> data: blob: <the origins of its url settings>; font-src <its files>;
connect-src 'none'; webrtc 'block'; frame-ancestors 'self'; base-uri 'none'; form-action 'none';
sandbox allow-scripts

What that means for your code:

  • No network at all. No request to any address, including the plugin's own files: put data in a script module (data.js) instead of a .json file you would load. Do not use WebRTC or prefetch hints either: not every browser blocks them, and the scan flags them as high risks.
  • No inline code or style. Scripts and styles come from the plugin's files only. No inline <script>, no <style> element, no style attribute, no inline event handler, no eval. Setting a property in script (el.style.width = '40px') works.
  • An opaque origin. No cookies, no localStorage, no IndexedDB: they fail. Keep state in memory; settings an administrator chooses come from the manifest's settings.
  • No popups, dialogs, forms or downloads. window.open, alert, confirm and form submission do nothing. Copy with ui.copy; hand files to the user through the app's own import and export.
  • No reach into the app. The page cannot read the app's page, its session or its storage. It only exchanges messages with it.
  • Fonts and images are its own files (or data: and blob: images).

The security scan

Every plugin's files are scanned when they are found or installed, before an administrator approves them. The scan reads script (.js, .mjs, .cjs), markup (.html, .htm, .svg) and style (.css) files line by line, comments included, and lists each finding with its severity, rule, file, line and an excerpt. Markup files are also read whole, so a <script> tag or an inline handler spread over several lines is found too. Libraries bundled into the plugin are scanned like your own code. The scan is a heuristic: it looks for known patterns in the text, so code written to hide from it (a name built from pieces, for one) is not found — a clean scan is no proof. A plugin with a high finding can be approved only after the administrator types its id to accept the risk; the server enforces it, and the audit log records the scan's counts and whether a risk was accepted. Avoid every high finding, and keep medium ones to what you can explain.

Severity Rule What it flags

How to pass it:

  • Write text with textContent, append('text') or the kit's h() helper; build elements with document.createElement. To clear an element, use replaceChildren(). None of these is ever flagged; assigning or appending markup (innerHTML = or innerHTML +=) always is.
  • Attach handlers with addEventListener, never in markup.
  • Pass functions to setTimeout and setInterval. Reach the app only through window.parent.postMessage.
  • Save every file as UTF-8, without NUL bytes (never as UTF-16).
  • Do not ship code that reaches out, even unused: check what a library brings. Prefer a build that is not minified, or explain the minified finding in your README, and keep large data out of base64 strings.
  • Remember that comments are scanned too: a comment that names eval( or innerHTML = is a finding.
  • Say in your README why each remaining finding is safe: which library, which line, why it never runs or why the sandbox stops it.

Only script, markup and style files are scanned; the manifest is read for documents:write (always a medium finding: ask for it only when the plugin changes documents). At most 10 findings of one rule in one file, and at most 200 findings in all (the most serious first), are listed; the counts always cover every finding. Every pattern runs in linear time, so the scan finishes quickly on any file. If the scan itself fails, the plugin is not marked broken: it has no scan, and (unless it is shipped with Mongo Manager) it can be approved only with its id typed, as with a high finding. The scan of a plugin shipped with Mongo Manager is shown too, but approving it never asks for its id.

UI and theming

A plugin should look like part of the app: its colours, its type, its spacing, in the user's theme and accent. Mongo Manager's own plugins use the plugin kit in packages/plugins/kit:

  • kit/src/ui.css: the app's design tokens (--ds-surface, --ds-fg, --ds-accent...) for light and dark and each accent, and components (mm-btn, mm-table, mm-empty, mm-callout...). Its fonts are files of the @fontsource packages: bundle them with your plugin, or remove the @font-face rules to use the system font.
  • kit/src/ui.ts: applyLook(theme, accent) sets html.dark and html[data-accent]; h(tag, props, ...children) builds elements where text is always text; and icon, button, segmented, switchControl, chip, badge, pageHeader, emptyState, skeleton, callout, table, valueView, describeValue, formatNumber, statusLine, setBusy, serialAsk.
  • kit/src/client.ts: createClient, AskError, askMessage.

The kit is TypeScript, meant to be bundled: copy kit/src into your project and build with Vite (or another bundler) into relative paths with no inline script, like the first-party plugins' vite.config.ts: base: './', modulePreload: { polyfill: false }, assetsInlineLimit: 0. Package the build output, not your sources. The starter instead carries a short copy of the client and the colours in plain JavaScript and CSS. 

import './kit/ui.css'
import { createClient } from './kit/client'
import { applyLook, h, pageHeader, emptyState, button } from './kit/ui'

const client = createClient()
client.onContext((locale, theme, accent) => applyLook(theme, accent))
client.onReady(async () => {
  const context = await client.ask('context.get')
  applyLook(context.theme, context.accent)
  document.body.append(
    h('div', { class: 'mm-page' },
      pageHeader({ icon: 'table', title: 'Hello', description: context.place?.coll ?? '' }),
      emptyState({ icon: 'search', title: 'Nothing yet', action: button({ label: 'Load', variant: 'primary' }) }),
    ),
  )
})

Design for the place the page appears in: a collection tab is wide, a document action is a dialog, a sidebar page fills the workspace. Show an empty state when there is nothing to show and place is null, a skeleton while reading, and the app's words for a refusal. Use buttons and real controls, so the page works from the keyboard.

Languages

The app speaks English, Turkish, Simplified Chinese, Japanese, Spanish, Brazilian Portuguese, Korean, German, French and Russian: context.locale is one of en, tr, zh, ja, es, pt, ko, de, fr and ru. A plugin should speak as many of them as it can, and English always:

  • In the manifest, give each language you have beside en in every localized text.
  • On the page, keep your words in a table by language, choose by context.locale (English for a language you do not have), set document.documentElement.lang to the language your words are in — en when you fell back to English — (zh-CN and pt-BR for Chinese and Portuguese, so the right glyphs show), format numbers in that same language, and render again on context.changed.
  • A cell renderer answers in the locale each batch is asked in.
  • Format numbers and dates for the language (Intl.NumberFormat, Intl.DateTimeFormat).
  • Add README.<language>.md beside README.md for each language (README.tr.md, README.zh.md, …), and release notes in each.

README and release notes

README.md at the plugin's top is shown on its details page, where administrators read it before they approve the plugin; README.<language>.md (README.tr.md, README.ja.md, …) is shown instead to someone using the app in that language. The localized README is shown only when README.md exists too. It is shown as safe Markdown: headings, paragraphs, lists (one level), bold, italics, inline code and code blocks. Links, images, tables and HTML are shown as plain text. At most 64 KB is shown.

A good README says, in this order:

  1. What the plugin does, in two or three sentences.
  2. Where it appears: which tab, action, page or cell text.
  3. How to use it, step by step, with an example.
  4. Each permission and why it is needed.
  5. Its settings, if any.
  6. Its limits: how many documents it reads, what it does not handle.
  7. Each scan finding that remains, and why it is safe.

Release notes go in the manifest's changelog, newest first, one entry per version with its day and notes in English and each of your languages. The details page shows them; after an update, the versions since the last one are marked new.

Versions and approval

  • An approval is for exact files: their digest, the SHA-256 of every file's path and SHA-256. The administrator sees it before approving.
  • Any change to any file of an uploaded plugin or a plugin folder (a new version, a fixed typo in the README) disables it until an administrator approves it again. Raise version and add a changelog entry for every release, so administrators know what they approve.
  • Uploading a plugin whose id is installed replaces it; it stays enabled only if the files are the very ones approved. Its settings are kept while the new manifest still declares them with the same type.
  • A plugin folder placed by hand is managed by hand: an upload of the same id is refused, and removing it in the app forgets it without deleting the folder.
  • Only plugins shipped with Mongo Manager keep their approval through an update, and only while they are enabled and the update asks for no new permission; nothing is asked of an administrator then, and the plugin's details page says it kept its approval. An update an administrator approved by hand says it was approved by an administrator.

Packaging

A plugin travels as a gzip-compressed tar archive (.tgz) whose files sit at the archive's root, mongo-manager-plugin.json among them. One top folder holding everything (like npm pack's package/) is accepted and taken off. The archive must hold regular files only (folders are implied); links, devices, special entries, paths that are not plain and paths given twice are refused; at most 500 files and 25 MB unpacked, and at most 30 MB uploaded.

The starter's scripts/pack.mjs does this with Node.js alone:

  README.ru.md

  style.css

hello-documents-0.1.0.tgz
digest (sha256): 9ac77c4a...

It checks the paths and limits as the app does, leaves out what is not part of the plugin (hidden files, scripts/, node_modules/, the AI assistant files, package files and archives; edit its SKIP list to suit you), writes <id>-<version>.tgz, and prints the digest the administrator will see. If you build with a bundler, pack the build output folder instead, with its manifest at the top.

Publishing on GitHub

Administrators can install a plugin straight from a public GitHub repository, on a server set to allow it (MM_PLUGINS_GITHUB=1; it is off by default). On the Plugins page they paste one of these addresses:

  • https://github.com/<owner>/<repo>, …/releases or …/releases/latest for its latest release;
  • https://github.com/<owner>/<repo>/releases/tag/<tag> for a given one. The tag may hold slashes (at most 4 parts).

The address holds nothing else: no query, fragment, port or credentials. A renamed repository is followed: the release's own page address names its repository. The app downloads that release's plugin archive, its one asset whose name ends with .tgz or .tar.gz. A release with no such asset, or with several, is refused. Tag and asset names must be printable ASCII. The asset must belong to that repository's releases, and it may be no larger than an upload (30 MB), both as declared and as read.

The app talks only to github.com, api.github.com, objects.githubusercontent.com and release-assets.githubusercontent.com, over https, at public addresses only, and sends nothing of the server's (no cookie, token or credentials). It follows at most 4 redirects, only among those hosts, reads the release's description up to 5 MB, and gives the whole install 4 minutes. The plugin is installed disabled, with its scan, and waits for approval like an upload. It remembers where it came from (repository, release and archive), shown on its details page.

When the install fails, the Plugins page says why: the repository has no published release, GitHub's rate limit was reached, GitHub refused (the repository is not public), GitHub cannot be reached from the server, a redirect went to a host that is not allowed, there were too many redirects, the release has no archive or several, or the archive is not on that repository's releases.

  1. Raise version, add a changelog entry and set publishedAt.
  2. Run node scripts/pack.mjs.
  3. Create a GitHub release (tag v0.1.0, for example) and attach hello-documents-0.1.0.tgz as its asset. Attach no other .tgz or .tar.gz file.
  4. Mark it as the latest release. Put the digest printed by pack.mjs in the release notes, so administrators can compare it with what the app shows.

Installs from GitHub are off unless MM_PLUGINS_GITHUB=1 is set; a server may also be unable to reach GitHub, or reach out only through a proxy (the install connects to GitHub directly and does not use HTTP proxy settings); its administrators then download the .tgz and upload it with Upload plugin.

To be found by others, list your plugin in Awesome Mongo Manager (github.com/mongo-manager/awesome-mongo-manager): open a pull request there that adds one line to its README. Its checks download your latest release and check it with the app’s own code, as an install from GitHub does; a maintainer then reads the plugin before listing it.

Testing on your own server

  1. Run Mongo Manager with plugins on (the default) and sign in as an administrator. Find its data directory: ~/.mongo-manager unless MM_DATA_DIR says otherwise.
  2. Copy the plugin into <data-dir>/plugins/<id>: node scripts/pack.mjs --folder ~/.mongo-manager/plugins. The folder's name must be the id, and it may hold no hidden files (which is why the script copies the plugin's files only). ~/ is your home folder in every shell; ~\ in cmd and PowerShell, or in quotes (bash and zsh drop an unquoted backslash, and the script then refuses what is left). The script replaces only a folder of this plugin that holds nothing but files and folders it could have copied (no scripts, hidden files, links, pipes or sockets) and has no file system mounted at it or in it, swapping the new copy in so that a copy that stops leaves the folder as it was. It refuses a target that is the plugin's own folder, inside it or containing it, however the path names it (a symbolic link, a junction or a share); nothing is written then.
  3. Open Plugins and click Scan again. A plugin that cannot be used says why (a manifest field, a path). Open its details: read the scan findings, the permissions and the README as an administrator would.
  4. Click Approve and enable, then open a collection and try every contribution.
  5. After each change, copy again, click Scan again and approve again (the files changed), then reopen the tab, page or dialog. Try several languages, both themes, a view, a collection with no documents, and a sidebar page opened with no collection.
  6. Finally, upload the .tgz itself with Upload plugin on a clean server, as your users will.

The browser's developer tools work inside the frame: pick the plugin's frame in the console to see its errors and messages. A policy violation in the console means the page tried something the sandbox forbids.

Building with an AI assistant

The starter holds instruction files that teach an AI coding assistant everything on this page: the manifest's rules, the bridge methods and permissions, the sandbox, the scan, languages, README, packaging and publishing. Keep them at the top of your plugin's repository; pack.mjs leaves them out of the archive. The Plugins page saves the starter as a .zip, and each file on its own, under Instructions for your AI assistant, to add to a plugin you already have; Copilot's is saved as copilot-instructions.md, for your repository's .github folder.

  • CLAUDE.md: Claude Code.
  • AGENTS.md: OpenAI Codex and other agents that read AGENTS.md.
  • GEMINI.md: Gemini CLI.
  • .github/copilot-instructions.md: GitHub Copilot.

Ask the assistant for what your plugin should do; it should answer with code that passes the scan and the checklist below. Read what it writes before you publish it: you are the one administrators trust.

Checklist before publishing

  • The id is unique and equals the folder name; the version is raised and has a changelog entry with today's day.
  • Every localized text has en and tr; the page follows locale and context.changed.
  • The permissions are the fewest that work, and the README says why each is needed.
  • The scan shows no high finding, and the README explains every other one.
  • Text is written with textContent or h(); no markup is built from text.
  • Nothing reaches the network (no fetch, WebRTC or prefetch hint), uses storage, opens popups or leaves the page.
  • No inline script, style or event handler; every path is relative (./main.js).
  • Every file is saved as UTF-8, without NUL bytes.
  • The page follows the theme and the accent, and works from the keyboard.
  • It handles place being null, a view, an empty collection and each error code it may meet.
  • Calls that need a click are made directly in the click handler.
  • Large reads are bounded: a limit, a projection, one pipeline at a time.
  • README.md and its translations describe the plugin; license, author and repository are set.
  • The .tgz was uploaded to a clean server, scanned, approved and tried there.
  • The GitHub release has exactly one plugin archive, named <id>-<version>.tgz.
