Deployment

As a system service

sudo mongo-manager service install          # Linux, macOS
mongo-manager service install               # Windows, elevated prompt
mongo-manager service status
mongo-manager service logs
sudo mongo-manager service open             # local mode: a one-time link that opens it
sudo mongo-manager service uninstall        # keeps data, config and key

The service runs as its own unprivileged account, from a program folder only administrators can change, in team mode on 127.0.0.1:4321. The first start keeps the one-time setup token in setup-token in the data folder, which only the service account and administrators can read; service install prints how to read it. The token is never written to the log, and the file is removed once the first administrator exists.

Installed in local mode (--no-auth), the service opens only from a one-time launch link: service install prints one, and service open prints a new one whenever you need it (as an administrator: it is made from launch.key in the data folder). Open it in your own browser, not an elevated one; that browser then stays in while it keeps this site's data, at most six months after its last use.

Docker

The image runs as an unprivileged user on a read-only root filesystem, in team mode. Data lives in the /data volume. Offline machines can load an image archive with docker load -i. The first start's setup token: docker exec <container> cat /data/setup-token. The compose file publishes the port on the host's loopback only (127.0.0.1:4321); to serve other machines, put an HTTPS reverse proxy in front rather than publishing plain HTTP. A proxy on the host reaches the container from the compose network's gateway: trust MM_TRUSTED_PROXIES=172.31.240.1, not 127.0.0.1.

Inside the container the server listens on every address, so without MM_ALLOWED_HOSTS it answers only to IP addresses and localhost (each start says so). Anything that reaches it by a name — a proxy forwarding the public name, another container by the service name (a Prometheus scraping mongo-manager:4321), a Kubernetes service — gets 403 until that name is listed: MM_ALLOWED_HOSTS=mongo-manager,mm.example.com.

In local mode (MM_AUTH=0), the container's log names the command that prints a link, never a link: docker exec <container> node /app/dist/cli.cjs open --no-open. It names the port the server listens on inside the container: published on another port of the host (-p 127.0.0.1:8080:4321), change the port in the link to the host's before opening it.

On a server, put an HTTPS reverse proxy in front that serves it as mongo.example.com, and start it like this; the last line reads the setup token. Finish the setup right away: until the first administrator exists, whoever has the token can become it. 

docker run -d --name mongo-manager --restart unless-stopped \
  -p 127.0.0.1:4321:4321 \
  -e MM_ALLOWED_HOSTS=mongo.example.com \
  -e MM_TRUSTED_PROXIES=172.17.0.1 \
  -v mm-data:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  ghcr.io/mongo-manager/mongo-manager:<version>
docker exec mongo-manager cat /data/setup-token

MM_TRUSTED_PROXIES is the address a proxy on the host reaches the container from: the Docker network's gateway, usually 172.17.0.1 on the default bridge network (docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}' shows it). Without it every request seems to come from the gateway, so the audit log and sign-in bans cannot tell users apart. Once MM_ALLOWED_HOSTS is set, only the names it lists are accepted: add 127.0.0.1 to it to keep opening http://127.0.0.1:4321 on the host. --read-only, --tmpfs /tmp, --cap-drop ALL and no-new-privileges are the hardening the compose file applies.

Reaching MongoDB from the container

Inside a container, localhost is the container itself, so mongodb://localhost:27017 fails with ECONNREFUSED even when MongoDB runs on the same machine.

  • MongoDB in another container: put both on one Docker network (docker network create mm, then docker network connect mm mongo-manager and docker network connect mm my-mongodb, or --network mm when you start them) and connect to mongodb://my-mongodb:27017.
  • MongoDB on the host, Docker Desktop (Windows, macOS): mongodb://host.docker.internal:27017.
  • MongoDB on the host, Linux: run Mongo Manager with --network host (then localhost is the host; keep it private with -e MM_HOST=127.0.0.1, behind the proxy, trusted as 127.0.0.1), or add --add-host=host.docker.internal:host-gateway. The latter reaches only a MongoDB that listens on the bridge's gateway address: not one bound to the host's 127.0.0.1, nor a container published only there (-p 127.0.0.1:27018:27017); use a shared network or the host network for those.
  • A replica set whose members are named localhost:27017 sends the driver back to localhost: add ?directConnection=true.

Behind a reverse proxy

  • Trust only the proxy: --trusted-proxies 127.0.0.1. Without it the server cannot tell a request came over HTTPS, so session cookies are not marked Secure; a team-mode start says so, and says when sign-ins would cross the network over plain HTTP.
  • Name the public host: --allowed-hosts mm.example.com.
  • Serve under a sub-path with --base-path /mm/.
  • Each client address may make 600 API requests a minute; raise it with MM_API_RATE_LIMIT (60–100000) when many people share one address.
  • At most 1000 connections are open at once (MM_MAX_CONNECTIONS, 16–100000), and at most 256 from one address (MM_MAX_CONNECTIONS_PER_IP, 2–100000); a connection past that is closed, and the log says so once a minute per address. A browser keeps about six connections open, so where many people reach Mongo Manager from one address — behind NAT, a VPN or Docker Desktop — raise MM_MAX_CONNECTIONS_PER_IP. Behind trusted proxies only the total applies: every connection comes from the proxy, which should limit its own clients.
  • Imported and exported files live under <data directory>/transfer: MM_TRANSFER_MAX_UPLOAD is the largest upload in MiB (default 1024, 1–65536), MM_TRANSFER_QUOTA the storage each user may hold in MiB (default 5120, 16–1048576), MM_TRANSFER_TOTAL_QUOTA what all users together may hold in MiB (default 51200, or MM_TRANSFER_QUOTA when that is larger; 16–16777216), MM_TRANSFER_TTL_HOURS how long a file is kept (default 24, 1–720), and MM_TRANSFER_MAX_JOB_HOURS how long one import or export may run (default 6, 1–72). Give that disk room for the total, or the quota times the number of people who transfer files if that is less.

Settings and environment variables

Each server setting can be given as a command-line option, as an environment variable or in a JSON config file named with --config or MM_CONFIG. The command line wins over the environment, and the environment over the file. A switch takes 1/0, true/false, yes/no or on/off. The settings of each feature are in its own section below.

Variable Option What it does
MM_WEB_PORT -p, --web-port Port of the web interface (default 4321).
MM_HOST --host Address to listen on (default 127.0.0.1). A network address needs team mode, or MM_UNSAFE_NO_AUTH.
MM_AUTH --auth Team mode: users, roles and sign-in (default off).
MM_DATA_DIR --data-dir The data directory (default ~/.mongo-manager).
MM_CONFIG --config A JSON config file. On Linux and macOS, one that holds a secret must not be readable by other users, or the server refuses it.
MM_SECRET_KEY The encryption key, instead of the data directory's secret.key.
MM_OPEN --open Opens the browser on start (default on): in local mode, on a loopback address, when started from a terminal.
MM_URI --uri A connection created on the very first start only. Use the variable for a connection string with a password: other users can see command lines.
MM_READ_ONLY --read-only No connection can change data, whatever its own setting.
MM_TRUSTED_PROXIES --trusted-proxies Proxy addresses or CIDR ranges whose X-Forwarded-* headers are believed.
MM_ALLOWED_HOSTS --allowed-hosts The only host names the server answers to. Unset, it answers to the loopback names when it listens on loopback, and otherwise to the loopback names and IP addresses only, never another name (a defence against DNS rebinding; the start says so). Name every host name people open it by here.
MM_BASE_PATH --base-path Serves the app under a sub-path, such as /mm/.
MM_UNSAFE_NO_AUTH --unsafe-no-auth Allows a network address without team mode. Anyone who reaches it has full access.
MM_LOG_LEVEL --log-level fatal, error, warn, info (default), debug, trace or silent.
MM_LOG_FILE --log-file Appends the JSON log to this file instead of standard output. The file is made private (mode 0600; on Windows, access for all users is taken away: this account, SYSTEM and Administrators keep it) and rotated at 10 MiB, the previous part kept as <file>.1. A path that is a link, a file with other names (hard links) or not a regular file is refused, and the start fails saying so: remove or rename it, or name another log file. A line that cannot be written (a full disk) is dropped and said once on standard error. Requests are logged by their path, with every query value and a GridFS file's id written as ***.
MM_REQUIRE_ADMIN_2FA Every administrator must set up two-factor sign-in before anything else; it cannot then be turned off in the app. Without it, an administrator can require the same in the app.
MM_REQUIRE_2FA Every user, whatever their role, must set up two-factor sign-in before anything else; it cannot then be turned off in the app. Without it, an administrator can require the same in the app.
MM_METRICS_TOKEN Turns on Prometheus metrics at <base path>metrics, read with this token as a bearer token (at least 32 characters). The numbers name no user, connection, database or collection.
MM_GRIDFS_MAX_MB The largest file uploaded to GridFS, in MB (default 512, 1–10240).
MM_MODEL_MAX_DOCS The documents one data model (a database's Model section) may sample in all (default 20000, 100–1000000): with many collections each one's sample is made smaller, and the section says so.
MM_ALLOW_KERBEROS Team mode: allows Kerberos (GSSAPI) connections (default off). They sign in with the Kerberos ticket of the account the server runs as — every user of such a connection signs in as that account. See Security.
MM_ALLOW_WORKLOAD_IDENTITY Team mode: allows OIDC connections to use the machine's workload identity (Azure, GCP, Kubernetes) when chosen on the connection (default off).
MM_OIDC_DEVICE_FLOW OIDC sign-in with a code (the device flow), for identity providers that cannot send the browser back to this server. Whoever approves the code signs in, so it is off in team mode unless turned on here; on in local mode.
MM_OIDC_PRIVATE_NETWORKS Private networks (comma-separated CIDRs) OIDC identity providers may be on; plain http is allowed there only. Without it they must be public https addresses.
MM_CRYPT_SHARED_LIB_PATH The absolute path of the crypt_shared library (mongo_crypt_v1) for client-side encryption. In team mode it is the only one loaded.
MM_KMS_PRIVATE_NETWORKS Private networks (comma-separated CIDRs) key management services (a KMIP server on premises) may be on. Without it they must be public addresses.
MM_KMS_ALLOWED_HOSTS Key management service hosts (comma-separated, host or host:port, port 443 by default) a connection may reach besides the providers' own (AWS KMS, Azure Key Vault and Managed HSM with Microsoft's sign-in, Google Cloud KMS) and the endpoints its settings name: a VPC endpoint, a KMIP server. Any other host, or another port, is refused — a data key's master key cannot send the KMS token elsewhere.

Kerberos and client-side encryption (npm package)

Kerberos (GSSAPI) and client-side field level / Queryable Encryption need native packages, which Mongo Manager does not install by itself: installing it runs no package's install script. To use them, install the packages next to the npm package, then restart: 

npm i -g @mongo-manager/app kerberos mongodb-client-encryption

Mongo Manager loads them only from the global node_modules folder that holds mongo-manager itself (checked by its real path, never a folder above it), and only when a connection first needs one; the connection form says which one is missing and how to install it. The standalone binaries, the Docker image (which sets MM_DISTRIBUTION=docker) and the copy a Windows service runs from keep no native module: there these two features say they are not available in this package — use the npm package, run in the foreground, instead. Queryable Encryption's automatic encryption also needs the crypt_shared library (MM_CRYPT_SHARED_LIB_PATH) or mongocryptd, and MongoDB Enterprise or Atlas; MongoDB Community decrypts only. MONGODB-OIDC needs no package: the identity provider must have this server's <address><base path>oidc/callback as a redirect address (or another one the connection names), and people can sign in with a code where it cannot.

Install as an app

In Chrome or Edge, choose Install Mongo Manager in the address bar to open it in its own window from your desktop or start menu.

Backup destinations

  • MM_BACKUP_FOLDER_ROOTS: the folders server-folder destinations may use, as absolute paths separated by the system's path separator (: on Linux and macOS, ; on Windows), at most 16. Default: none, so no folder destination can be made. A relative path stops the server at start. Give the service account write access to each root, and keep the roots outside the data directory: a folder destination inside it is refused. Each start logs a root the server cannot write into. For the Linux service:
    • Its sandbox lets it write only into its data directory and the roots its config and env file name when it is installed: after changing them, run sudo mongo-manager service install again (it keeps the data, config and key), and restart the service after creating a root that was missing. Roots set anywhere else, such as an Environment= in a drop-in, install does not see: their folders stay read-only to the service.
    • Install leaves out a root under /home, /root, /run/user, /tmp, /var/tmp or /dev, which the service cannot reach, and one that would undo the sandbox: one that holds a system directory (/, /var, /var/lib and the like) or is inside /etc, /usr, /run or another system directory (under /var only folders inside /var/backups are open). A folder inside /srv, /opt or a mount under /mnt or /media suits, not those folders themselves; on a removable or network file system, whoever controls the disk or share controls the folders on it, so make the mount point itself the root (a user's FUSE mount says what it likes of its owners and links). A root inside another root is in the sandbox by that one. Where /srv, /opt or /mnt is itself a link into /var, as on ostree systems (Fedora Silverblue, CoreOS), install says where a root leads, and it is refused there: choose a folder inside /var/backups.
    • A link is judged by where it leads, and the unit names that place; a link that leads nowhere is left out: for one to a folder not made yet, make that folder, then run service install again; for one round in a loop or through a file, choose another folder or remove the link. Keep each folder above a root, and the folders the links on its way are in (a link in a link's target included), owned by root and closed to its group and others, so that no one can put a link in a folder's place there; in a folder others may write into, sticky or not, have root own the folder in it, and make the root inside that one.
    • A root below a folder the service's user could change, anywhere up to / and along the links on its path, is left out: one that user owns, or may write into through one of its groups, an ACL or as anyone may, where a process running as that user could put a link to /etc in a folder's place. That includes a link in another root, which the service writes into. Install, and doctor run with sudo, also ask the system: with setpriv they run test -w as that user, so the kernel applies its groups (those the unit gives the service with Group= or SupplementaryGroups=, a drop-in's included) and ACLs. Without setpriv, or without root, only the folders' modes and the user's groups are read, and both say so. What the modes allow counts even where an ACL takes it away, so such a folder leaves its roots out too.
    • Install asks systemd who runs the service, with every drop-in read. A drop-in that runs it as a user other than --user (or as root), with DynamicUser=yes and no account of that name, with a Group= other than the user's own, or with a group the system does not know (with which systemd refuses to start it) stops the install before the data directory and config change; it says why and leaves the service stopped and disabled. A group whose lookup fails, or a systemd that cannot be asked, leaves every root out.
    • sudo mongo-manager doctor --config /etc/mongo-manager/config.json checks the installed service (plain mongo-manager doctor checks your own data directory, and says the service is not what it checked). It checks each root: that it exists, is a directory the server can write into, is inside the sandbox, and is not inside the data directory; it also names a folder the sandbox lets the service write into that no root names any more, or that leads to a root or the data directory through a link someone other than root may change, and warns of a service that runs as root, a group no one has or whose lookup fails, and of DynamicUser=yes with no account of its name. It checks the roots the service's config and env file name, which is why it needs sudo: only root may read the env file, which is also where the service's secret key is. It checks write access as the user it runs as; run as root, it reads the root's owner and mode for the user who owns the data directory instead, and takes the system's word where that user may write into it. The folders above the roots it judges for the user the unit runs the service as (its User=).
  • MM_BACKUP_PRIVATE_NETWORKS: private ranges destinations may reach, as a comma-separated list of at most 64 CIDRs (for example 10.0.5.0/24); plain HTTP is allowed inside them. Default: none. Loopback, 10/8, 172.16/12, 192.168/16, CGNAT (100.64.0.0/10) and unique-local (fc00::/7) ranges are accepted. A public range stops the server at start, and so does a range inside a link-local or cloud metadata range (169.254.0.0/16, fe80::/10, 169.254.169.254, fd00:ec2::254, 100.100.100.200), in any form, IPv4-mapped and NAT64 included; the message names the range. Those addresses can never be reached, even inside a listed range.
  • MM_BACKUP_PROXY: an HTTP(S) proxy destinations are reached through, such as http://proxy.corp:3128 or https://user:password@proxy.corp; no path or query. Default: none (no environment proxy variable is ever read). Mongo Manager still resolves and checks each destination's address itself and asks the proxy to connect to that address, so the address rules above hold through the proxy; TLS runs end to end to the destination, whose certificate is checked as without a proxy. Destinations inside MM_BACKUP_PRIVATE_NETWORKS are reached directly. A proxy at a link-local or metadata address stops the server at start. Keep the proxy's password out of shared shell histories: it is part of the address. Only backup destinations use it: alert channels (email and webhooks), AI providers and plugins never go through it. Things to know before choosing a proxy: an http:// proxy receives its user name and password in clear (Basic), so prefer https:// or a proxy inside a trusted network; a proxy that only allows CONNECT to listed host names refuses these connections, since it is asked for an IP address; an https:// proxy's certificate must be signed by an authority Node.js trusts (its built-in list, or one added with NODE_EXTRA_CA_CERTS): no CA of its own can be given.
  • MM_BACKUP_DEST_PART_MB: the upload part size, 16 to 512 MiB (default 64).
  • MM_BACKUP_DRILL_MAX_MB: the most a restore drill writes, in MiB. Default: none — a drill stays under half the free disk space MongoDB reports (the fullest shard's, through a mongos). Where MongoDB does not report it (Atlas shared tiers), drills run only with this set.
  • MM_BACKUP_DEST_TRANSFERS: sends and downloads running at once on each destination, 1 to 8 (default 2). Further ones wait, shown as "Waiting for" that destination in the jobs list.

Scheduled backups

  • MM_BACKUP_SCHEDULES: the scheduler, on by default. 0 turns it off: schedules keep their settings, nothing runs, and the Scheduled backups tab says scheduling is off. Runs a stopped server left unfinished are closed at start.
  • MM_BACKUP_SCHEDULE_CONCURRENCY: scheduled runs working at once, 1 to 8 (default 2). Further due runs wait up to six hours.

Watching changes

  • MM_WATCH: change-stream feeds, on by default. 0 turns them off: the Watch sections say watching is off, and nothing is opened on MongoDB.
  • MM_WATCH_MAX_FEEDS: live feeds on this server at once, 1 to 500 (default 50). Each user may have 5 and each browser window 3. Every feed holds one change stream cursor on MongoDB.
  • Watching needs a replica set, a sharded cluster or a load-balanced deployment, and the connection's database user needs changeStream and find on what is watched. See Watching changes.

Live sync

  • MM_LIVE_SYNC: live syncs between connections, on by default. 0 turns them off: running syncs wait with the reason and nothing is read or written; new ones are refused. Turned on again, they carry on from where they were.
  • MM_LIVE_SYNC_MAX: live syncs that have not ended on this server, 1 to 100 (default 10). Each user may have 3. Each running sync holds one change stream on its source and keeps both connections open.
  • The source must be a replica set, a sharded cluster or a load-balanced deployment (MongoDB 6.0 or later); a copy that may outlast the source's oplog asks for a confirmation. See Live sync.

Alerts

  • MM_ALERTS (config file: alerts.enabled): alerts, on by default. 0 turns them off: nothing is evaluated or sent, and the Alerts page says alerts are off.
  • MM_ALERTS_PRIVATE_NETWORKS (config file: alerts.privateNetworks, a list): networks the alerts' mail servers and webhooks may reach besides public addresses, as a comma-separated list of at most 64 CIDRs (for example 10.0.5.0/24). Default: none. Plain http to a webhook is allowed only inside them. The same ranges are accepted and refused as for MM_BACKUP_PRIVATE_NETWORKS: link-local and cloud metadata addresses can never be reached.
  • In a config file: "alerts": { "enabled": true, "privateNetworks": ["10.0.5.0/24"] }. See Server administration.

The advanced shell

  • Disable it entirely with --no-shell (or MM_SHELL_ENABLED=0).
  • Limits: MM_SHELL_MAX_PER_USER, MM_SHELL_MAX_TOTAL, MM_SHELL_COMMAND_TIMEOUT_MS, MM_SHELL_IDLE_MS, MM_SHELL_LIFETIME_MS. A shell its page holds stays open however long it is not used, as in Compass; one no page holds closes two minutes after its page goes. The idle limit is off (0) unless you set it (10000 to 86400000 ms); a shell lives at most 12 hours unless you set another lifetime (60000 to 86400000 ms, or 0 for none). Shells held open count toward MM_SHELL_MAX_TOTAL until their pages close; on a server many people share, set MM_SHELL_IDLE_MS so shells left open and unused are freed. With sign-in on, a shell also ends when its user's sign-in session ends, and when the user's role changes or the account is disabled.
  • MM_SHELL_RSS_MB: the memory a shell's process may hold, 128 to 16384 MB (default 384). The server measures it itself from the operating system (on Windows with tasklist, on macOS with ps) and restarts a shell past it; the shell's variables are lost. A shell that stops answering for 15 seconds while no command runs is restarted too. MM_SHELL_OUTPUT_MB: the output of one command, 1 to 64 MB (default 5); the rest is cut. MM_SHELL_COMMANDS_PER_SECOND: commands per shell a second, 1 to 1000 (default 20).
  • On a root POSIX server the shell worker drops to MM_SHELL_UID/MM_SHELL_GID (default 65534); do not run the service as root.

AI assistant

  • MM_AI: the AI assistant, on by default; it shows only once an administrator adds a provider (Settings → AI assistant). 0 hides it everywhere and refuses requests.
  • MM_AI_PRIVATE_NETWORKS: networks (CIDR, comma-separated) a provider may be on besides public addresses, for example an Ollama at 10.0.0.5; plain http only there. Cloud metadata and link-local addresses are never reachable. In local mode this machine is always allowed.
  • MM_AI_PER_MINUTE (default 10, 1–120) and MM_AI_PER_DAY (default 200, 1–10,000): requests per person. MM_AI_MAX_CONCURRENT (default 8, 1–64): requests at once on the server; each person may have 2. MM_AI_AGENT_PER_MINUTE (default 30, 1–120): an agent's further requests to the provider within one message, per person a minute (they count for the day too).
  • MM_AI_CHAT_DAYS (default 30, 0–365): how long a chat is kept after its last message. 0 keeps chats in memory only (12 hours) and removes chats stored under an earlier setting when the server starts.

Plugins

  • MM_PLUGINS: plugins, on by default. Each one still needs an administrator's approval, after its security scan. 0 finds, installs and runs none (see Plugins).
  • MM_PLUGINS_GITHUB: installing a plugin from a public GitHub repository's release, off by default (plugins are installed by upload or from a folder); 1 allows it. The server then reaches api.github.com, github.com and GitHub's release-asset hosts, over https, sending nothing of its own. Left off, a server never reaches GitHub. The server connects to GitHub directly: HTTP proxy settings are not used, so a server that can reach out only through a proxy installs plugins by upload. A system service reads it from its config.json as "pluginsGithub": true (Linux /etc/mongo-manager/config.json, Windows %ProgramData%\Mongo Manager\config.json, macOS /Library/Application Support/Mongo Manager/config.json); restart the service after.
