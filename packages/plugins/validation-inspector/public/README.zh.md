# 验证检查

验证检查会拆分集合的验证规则，并按每条规则单独检查其文档：整体上有多少文档违反规则，每个必填字段、每个属性、每个条件各有多少文档违反。许多文档都违反的规则，应在将其设为严格之前，先在数据或规则本身中修正。

该插件只读取数据，不会更改数据库或规则中的任何内容。

## 出现的位置

- **集合标签页：** 每个集合都会在“文档”“聚合”及其他标签页旁出现一个**规则检查**标签页。

## 使用方法

打开一个集合，然后打开**规则检查**标签页。标签页一打开，检查就会在随机 1,000 个文档上运行。选择**随机 10,000 个**或**全部**可检查更多文档；点击**检查**会重新运行。

标签页会列出各条规则，违反最多的排在最前。每条规则会显示已检查的文档中有多少违反它及其占比。**在文档中显示**会在文档查询中放入一个筛选条件，用于选出这些文档，以便在那里查看和修正。**显示所有违反规则的文档**会对规则整体执行同样的操作。

验证级别和操作会被标明。级别为 `moderate` 时只检查已符合规则的文档，操作为 `warn` 时会在违反规则时记录日志，而不是拒绝写入：设置了其中任何一项时，标签页都会说明。

## 规则如何拆分

- **`$jsonSchema`：** `required` 中的每个字段是一条规则；`properties` 中的每个属性是一条规则（其检查项：类型、最小值、模式等）；不为 `true` 的 `additionalProperties` 与 `properties` 和 `patternProperties` 一起构成一条规则，即“除模式自身定义的字段外，不允许其他字段”；其他每个关键字（`minProperties`、`dependencies`、`anyOf` 等）各自是一条规则。`title` 和 `description` 不涉及文档本身，因此被省略，顶层的 `bsonType: "object"` 也一样。
- **查询验证器：** 每个字段的条件是一条规则，顶层 `$and` 的每个子句也是；`$or`、`$nor` 和 `$expr` 各自是一条规则。

文档不满足某条规则时即违反该规则：使用的筛选条件为 `{ $nor: [规则] }`。

## 示例

在一个 `customers` 集合上，其验证器要求 `email` 必填，并规定 `age` 为不小于 0 的 int：

```
email 为必填          12 个文档（1.2%）
age  bsonType: 'int', minimum: 0     3 个文档（0.3%）
name 为必填           没有文档违反
```

在第一条上点击**在文档中显示**，会在文档中放入 `{ $nor: [{ $jsonSchema: { required: ["email"] } }] }`。

## 关于视图

视图本身没有验证规则：标签页会说明这一点，并指向它所读取的集合。

## 权限

- **读取文档**（`documents:read`）：通过一次只读聚合统计违反每条规则的文档。
- **读取此集合的定义**（`collection:read`）：读取其验证规则。

读取通过应用并以已登录用户的权限和字段掩码进行。规则中关于值对用户隐藏的字段的内容不会提供给插件（字段名会提供）：这样的规则不会被检查，统计的是所显示规则的结果。该插件无法读取其他集合。

## 设置

无。

## 限制

- 随机采样只能说明某条规则被违反的频率，而不是整体上有多少文档违反它：如需精确数量，请选择**全部**。
- 检查是一条最长运行 10 秒、不使用磁盘的管道。在大型集合上，**全部**可能超时；采样则不会。
- 最多统计 40 条规则；超出时标签页会说明。
- 规则按原样统计。仅在与另一条规则一起时才成立的规则（例如跨属性的 `anyOf`），会像 MongoDB 检查的那样作为整体统计。
