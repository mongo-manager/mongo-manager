# Проверка валидации

Проверка валидации разбирает правила валидации коллекции на части и проверяет ее документы по каждому правилу отдельно: сколько документов нарушают правила в целом и сколько нарушают каждое обязательное поле, каждое свойство, каждое условие. Правило, которое нарушают многие документы, нужно исправить в данных или в самом правиле, прежде чем делать его строгим.

Плагин только читает. Он ничего не изменяет ни в базе данных, ни в правилах.

## Где он появляется

- **Вкладка коллекции:** вкладка **Проверка правил** рядом с «Документами», «Агрегациями» и другими вкладками каждой коллекции.

## Как пользоваться

Откройте коллекцию, затем вкладку **Проверка правил**. Проверка запускается на 1 000 случайных документов сразу после открытия вкладки. Выберите **10 000 случайных** или **Все**, чтобы проверить больше; кнопка **Проверить** запускает проверку заново.

На вкладке перечислены правила, сначала самые нарушаемые. Для каждого указано, сколько из проверенных документов его нарушают, и их доля. **Показать в «Документах»** помещает в запрос «Документов» фильтр, выбирающий эти документы, чтобы их можно было просмотреть и исправить там. **Показать все документы, нарушающие правила** делает то же для правил в целом.

Уровень и действие валидации указываются. Уровень `moderate` проверяет только документы, которые уже соответствуют правилам, а действие `warn` записывает нарушенное правило в журнал вместо отклонения записи: вкладка сообщает об этом, если задано что-либо из двух.

## Как разбиваются правила

- **`$jsonSchema`:** каждое поле из `required` — это правило; каждое свойство из `properties` — это правило (его проверки: тип, минимум, шаблон и прочее); `additionalProperties`, отличное от `true`, — одно правило, «нет полей, кроме определенных в схеме», вместе с `properties` и `patternProperties`; каждое другое ключевое слово (`minProperties`, `dependencies`, `anyOf`, …) — отдельное правило. `title` и `description` ничего не говорят о документе и опускаются, как и `bsonType: "object"` верхнего уровня.
- **Валидатор запроса:** условие каждого поля — это правило, как и каждая часть `$and` верхнего уровня; `$or`, `$nor` и `$expr` — по одному правилу.

Документ нарушает правило, когда не соответствует ему: используется фильтр `{ $nor: [правило] }`.

## Пример

В коллекции `customers`, валидатор которой требует `email` и задает для `age` тип int со значением 0 или больше:

```
email: обязательное поле          12 документов (1,2 %)
age  bsonType: 'int', minimum: 0     3 документа (0,3 %)
name: обязательное поле           Нарушающих документов нет
```

**Показать в «Документах»** для первого правила помещает `{ $nor: [{ $jsonSchema: { required: ["email"] } }] }` в «Документы».

## О представлениях

У представления нет собственных правил валидации: вкладка сообщает об этом и указывает на коллекцию, которую оно читает.

## Разрешения

- **Чтение документов** (`documents:read`): чтобы подсчитать документы, нарушающие каждое правило, одной агрегацией только для чтения.
- **Чтение определения этой коллекции** (`collection:read`): чтобы прочитать ее правила валидации.

Чтение идет через приложение с правами и маскированием полей вошедшего пользователя. То, что правило говорит о поле, значения которого скрыты от пользователя, плагину не передается (имя поля передается): такое правило не проверяется, а числа относятся к показанным правилам. Плагин не может читать другие коллекции.

## Настройки

Нет.

## Ограничения

- Случайная выборка показывает, как часто нарушается правило, а не сколько всего документов его нарушают: выберите **Все**, чтобы получить точные числа.
- Проверка — это один конвейер, который выполняется не дольше 10 секунд и не использует диск. В большой коллекции вариант **Все** может не уложиться во время, а выборка — уложится.
- Подсчитывается не более 40 правил; вкладка сообщает, если их больше.
- Правило подсчитывается так, как записано. Правило, которое выполняется только вместе с другим (например, `anyOf` по нескольким свойствам), подсчитывается целиком, как его проверяет MongoDB.
