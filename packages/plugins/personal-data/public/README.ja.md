# 個人データ検索

個人データ検索は、コレクション内で個人データを含むフィールド（メールアドレス、電話番号、カード番号、IBAN、身分証明書番号、IP アドレス、氏名、住所、生年月日、パスワード、キー）を探します。見るべきでない人に見られる前に、個人データのルールで非表示にできるようにするためです。コレクションのドキュメントからランダムなサンプルを読み取り、見つけた各フィールドを値と名前の両方から判定し、確度と理由を示します。

このプラグインは読み取りのみを行います。マスクされたもの以外の値は表示されず（`u•••@e•••.com`、`+•• ••• ••• •• 67`）、保存も送信もされません。値は種類を見分けるためだけに読み取られます。

## 表示される場所

- **コレクションタブ：** すべてのコレクションの、ドキュメントや集計などのタブの隣に **個人データを検索** タブが表示されます。

## 使い方

コレクションを開き、**個人データを検索** タブを開きます。タブを開くとすぐにランダムな 300 件のドキュメントをサンプリングします（大きなドキュメントの場合は 1 回の応答に収まる件数だけを取り、読み取った件数を示します）。**再スキャン** で新しいサンプルを取得します。

見つかった各フィールドが 1 行になります。

- **内容：** 何に見えるか。メールアドレス、電話番号、カード番号、IBAN、身分証明書番号、IP アドレス、氏名、住所、生年月日、パスワードまたはキーのいずれかです。
- **確度：** 値の大半がその種類である場合（または値と名前が一致する場合）は **高**、多くの値がそうである場合や名前がそれを示している場合は **中**、一部の値だけがそうである場合や、名前はそれを示しているが値がそう見えない場合は **低** です。
- **理由：** サンプルの値のうちいくつがそれに見えるか、および名前がそれを示しているかどうか。
- **例：** 値を最大 2 つ、マスクして表示します。

可能性の高いフィールド（確度が高と中）はあらかじめ選択されています。必要に応じてチェックを付けたり外したりしてください。**ルールとして提案** は、コレクションの **個人データ** セクションを、選択したフィールドをこのプラグインからの提案として一覧表示した状態で開きます。接続の管理者がそこで 1 つずつ（またはまとめて）追加し、以降、個人データを閲覧できないユーザーには値が `***` と表示されます。プラグインの指示だけで何かが保存されることはありません。**リストをコピー** は、選択したフィールドを 1 行に 1 つずつ（`データベース.コレクション.フィールド`、内容、確度）コピーします。管理者に送るときに使えます。

## 値の判定方法

- **メールアドレス** と **IP アドレス**（IPv4 と IPv6。`12:30:45` のような時刻は対象外）。
- カードネットワークの範囲と桁数に合い（Visa、Mastercard、Mir、American Express、Discover、UnionPay、Diners Club、JCB、Troy）、Luhn チェックを通る **カード番号**。Luhn チェックだけでは 10 個に 1 個の数字が通ってしまいます。
- mod-97 チェックを通る **IBAN**（トルコのものはさらに 26 文字であること）。
- **身分証明書番号：** 2 つのチェックディジットが正しいトルコの身分証明書番号と、`123-45-6789` の形式で書かれた米国の社会保障番号。
- ひとまとまりで書かれた 9〜15 桁の **電話番号**：`+` または `00` が付く、区切り文字がある、または 9 桁か 10 桁の前に先頭の 0 がある場合。数字だけの値や、数値として保存された値（座標や金額）は、電話のような名前のフィールドにあり、かつ全体が 1 つの番号である場合にのみ電話番号と見なされます。
- それぞれが書かれる形式で判定する **パスワードとキー**：bcrypt、Argon2、scrypt のハッシュ、JSON Web Token、AWS アクセスキー、GitHub と Stripe のトークン、秘密鍵。
- **名前から：** `email`、`phoneNumber`、`iban`、`cardNumber`、`tckn`、`ssn`、`passportNumber`、`ipAddress`、`firstName`、`lastName`、人の `name`（`customer.name`）、`billingAddress`、`street`、`postalCode`、`birthDate`、`dateOfBirth`、`password`、`apiKey`、`accessToken` とその類似名。英語、トルコ語、およびアプリのほかの言語に対応しています（`eposta`、`telefon`、`soyad`、`dogumTarihi`、`telefono`、`nachname`、`date_naissance`、`телефон`、`电话`、`電話番号`、`전화번호` など）。データそのものではなくデータに関する名前は対象外です：`emailVerified`、`phoneType`、`passwordChangedAt`、`isMobile`。

オブジェクトや配列の中にあるフィールドは、個人データのルールが指定するのと同じ形式で表します。たとえば連絡先の配列にあるメールアドレスは `contacts.email` です。

## 例

`users` コレクションの場合：

```
フィールド  内容                 確度   理由                                         例
email       メールアドレス       高     200 個の値のうち 200 個。名前もそれを示している   u•••@e•••.com
phone       電話番号             高     196 個の値のうち 196 個。名前もそれを示している   +•• ••• ••• •• 67
apiToken    パスワードまたはキー 高     名前がそれを示している                         ••••••••
firstName   氏名                 中     名前がそれを示している                         A•••
```

パスワードまたはキーが見つかった場合は注意書きが表示されます。ルールはアプリ上で表示を隠すだけで、データベースでは隠しません。パスワードは低速なハッシュで、キーはシークレットストアに保存してください。名前がパスワードであることを示すフィールドは、値がどう見えてもパスワードとして表示されます。

## ビューについて

ビューはコレクションと同じように読み取られますが、そのデータは参照元のものです。ルールは、ビューが読み取るコレクションに提案します。そのコレクションのルールがビューにも適用されます。ビューでは **ルールとして提案** は無効です。

## 権限

- **ドキュメントの読み取り**（`documents:read`）：コレクションのドキュメントをサンプリングし、フィールドを個人データとして提案するために使います。

読み取りは、ログインしているユーザーの権限とフィールドのマスキングを適用して、アプリを通じて行われます。すでに非表示になっているフィールドは `***` として届き、データとは見なされず、非表示済みとして示されます。提案されたフィールドを受け取れるのは、接続の管理者（その接続を管理できる人）だけです。それ以外のユーザーには、**ルールとして提案** がその旨を表示し、**リストをコピー** で管理者に渡せます。

## 設定

なし。

## 制限

- サンプルであるため、個人データを含むドキュメントが少ないフィールドはサンプルに現れないことがあります。フィールドごとに 200 個の値、配列は 50 要素、深さは 6 階層まで読み取ります。
- どのルールでも指定できないフィールド（キーにドット、先頭の `$`、非表示文字、前後の空白が含まれる場合や、ルールが 512 バイトを超える場合）は、理由とともに一覧表示されますが、選択できません。
- 一度に提案されるのは最大 50 個のフィールドです。タブは提案する前にそのことを知らせ、「個人データ」セクションが表示されている間も開いたままなので、残りを提案しに戻れます。
- 「個人データ」セクションが提示するのは、提案されたフィールドのうちコレクションのサンプルに含まれるものだけです。含まれないものは、提示されないものとして一覧表示されます。
- 氏名と住所はフィールドの名前だけから判定されます。`title` という名前のフィールドにある氏名は見つかりません。
